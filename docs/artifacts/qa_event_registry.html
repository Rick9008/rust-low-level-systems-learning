event registry:id 密集就直接當索引、Remove 用回報的

硬體訊號帶著 event id 進來,掛 handler、事件來就 dispatch——幾千種 id、高事件率。這題考兩件事:查找結構的階梯(第一個 clarify:id 密集還是稀疏?)和一個 Rust 特有的殺手:dispatch 進行中 handler 想把自己移除,撞上 borrow checker——After::Keep / Remove 回報制就是為它而生。這頁是 e2(fd_registry)的前傳:同一套「id 當索引」思想,少了 generation 那層。

0 · 查找結構的階梯:第一問永遠是「id 密集還是稀疏?」

結構dispatch 查找記憶體什麼時候對
naive Vec<(id, handler)> 線性掃O(n)O(live)十幾個 handler 的玩具;高事件率下每次 dispatch 全掃 = 自殺
HashMap<id, Vec<Handler>>O(1) 攤銷(hash + probe,常數大、cache 差)O(live)id 稀疏 / 無界(隨機 u64、字串)時的正解
direct-index Vec<Vec<Handler>>O(1) worst-case,一次 array load,零 hashingO(max_id)id 密集有界(硬體 opcode、中斷號、fd)——本題的正解

O(max_id) 的入場券是密集性:硬體 event id 是人定的小整數表(幾千種、從 0 編起),max_id ≈ 種類數,不會稀疏爆炸——跟 fd 的「最小可用號碼」同一個入場券。id 若是隨機 u64,這招就死,退回 HashMap。把這個判準問出口,就是 Q4 的 clarify 得分點。

“Are the ids dense and bounded — like hardware opcodes — or sparse? Dense means the id is the index: one array load, O(1) worst-case, no hashing on the hot path. Sparse means HashMap and I pay hash-plus-probe per event.” 階梯一句話講完,附帶把 clarify 問了。

1 · 為什麼是 After::Keep / Remove,不是 handler 自己 unregister?

直覺 API 是給 handler 一個 registry.unregister(...)。在 Rust 裡這直接撞牆:dispatch 正拿著 &mut handlers[i] 在呼叫它,handler 再回頭改同一個 registry = 同一份資料的兩個 &mut 同時活著——borrow checker 拒編。這不是 Rust 找碴:C++ 版同樣的寫法是「iterator 失效 + 邊走邊改」的經典 UB,只是 C++ 讓你編過、上線才炸。

繞法是控制反轉:handler 不動手,只回報意圖(After::Keep / After::Remove),移除由 dispatch 迴圈自己做——同一時間只有迴圈一個人拿著 &mut。題目那句「dispatch 進行中不會有人 register(caller 保證)」是同一個問題的另一半:對 registry 的其他寫入也被推到 dispatch 之外。

// canonical:手動控制 index 的迴圈——Remove 時「刪、不前進」
pub fn dispatch(&mut self, id: usize, payload: &[u8]) -> usize {
    let Some(list) = self.table.get_mut(id) else { return 0 };  // 未知 id = no-op
    let mut i = 0;
    let mut ran = 0;
    while i < list.len() {
        ran += 1;
        match list[i](payload) {
            After::Keep   => i += 1,          // 留任 → 前進
            After::Remove => { list.remove(i); } // 移除 → 原地(下一位滑進 i)
        }
    }
    ran
}

Vec::remove(i) 是 O(n) 搬移,但保序——「依註冊順序執行」是題目的 contract。想省搬移用 swap_remove?下面 stepper 親手走一次它的雙重災難。

3 · 跟 e2(fd_registry)的關係:同一招,差一層

所以答 e 時順口補一句「if the ids could be recycled — like fds — I'd add a generation per slot」,就是把 e 和 e2 一起收掉的加分動作。

4 · 面試句庫

“A handler can't unregister itself mid-dispatch — that's two mutable borrows of the same registry, and in C++ the same shape is iterator invalidation. So handlers report Keep-or-Remove, and the dispatch loop — the sole borrower — applies it: remove-at-i without advancing, preserving registration order.” 控制反轉 + borrow checker,一次講完。
“swap_remove is O(1) but double-broken here: it skips the swapped-in handler this round, and it permanently breaks registration order. remove is O(n) on a rare path — removal — to keep the hot path contract correct.” 被追問「為什麼不用 swap_remove」的完整回答。
