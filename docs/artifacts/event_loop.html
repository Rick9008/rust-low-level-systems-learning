reference / stage 6  ·  epoll & readiness model

event_loop

epoll 不給你資料,只給你一句話:「fd 7 現在可讀了。」IO 還是你自己做。 整個模組的難度不在 epoll_wait 怎麼呼叫—— 在「可讀了」這句話,kernel 到底打算跟你講幾次。

1 · LT 寬容,ET 不寬容

同一個 fd、同一批資料、同一個 handler,只差註冊時多了一個 EPOLLET。 左邊 level-triggered:只要緩衝裡還有資料,每次 epoll_wait 都報。 右邊 edge-triggered:只在「有新資料抵達」那個瞬間報一次,報完就當作講過了。

handler 預設是壞的——它讀 32 bytes 就 return,沒讀到 EWOULDBLOCK。 照著按:資料抵達 → epoll_wait → dispatch → epoll_wait。看第二次 epoll_wait 兩邊回什麼。

目前狀態 緩衝是空的。按「client 送來 100 bytes」開始。

ET 那條連線死掉的方式很安靜:epoll_wait 沒報錯、read 沒報錯、 process 沒 crash,只是那 68 bytes 永遠停在 kernel 收信緩衝裡,而 client 在等一個永遠不會來的回應。 只要你的 event loop 還服務著別的連線,主迴圈根本不會卡—— 卡住的只有這一條。所以它在 dev 機上看不出來,在 production 變成「偶發 timeout」。

再按一次「client 送來 100 bytes」:新資料 = 新的 edge,那條被餓死的連線會復活。 這就是為什麼這個 bug 這麼難抓——只要對端還在噴資料,它就被掩蓋。 它只在 request/response 協定下現形:client 送完就閉嘴等你回應,沒有下一個 edge 來救你。
結論只有一條:ET 模式下,你欠 kernel 一個 EWOULDBLOCK。 read 要讀到 EAGAIN、write 要寫到 EAGAIN、accept 也要 accept 到 EAGAIN (只 accept 一個,積在 backlog 裡的其他連線同樣不會有第二次通知)。

2 · 事件回來之後:token 就是你的 O(1) 索引

epoll_wait 回來的是一批 epoll_event,裡面只有兩個欄位: 一個 u32 遮罩、一個 u64 使用者資料。 kernel 原樣把當初註冊時給它的那 8 bytes 還你——它不知道那是什麼,也不在乎。 連線狀態一直在你手上,事件只是一把鑰匙。

這就是為什麼 poll() 不回傳 &[Event]:那會借走 &self, 你在 dispatch 迴圈裡就不能 el.register(...) 了。 事件緩衝 Events 由 caller 持有,兩個借用天然分離(mio 同款解法)。

epoll_wait 寫回 events 緩衝(點一個) HashMap<Token, Conn> — 狀態在 caller 手上

42Conn { fd: 15, state: Flushing }

Token(u64::MAX) 是保留值:那是 event loop 自己的 wake fd。 它在翻譯層就被吃掉(drain eventfd、設 woken 旗標),不會進事件列表, caller 的 HashMap 裡也不該有它——register() 的 assert!(token.0 != WAKE_TOKEN) 就是在守這件事。下一節就是它。

3 · EPOLLIN | EPOLLOUT | EPOLLET 是什麼數字

Interest 與 Trigger 最後都會塌成一個 u32。 值得記住的是那兩個高位:EPOLLET 是 1 << 31—— 整個 LT/ET 的分水嶺,就是第 31 個位元。

0x00000000
bit 31 → bit 0 

  


  

    EPOLLERR 與 EPOLLHUP 你不必註冊,kernel 一律會報——
    所以翻譯層必須無條件檢查它們。
    EPOLLRDHUP 則是本實作在 Interest::to_epoll 裡永遠掛上的:
    半關閉(對端 shutdown(SHUT_WR))比 read() == 0 早一步在事件層看得到,而且免費。
  






  
4 · 睡在 epoll_wait 裡的執行緒,只聽得見 fd

  

    epoll_wait(epfd, ev, n, -1) 沒有 timeout,執行緒真的睡死在 kernel 裡。
    現在另一條執行緒要它停機——它把 running = false 設好了,然後呢?
    沒有然後。那個 flag 要等迴圈醒來才會被讀到,而迴圈只有 fd 就緒才會醒。
  

  

    解法只有一個形狀:給它一個「它有在聽」的 fd。
    eventfd 就是為此而生——一個 fd、8 bytes 的計數器、多次 notify 自動合併。
    切換下面的開關,看同一個 shutdown() 在兩個世界裡的下場。

    順序反過來也不能丟訊號:先 wake() 再 poll()——
    eventfd 計數器已經 +1,下一次 epoll_wait 立刻返回。
    這和 executor 的 park permit、condvar 的 predicate 是同一課的三種面貌:
    喚醒訊號必須帶狀態,對著已經醒著的人喊話,那句話必然丟。
    (試試看:reset,切到 eventfd,先按 shutdown、再按 loop 跑一輪。)
  

  

    wake fd 自己一定用 LT 註冊:翻譯層每次都會 drain(),
    不需要 ET 的紀律,卻能在「漏 drain」時靠 LT 的重複通知自救。
    在你自己的基礎設施上,寬容比省一次假醒值錢。
  






  
5 · 兩種模式的完整帳單

  

    

      
        
Level-Triggered(預設)Edge-Triggered(EPOLLET)

      
      
        

          何時通知
          狀態成立就報
          狀態「發生變化」才報
        

        

          沒讀乾淨
          下一輪再報一次(慢,但活著)
          永遠不再報 — 這條連線 stall
        

        

          非阻塞 fd
          建議(不然一次 read 就卡死全部連線)
          強制(要 drain 到 EAGAIN,阻塞 fd 直接死在最後一次 read)
        

        

          常掛 EPOLLOUT
          緩衝有空位就一直報 → busy loop。要在寫完後 reregister 拿掉
          可以一直掛著(只在 不可寫 → 可寫 的那一刻報)
        

        

          accept 迴圈
          一次 accept 一個沒關係
          必須 accept 到 EAGAIN,否則 backlog 裡的連線沒人理
        

        

          假醒 / syscall 數
          多(高負載下重複喚醒)
          少

    boundary_lt_rereports_et_does_not 這個測試用兩行 assert 就把整節內容鎖住:
    寫一個 byte、不讀走、連 poll 兩次——LT 第二輪 len() == 1,ET 第二輪 len() == 0。
    ET 的性能優勢是真的,但它把「正確性」外包給了你的 handler。
    先用 LT 讓它跑對,量到 syscall 真的是瓶頸,再換 ET。
