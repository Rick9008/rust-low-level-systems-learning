Atomic ordering 速查:RMW 的兩個 ordering、填錯會怎樣

為什麼 fetch_add 只要填一個 ordering,compare_exchange / fetch_update 卻要填兩個?為什麼 store 給 Acquire、load 給 Release 會直接 panic?這頁把「哪個 op 填幾個、能填什麼、填錯會怎樣、該用什麼」一次講清——底層只有一條原則:ordering 描述的是「這個原子操作跟『它周圍那些非原子的讀寫』之間的可見性關係」。

0 · 誰填一個、誰填兩個

opordering 數為什麼
load1只讀
store1只寫
swap / fetch_add / fetch_*1一定會寫(RMW 不會失敗)→ 只有一種結果
compare_exchange(_weak)2:success, failure兩種結果:成功 = 讀+寫;失敗 = 只讀
fetch_update2:set_order, fetch_order內部是 CAS 迴圈:寫成功 = set;讀(初次+每次重試)= fetch

1 · 為什麼 CAS 要兩個:成功「有寫」、失敗「只讀」

一個 compare_exchange 有兩條命運:

  • 成功 → 真的做了 read-modify-write。這時可以是 Release / AcqRel(有 store 可以「發布」)。
  • 失敗 → 現值不合預期,只發生了一次 load,沒有 store。

你不能「release 一個沒發生的 write」。所以失敗那條的 ordering 只能是 load ordering(Relaxed / Acquire / SeqCst)——給它 Release / AcqRel 會 panic。fetch_update 的 fetch_order 同理(它涵蓋初次 load 和每次 CAS 失敗的 re-load)。

// 成功時 Release(發布),失敗時只讀所以 Acquire/Relaxed 皆可
tail.compare_exchange(t, t + 1, Ordering::Release, Ordering::Relaxed)
//                                 ^success(有寫)    ^failure(只讀)
// tail.compare_exchange(t, t+1, Relaxed, Release)  // ✗ panic:沒有「release 的失敗」

3 · 每個 op 能填什麼 · 填錯會怎樣

op允許的 ordering填錯 →
loadRelaxed / Acquire / SeqCst給 Release / AcqRel → panic(load 不能 release)
storeRelaxed / Release / SeqCst給 Acquire / AcqRel → panic(store 不能 acquire)
swap / fetch_*全 5 種—
compare_exchange failure
fetch_update fetch_order		Relaxed / Acquire / SeqCst給 Release / AcqRel → panic

語意錯(不是 panic、而是靜默 bug)只有一種來源:該用 Release/Acquire 卻用了 Relaxed——原子性還在,但 happens-before 邊消失(見上面 stepper 的紅色分支)。太強(到處 SeqCst)不會錯、只會慢。

4 · 該用什麼:對著「你在做什麼」查

你在做什麼用什麼
交棒:寫完 data 才發布 index/flag寫側 Release(store,或 CAS 的 success=Release/AcqRel)
接棒:讀 index/flag 才去讀 data讀側 Acquire(load,或 CAS 的 failure/fetch=Acquire)
一個 CAS 同時接舊、發布新(lock-free stack push/pop)AcqRel(success),failure=Acquire/Relaxed
純計數,只在最後讀總和、不靠它 handoff 別的 dataRelaxed(如 fetch_add(1, Relaxed))
多變數 litmus(store-buffer / IRIW,要所有 thread 同意一個總序)SeqCst

SPSC 對應:producer tail.store(t+1, Release) / consumer tail.load(Acquire);各自讀「自己寫的那個」計數器用 Relaxed。單寫者不需要 CAS,所以連 success/failure 兩個 ordering 的問題都不會遇到——那是 MPSC 才開始的稅。

5 · 面試句庫

“RMW ops that always write take one ordering; compare_exchange takes two because it has two outcomes — a full read-modify-write on success, but only a load on failure. You can't release a store that didn't happen, so the failure ordering must be a load ordering.” 直接回答「為什麼兩個」。
“Ordering isn't about the atomic itself — it's the visibility contract for the non-atomic data around it. Release publishes prior writes; a matching Acquire consumes them. Downgrade that pair to Relaxed and the atomic is still atomic, but the reader can see the flag without the data — a torn/uninitialized read that stress tests miss and loom catches.” 把「太弱」的後果講到位。
“Wrong-direction orderings panic, not miscompile: store can't take Acquire, load can't take Release, and a CAS failure ordering can't be Release/AcqRel.” 秀你知道哪些是編譯期/執行期擋下、哪些是靜默 bug。
