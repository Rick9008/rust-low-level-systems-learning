thread_pool

把 closure 丟給四條常駐 worker 執行——這部分十分鐘就寫得出來。 真正的難點在停:stop 旗標要在哪裡被看見、誰負責叫醒睡著的 worker、 Drop 回傳的那一刻到底保證了什麼。

1 · shutdown 模擬器

四條 worker 圍著同一個 Mutex<State>——裡面只有兩個欄位:jobs: VecDeque 與 stop: bool。丟幾個 job 進去,看 worker 搶鎖、拿 job、在鎖外執行; 然後按 drop(pool),盯著每一條 worker 怎麼收尾。 右邊四個開關各自埋著一種真實的 bug——切過去再跑一次,壞掉的地方會自己現形。

狀態 四條 worker 已 spawn,佇列空,全部停在 cv.wait_while 裡睡覺——這是 pool 的靜止態。按 execute 丟工作進來。

先玩正確版:丟 8 個 job,趁 worker 還在跑的時候按 drop(pool)。 你會看到手上有 job 的 worker 先把它做完(job 在鎖外執行,stop 打不斷它), 回到迴圈頂端重拿鎖、看見 stop、退出;main 則卡在 join(W0) 等它。 Drop 回傳的那一行,done == submitted——這正是 executes_all_jobs_before_drop_returns 這個測試在斷言的東西。

時間尺度的誠實聲明:模擬器把一次 burst 的多個 execute() 畫在同一格。 每個 execute() 仍然各自 lock / push_back / unlock / notify_one—— 只是它持鎖的時間是幾十奈秒,而一個 job 要跑幾毫秒。job 遠比鎖貴, 這就是為什麼佇列會積壓、也是為什麼 job 絕對不能在鎖裡跑。

2 · predicate 是唯一的真相

condvar 的 wait() 沒有記憶。它不會告訴你「你是被 notify 叫醒的,還是 spurious 醒的」, 更不會告訴你「醒來的時候世界變成什麼樣」。唯一能回答這件事的東西是你自己重查的那個條件。 所以 wait_while 展開之後長這樣: 

// 錯的:stop 對這條 worker 不存在
while jobs.is_empty() {
    guard = cv.wait(guard);
}
// Drop 置 stop + notify_all 之後,
// worker 醒來 -> 佇列還是空 ->
// 條件仍成立 -> 睡回去 -> join 永久卡死
// 對的:等待條件 = 沒事做 且 未停
while jobs.is_empty() && !stop {
    guard = cv.wait(guard);
}
// 醒來重查時 stop 已為 true ->
// 條件不成立 -> 離開等待 -> pop_front()
// 回 None -> return,worker 乾淨退出

「醒來先查 stop」不是一句口號,它的具體落點就是 predicate 的第二個合取項。 把開關切到 predicate 漏了 stop 再跑一次:worker 會照樣 drain 完佇列, 然後在空佇列上睡死——join 永遠不回來。這是 thread pool 面試題的第一大坑, 而且它不是機率性的:佇列空的時候 100% 卡死,所以 boundary_drop_with_zero_jobs_does_not_hang 這個「看起來很無聊」的測試才是最有價值的那一個。

條件誰負責少了會怎樣
wait_while(而非 if + wait) worker spurious wakeup 直接把 worker 送進 pop_front(),拿到 None 就誤以為要退出
predicate 含 !stop worker 醒來看到空佇列就睡回去,永久 park(模擬器裡的紅色 WEDGED)
close 用 notify_all Drop notify_one 只放行一條,其餘 N−1 條沒人叫得醒——一樣是 WEDGED
先 drop(guard) 再 notify execute 不是正確性 bug,是效能 bug:被喚醒的 worker 立刻撞上還沒放開的鎖,再睡一次

為什麼 notify_one 在 execute() 裡是對的、在 Drop 裡卻是錯的? 因為兩者發布的東西不同。execute 發布的是一個 job:只需要一條 worker 醒來消化它, 叫醒四條只是讓另外三條白搶一次鎖(thundering herd)。Drop 發布的是 stop—— 那是一個所有 worker 都必須觀察到的狀態轉換,它不會被誰「消耗掉」。 廣播與單播的分界線,就在「這個事件會不會被一個 waiter 吃掉」。

3 · drain 還是 abandon

shutdown 時佇列裡還躺著 job,你有兩個選擇,而且必須明講你選了哪一個—— 沉默地丟掉工作是 bug,不是 feature。execute() 的簽章回傳 (), 呼叫端據此認定「工作已被接受」;若 pool 偷偷把它扔了,這個承諾就是假的。

策略worker 看到 stop 時Drop 回傳時保證適用
drain(本實作) 佇列非空就繼續拿 job,直到空了才退 所有已提交的 job 都執行完 job 不可丟:寫檔、回應請求、記帳
abandon 立刻退出,pending job 直接 drop 只保證 worker 都死了,工作量未知 job 可重建:cache 預熱、推測性工作

drain 版最漂亮的地方在於它不需要任何額外程式碼:predicate 是 jobs.is_empty() && !stop,佇列非空時它本來就不成立,worker 自然放行去拿 job; 只有「空 且 stop」才走到 pop_front() -> None -> return。 drain 是 predicate 的自然結果,abandon 才是要特地寫的例外。 切到 abandon 開關跑一次,看 dropped 那個計數器變紅——那些 job 的呼叫端,永遠不會知道。

4 · 一個 panic 不能吃掉一條 worker

job 是別人寫的閉包,它會 panic。沒有 catch_unwind 的話:panic 從 job 一路 unwind 出 worker_loop,worker 的 thread 就此結束——池容量悄悄從 4 變成 3, 沒有任何錯誤訊息,沒有 log,吞吐量掉 25%。四個 job 各 panic 一次,池就變成一個只會收 job、 永遠不執行的黑洞。把開關切到「不接住」,連按四次紅色按鈕,看 live workers 歸零。 

// job 在鎖外執行(鎖已在上一個 scope 結束時釋放)
let _ = std::panic::catch_unwind(std::panic::AssertUnwindSafe(job));

AssertUnwindSafe 為什麼成立:job 是 FnOnce, panic 之後它不會再被呼叫,不存在「有人觀察到一個被 unwind 撕成一半的閉包狀態」的機會。 這不是「編譯器囉唆所以我加個 Assert」,是一個可以在面試現場講清楚的證明。

延伸一步:如果 job 是持著鎖執行的呢?那 panic 會讓 Mutex 中毒, 其他 worker 的 lock().unwrap() 全部跟著 panic——一個 job 的 bug 連鎖處決整個池。 這就是為什麼 worker_loop 必須在拿到 job 之後、執行之前先讓 guard 出 scope: 既是為了並行度(否則池退化成序列執行),也是為了故障隔離。 production 還會再往上加一層:panic 計數器上報、或直接重啟一條新的 worker 補位。

5 · Drop 的三個步驟,一個都不能少

步驟沒有它會怎樣
stop = true(持鎖寫) worker 永遠等不到終止訊號,join 等到宇宙熱寂
cv.notify_all() 睡著的 worker 沒人叫醒。stop 寫了也沒用——它們根本沒機會重查 predicate
w.join() 每一條 Drop 立刻回傳,worker 還活著。見下

Rust 裡 JoinHandle 被 drop 的語意是 detach,不是 join—— 這一點跟 C++ 的 std::thread(未 join 直接 terminate)完全相反, 也是最容易被誤記的一條。把開關切到「不 join(detach)」:Drop 會在毫秒內回傳, 而 worker 還在跑你剛丟進去的 job。後果有三層:

  • 斷言變成擲骰子:drop(pool); assert_eq!(counter, 100); 讀到的是一個 還在被別的 thread 遞增的中間值——時好時壞,CI 上偶爾紅一次的那種 bug。
  • process 退出時工作蒸發:main 回傳 = 整個 process 結束, 沒跑完的 job 連同 worker 一起被作業系統回收,沒有任何人被通知。
  • 真正的 use-after-free:這裡靠 Arc<Shared> 撐著,記憶體還沒被釋放; 但只要 pool 改成借用外部狀態(&'a mut / scoped thread 的形狀), detach 就是 worker 拿著懸空指標繼續寫。std::thread::scope 存在的唯一理由, 就是把這個 bug 變成編譯錯誤。

順帶一個 API 設計的漂亮之處:ThreadPool 沒有 Clone,shutdown 只發生在 Drop(&mut self)。借用檢查器保證那一刻不可能還有 &self 能呼叫 execute()——「shutdown 後又提交 job」這整類競態,被型別的形狀消滅了, 不需要任何 runtime 檢查。這比「在 execute 裡查 stop 然後回 Err」高明一個層次。

6 · 為什麼一開始要有池

thread::spawn 一次約 10µs 級,外加預設 8MB 的 stack 位址空間保留。 對一個做 200µs 的 job 來說,建執行緒的成本比工作本身還高; 對十萬個 job 來說,你會先撞到 ulimit -u。 池把 spawn 攤平成一次性成本,代價是所有 worker 搶同一把鎖—— 模擬器裡那個「只有一條 worker 能是 HOLDS-LOCK」的畫面,worker 數上去之後就是實測的瓶頸。

往上一層的解法是 per-worker deque + work-stealing(rayon): 每條 worker 有自己的佇列,空了才去偷別人的,把中央鎖的競爭壓到偷竊發生時。 tokio 的 spawn_blocking 背後就是本模組這個形狀,再加上動態擴縮與 idle timeout。 知道自己這版的瓶頸在哪、下一步往哪走,比把 work-stealing 硬塞進四十行的面試答案裡有用得多。
