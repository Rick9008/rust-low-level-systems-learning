lru

LRU 的難點不是「淘汰最久沒用的那個」——是兩個 O(1) 必須同時成立: 用 key 找值要 O(1),把值挪到最新端也要 O(1)。 單一資料結構做不到,所以答案是兩個結構互相持有對方的座標。

1 · 兩個結構,一個真相

左邊的 HashMap<K, usize> 只回答一個問題:這個 key 在 arena 的哪一格。 它對「多久沒用」一無所知。右邊的 Vec<Node> 是 arena, 每個 node 用 prev / next 兩個索引(不是指標) 織成一條雙向鏈表,鏈表的順序就是 recency:head 是最新,tail 是下一個要死的。

兩邊靠 map 的 value(也就是 arena 索引)黏在一起。跑幾次 get / put, 盯著 prev / next 欄位:每次操作被改寫的欄位永遠是個小常數, 跟 cache 裡有幾個元素完全無關。這就是 O(1) 的全部內容。

2 · promote = unlink + push_front

get 命中之後要把節點搬到 MRU 端。搬動一個節點在雙向鏈表裡永遠只碰 它的兩個鄰居,加上可能的 head / tail。 節點自己在 arena 的位置一格都不動——動的只有索引欄位。

步驟賦值次數為什麼
unlink(i) prev == NIL ? head = next : nodes[prev].next = next 1 把 i 的前驅接到 i 的後繼;i 是頭就改 head
next == NIL ? tail = prev : nodes[next].prev = prev 1 對稱的另一邊;i 是尾就改 tail
push_front(i) nodes[i].prev = NIL
nodes[i].next = head		 2 i 自己的兩根線重新指向。注意 unlink 沒有清掉 i 的舊 prev/next——反正這裡會蓋掉,少寫兩次
if head != NIL: nodes[head].prev = i 0 或 1 舊頭要回指新頭。空表時沒有舊頭
head = i
if tail == NIL: tail = i		 1 或 2 空表插入時,唯一節點同時是頭也是尾

if self.head != i 這個短路值得寫:節點已經是 MRU 時, unlink + push_front 的結果跟不做完全一樣(兩步都是冪等形狀), 但會白白付 5 次寫。連續讀同一個 hot key 是 cache 最常見的流量模式——這行是免費的。

3 · 滿了:淘汰 tail,原地回收槽位

put 有三條路。同 key:改值 + promote,沒人被淘汰。有空位: nodes.push(),新索引 = 目前長度。滿了: 受害者一定是 tail——這是唯一不用搜尋就知道的答案,而這正是鏈表存在的理由。

淘汰時不從 Vec 刪掉那個 node。 Vec::remove(i) 會把後面所有元素往前搬(O(n) memmove), 而且會讓所有 > i 的索引失效——map 裡存的全是索引,整張表當場報廢。 改成 mem::replace(&mut nodes[i], new_node):同一塊記憶體換人住, 舊的 (K, V) 完整取出來還給 caller。零 alloc、零 free、零 memmove。

這也是為什麼 Node 裡要存一份 key:淘汰時手上只有 arena 索引, 但你必須把 map 裡那條 key -> i 也刪掉,否則 map 會指向一個已經換人的槽位。 代價是 K: Clone,key 存兩份。省掉這份 clone 的路(Rc<K>、raw entry) 都更複雜——面試時把這個取捨講出來,然後往前走。

4 · 為什麼不是 Vec::remove?為什麼不是 Rc<RefCell>?

面試官問「你為什麼這樣存鏈表」時,他要的不是「因為 Rust 借用檢查很麻煩」, 而是這張表。每一列都是一個真的有人寫過的方案,每一列都在某一欄破功。

Rc<RefCell<Node>> 版還有一個 Rust 專屬的坑:雙向鏈表是環, prev 必須用 Weak,否則 refcount 永遠歸不了零——整個 cache 洩漏。 index 版連這個問題都不存在:usize 沒有 ownership,借用檢查器根本不參與。 節點的生命週期由 Vec 統一管,這才是「把 unsafe 的形狀寫成 safe 的」的標準做法。

5 · 沒做的 remove():free list 的伏筆

這版只有 get / put / peek,沒有 remove(&K)。 因為 remove 會在 arena 中間留下一個洞——而洞不能靠 Vec::remove 填(索引會全爛), 只能記進一條空閒槽位鏈(free list),下次 insert 優先從那裡取。

這條 free list 用什麼串?還是索引,存在那個空槽的 next 欄位裡—— 空節點的 prev/next 反正沒人用,拿來當 free list 的指標,零額外空間。 這正是 arena_lockfree 的主題;加上多執行緒之後,同一個索引被兩個 thread 同時 pop 就會撞出 ABA,於是需要 generation tag。這一課的 usize 索引,就是那一課的地基。
