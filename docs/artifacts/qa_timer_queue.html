qa 圖解 · timer queue · Q7 認題:periodic / interval / what runs next

timer queue:park 不輪詢、舊 deadline 不飄移、eventfd 戳醒

N 個 node 各有自己的健檢週期——誰下一個跑?該睡多久?每個 event loop / async runtime 裡都有一顆這種東西(Delay 的計時 thread、heartbeat 偵測、epoll_wait 的 timeout 參數,背後全是它)。這頁釘死四件事:deadline vs interval、從舊 deadline 重排為什麼不飄移(互動 stepper 對照錯誤版)、為什麼不 thread-per-timer、以及 park 中的 loop 怎麼被跨 thread 的 schedule 戳醒。

0 · 它是誰:兩個 API,一個被動資料結構

schedule(id, first_at, interval)  // 「id 第一次在 first_at 響,之後每 interval 響一次」
next_deadline() -> Option<u64>    // 「下一個最早要響的時間點」= park 的目標
pop_due(now) -> Vec<id>           // 「到 now 為止全部到期的,吐出來 + 自動重排」

關鍵定位:它刻意只當被動的資料結構——「等待」是呼叫它的 event loop 的工作。迴圈形狀:

loop {
    let timeout = q.next_deadline().map(|d| d.saturating_sub(now()));
    poller.wait(timeout);              // epoll_wait(timeout) 或 Condvar::wait_timeout
    for id in q.pop_due(now()) { fire(id); }
}                                      // park 到 deadline,不是每 10ms 醒來輪詢

deadline vs interval:deadline 是絕對時間點(幾點響),interval 是相對時距(響完隔多久再響)。schedule(1, 100, 100) → 響鈴序列 100, 200, 300…;schedule(2, 150, 300) → 150, 450, 750…。內部一顆 BinaryHeap<Reverse<(deadline, id, interval)>>:tuple 排序天然給出 (deadline, id) 的 tie-break,Reverse 把 max-heap 翻成 min-heap——免手寫 Ord。

1 · 互動:pop_due(300)——從「舊 deadline」還是「now」重排?

情境:loop 忙別的事,忙到 t=300 才回來看 timer(遲到了)。t1 = (100, 每100),t2 = (150, 每300)。切換兩種重排策略,走同一次 pop_due(300):

heap(最小在上)

(100, t1)
(150, t2)
now = 300,開始收帳

pop_due 吐出

[]
 
 

正解版收 [1, 2, 1, 1](100/150/200/300 四響全補發)、下一響 400——網格固定在 100 的倍數,遲到不改變節奏。飄移版只收 [1, 2],漏掉 200/300 兩響,而且之後每次晚 5ms 醒來,整個節奏就永久往後滑 5ms——監控系統的「每分鐘一筆」會慢慢變成「每 61 秒一筆」。assert!(interval >= 1) 的理由也在這:interval 0 會讓「重排後仍 ≤ now」永遠成立,pop_due 停不下來。

2 · 為什麼不 thread-per-timer?

理由帳
規模伺服器 timer 動輒上萬(每條連線一個 idle timeout)。一萬條 sleep thread = 20 GB stack + scheduler 負擔;一顆 heap + 一個等待者管百萬個 timer——tokio 內部就是這樣。
跟 IO 等待合併event loop 本來就 park 在 epoll_wait 等 socket;把 next_deadline() 塞進它的 timeout 參數,一次等待同時服務 IO 和 timer。thread 睡覺沒辦法合併。
可測試性pop_due(now) 把「現在幾點」當參數注入,不碰真實時鐘——測試決定性、瞬間跑完、不用 sleep。面試加分句。

3 · park 中,別的 thread 呼叫 schedule(9, 350, …) 會怎樣?

loop 正 park 到 400,heap 裡多了 (350, 9)——但沒有人看。timer 9 會遲到到 400(或碰巧被 IO 事件吵醒)才補發。資料結構是對的,錯過的是「醒來的理由」。解法 = 跨 thread 戳醒睡著的人,按 park 形式分兩條,形狀同構:

park 在哪叫醒的工具
Condvar::wait_timeoutschedule 之後 notify_one()——executor drill 的 park-token 近親
epoll_wait(timeout)一顆 eventfd 常駐 epoll set;scheduling thread 對它 write(1) → loop 立刻返回。tokio(mio 的 Waker)在 Linux 上就是這個;eventfd 出現前的老寫法叫 self-pipe trick

醒來後 loop 不需要任何特殊處理——回到迴圈開頭重算 next_deadline(),看到 350,重新 park。這就是「重算、再睡」迴圈形狀的好處:真事件、eventfd、spurious wakeup 一律走同一條路,天然正確。標準優化:只在新 deadline < 目前最早時才戳——排 500 的話 loop 本來就會在 400 醒來自然看到,戳了是白醒。

“Scheduling from another thread needs a wakeup path: on Linux that's an eventfd registered in the same epoll set — and you only write to it when the new deadline beats the current earliest.” 跨 thread schedule 的一句話版。

認模式:「資料結構被動、等待者主動、外人用一根 fd/condvar 戳醒」——executor 的 park-token、mio 的 eventfd Waker、self-pipe trick,同一題的三次出現。面試裡認出「這是同一題」比背三套實作值錢。

4 · 規模轉折點 + 句庫

heap 是 O(log n) / op。timer 極多(百萬級、大多會被取消,像 TCP retransmit timer)時換 hashed timer wheel:O(1) 攤銷,代價是精度(槽粒度)——「用精度換吞吐」。kernel 和 tokio 的 timer 都是 wheel。面試預設 heap 起手,被追問再講轉折。

“The heap answers ‘who's earliest' in O(log n); next_deadline is my park target — park, don't poll. I reschedule from the old deadline, not from now, so lateness never shifts the grid — missed periods replay naturally because the new deadline can still be ≤ now.” Q7 口述的骨幹,一口氣講完三個設計點。
“Ordering-hungry APIs pay for ordering: epoll's ready list is O(1) because it promises none; a timer queue must answer ‘who's next', so it pays the log — or trades precision for O(1) with a timer wheel.” 跟 epoll 內部那頁的收束句對接。
