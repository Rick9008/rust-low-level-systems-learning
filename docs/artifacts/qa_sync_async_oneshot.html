sync JobHandle vs async JoinFuture:同一個 oneshot,換一個等待機制

thread_pool 的 JobHandle 和 file_io_offload 的 JoinFuture 是同一個 oneshot 骨架——同一塊 Arc<Mutex<Option<Result<T>>>>、同一個 take()(單消費者)、panic 同樣用 resume_unwind 在等待端重拋。整條差別只有一個零件:怎麼「等」。搞懂這一頁,sync/async 到底差在哪就清了——它差的是「怎麼等」,不是「能不能做」。

反白的兩列就是全部差異:Condvar → Waker。其餘每一格都相同——包含 panic 那條 resume_unwind,因為兩邊都是 單消費者(take 把值 move 給唯一的等待者)。

1 · 唯一被換掉的零件:等 = 佔住 thread,還是讓出 thread

為什麼要換?因為「等」的成本完全不同。sync 的等是把整條 OS thread park 在那裡空轉;async 的等是把 task 讓出去,讓 executor 拿同一條 thread 去跑別的 task。

2 · poll() 三條 arm = join() 三條 arm,換個殼

把兩邊的核心並排,你會發現邏輯一比一對應——只有「還沒好」那條 arm 的動作不同(park vs 掛 waker):

// async:JoinFuture::poll(reference/src/file_io_offload.rs)
match st.result.take() {                 // take → 單消費者(oneshot)
    Some(Ok(v))  => Poll::Ready(v),       // 好了 → 交值
    Some(Err(p)) => resume_unwind(p),  // worker panic → 等待端重拋(= join 那行)
    None => {                             // 還沒好
        st.waker = Some(cx.waker().clone());  // ← 掛 waker,不 park
        Poll::Pending                          // ← 讓出去
    }
}

對照 sync 的 JobHandle::join:Ok → 回值、Err → resume_unwind(同一行)、None → Condvar::wait_while 睡。同構到只差「還沒好時做什麼」。

3 · async 專屬的一個正確性契約:每次 poll 存「最新」的 waker

None arm 那行 st.waker = Some(cx.waker().clone()) 是覆蓋,不是「只存第一次」。因為同一個 future 可能被不同 task poll、waker 會變——存了舊 waker,喚醒時會敲錯人(甚至敲一個已經移走的 task),結果就是永遠醒不過來。

這是「醒來重查 predicate」在 async 世界的對應物:sync 靠 wait_while 每次醒來重查狀態;async 靠「存最新 waker + poll 時重查槽」。兩邊都不信任「喚醒事件本身」,只信任「持久狀態 + 重查」。

4 · 兩條正交軸 + 一條階梯

把整串收成一張圖:「怎麼等」和「幾個人拿」是兩條互相垂直的軸,四格都做得出來。

oneshot(1 消費者)broadcast(N 消費者)
sync(Condvar,park thread)JobHandle手搓 Mutex+Condvar+clone+notify_all
async(Waker,讓出 task)JoinFuture / tokio::sync::oneshotfutures::Shared / tokio::sync::broadcast
  • 縱軸 sync↔async = 怎麼等:park OS thread,還是掛 waker 讓出。換的是 Condvar ↔ Waker。
  • 橫軸 oneshot↔broadcast = 幾個人拿:take()(move,1 人)還是 clone()(peek,N 人);broadcast 還要 notify_all / 存多個 waker,且 panic 只能降級成可 Clone 的失敗值。

一條線收乾淨:JobHandle(sync oneshot)→ 換 Waker → JoinFuture(async oneshot)→ 多消費者 → futures::Shared(async broadcast)。同一個骨架,沿兩條軸各走一步。

5 · 面試句庫

“JoinFuture is the async twin of JobHandle: same Arc<Mutex<Option<Result<T>>>> oneshot, same take, same resume_unwind on the panic arm. The only difference is how you wait — sync parks the OS thread on a Condvar; async stores a Waker and returns Poll::Pending, handing the thread back to the executor to run other tasks.” 一句話把 sync/async 的本質差異釘死在「怎麼等」。
“That's why one async thread can hold tens of thousands of connections that are all ‘waiting’ — they're all Pending, yielded; sync would need one parked thread each.” 接著把「為什麼 async 省 thread」講出來。
“sync/async is orthogonal to oneshot/broadcast. Waiting is one axis (Condvar vs Waker); how many consumers get the result is the other (take vs clone). All four cells exist.” 秀你知道這是兩條軸、不是一條。
