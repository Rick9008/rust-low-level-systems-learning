CAS 只會問一個問題:「這個字,還是不是我上次看到的那個值?」 它問不出「這中間發生過什麼」。ABA 就住在這個縫裡—— 而修補它的東西,只是把一個計數器塞進同一個 u64 的高 32 位。

1 · ABA 重現機

下面是教科書級的 ABA 劇本,一步一步排出來。 stack 是 top → A → B → C;T1 進了 pop()、 讀完 (top, A.next) 就被搶佔;T2 在它睡著的期間把整個世界翻了一遍。 先用沒有 generation tag 的版本跑一次(CAS 只比 index), 再把開關打開,用同一組交錯再跑一次。

不變量只有一條:任一時刻,一個槽位只能待在一條鏈上 ——stack 鏈、free 鏈,或某個執行緒手裡,三選一。 無 gen 版的 CAS 成功之後,slot[1] 同時掛在 stack 頂與 free 鏈上,這條線就斷了。 注意最毒的地方:當下沒有任何東西爆炸。元素數看起來還對, 程式繼續跑,直到某個 push 把 B 當空槽 alloc 出去、覆寫、改寫 B.next ——那一刻 C 從 stack 上蒸發,而現場離犯罪現場已經十萬八千里。

2 · 為什麼是 index 的 ABA,不是 pointer 的 ABA

課本的 Treiber stack 用裸指標:Box::into_raw 推進去、Box::from_raw 撿回來。 它同時踩兩顆雷——ABA(同一個位址被 malloc 重新發出來)與 use-after-free(落後的 popper 去讀 A.next,而 A 的那塊記憶體已經還給 allocator 了)。 後者是立即的 UB:讀已釋放記憶體,ASan 會叫,但通常太晚。

這個模組把指標換成 arena 索引:所有節點住在一個 Box<[Slot<T>]> 裡,永遠不釋放。於是:

裸指標 Treiberarena + index(本模組)
落後的 popper 讀 A.next use-after-free — A 可能已被 free 安全 — 索引永遠在 bounds 內,最壞讀到 stale 值
身分被重複發放 malloc 把同一個位址發回來 free 鏈把同一個 index 發回來
ABA 還在 還在 — arena 只解掉回收安全,沒解掉身分重用
回收成本 epoch / hazard pointer(才敢真的 free) 零 — 從來不 free,只是換一條鏈掛

這就是 Rust 學 lock-free 先走 arena 的原因:它把「什麼時候可以真的釋放記憶體」這個最難的問題整個拿掉, 只留下 ABA 一顆雷,而 ABA 有一個 30 行的解。 next 也因此必須是 AtomicU32 而不是普通欄位——落後的 popper 會 讀到「已被回收再利用」槽位的 next。那個值 stale 沒關係(gen 會讓它的 CAS 失敗), 但那個並發讀寫本身在 C11 模型裡就是 data race = UB。 「無害的競爭」在 Rust 裡不存在,loom 會直接抓。

3 · 一個 u64 裡的兩個世界

generation tag 要跟 index 原子地一起比對——分成兩個 atomic 就白做了 (你會在讀 gen 與讀 idx 之間再開一個新的 ABA 視窗)。 做法:塞進同一個字,用一次單字 CAS 同時比對兩者。 

/// head 打包格式:[generation:32 | index:32]
fn pack(generation: u32, idx: u32) -> u64 {
    (u64::from(generation) << 32) | u64::from(idx)
}
fn unpack(v: u64) -> (u32, u32) {
    ((v >> 32) as u32, v as u32)
}

// 每一次成功的 CAS 都 bump gen —— 這是整個修補的全部內容
self.head.compare_exchange_weak(
    cur,
    pack(generation.wrapping_add(1), next),
    Ordering::Acquire,
    Ordering::Acquire,
)

上面那台重現機的 head 欄位就是這個字。開著 gen 跑到第 5 步,你會看到 cur = 0x0000_0005_0000_0000 而 head = 0x0000_0008_0000_0000 ——低 32 位一模一樣(都是 index 0),高 32 位差了 3。 CAS 比的是整個 64 bit,所以它失敗。這就是全部的魔法。

誠實聲明的殘餘風險:gen 是 u32,wrapping_add 在 232 次成功 CAS 後迴繞。 要中招,一條執行緒得剛好卡在 CAS 前、睡到另外 42 億次操作跑完、 而且醒來時 index 也剛好對上。實務上接受;不接受的話,答案是 128-bit CAS (AtomicU128 不在 stable std)或直接跳到 epoch-based reclamation。 面試被問「gen 幾位夠?」——正確答案不是數字,是「取決於你願意承擔多長的 stall」。

4 · free 鏈也是同一個 stack

空槽管理用第二條 lock-free 鏈(free: AtomicU64),和主鏈共用 Slot::next 欄位—— 一個槽位任一時刻只在其中一條上。它是 stack,所以它也會 ABA,所以它也帶 gen。 整份 code 裡只有兩個 AtomicU64,兩個都是 (gen, idx),理由一模一樣。

值的所有權像接力棒: stack 鏈 → popper 手中 → free 鏈 → allocator 手中 → stack 鏈。 每一棒交接都必須是一條 Release → Acquire 邊,否則下一任會看到上一任沒寫完的 value。

交接ordering它保證什麼
push:寫 value/next → CAS headRelease任何 Acquire 讀到新 head 的 popper,必看到完整的 value
pop:CAS head 成功Acquire配 pusher 的 Release,才敢 assume_init_read
free_slot:CAS freeRelease「我讀完 value 了」——下一任才能安全覆寫
alloc_slot:CAS free 成功Acquire配前任的 Release,獨佔這個槽位直到 push 發布它
迴圈裡讀 slots[i].nextRelaxed讀到 stale 值是被允許的——gen 會讓後面的 CAS 失敗;它只需要不是 UB

誠實補充(這個 arena 其實比課本更難壞):上面那台重現機是教科書劇本 ——「T2 pop A、pop B,再把 A push 回來」。但本模組的 free 鏈是 LIFO: 連續 free 掉 A、B 之後,鏈頂是 B,所以下一個 alloc_slot 其實會拿到 B、不是 A。 事實上,只要干擾者只有一條執行緒、而且每個 push/pop 都完整跑完, LIFO free 鏈會把 next 鏈原封不動地還原回去,舊 CAS 就算成功也剛好是對的。 真正會炸的交錯需要第三個角色:一條執行緒 alloc_slot 之後、CAS head 之前被搶佔 (手上握著一個槽位),它的 push 讓 stack 頂在 A 被重新 alloc 之前就已經換人。 機制完全相同,只是觸發條件更刁——這正是為什麼要用 loom 窮舉,而不是靠人腦想交錯。

5 · lock-free != wait-free

開著 gen 跑重現機,T1 的 retry 計數會變成 1:它的 CAS 失敗、重讀、重試。 這不是 bug,是 lock-free 的定義: 每一次 CAS 失敗,都代表別人成功了 ⇒ 系統整體必有進展。 但單一執行緒可能每次都輸、永遠餓死——所以 lock-free 不保證延遲上界。

wait-free(每條執行緒都在有界步數內完成)更強,實作也貴得多 (通常要 announce array + helping)。這個模組不做,也不該做: 面試講得出這兩者的差別,比實作 wait-free 值錢得多。

6 · loom 抓得到,壓力測試抓不到

ABA 的觸發視窗是「讀完 next、CAS 之前」的幾個 cycle。 用真 OS thread 壓力測試去撞它,是拿亂數當證明: x86 上跑上億次可能一次都排不到那條交錯。 loom 不是跑很多次,是在 C11 模型上窮舉所有交錯。 

cargo test -p reference --test loom_arena

三個 model:雙 pusher(不丟不重)、雙 popper 搶同一個 head(恰好一人得手)、 以及 loom_aba_recycle_race——一條執行緒 pop 卡半路, 另一條 pop → 槽位回收 → push 重用同一槽位。 sync_shim 讓同一份 core_impl.rs 被兩套記憶體模型實例化: lib 走 std(production 路徑零依賴),loom 測試用 #[path] include 同一份原始碼。 loom 驗過的,就是出貨的那份邏輯。

Production 對照:真實世界的 lock-free 容器不靠 generation tag,靠 crossbeam-epoch(epoch-based reclamation)——每條執行緒進臨界區時「pin」一個 epoch, 退休的節點掛進 garbage list,等到所有執行緒都推進過那個 epoch 才真的 free。 好處:不限容量、沒有 gen 迴繞、也能回收記憶體。代價:每次操作要 pin/unpin, 而且 reclamation 本身是一整套機制。 另一條路是 hazard pointer(每條執行緒公告它正在讀哪個節點)。 bounded 池的現成品:crossbeam::queue::ArrayQueue。
