trie

左邊是你在白板上畫的那棵樹,右邊是它在記憶體裡真正的樣子:一個 Vec<Node>。 這個模組要教的不是「什麼是 trie」——是為什麼子節點存的是 usize 索引,而不是 Box。

1 · 一棵樹,兩種看法

insert 就是沿著字元往下走;走不到的地方就 nodes.push(Node::new()), 而新節點的索引就是 push 之前的 len()——arena 手法的全部魔法就這一行。 盯著右邊那個 Vec:節點只會往尾巴長,沒有任何一次「為單一節點」的 heap 配置。

樹  /  你腦中的模型

2 · contains("app") 與 starts_with("app") 差在最後一行

兩個查詢共用同一個 walk(),差別只在拿到節點索引之後看不看 is_end。 面試第一坑就在這:只 insert 過 "apple" 的 trie 裡,"app" 的 路徑是存在的——但沒有詞在那裡結束。答 true 就掛了。 

fn walk(&self, s: &str) -> Option<usize> { /* 逐字元跳索引,斷了就 None */ }

pub fn contains(&self, word: &str) -> bool {
    self.walk(word).is_some_and(|n| self.nodes[n].is_end)  // 路徑存在,且是詞尾
}
pub fn starts_with(&self, prefix: &str) -> bool {
    self.walk(prefix).is_some()                            // 路徑存在就夠
}

arena  /  兩種情況的節點完全一樣

切換兩個情境:arena 的 6 個節點一格都沒變,連 children 欄都一樣—— 唯一的差別是 nodes[3].is_end 那一個 bool。 starts_with("app") 兩邊都是 true;contains("app") 卻從 false 翻成 true。 這個 bool 就是「路過」與「抵達」的全部區別,也是 remove() 只要清掉它、不必動任何節點的原因(懶刪除:節點留在 arena,前綴詞不受影響)。

3 · 為什麼 child 是 usize,不是 Box<Node>

「節點指向子節點」在 Rust 裡是出了名的痛。Box 給你單一所有權; Rc<RefCell<Node>> 給你共享,代價是執行期 borrow 檢查、環狀洩漏、 每個節點一次配置。arena 的做法是直接繞開整個問題:節點全部歸那個 Vec 所有, 節點之間只用 usize 互相參照——索引不是借用,借用檢查器不會看它一眼。

做法配置Drop借用檢查走訪局部性
[Option<Box<Node>>; 26] 每個節點一次 malloc 遞迴析構,深 trie 可能爆 stack 單一所有權;要回頭指 parent 就卡死 節點散落 heap,每跳一層一次 cache miss
Rc<RefCell<Node>> 每節點一次配置 + 兩個 refcount 有環就洩漏,parent 得改用 Weak 推到執行期:borrow_mut() 會 panic 最差:多一層間接
Vec<Node> + usize(本實作) 攤平成 Vec 的 O(log n) 次成長 drop 一個 Vec,一次 free 不存在:索引不是引用 節點連續,walk 幾乎是線性掃

這就是「索引是窮人的指標」——它是這個 repo 的骨幹手法,不是 trie 專屬的小聰明: lru 的雙向鏈表(prev/next 是 usize,躲掉 Rc<RefCell> + Weak)、 tree 的 parent/child(同一組對照寫得最完整)、 arena_lockfree 的 free list(索引再加上 generation tag 去打 ABA)。 先在 trie 這個最單純的場景把它看熟,後面那三個模組是同一招的變奏。

代價要說清楚:索引沒有型別安全。編譯器不會阻止你拿 A 樹的索引去查 B 樹, 也不會阻止你用一個已經被回收的槽位索引(在會回收的 arena 裡,那就是 use-after-free 的邏輯版)。 Rust 只把它降級成「錯的答案」而非 UB——真要修就得上 generation tag, 那正是 arena_lockfree 在做的事。本實作靠「arena 只長不縮」把這個問題定義掉了。

4 · children 怎麼存:26 格陣列 vs HashMap

本實作選 [Option<usize>; 26]:字母表約束死在 a-z (其他字元在 Trie::idx 這個唯一入口直接 assert! panic), 查 child 就是一次陣列索引——零 hash、零分支預測失敗。 代價是稀疏節點的浪費:只有一個 child 的節點,照樣扛著 26 個槽。

存法child 查找每節點空間適用
[Option<usize>; 26](本實作) O(1) 陣列索引 424 B 固定 字母表小且密(a-z):autocomplete、字典
HashMap<char, usize> O(1) 期望 + hash 成本 按需 + HashMap 開銷 字母表大(Unicode)、極稀疏
排序 Vec<(char, usize)> O(log deg) 二分 最省 記憶體敏感、degree 小

順帶一個實測到的坑:size_of::<Node>() 是 424 B, 不是直覺的 26 × 8 = 208 B。因為 usize 沒有 niche(0 是合法值), Option<usize> 得額外帶一個 tag word,整整 16 B。 把型別換成 Option<NonZeroUsize>(root 固定是 0,子節點索引本來就 >= 1) 就吃得到 niche optimization,一路降回 216 B;改用 u32 + 哨兵值再降到 108 B。 「字母表多大」只是空間帳的一半,另一半是你有沒有給編譯器一個 niche。

5 · O(L),而且與詞庫大小無關

insert / contains / starts_with / remove 全是 O(L),L = key 長度。 存 10 個詞跟存 1000 萬個詞,查一個 5 字母的詞都是走 5 步、跳 5 次索引。 但這不是「比 HashSet 快」——HashSet 光是把字串 hash 過一遍也是 O(L)—— 真正的賣點是 trie 能做 HashSet 根本做不到的事。

操作HashSet<String>trie
精確查詢 contains(w)O(L) hash + O(L) 比對O(L) 跳索引
前綴查詢 starts_with(p) 做不到:只能掃全表 O(N · L) O(L),而且走完就站在子樹的根上
列出所有以 p 開頭的詞O(N · L)O(L) + 輸出量
空間每個詞完整存一份共享前綴,但每節點 424 B

autocomplete、IP 路由表的 longest prefix match、fst crate 的靜態詞典—— 它們要的都是「走到前綴末端那個節點」這件事本身, 因為那個節點就是「所有以 p 開頭的詞」的子樹根。HashSet 手上沒有這個東西。
