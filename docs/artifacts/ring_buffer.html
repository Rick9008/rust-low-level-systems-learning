ring_buffer

固定容量、push/pop O(1)、零 realloc。難度不在資料結構——在 wrap 那一步的算術,以及一個面試必問: 為什麼經典 head/tail 版要犧牲一格,而這版一格都不用犧牲。

1 · 環是怎麼轉的

這個實作只存兩個數字:head(最舊元素的實體索引)和 len(現在有幾個)。 寫入位置不是存出來的,是算出來的:wrap(head + len)。 len 一存在,滿/空就沒有任何歧義——len == cap 是滿,len == 0 是空。 按按鈕,盯著下面那三行算術。

實體索引: 0 → 1 → 2 → 3 → 4 ↺ 回到 0 接縫在 slot 4 與 slot 0 之間
head0
len0
cap5
write idx0
read idx0
stateempty

cap = 5,故意不是 2 的冪。這版的 wrap 是條件減法,不是 & mask—— 容量可以是任意正整數。
滿的時候看那格。len == cap 時 wrap(head + len) == head: 寫入位置與讀取位置疊在同一格。兩個 tag 同時亮起來的那一瞬間,就是下一節整節在講的東西—— 如果你手上只有 head 和 tail 這兩個索引,你根本分不出這是滿還是空。

滿時的兩種策略,這個 crate 兩種都給,由 caller 選。
push_back 回 Err(item):值歸還呼叫端,ring 不替你決定要 spin、park 還是丟棄 ——backpressure 是 caller 的事。工作佇列用這個。
push_overwrite 回 Some(evicted):擠掉最舊的那個並交還給你。 telemetry、最近 N 筆 log 用這個——新資料比舊資料值錢。

2 · 那一格,你到底有沒有浪費

經典教科書版本存的是 head 和 tail,沒有 len。 問題來了:head == tail 是空,還是滿?下面這個環沒有 len, 你只能看那兩個數字。把它填滿,再把它清空,比對一下那兩個數字。

head0
tail0
cap4
可用容量4
真實元素數0
判定 head == tail == 0。環是空的——目前為止沒問題。

「真實元素數」那一格是作弊用的:它不存在於這個表示法裡,只是讓你看見 head/tail 看不見的真相。 左邊模式按 4 次 push,tail 繞回 0,head == tail == 0—— 和全空時一模一樣的兩個數字。判定崩潰。
右邊模式是教科書解法:規定滿 = wrap(tail + 1) == head,永遠留一格不填。 head == tail 於是只可能是空。代價:4 格只裝得下 3 個,cap 越小虧越大 (cap = 2 直接砍半)。

第三條路就是第 1 節那個環:多存一個 len。 len == 0 空、len == cap 滿,兩個狀態的數字不同,不需要犧牲任何一格, 也不需要 cap 是 2 的冪。單執行緒下,這是最簡單而且正確的形狀。 ——這正是面試官問「你怎麼判斷滿」時真正想聽的:三種表示法,各自的代價是什麼。

索引表示法滿 / 空判定代價
head + tail,犧牲一格 滿 wrap(tail+1)==head
空 head==tail		 浪費 1 slot;每個 next() 都要 wrap
head + tail,自由跑計數器(不 wrap) 滿 tail-head==cap
空 tail-head==0		 要求 cap 是 2 的冪(& mask 取實體位)+ wrapping 算術。但兩個計數器各自只有一個寫者——這就是 SPSC 選它的原因
head + len(本實作) 滿 len==cap
空 len==0		 最直白,不浪費格、不限 cap。但 len 被 push 和 pop 兩方共寫——並發下不可用(第 5 節)

3 · wrap 的三種寫法

wrap(i) 每次 push 和每次 pop 都會跑到。它是這個資料結構的熱點, 而它的三種寫法差了一個數量級。

寫法成本限制
i % cap 整數除法,x86 約 20-40 cycle 無。任意 cap 都對——只是慢
i & (cap - 1) 1 cycle 強制 cap 是 2 的冪。不是的話會跳格——那是正確性 bug,不是效能問題
if i >= cap { i - cap } else { i } 1 cmp + 1 sub 前置條件 i < 2*cap。cap 任意

條件減法為什麼一次就夠?不變量是 head < cap 且 len <= cap, 所以送進 wrap() 的最大值是 head + len <= (cap-1) + cap = 2*cap - 1。 減一次 cap 之後必然落在 [0, cap)。pop 那邊 head + 1 <= cap,更寬鬆。 ——這個前置條件必須證明,不能用感覺的;它是把 % 換掉的唯一憑據。

4 · Vec<Option<T>> 還是 Vec<MaybeUninit<T>>

這版用 Vec<Option<T>>:每格多一個 discriminant(T 有 niche 時, 像 NonZero 或參照,那個 tag 是免費的),換來零 unsafe。 pop 就是 self.buf[self.head].take(),Drop 由編譯器處理,不用你維護任何東西。

MaybeUninit 版密實一點,但你要自己維護「哪幾格已經初始化」這個不變量, 還要手寫 Drop 去 drop 剩下的元素——一整類 UB 風險,換幾個 byte。 面試先寫 Option 版,被追問再談升級路徑。真的非升不可的場景是下一節: 跨執行緒共享時,Vec 的 &mut 拿不到,你會被逼到 UnsafeCell<MaybeUninit<T>>。

5 · len 活不過並發

len 是這整個模組的支柱:它讓滿/空判定變成一行,讓那一格不必被犧牲。 但把同一份程式碼放進兩條執行緒——一條只 push,一條只 pop,連 SPSC 都算不上激烈—— 它立刻壞掉,而且壞在你看不見的地方。 len 是唯一被兩個角色同時寫的變數:push 做 +1,pop 做 -1。

thread A — push_back

if len == cap { return Err }
buf[wrap(head + len)] = x
len = len + 1
shared 3 len

thread B — pop_front

if len == 0 { return None }
head = wrap(head + 1)
len = len - 1
結果 起始 len = 3。A 推入一個、B 取走一個,正確的結果是 len = 3。按「執行」。

「那我把 len 換成 AtomicUsize 就好了吧?」——不行,而且錯兩層。
第一層:len += 1 是 read-modify-write,必須換成 fetch_add, 否則就是上面那個 lost update。這層還救得回來。
第二層救不回來:if len == cap 和 len = len + 1 是兩個記憶體操作。 fetch_add 只讓「加」變原子,不讓「檢查完再加」變原子。 A 檢查完發現沒滿,還沒寫進去,B 就把它的觀察作廢了。這是 TOCTOU,不是 ordering 問題—— 要修就得上 CAS 迴圈或鎖,而那正是我們想避開的東西。

spsc_ring 的答案是把 len 丟掉。改存兩個只增不減的自由跑計數器: head 只有 consumer 寫、tail 只有 producer 寫。 每個變數恰好一個寫者,於是沒有 read-modify-write,沒有 CAS,沒有鎖。 tail - head 就是元素數,滿/空判定跟這裡一樣不必犧牲格子。 代價是容量必須是 2 的冪(要用 & mask 取實體位), 以及一個全新的、遠比 index 算術難的問題:那兩個計數器之間看不見的 happens-before 邊。

追問:那 push_overwrite(滿時擠掉最舊)能 lock-free 嗎?
能,但要換招。producer 用 pop_front 擠舊的會動到 head——雙寫者,單寫者不變量破功; 而且滿時的寫入格正是 consumer 要讀的格,payload 直接 data race。 正解是反轉責任:producer 無條件覆寫、永不看 consumer;每格掛一個 sequence number, consumer 讀前讀後驗序號——序號變了 = 撕裂丟棄,跳了一整圈 = 被套圈,跳段追上並計數。 這就是 perf ring buffer / seqlock 一族;Disruptor 是同骨架的無損表親(producer 等最慢 consumer,不套圈)。 完整圖解 → qa_overwrite_ring.html。 45 分鐘的正解仍是 Arc<Mutex<SensorRing>> + AtomicU64 dropped 計數。
