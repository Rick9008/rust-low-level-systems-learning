reference / stage 2  ·  mutex & condvar

bounded_queue

Mutex 保護狀態,Condvar 傳遞「狀態變了」的消息。難的不是這兩個物件—— 是那句你以為只是風格問題的 while: 一次喚醒只是提示,不是保證。

1 · Condvar 的兩條不可依賴

wait() 做三件事:原子地放開 Mutex、睡下、被喚醒後重新搶回 Mutex。 放開與睡下必須原子,否則 notify 會插在中間,喚醒打在空氣上(lost wakeup)。 這部分作業系統幫你做對了。剩下兩件事它明說做不到:

一、spurious wakeup。 wait 可能沒有任何人 notify 就自己返回—— POSIX 明文允許,futex 實作上真實存在。 二、喚醒與搶鎖之間有窗口。 被 notify 的執行緒只是「被放進搶鎖佇列」, 不是「鎖已經是你的」。Rust 的 Mutex 不保證公平: 在它重新拿到鎖之前,一個剛好路過的執行緒可以直接插隊搶走鎖,把條件消費掉。

兩條合起來只推出一個結論:醒來必須重查條件。 所以形狀是 while !pred { wait() },不是 if !pred { wait() }。 下面那台機器就是為了讓你親眼看到 if 版怎麼死。

2 · predicate wait 模擬器

容量 3 的佇列,兩個 producer、三個 consumer,一把 Mutex、兩個 Condvar。 每張卡片按一次走一步:lock() → 查條件 → wait() 或進 body。 只有一個執行緒能持有 Mutex——鎖是畫面上一個真的物件,誰拿著就寫誰的名字。

「喚醒被偷走」是這台機器的核心:C1 空佇列 pop → 睡在 not_empty;P1 push(1) → notify_one 把 C1 放進搶鎖佇列; 但 C1 還沒拿到鎖,此時剛進門的 C2 直接搶走鎖、把那個元素拿走。 C1 終於拿到鎖時,佇列已經空了——它醒來的那個「理由」早就被消費掉了。 while 版重查條件、睡回去;if 版直接走進 body,在空佇列上 pop_front()。

3 · 同一組交錯,兩種形狀

Rust 的 Condvar::wait_while 就是把 while 迴圈包起來—— 它的存在本身就是在告訴你:這個迴圈不是選配。

if — 一票否決級的 bug

let mut st = lock().unwrap();
if st.buf.is_empty() && !st.closed {
    st = not_empty.wait(st).unwrap();
}
// 假設:醒來 ⇒ 有資料
st.buf.pop_front().unwrap()   // 空佇列 → panic

醒來只證明「曾經有人 notify 過,或什麼都沒發生」。 它不證明條件現在成立。這行 unwrap() 是在一個過期的前提上做決策。

while / wait_while — 唯一正確形狀

let mut st = lock().unwrap();
st = not_empty
    .wait_while(st, |s| s.buf.is_empty() && !s.closed)
    .unwrap();
// 保證:非空,或已 closed
let item = st.buf.pop_front();

每次醒來(含 spurious)都重查。條件不成立就再睡回去。 走出迴圈時,條件是在持鎖狀態下剛驗過的——沒有人能在中間插隊改掉它。

這也解釋了為什麼「wait 之前必須先持鎖」不是形式主義:條件的檢查與睡下之間若鬆手, 那個檢查結果立刻過期。Mutex 把「查條件」和「決定睡」黏成一個不可分割的動作。

4 · close 語意的三個決策點

close() 不只是把旗標設起來。它是 shutdown 路徑上唯一能把所有阻塞執行緒撈回來的機會, 三個決策點各對應一種資料遺失或永久卡死。

決策點本模組的選擇選錯的後果
pop() 遇到 closed 先 drain,空了才回 None。predicate 是 is_empty() && !closed—— closed 只讓等待者離開等待,不讓它跳過既有資料。 closed 立刻回 None → 佇列裡的工作項直接蒸發。close 只該擋新資料進來,不該擋舊資料出去。
push() 遇到 closed Err(PushError(item)) 把元素歸還。caller 保有所有權,可以記 log、走 fallback、或自己 drop。 回 Err(()) 吞掉元素 → caller 連「我丟了什麼」都不知道。這是靜默資料遺失。
close() 怎麼通知 兩個 condvar 都 notify_all。所有等待者都必須觀察到 closed 並離場。 notify_one 只放行一個,其餘永遠留在 condvar 佇列上——沒有下一次 notify 會來了(push 被拒不 notify、空 pop 也不 notify)。永久 deadlock。

上面模擬器的「三個 consumer 都在等」+「close() 只 notify_one」就是第三列: 一個被放行、兩個永遠停在 not_empty 上,程式再也不會結束。 這種 bug 不會在單元測試裡出現——它出現在 CI 的 timeout 裡。

5 · 一個 condvar 還是兩個

mod naive 用單一 condvar,正確,但不能用 notify_one: 等資料的 consumer 和等空位的 producer 睡在同一個佇列上, notify_one 可能叫醒一個 producer,它重查條件發現佇列還是滿的,睡回去—— 真正該醒的 consumer 沒被叫到。那是 lost wakeup,而且是你自己造成的,不是 OS 的鍋。

單 condvar(naive)雙 condvar(主體)
push 完成後notify_all(不知道誰在等什麼)notify_one(not_empty)
每次操作喚醒O(waiters) — thundering herdO(1)
正確性相同相同
代價被誤醒的執行緒重查條件再睡回去,白付一次 context switch多一個 Condvar 物件

把「等資料」與「等空位」拆成兩個 condvar 之後,notify 的目標明確了,notify_one 才安全。 這是把「誰在等什麼」這個資訊編碼進資料結構,而不是每次都廣播出去讓大家自己判斷。

6 · 先解鎖再 notify

drop(st) 之後才 notify_one()。若持鎖 notify,被喚醒的執行緒立刻嘗試搶鎖、 立刻失敗,再睡一次——多一趟 context switch,經典的 hurry-up-and-wait。

但要說清楚:順序反過來不影響正確性。被喚醒者拿到鎖後還是會重查條件 (只要你寫的是 while)。這純粹是效能取捨,不是 bug。 把效能取捨講成正確性問題,面試時會被追問到穿幫。
