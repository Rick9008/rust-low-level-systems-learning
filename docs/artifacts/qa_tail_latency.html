clarify playbook · Q4 圖解

Average throughput 與 tail latency 是兩個世界

同一個系統、同一批請求:吞吐問「一秒做完幾筆」,是系統視角的面積;延遲問「這一筆等了多久」,是單筆視角的分布。Q4(“Are we optimizing average throughput, or tail latency?”)問的是:你的 SLA 付錢買分布的中間,還是分布的最右端。

定義

先把兩個字拆開

Average throughput
一秒鐘做完幾筆(p50 世界)

看的是總量:1M ops/s。個別請求慢一點沒關係,只要輸送帶整體夠快。優化手段:批次、減少 syscall、cache 友善——這些常常犧牲單筆延遲換總量。

Tail latency
最倒楣那 0.1% 等了多久(p99.9 世界)

看的是分布最右端:一千筆裡最慢那一筆。平均再漂亮,只要偶爾有一筆卡 8ms,p99.9 就是 8ms。優化手段:消滅「偶發的壞事件」——preemption、page fault、鎖 convoy。

兩者不是蹺蹺板的兩端——批次可以同時把吞吐「和」單筆延遲都變大,所以它們是兩條獨立的軸,優化方向可以互相打架:

逐筆處理
~10 µs

吞吐

每筆立刻送,每筆都付一次 syscall 的錢。

第一筆得等最後一筆湊齊——兩個數字一起變大。

上面的 convoy 是「擴大器」;這裡是氣泡本身的型錄。共同點:每一個都藏在你看不見的層(scheduler、MMU、cache),在任何一條指令上隨機引爆,而且平均值幾乎看不到它們。

Preemption · ms 級
排程器把你換下 CPU,你沒有投票權

timeslice(典型 1–10ms)到期或更高優先級 thread 醒來,scheduler 強制收回 CPU——可能發生在任何指令上,包括握著鎖的時候。context switch 本體 ~1–5µs;真正貴的是「你睡了一整個 timeslice」和右邊那張卡。

“The scheduler can pause my thread mid-critical-section for a whole timeslice — and I don’t get a vote.”

Cache 汙染 · 恢復後數十 µs 的鈍化
你回來時,cache 已經是別人的了

你被換下去的期間,別的 thread 用同一顆核,把 L1/L2(和 TLB)住滿它的資料。你恢復後前幾千次存取全部 miss:每次 ~100ns DRAM,而不是 ~1ns L1。context switch 帳面 1–5µs,這條隱形尾巴常常更貴。

別跟 false sharing 混:那是兩顆核搶同一條 cache line 的互踢(單價 ~40–100ns/次);汙染是「無關資料把你擠出去」。

“After a context switch the caches belong to someone else — I pay thousands of misses to warm them back up.”

Page fault · minor ~µs / major 到 ms
一次記憶體存取,悄悄變成 kernel 之旅(或磁碟之旅)

Minor:page 在記憶體但你的 page table 還沒掛上——剛配置的 Vec 第一次寫、fork 後 copy-on-write;kernel 補個對應,~1µs 內。Major:page 在磁碟(被 swap 出去、mmap 還沒讀入)——一次隱形磁碟 I/O,數十 µs 到 ms。

對策:hot path 不配置、啟動時 pre-touch(with_capacity 只保留位址空間,每頁第一次寫還是會 fault)、latency 敏感就 mlock。

“Any memory touch can silently become disk I/O — that’s why latency-critical code pre-touches and never allocates on the hot path.”

Lock convoy · 上面任何一顆 × N 個 waiter
一個人的氣泡,全隊一起吃

第一層:持鎖者停擺(被 preempt / page fault),所有等鎖的人排在後面陪等——上圖 gantt。第二層:隊形一旦形成,鎖改用「叫醒睡著的人」交接,每次 handoff 付 µs 級 context switch,而 critical section 才幾十 ns——流量掉到 scheduler 檔,隊伍自我維持。公平鎖(FIFO)反而更糟:它保證把鎖交給睡著的人。

lock-free 消滅的是傳染,不是氣泡本身——你自己該倒楣還是倒楣,但別人照走。

“A preempted holder makes every waiter eat its timeslice — that’s the p99.9 story, and the only reason to go lock-free.”

儀表板級 SLA:答案是「便宜的都能用」

卡 1 的讀者是人,預算是秒。上面兩張圖的整場戰爭(20ns vs 3ms)發生在你預算的百萬分之一以下——人眼根本看不到 p99.9。這一句假設鎖進定界宣言後,設計全面降檔:

決策點儀表板級(秒)這樣做如果是機器級(ms/µs)才需要
鎖策略Arc<Mutex<…>> 直接上——預算差 6 個數量級,鎖成本隱形per-producer SPSC、lock-free ring(買 p99.9)
聚合1s tumbling window,每格折 count/sum/min/max更細的 window、增量 sketch
ingest 路徑放心批次:多攢幾 ms 沒人看得到,吞吐白拿逐筆低延遲路徑,避免攢批
讀路徑dashboard 每秒拉一次:拿鎖 → snapshot/merge,O(格數)無鎖讀(seqlock/RCU 風格)
不做清單busy-spin、lock-free、每筆 fsync——在 45 分鐘面試裡是負分的複雜度:你花掉的是寫完 core 的時間,買到的是沒人看得到的尾巴
“Since a human is reading this dashboard, I’ll assume seconds-level freshness. That lets me keep everything behind a plain mutex — lock-free only pays for itself at p99.9, and no human can see p99.9.” 定界宣言裡的 SLA 一句 + 它殺掉的整排昂貴設計。面試官若糾正(「這要餵自動告警,ms 級」),當場改一次、再鎖。
