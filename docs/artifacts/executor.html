executor

loop { poll; 沒事做就睡 }——六行程式碼,是整個 tokio 的骨架。 難的不是這個形狀,是那個把「睡」變成安全操作的東西: park 的 token 語意。沒有它,這個 loop 每天都會死鎖一次。

1 · 一輪:poll → Pending → park → wake → poll → Ready

poll 回 Pending 是一個承諾: 「我已經把你給我的 waker 交給某個未來會叫它的人。」 executor 敢睡,唯一的理由就是這個契約。 但契約沒說「那個人一定會等你睡著才叫」—— 下面兩個開關讓你自己排時序,看誰先誰後。

「wake 在 park 之前」不是理論上的怪例。三種常見走法都會踩到:deadline 幾乎已到、 OS 在 poll 返回後立刻搶佔 main 讓 timer 先跑、 或者根本是 YieldNow 這種在回傳 Pending 之前就自己 wake_by_ref() 的 future ——那時 executor 連 match 都還沒走完。reference 的測試兩種都有。

2 · token:讓「訊號」帶上「狀態」

unpark 不是一聲喊叫,是放一張通行證。 park 先看有沒有證:有就撕掉、立刻返回;沒有才睡。 證是飽和的——連叫十次 unpark 也只留下一張。 這一個設計決定,把下面這個致命窗口整個抹平: 

executor:  poll ── Pending ──┐                    ┌── park ──→ ?
                             └── 這幾十 ns 的窗口 ──┘
timer:                            └─ wake() → unpark() ─┘
時序真實 park(有 token)假想 park(無 token)
wake 在 park 之後 ✓ unpark 叫醒 sleeper → Ready ✓ 也能動 — bug 藏住了
wake 在 park 之前 ✓ permit 已放,park 直接穿過 → Ready ✗ 訊號蒸發 — parked forever

四格裡只有一格是紅的——而且是時序決定的那一格。 這就是為什麼「跑一百萬次壓力測試都過」證明不了任何事: 你只是沒排到那個交錯。跟 spsc_ring 的 Relaxed bug 是同一種病。

喚醒機制訊號早到會怎樣判決
park / unpark permit 存著,下次 park 消耗掉 安全 — 訊號帶狀態
裸 condvar.notify_one() + wait() 沒人在 wait → notify 當場丟棄 lost wakeup — 永眠
condvar + while !pred { wait } notify 丟了沒關係,醒來/進來都重查 predicate 安全 — 醒來重查條件
eventfd / self-pipe 計數器累加在 fd 裡,epoll 下次就看到 安全 — 同一招(見 event_loop)

一句話收掉:喚醒訊號要嘛帶狀態(permit / counter),要嘛醒來重查條件(predicate)—— 裸訊號不可靠。park 選前者,bounded_queue 選後者,兩者是同一課的兩面。 另外 park 允許虛假返回,所以 loop 裡醒來一律 re-poll: 「醒了」永遠不等於「好了」,只有 future 自己能回答。

3 · Waker 到底是什麼(這題一定會考)

Waker 是手寫的 trait object:一個資料指標 + 一張函式指標表。 它不能用 Box<dyn Fn>,因為它得是 Clone + Send + Sync 且 wake 要能吃掉自己(by value)——所以 RawWakerVTable 裡有四個槽, clone / wake / wake_by_ref / drop 各一。 

Waker
 ├─ data:   *const ()  ←── Arc::into_raw(Arc<ThreadWaker>)      ThreadWaker { thread: Thread }
 └─ vtable: &'static RawWakerVTable
             ├─ clone(p)        → Arc::increment_strong_count(p); RawWaker::new(p, VT)
             ├─ wake(p)         → Arc::from_raw(p).wake()          // 吃掉一次 strong
             ├─ wake_by_ref(p)  → (&*p).wake_by_ref()              // 不吃 strong
             └─ drop(p)         → drop(Arc::from_raw(p))           // strong -= 1

impl Wake for ThreadWaker {                  // std 幫你把上面那張表生出來
    fn wake(self: Arc<Self>)      { self.thread.unpark(); }
    fn wake_by_ref(self: &Arc<Self>) { self.thread.unpark(); }   // 省一次 Arc bump
}
let waker: Waker = Waker::from(Arc::new(ThreadWaker { thread: thread::current() }));

為什麼一定要 Arc?因為 waker 會被 clone 進任意執行緒 (timer、IO reactor、另一個 task),在未來任意時刻呼叫。 誰負責釋放?沒人知道——這正是共享所有權的定義。上面互動的 strong 計數走的就是這條路:

時刻strong發生什麼
Waker::from(Arc::new(..))0 → 1Arc 建立,into_raw 存進 RawWaker.data
cx.waker().clone() 進 slot1 → 2vtable 的 clone fn:increment_strong_count
timer w.wake()2 → 1wake(self: Arc<Self>) 按值吃掉,unpark 後 drop
block_on 返回1 → 0區域 waker drop → vtable 的 drop fn → 釋放

差別題:wake() 吃掉 Arc(恰好叫一次的場景,如 timer take() 後), wake_by_ref() 不吃(reactor 要留著 waker 給下一輪 IO)。 預設實作是 clone + wake,能跑但多一次 atomic bump——熱路徑上手動覆寫是有意義的。

4 · Pin:為什麼 future 一開始 poll 就不准搬家

async fn 編譯成一個 enum 狀態機。跨 await 存活的區域變數變成欄位, 而跨 await 的借用會變成指向自己欄位的指標——這個結構是 自引用的。memmove 一搬,內部指標就懸空。

Pin 就是那個承諾:「這個值直到 drop 為止不會再移動。」 std::pin::pin! 把 future 釘在當前 stack frame(零配置,block_on 用這個); Box::pin 釘在 heap(要把 future 塞進集合、跨函式回傳時用)。 loop 裡每輪的 fut.as_mut() 只是對同一個 pinned future 重新借一次 Pin<&mut F>——沒有搬家。

Delay 沒有自引用欄位 ⇒ 自動 Unpin ⇒ self.get_mut() 安全。 「所有 future 都得小心 Pin」是誤解;真正需要 Pin 保護的是編譯器生成的 async 狀態機。

5 · 這個 executor 缺什麼

單 future、單執行緒、沒有任務佇列。往 production 的距離,全部是「誰被喚醒」的翻譯層, 骨架 loop { poll; 沒事做就睡 } 一行都不用改:

缺的東西wake 變成什麼睡變成什麼
spawn / 多任務把 task 推回 ready queue(不是 unpark)queue 空了才 park
多執行緒推進本地 queue + work-stealingworker 各自 park / 條件變數
IO(見 event_loop)reactor 把「fd ready」翻成 waker.wake()epoll_wait(timeout) 取代 park
timertimer wheel 到期 → wakepark 的 timeout = 最近 deadline

這裡 thread-per-Delay 是刻意的 stub(面試時要主動聲明): production 是分層 timer wheel,一條 driver thread 管上百萬個 deadline,O(1) 插入。 epoll_wait 的 timeout 參數本身就是「park with deadline」——同一個形狀,換了個系統呼叫。
