dsu

union-find 沒有節點、沒有指標、沒有 Box。只有一個 parent: Vec<usize>——「樹」是我們畫給自己看的。 整個模組的難度不在合併,在兩個優化各自擋掉哪一種退化。

1 · 樹是畫給人看的,陣列才是真的

左邊是森林,右邊是 parent[]。它們是同一份資料: parent[i] == i 就是根,否則往上指。 按 find(x) 看游標一路爬到根,然後看第二趟—— 沿路每個節點的 parent 被直接改寫成根。 右邊那幾格跳動的數字,就是 path compression 的全部。

先照預設(兩個都 ON)按「建立退化鏈」——樹高停在 1,鏈根本長不出來。 再把 union by rank 切成 OFF、reset、按同一顆按鈕: 這次 0 → 1 → 2 → … → 9 疊成一根竹竿,樹高 9。 對 find(0) 按下去,步數計數器會一路數到 9 ——這就是退化的 O(n)。 然後看第二趟壓縮:8 格 parent[] 被改寫成 9,樹高瞬間掉到 1。 再 find(0) 一次,步數 = 1。

為什麼是 8 格不是 9 格?因為節點 8 本來就直指根,不必改—— 這正是 Rust 那句 while self.parent[x] != root 的迴圈條件在做的事。 互動裡的「壓縮改寫格數」就是這個 while 迴圈跑了幾圈。

2 · find:兩趟迭代,重點在第二趟

第一趟只是「爬到根」——任何 naive 實作都會做。真正把複雜度壓下來的是第二趟: 把沿路每一個節點重新掛到根底下。這是一次寫入換未來所有讀取, 典型的攤銷分析場景:單次 find 可能很貴,但它順手把路鋪平了, 貴不了第二次。 

// reference/src/dsu.rs
pub fn find(&mut self, mut x: usize) -> usize {
    let mut root = x;
    // 第一趟:爬到根
    while self.parent[root] != root {
        root = self.parent[root];
    }
    // 第二趟:沿路全部直掛根,下次 find 這條路徑 1 步
    while self.parent[x] != root {
        let next = self.parent[x];
        self.parent[x] = root;
        x = next;
    }
    root
}

為什麼不用遞迴版的 parent[x] = find(parent[x])?一行就寫完,而且更漂亮。 因為遞迴深度 = 壓縮前的樹高。壓縮還沒發生的那一刻,樹高可能就是 O(n)—— 對一條 106 長的鏈做第一次 find,你會先 stack overflow, 根本活不到享受攤銷的那一天。這不是風格偏好,是正確性。

注意 find(&mut self, …) 要 &mut——它是個查詢,卻會改資料。 這在 Rust 裡不是小事:它讓 DSU 不能放進 &self 的 API, 也不能兩個執行緒同時查。想要 &self 版就得放棄壓縮,或改用 atomic/內部可變性。 攤銷複雜度的代價,在型別簽名上收。

3 · 一個治療,一個預防

兩個優化常被當成同一件事的兩半,其實它們的作用方向相反, 所以互補而不是重複。上面那個互動的四種開關組合,就是在演這張表:

組合退化鏈之後攤銷複雜度
都 OFF 樹高 9,find(0) 每次都 9 步——永遠不會變好 O(n)
只有 compression 第一次 find(0) 9 步,之後全部 1 步——事後把爛樹壓平 O(log n)
只有 by rank 鏈根本沒長出來,樹高 1——事前不讓爛樹發生 O(log n)
都 ON 樹高 1,而且任何路徑走過一次就永久扁平 O(α(n))

path compression 是治療:它不阻止你長出爛樹,只在你踩到的時候順手修好。 單獨用時,對手可以構造一堆「只 union 不 find」的操作序列,把樹疊高後才開始查—— 所以界只到 O(log n)。

union by rank 是預防:矮樹掛到高樹下,樹高只在兩棵同 rank 的樹相遇時 +1。 要讓樹高變成 h,底下至少得有 2h 個節點,所以樹高天生不超過 log n。 但它不會把已經走過的長路徑變短——查一百次同一條 log n 路徑,就付一百次 log n。

疊在一起才會出現 α(n):by rank 把樹高壓進 log n,compression 再把「走過的路」永久攤平, 兩者的交互作用讓整段操作序列的總成本掉到近乎線性。 Tarjan 1975 證的就是這個組合——單獨任一個都證不到。

4 · α(n):誠實一點,它不是 O(1)

α 是 Ackermann 函數的反函數。它長得有多慢,看這張表就懂 (CLRS 定義:α(n) = min{ k : A_k(1) >= n }):

所以:你這輩子能配置出來的任何 n,α(n) 都不超過 4。 不是「通常」,是物理上——你把整個宇宙的原子拿來當元素,它還是 4。 工程上把它當常數,完全正當。

但別在面試裡說「union-find 是 O(1)」。它真的不是,而且不是「我們證不出來」—— Fredman & Saks 1989 在 cell-probe 模型下證明了 α(n) 是下界: 任何實作都不可能做到攤銷 O(1)。這是個罕見的、複雜度上真的卡在非常數的自然問題。 正確說法是:攤銷 O(α(n)),實務上與常數無法區分。

還有兩個常被吞掉的字:攤銷。α 界是攤在 m 次操作上的 (總成本 O(m·α(n)))——單次 find 仍可能走 O(log n) 步, 第一次踩到深樹甚至更多。要的是 worst-case 單次界?那得換資料結構,DSU 給不了。

5 · 面試會追問的四件事

追問答案
rank 為什麼敢用 u8? rank 只在兩棵同 rank 樹合併時 +1,而 rank = r 的樹至少 2r 個節點。 要讓 rank 溢位到 255,需要 2255 個元素。省下 7/8 的 rank 記憶體,空間 n + n/8 字。
by rank 還是 by size? 攤銷界相同。size 版順便給你 O(1) 的「這個集合幾個元素」 (很常見的 follow-up:「這個 partition 有幾台機器」);rank 版少存一個 usize。 答得出這個差異就行,選哪個都對。
components() 怎麼 O(1)? 不要掃一遍數根(O(n))。開個計數器,union 真的合併成功時才 -= 1。 這也是 union 回傳 bool 的理由——呼叫端常常想知道「這次真的合了嗎」。
能 un-union 嗎? 不能。拆集合要 rollback DSU(操作堆疊 + 放棄 path compression, 因為壓縮把歷史改掉了),或整批 offline 重算。 面試時先聲明「只合不拆」再往前走,比中途發現卡死好。
