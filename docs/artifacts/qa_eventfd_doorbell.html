eventfd 與門鈴哲學:誰叫醒 event loop、憑什麼、然後呢

一條追問鏈的完整沉澱:eventfd 是 spawn 專用嗎(不是)、write(efd,1) 到底寫了什麼(一顆計數器)、回來的事件怎麼分辨是誰(號碼牌)、events 怎麼交給 executor(不交——只有 wake 跨界)。加上三個特殊客戶:signal 的 self-pipe 本尊、timer 的零 fd 方案、file IO 的 offload 回收,收尾補 Handle 通行證與 tokio 的 thread-local 魔法。行號全部指 reference/src/event_loop.rs 與 mini_runtime.rs。

0 · fd 是 kernel 物件的 handle,read/write 是動態分派

write(2) 不是 epoll 的 API(epoll 只有 create/ctl/wait 三招,完全不做 IO)。fd 本質是「process 檔案表的索引 → kernel 物件」,而每種物件自帶一張 function pointer 表(struct file_operations)——同一個 syscall,語意由物件決定,像 Box<dyn FileLike> 的動態分派:

fd 背後的物件write 做什麼read 做什麼
regular file拷 bytes 進 page cache(→磁碟)從檔案偏移拷 bytes 出來
socketbytes 排進 send buffer(→網路)從 receive buffer 取 bytes
pipebytes 進 kernel 環形 buffer消費 buffer 裡的 bytes
eventfd把 8-byte 值當 u64:counter += v回傳 counter 並歸零
timerfd—回傳「到期了幾次」

eventfd 沒有 buffer、不存你的 bytes——整個 kernel 物件就是一顆 u64。它是偽裝成檔案的同步原語。而它為什麼要偽裝?因為 epoll_wait 只聽得見 fd:event loop 要在一個 blocking call 裡同時等「千條 socket」和「有人要我醒」,後者本是 condvar 的地盤,但一條執行緒不能同時睡在兩種等待裡——把喚醒訊號做成 fd,它就能跟 socket 們睡同一張床。LT 語意下:counter > 0 ⟺ 可讀 ⟺ epoll_wait 會醒(或根本不睡)。

1 · 互動:門鈴的一生——兩種時序,同一結局

門鈴協定永遠兩步:先放貨(queue.push),再按鈴(write efd)。切換 loop 當下的狀態,走一遍看計數器怎麼把「wake 先於睡」的 race 變成非事件:

別的執行緒(按鈴的人)

queue: []
ready queue = 資料

eventfd

counter = 0
counter > 0 ⟺ 可讀

event loop 執行緒

處理 socket 事件中
 

關鍵在 toggle 左邊那條:wake 落在「還沒睡」的窗口裡,counter 已經掛著,隨後的 epoll_wait 看到 efd 可讀直接返回、根本不睡——跟 thread::park 的 permit 穿過一模一樣。多次 wake 合併成一次計數(write 是加值),loop 反正整條 queue 收割,一聲不多、一件不漏。

2 · 同一課的五個化身:訊號不可靠,狀態才可靠

原語訊號的「狀態」存哪解掉的 race
condvar + predicate訊號本身無狀態 → 醒來重查條件notify 先於 wait 就蒸發
park / unparkpermit,飽和在 1wake 先於 park 不丟
eventfdcounter,累加(fd 版 permit)wake 先於 epoll_wait 不丟
signal handlerper-signal atomic flag + self-pipe 一 bytehandler 環境放射性,正常手段全禁用
timer(§5)timeout 只是提示,真相 = 時鐘 vs deadline 表提早醒/晚醒/假醒全無害——醒來重查

裸訊號在五個場景全都會蒸發或說謊;每次解法都是同一句:讓訊號留下狀態,醒來查狀態。面試被追問任何一個,拿另外四個當佐證,就是深度。

3 · 回程:號碼牌分流,woken 是字條、不是喚醒

token 是註冊時每個 fd 各掛各的號碼牌(epoll_data u64,kernel 不看不存、事件時原樣奉還):socket 們掛 slab index(0、1、2…),只有 loop 自己的 eventfd 掛保留牌 WAKE_TOKEN = u64::MAX(event_loop.rs:47;register() 直接 assert! 不准外人用,行 183/196——否則某條 socket 的事件會被誤認成門鈴、整條連線沒人理)。dispatch 就是認牌:

for raw in &events.raw[..n] {
    let raw = *raw;                       // packed struct:整值 copy 再讀欄位
    if raw.data == WAKE_TOKEN {
        self.wake.drain()?;               // 消音:read 歸零。LT 不 drain 下輪還報 → 空轉
        events.woken = true;              // 字條:「你這次醒,是因為有人按鈴」
        continue;                         // 不進事件列表——它不在連線註冊表裡,查表只會查空
    }
    // 走到這的才是真連線事件 → (token, readiness) 進列表給 caller 查表
}

時序上要看清:整條鏈只有一次「真正叫醒執行緒」——kernel 讓 epoll_wait 返回的那一瞬。執行到 drain() 時你早就醒了;它不喚醒任何人,只是把計數歸零免得 LT 下輪空轉。而 woken 存在的理由:按鈴的證據(counter)剛被 drain 消滅了,不留字條,「有人找過你」這個資訊就丟了——caller(擁有 task queue 的那層,例如 mini_runtime 的 run loop)拿這個 bool 決定要不要去收割自己的佇列。

順帶:self.wake 的型別是 Arc<EventFd>——同一顆鈴兩張臉:WakeHandle(發給別的執行緒,write 側按鈕)與 loop 自己(drain 側消音器)。Arc 的理由是 handle 可能活得比 loop 久:loop 先 drop 就 close fd,handle 再 wake 就是對可能已被 kernel 重發給別人的 fd 編號寫 8 bytes——fd 重用大坑,與 fd_registry 的 generation 同族。

4 · Events 死在 reactor 邊界:分層與唯一介面

「events 怎麼吐給 executor?」——不吐。token 在 reactor 手上換到的唯一東西是 Waker;executor 從頭到尾沒見過 token。mini_runtime.rs:299-348 的 block_on 三段迴圈就是這張圖:

executor(block_on ②段)

▲ 唯一介面:Waker(wake = task 進 queue / 設旗)——事件到不了這層

翻譯層 event_loop(其實是 mio 的 Poll)

register / reregister / deregister 1:1 映射 kernel 三 opcode;WAKE_TOKEN 走旁路(drain + woken + continue)。它不 loop——loop { } 在 caller 手上,所以 mio 誠實地叫它 Poll 不叫 EventLoop
▲ raw epoll_event

那被 wake 的 task 怎麼拿到資料?——自己再試一次。readiness 模型的事件不帶資料,只帶「現在再試會成功」:task 下輪被 poll 時重跑 read(),有資料就 Ready,又 WouldBlock 就再登記 waker(arm_io:更新 slot 裡的 waker + poller.arm)。對照組:io_uring 的 completion 模型才是「事件帶著讀好的資料回來」。

而 arm 為什麼分 register / reregister?kernel 本來就是三個 opcode、沒有 upsert:double-ADD 回 EEXIST(暴露「兩處 code 都以為自己擁有這個 fd」)、MOD 不存在的 fd 回 ENOENT(暴露 use-after-deregister)。翻譯層不發明 kernel 沒有的語意;想要 upsert 的便利,上層轉接頭自己搭(mini_runtime.rs:144:查 registered: HashSet 決定走 ADD 還是 MOD)。

5 · 兩個特殊客戶:signal 與 timer

signal = self-pipe trick 本尊(這招就是為 signal 發明的,eventfd 是它的 Linux 後代)。signal handler 會在任意兩條指令間打斷任意執行緒,裡面只准呼叫 async-signal-safe 白名單(不能 malloc / 拿鎖 / println——被打斷的可能正是持鎖中的自己)。而 sigaction 是 process 一張表、同一 signal 只能一個 handler,所以架構天生是漏斗:kernel 呼叫 handler(signum) 把編號當參數點名 → handler 只做兩件白名單的事:PENDING[signum].store(true) + 對唯一那根 pipe write 一 byte → driver 醒(TOKEN_SIGNAL)→ 讀乾 pipe → 掃 64 格 flag 表 → 對每種 pending 的 signal 喚醒它的訂閱者清單。「哪種 signal」在狀態表,「誰要收」在訂閱表,pipe 只負責叫醒。(Linux 有 signalfd 但 tokio 不用:它要求全 process 所有執行緒 block 該 signal,library 保證不了;而且 kqueue 平台沒有。)

timer = 零 fd。timer driver 只是包住 IO driver:查 wheel 最早 deadline → 換算成 epoll_wait 的 timeout 參數。它不需要被通知——返回路徑必經它家門口(呼叫堆疊退回時穿過包裝層),每次返回無條件拿 now 對 wheel 查「誰到期」,不管返回原因是 fd 事件、門鈴還是超時。睡著時冒出更早的 deadline?——按 eventfd 門鈴,醒來重算 timeout。所以那顆 eventfd 是萬用門鈴:spawn 新 task、跨執行緒 wake、更早的 deadline、offload 完成(下一節),全是同一句「醒來,重查你的狀態表」。

6 · 互動:file IO 的 offload 回收——門鈴的第四個客戶

regular file 進不了 epoll:它永遠報 ready,read() 照樣卡在磁碟上——readiness 模型對檔案無意義。std-only 正解:把 blocking 讀寫丟給 thread pool,用 completion queue + eventfd 把結果送回 loop。這正是 tokio spawn_blocking / tokio::fs 的做法,沒有魔法 async file syscall:

event loop 執行緒

task 要讀檔
loop 絕不准阻塞

blocking pool worker

idle
阻塞在這裡是合法的

completion queue + eventfd

completion: []
counter = 0

帳要會算:worker 阻塞在磁碟 IO 是設計內(它不是 loop thread,卡住不擋任何 socket);loop 從頭到尾零阻塞。std-only 手刻 = thread pool + mpsc 佇列 + eventfd 回收——三個你都寫過的零件。

7 · Handle 通行證:誰拿票、怎麼傳、await 為什麼不用它

#[derive(Clone)] pub struct Handle { inner: Arc<Inner> }(mini_runtime.rs:204)是 capability(通行證)模式:Inner 裝著 runtime 僅有的兩個共享結構(run queue + reactor),Handle 就是「允許使用 runtime 服務」的門票——clone 一次 refcount bump,Send 跨執行緒。三種持票人:

持票人拿票做什麼票怎麼到手
使用者 codehandle.spawn(fut):背景 task 進 run queueruntime 建構時發的
IO 物件(AsyncTcpListener,行 355)poll 遇 WouldBlock → arm_io(waker 進 reactor);Drop → disarm_io(退租 + bump generation)建構函式收 &Handle,clone 進口袋(行 365)
Task 自己(行 213)Wake impl 把自己 push 回 queuespawn 時 Arc::clone(&inner)

.await 完全不認識 Handle——await 編譯出來只是「poll 內層,Pending 往上傳」的純狀態機機械。Handle 唯一出場點是 leaf future 的 poll 內部(accept / read 遇 WouldBlock → arm_io);中間所有組合層(async fn / join / select)對它零知識。

那 tokio 為什麼不用塞?——把「遞票」變「摸口袋」:worker 啟動 / block_on / enter() 時把 handle 存進 thread-local,TcpStream::connect 內部 Handle::current() 讀 TLS 拿票。前提:async code 只會在 runtime 自己的 worker 上被 poll,所以口袋恆有票。代價:runtime 外呼叫 = 著名的 "there is no reactor running, must be called from the context of a Tokio 1.x runtime" panic——錯誤從編譯期搬到執行期(mini_runtime 的顯式票沒票根本編不過):

設計誰用好處代價
顯式 Handlemini_runtime編譯期保證、零魔法、可測試病毒式:每個做 IO 的函式簽名都多一個參數,感染整個生態
thread-local ambienttokioAPI 與 std 同形(connect(addr) 就是 connect(addr))、生態乾淨錯誤變執行期 panic;TLS 讀取 ~ns;多 runtime 要 enter guard 管「current 是誰」
全域單例async-std、smol(async-io 全域 reactor thread)連票都沒有,永不 panic只能一個 runtime,不可配置

決定性理由是「病毒式」那格:顯式路線會讓生態系每個 async library 函式都多收一個 handle 參數——function coloring 問題長出第二種顏色。正確敘事不是「tokio 不用 Handle」,是 「tokio 預設 ambient、保留顯式當逃生門」:Handle::current() 之外,handle.spawn / handle.block_on 都存在,專治跨 runtime 與 runtime 外部這些 TLS 罩不到的場景。教學品(mini_runtime)顯式是美德——機制全攤在檯面上;公共 runtime ambient 是生存需求。

8 · 面試句庫

“An fd is just a handle to a kernel object with its own read/write implementation — eventfd implements them as ‘add to a counter’ and ‘take and reset’. It exists so a wakeup signal can sit in the same epoll_wait as the sockets.” fd 動態分派 + 門鈴為什麼是 fd,一句講完。
“The doorbell carries no payload — state lives in the queue. Ring it three times before I wake and I still read the counter once and drain the whole queue.” 門鈴≠資料;合併喚醒無害。
“The reactor's job ends at waker.wake(); the executor's job starts at queue.pop(). Events never cross that boundary — the Waker is the only interface, and data moves when the task retries its syscall.” executor×reactor 接縫的滿分收束。
“I'm calling it Poller, not EventLoop — the loop belongs to the caller. mio makes the same distinction with its Poll type.” 命名品味,一句話的 green flag。
“tokio doesn't skip the handle — it defaults to ambient context in a thread-local and keeps the explicit Handle as the escape hatch. Explicit passing would tax every async signature in the ecosystem; ambient moves that cost to a runtime panic instead.” Handle 三設計的一句話收束;await 自己從不碰票——只有 leaf future 的 poll 會。
