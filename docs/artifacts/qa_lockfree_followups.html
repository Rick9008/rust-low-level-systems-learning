lock-free 追問串:swap、CAS、seq 時鐘與時代數

7/22 清晨的連環追問照原脈絡收錄:swap 換的是什麼?它會失敗嗎?CAS 長什麼樣、失敗了怎麼辦?seq 為什麼是 pos+cap、繞不繞回起點?dif<0 憑什麼直接說「滿」?pop 端的 head 憑什麼連 atomic 都不是?M-S 的 help 分支是誰在幫誰?階梯總覽(why)在前置頁 qa_lockfree_pc.html;這頁是 how——對著 reference 的三份 core_impl(mpsc_list / mpmc_ring / mpmc_list)逐行拆。

公理:佔位點和發布點是不是同一個位址,決定有沒有「縫」。整頁九題都是這句的展開。

Q1 · swap 換的是什麼?為什麼可以直接換?沒成功怎麼辦?

換的是一個 8-byte 指標值,而且 swap 沒有「不成功」。tail 是 AtomicPtr——一個機器字,存「最新 push 的節點位址」。swap(node) 是一條硬體 read-modify-write 指令(x86 的 XCHG):原子地「把 tail 改成我的節點,同時回傳原值」。它把兩件事綁成不可分割的一步:宣告我是最新節點 + 得知前任是誰。十個 producer 同時 swap,硬體排成全序,每人拿到的 prev 互不相同、不遺失——這一發就是全部仲裁。

// mpsc_list/core_impl.rs:105-127(節)
let prev = self.list.tail.swap(node, Ordering::AcqRel);  // 佔位:必成功
// ↑↓ 之間是「縫」:tail 已指向新節點,鏈還沒接——
// consumer 走到 prev 見 next==null 而 tail!=prev ⇒ Inconsistent
unsafe { (*prev).next.store(node, Ordering::Release); }  // 發布
  • AcqRel 兩半各有職責:Release 半——下一個 producer 會 swap 到「我」當 prev 並寫我的 next 欄位,我的節點必須在它眼裡建構完整;Acquire 半——我要寫 prev 的 next,得先看見 prev 完整(配對前任的 Release 半)。鏈上每人同時是接收方和提供方。
  • 無失敗路徑 = 無迴圈 = push wait-free——這是 MPSC list 的奢侈品,也是 tokio 用它收 remote wake 的原因(wake 端絕不能被卡住)。
  • 佔位(swap 在 tail)與發布(store 在 prev.next)是兩個位址——一次原子操作最多改一個機器字,所以縫不可消除,只能顯式化成 PopResult::Inconsistent(不是空,等一下再來)。

Q2 · CAS 長什麼樣?它會失敗嗎?

會,而且失敗是常態、是設計的一部分。會失敗的是 CAS,不會失敗的是 swap——兩種指令,別混。

// CAS:有條件交換。「若現在還是 expected 才換」。x86 = LOCK CMPXCHG
match tail.compare_exchange_weak(
    expected,      // 我的快照:我以為 tail 現在是這個
    expected + 1,  // 若真是,原子地改成這個
    Ordering::Relaxed,  // 成功時(仲裁不揹資料,同步全在 seq 上)
    Ordering::Relaxed,  // 失敗時
) {
    Ok(_)       => { /* 換到了;世界如我所知 */ }
    Err(actual) => { /* 沒換;actual = 免費附贈的最新值,拿去重試 */ }
}
  • 失敗的語意很精確:「你以為的世界過期了」——快照與 CAS 之間有人先改了。Err(actual) 直接給最新值,重試不用重 load。
  • weak:允許「值明明相等卻偽失敗」(ARM LL/SC 較省);反正外面就是重試迴圈,偽失敗只是多繞一圈。
  • 進度保證的分界:swap 必成功 → wait-free;CAS 可失敗 → lock-free(我輸必因別人贏,系統整體有進展;個體可能餓)。
原語跟著「佔位語意」走,不是隨便挑

mpsc_list:swap

佔位 =「把自己掛上鏈尾」——無條件可做,拿到 prev 就夠 → 配無條件的 swap

mpsc/mpmc_ring:CAS

佔位 =「領票號 pos」——有前提(槽得空、票得沒被領)→ 配有條件的 CAS

Q3 · seq 為什麼是 pos+cap?它跟 pos 是同一個東西嗎?

同一個數字空間(才能相減比較),不同的角色。pos 是取號機發給你的票號;seq 是槽位自己的時鐘,slot i 一輩子只取 i, i+1, i+cap, i+cap+1, …,單調遞增。dif = seq − pos 就是「拿槽位時鐘對我的票」。

cap = 4,slot 0 的一生:
初始           seq = 0            // 等第 0 圈 producer(pos=0)
producer 發布  seq = 1 (= pos+1)   // pos=0 的 consumer 可讀
consumer 釋放  seq = 4 (= pos+cap) // 等下一圈:pos'=4 的 producer
producer 發布  seq = 5 (= pos'+1)
consumer 釋放  seq = 8 (= pos'+cap)  …只進不退

為什麼釋放不能把 seq 歸零回 pos?反證:假設 consumer 讀完把 seq 設回 0。下一圈 producer 拿票號 4 來,算 dif = 0 − 4 = −4 < 0 → 判「滿」→ 這格永遠賣不出去。時鐘必須走到 pos+cap,才對得上「下一個合法客人」的票號。seq 一個數字同時編碼狀態(空/滿)和圈數(服務第幾圈)——這就是它不能回頭的原因。

seq 對票號 pos 的三態

seq == pos

本圈輪空,producer 可搶

seq == pos+1

已發布,consumer 可讀

seq == pos+cap

已釋放,等下一圈(pos' = pos+cap 的 dif 恰為 0)

Q4 · 計數器會 wrapping 繞回起點嗎?

兩層「繞」,答案相反:

  • 繞 ring(空間):不繞。pos 與 seq 都只增不減,槽位位址是投影算出來的:buf[pos & mask]。自由跑的紅利:tail − head 直接是元素數、滿/空不用犧牲一格、三態不歧義。若計數器真繞 cap 回 0,「第 3 圈的 slot 2」和「第 7 圈的 slot 2」就無法區分——圈數情報消失。
  • 繞 2⁶⁴(數字空間):會,wrapping_add/sub 就是為它。所有判斷都走差值:seq.wrapping_sub(pos) as isize 在真實距離 ≤ cap ≪ 2⁶³ 時,跨過溢位點也給出正確符號——serial number arithmetic,TCP seq 同款。repo 的 with_start 測試後門就是把起點設在溢位邊上驗這件事。

量級:64-bit @ 1G ops/s ≈ 584 年繞一圈;但 32-bit 目標 usize 是 2³²,高流量幾十秒就繞——wrapping 是真需求,不是潔癖。

Q5 · dif < 0 憑什麼直接說「滿」?(cap=4 手算 + 單調性證明)

四個 producer 各推一件,無人消費:
push A(票0)seq[0]←1 | push B(票1)seq[1]←2
push C(票2)seq[2]←3 | push D(票3)seq[3]←4
現況:tail=4,head=0,seq=[1,2,3,4]

P 來推第五件:
snapshot = 4;slot = buf[4 & 3] = buf[0];seq = 1
dif = 1 − 4 = −3 < 0 → Err(item)
// 票號 4 期望時鐘 = 4(pos0 的 consumer 釋放後寫 0+4);
// 時鐘停在 1 =「pos0 已發布沒人消費」——前一圈房客還在,房間沒空

consumer 拿走一件:pop(票0)讀走 A,seq[0]←4,head=1
P 重試:dif = 4 − 4 = 0 → 輪到它

「萬一快照過期,其實有位子呢?」——不可能,三步證明:

  1. seq 只增不減(Q3 的時鐘性質)。
  2. 票號 4 要被領走,領票人必須先看到 seq[0]==4(先驗貨再取票的順序保證)。
  3. 我現在讀到 seq[0]=1 < 4 ⇒ seq 從未到過 4 ⇒ 票 4 從未被領 ⇒ tail 從未越過 4;而快照本身來自 tail ⇒ 讀 seq 那一瞬 tail 恰好 = 4,快照不但沒過期還是精確值。

所以一個 dif<0 讀數同時證明「快照新鮮」+「我的位置上前一圈住戶還在」⇒ 隊列在那一瞬確實滿(可線性化)。而且這條路零副作用:兩次 load、零寫入、票還沒領,Err(item) 把所有權原封還給 caller。對照 fetch_add 流派(先取票):滿時攥著票無處寫、票不能退——try_push 語意直接做不出來。

Q6 · producer 5 比 6 晚完成怎麼辦?

三層拆開,只有中間那層會亂

取號層:嚴格有序

tail 只能被 CAS 一格格推 5→6→7;B 拿到 6 的前提是 A 已拿走 5。跳號不存在

交貨層:可以亂序

A(票5)還在寫,B(票6)先 store seq=7——這正是 per-slot seq 存在的理由:全域水位線答不了「6 好了、5 還沒」

消費層:嚴格按號

head=5 的 consumer 只看 slot[5],dif<0 → None。6 好了也輪不到——FIFO 按票號,不按完成順序
對外的全部可見後果:queue 暫時顯得「空」;順序永不亂

代價(誠實邊界):A 若在縫裡卡死,5 永不發布,6 之後所有已發布元素全被堵住——Vyukov 是 lockless,不是正式 lock-free。與 mpsc_list 的 Inconsistent 同病(佔位≠發布),症狀一個叫 None、一個叫 Inconsistent。

"Claims are strictly ordered — the ticket counter moves one step at a time. Publications can complete out of order, which is exactly why the publish signal is per-slot. Consumers take tickets too, so FIFO is by position, not completion."

Q7 · pop 端的 head 憑什麼連 atomic 都不是?(兩軸判準)

先糾正前提:MPSC ring 的 pop 每次仍做一個 Release store——搬到 slot.seq 上了(seq.store(head+cap, Release))。消失的不是原子寫,是 index 的原子性。SPSC 的 head 本來身兼二職:①私有 cursor(我讀到哪)②跨執行緒水位線(producer 判滿要讀它)。Vyukov 把發布、釋放兩個方向的信號都下放到 per-slot seq 之後,head 再無任何外部讀者——職務②歸零,剩下的私有 cursor 不需要原子。

這個 index 被誰存取用什麼例子
多執行緒寫CASmpmc 兩端、mpsc_ring 的 tail
單執行緒寫、他端要讀atomic store/load(Release/Acquire)spsc_ring 的 head/tail(producer 判滿讀 head、consumer 判空讀 tail)
單執行緒寫、沒人讀UnsafeCell(非原子)mpsc_ring 的 head
  • 單寫者 ≠ 私有:SPSC 的 head 也是單寫者,但 producer 在讀 → 一寫一讀跨執行緒無同步 = data race = UB。沒有 atomic 會發生:編譯器把 load 提出迴圈(producer 對著陳年快照 spin 到死)、資料 happens-before 斷裂(看到新 tail 讀到半成品槽)、撕裂讀(語言不保證)。
  • 用 AtomicUsize 會說謊 + 廢掉 loom 驗證:atomic 語意=「預期並發存取」,但設計不變量是 head 私有(Consumer 非 Clone + &mut self)。loom 版 UnsafeCell::with/with_mut 登記每筆存取、任一 interleaving 重疊即判死——「私有」是被模型檢查證明的定理,不是註解裡的主張;換 atomic,loom 就閉嘴了。
  • 順帶的 cache 紅利:producer 判滿讀的 seq 就在它即將寫資料的同一條 cache line(Slot 內);head 不再 ping-pong,連 padding 都省。
"Single-writer tells you whether you need CAS; whether anyone on another thread reads it tells you whether you need atomicity at all."

Q8 · M-S 的 help 分支是啥?為什麼它是正式 lock-free?

M-S push 兩步:①接鏈 CAS(t.next: null → 我)——佔位+發布合一(搶到的瞬間 consumer 就走得到你);②推路標 CAS(tail: t → 我)。①②之間路標落後真隊尾一格。help = 路過的人替贏家做步②:

let t = self.tail.load(Acquire);
let next = unsafe { (*t).next.load(Acquire) };
if !next.is_null() {
    // help 分支:路標落後了,幫原主推一把(資訊全公開,誰都能代勞)
    let _ = self.tail.compare_exchange_weak(t, next, Release, Relaxed);
    continue;  // 推完(或別人推完)重讀,再找真隊尾接鏈
}
  • 多人同時 help 不會推壞:大家拿同一個期望值 t 去 CAS,恰好一人成功、其餘無害失敗;tail 只往前。贏家自己的步② CAS 失敗就 let _ = 丟掉——「失敗 = 有人幫忙推了」。
  • 不變量:路標最多落後一格(接鏈前提是從 tail 讀到 next==null,路標沒追上誰都接不了)→ help 工作量恆為一次 CAS。
mpsc_listmpmc_ringmpmc_list(M-S)
仲裁原語swap(必成功)CAS 打在計數器CAS 打在 t.next 指標
佔位 vs 發布兩步 → 縫(Inconsistent)兩步 → 縫(堵隊)合一 → 無縫,None 就是真空
進度保證push wait-freelockless正式 lock-free
記憶體每 push 一次 Box預配置陣列,零配置每 push 一次 Box;退休節點 Drop 才收

分水嶺:懸空的工作別人幫不幫得了。M-S 的懸空步(推路標)純機械、資訊公開 → 人人可代勞 → 沒人等特定某人醒來。Vyukov 的懸空步(把 item bytes 寫進槽)只有本人知道內容 → 無人能代勞 → 卡死的贏家堵全隊。

"Lock-freedom isn't about avoiding waits — it's about never waiting on a specific stalled thread. Michael-Scott makes the only dangling step mechanically completable by anyone; Vyukov's dangling step is writing your own payload, which nobody can do for you."

Q9 · 時代數統一 + AtomicPtr vs AtomicUsize

結構「位置」被重用時代數防什麼
mpmc_ring 的 seq槽位每圈重用seq 編碼圈數舊圈的 P/C 誤動槽位(+揹資料 happens-before)
arena_lockfree 的 genfree 鏈節點重用pack 進 CAS 字 [gen:32|idx:32]ABA:舊快照的 CAS 誤成功
fd_registry 的 generationkernel 重發 fd每 slot 一個 genstale token 打到新連線

一句收攏:位置一旦會被重用,光比位置就不夠——給位置配一個時代數,舊時代的人拿舊票,做什麼都會被拒。(ABA 場景:讀 head=A、next=B → 被 deschedule → 別人 pop A、pop B、又把 A 推回 → 醒來 CAS(A→B) 只比值、誤成功 → 鏈頭指向別人手上的 B。gen+1 讓舊快照必失敗。)

AtomicPtr vs AtomicUsize 其實是 index-based vs pointer-based 的選擇:ring 共享的是「第幾個」(自由跑計數器,要做算術、編碼圈數,位址是 & mask 投影出來的);list 共享的是「在哪裡」(節點散落 heap,唯一指認方式是位址)。且 Rust 裡位址必須保持指標身分——繞道 usize 會洗掉 provenance(strict provenance 要禁、Miri 會抓),而 swap 完馬上要 (*prev).next 解參考。

30 秒口述(SPSC → MPSC → MPMC 要改哪裡)

"SPSC works because every atomic has exactly one writer — plain acquire/release stores, no CAS. Add a second producer and the producer index needs arbitration: for an unbounded list the cheapest is Vyukov's MPSC — push is one unconditional swap, wait-free, at the cost of a per-push allocation and a pop-side gap. For a bounded ring you CAS a free-running ticket counter, and because claim order diverges from publish order, each slot carries a sequence number that encodes both state and lap. What you pay: CAS retries and cacheline ping-pong under contention; what you dodge by staying bounded: the whole memory-reclamation swamp. In an interview I'd write Mutex<VecDeque> + condvar first and narrate this upgrade path."收尾永遠接:哪端是單,那端 index 保持單寫者,同步機制整格降級。
