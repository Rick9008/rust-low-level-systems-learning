reference / stage 7  ·  binary protocol over TCP

hw_bridge

TCP 只保證 byte 的順序,不保證你 write() 的切割方式。 一次 read() 拿到的可能是半個 frame、一個半 frame、三個 frame。 message 邊界是你的協定要重建的東西——kernel 不管。 這個模組的全部難度就在那個 Ok(None)。

1 · wire format:一行註解決定成敗

整個協定只有三個欄位。難的不是佈局,是一句話的定義: len 到底含不含它自己?兩種定義業界都有,拿錯對方的 = 永久錯位 4 bytes、 第一個 frame 之後全爛。本協定寫死:不含。

len : u32 BE 4 bytes · opcode + payload 的長度 · 不含自己
opcode : u8 1 byte · 最高位 0 = 命令,1 = 回應
payload : (len - 1) bytes 定長欄位 · 整數一律 big-endian(network byte order)

MAX_FRAME_LEN = 64 KiB 不是效能參數,是防禦線: 沒有它,對面宣稱 len = 0xFFFFFFFF,server 就會乖乖預留 4 GB 緩衝等它。 一個 byte 的攻擊面,一行常數擋掉。

2 · 逐 byte 餵進 FrameReader:那個 Ok(None)

drip 1 byte 模擬最壞的 TCP 切割:一次 read() 只拿到 1 byte。 看 next_frame() 一次一次回 Ok(None)——它什麼都不能做, 只能把殘料留在 buffer 裡等。len 沒湊滿 4 byte 時不行; 湊滿了但 payload 還差 1 byte 時仍然不行。 這條路徑在單元測試裡是 assert_eq!(reader.next_frame(), Ok(None))—— 餵完 5 個 byte,那個 Ok(None) 就有體感了。

三個 off-by-one 埋伏點,全在這個小狀態機裡: (1) len 含不含自己 → total = 4 + len,不是 4 + len - 4; (2) 殘料的起點是 buf[read_pos..],不是 buf[0..]; (3) 等待條件是 buf.len() < 4 + len——差 1 byte 也是差。 reference 的測試不靠手挑案例:窮舉 7-byte frame 的每一個切割點(1..6) 再加 byte-by-byte 餵三個 frame。這種 bug 挑幾個 case 抓不乾淨。

3 · 兩種錯誤,兩種命運

上面那個 stepper 裡有兩顆按鈕會出錯,結果完全相反。這不是實作細節, 是協定的設計決策:framing 層與語意層必須分開, 因為它們對「stream 還能不能信」的答案不同。

語意錯 — 未知 opcode

00 00 00 01 7e

frame 切得出來:len = 1 合法,frame 佔滿 5 bytes, server 明確知道下一個 frame 從第 6 個 byte 開始。 只是 0x7e 不在 opcode 表裡——可能對面版本比你新。 回 Response::Error{code: 1},byte 流完全沒失去同步。

connection LIVE — 可恢復

framing 錯 — malformed len

ff ff ff ff

len 宣稱 4294967295 bytes,遠超 MAX_FRAME_LEN。 為什麼不能像左邊一樣回個 Error 就算了?因為 length-prefix 協定 沒有 resync 點:len 一旦不可信,server 就不知道 下一個 frame 從哪一個 byte 開始。stream 已經失去意義。 唯一正解是 close(conn)。

connection DEAD — 不可恢復

按了 malformed len 之後回頭看 stepper:所有 client 按鈕都灰掉了—— 連線真的死了,不是印個紅字了事。 這正是 delimiter 協定(\n 結尾)唯一贏過 length-prefix 的地方: 損毀後可以掃到下一個分隔符重新同步。代價是 payload 含分隔符要 escape ——二進位資料必然含,所以這個協定不能用 delimiter。

4 · binary vs text、length-prefix vs delimiter

維度選了沒選的理由
binary(BE 整數) ✓ text / JSON:嵌入式對端要塞一個 parser + 浮點。binary 定長欄位 O(1) 解析、頻寬小。 text 的優勢(可讀、telnet 好 debug)用 wireshark dissector 補回來
length-prefix ✓ delimiter(\n):payload 含 delimiter 就要 escape,而二進位 payload 必含。 length-prefix 讀 4 bytes 就知道要等多少,切分零拷貝
delimiter 的優勢 — 人可以 telnet 手打;損毀後可 resync(掃下一個 \n)。 length-prefix 損毀 = 只能斷線(見上一節)
len 不含自己 ✓ 含自己也有人這樣定。重點不是哪個對,是當場說死並寫進註解—— 這是整個協定唯一的 off-by-one 決策點

6 · 為什麼 command worker 只有一條

evented server 是三段式:IO thread(epoll + framing)→ command worker(執行硬體命令,慢也不卡 IO)→ outbox + eventfd wake → IO thread 路由回應。 worker 恰好 1 條不是偷懶。

本協定沒有 request-id。client 靠 FIFO 順序對應回應: 第 n 個回應 = 第 n 個請求。多開一條 worker,同一連線的兩條命令就會亂序完成, 回應錯位——client 拿到的是別人的溫度值,而且不會報錯。

要多 worker,得先改協定加 request-id,client 端變成 HashMap<id, waker>。這是「協定設計決定並發上限」的活教材: 你的並發模型不是實作選擇,是協定的推論。

in_flight 計數器守住最後一哩:EOF 之後不能立刻關線, 要等已派給 worker 的回應全部路由回來、flush 完才能關。 少了它,對端關閉 write 端的那一刻,最後幾個回應就被吞掉。
