reference / stage 3  ·  單執行緒資料結構

tree

同一棵 BST,寫兩遍。左邊節點住在一個 Vec 裡,「指標」是 usize; 右邊每個節點自己 malloc,指標是 Rc<RefCell<Node>>。 這個模組存在的唯一理由,就是讓你親眼看見這兩條路在哪裡分岔—— 而分岔點不在 insert,在 Drop。

1 · 同一棵樹,兩種所有權

插入的邏輯兩邊一模一樣:比大小、往左往右、掛上去。差別全在「掛上去」這個動作是什麼。 arena 版是寫一個整數到 Vec 的某個欄位;Rc 版是把一個 owning handle 移進去, 順手把 refcount 加一。按下去看。

arena  ·  Vec<Node>

nodes: Vec<Node>, root: Option<usize>
left/right/parent: Option<usize>
配置次數0
refcount0
T::clone0
height0

rc_refcell  ·  n 次 malloc

root: Option<Rc<RefCell<Node>>>
left/right: Rc (strong)  parent: Weak
配置次數0
refcount0
T::clone0
height0

按 inorder():兩邊走的路徑完全相同,但右邊每一步都在動 refcount—— n.borrow().left.clone() 是 Rc::clone,strong 從 1 跳到 2,節點被 pop 出 stack 時再掉回 1。 n 個節點 = 2n 次 refcount 讀改寫。而且回傳型別不一樣: arena 是 Vec<&T>(借用逸出函式),Rc 版只能 Vec<T>—— Ref<T> guard 的生命週期綁在 borrow() 呼叫點,帶不出去,只能 clone。

注意:reference/src/tree.rs 的兩版都沒有 parent 欄位(BST 用不到)。 這裡把 parent 加回來,因為那正是兩版真正分岔的地方——下一節就是為了它而存在。

2 · 環:Rc 洩漏,usize 不會

現在讓 child 指回 parent。arena 版:多存一個 usize,結束。 Rc 版:你有兩個選擇,而選錯的那個編譯得過、測試也過、只是記憶體再也回不來。 切換開關,然後把樹 drop 掉。

arena  ·  parent: Option<usize>

索引不是所有權。1 ⇄ 0 互指也只是兩個整數。
存活節點3
洩漏0 B
free()0

rc_refcell  ·  parent: Weak

strong = 幾個 Rc 指著我  ·  weak = 幾個 Weak 指著我
strong → 0 才會執行 Drop
存活節點3
洩漏0 B
Drop 次數0
結果 parent 用 Weak:child 指回 parent 不算所有權,parent 的 strong 停在 1(只有它自己的 parent 連結持有它)。 按 drop(tree),strong 會一路歸零。

Rc 模式的關鍵讀數:drop 之後沒有任何一次 Drop 被執行。 root 的 strong 從 3 掉到 2 就停住了——它的兩個小孩還握著指回它的 strong ref,而那兩個小孩又被 root 的 left/right 握著。 這是一個誰都不肯先鬆手的圈。編譯器全程沒有意見,cargo test 也全綠: 洩漏不是 unsafe,Rc 的 API 契約本來就允許你做出環。 只有 valgrind / heaptrack 或線上的 RSS 曲線會告訴你。

Weak 修好的到底是什麼:Weak 不參與 strong count,所以「誰擁有誰」重新變成一棵樹(單向、無環)。 升級時 weak.upgrade() -> Option<Rc> 逼你處理「parent 已經死了」——那個 None 就是它替你擋掉的 use-after-free。 另外看 log 的釋放順序:root 的值先被 drop(它是遞迴的起點),但它的 heap block 最後才 free—— 因為小孩手上的 Weak 還吊著那塊記憶體,weak 歸零它才真的還給 allocator。 Rc 的 strong 管值的生命,weak 管 allocation 的生命,這是兩件事。

順帶一提,那條「遞迴的起點」不只是修辭:Rc 版的解構是真的遞迴—— drop root 會在 stack 上一路展開到最深的葉子。退化鏈 100 萬個節點,drop 就會爆 stack。 arena 版沒這問題:一個 Vec 就地釋放,i32 沒有 Drop,連走訪都不用。

3 · RefCell:借用檢查被搬到執行期

RefCell 沒有把借用規則刪掉,只是把檢查從編譯期挪到執行期—— 一個 Cell<isize> 的 borrow flag,違反就 panic!。 下面兩段程式碼做同一件事:讀 node 決定方向,然後寫 node。左邊是 arena,右邊是 Rc。 各按一次,看誰的錯誤在哪一個階段被抓到。

arena  ·  編譯期

let n = &self.nodes[cur]; // &Node:不可變借用
let go_left = val < n.val;
self.nodes[cur].left = Some(i); // 想可變借用
println!("{}", n.val); // n 還要用 -> 借用還活著
狀態 尚未編譯

rc_refcell  ·  執行期

let n = cur.borrow(); // flag = Shared(1)
let go_left = val < n.val;
cur.borrow_mut().left = Some(c); // 要 Writing
println!("{}", n.val); // n 還活著 -> Ref 沒 drop
borrow flag UNUSED
結果 兩段程式碼結構完全一樣。按左邊的按鈕編譯 arena 版,再按中間的按鈕跑 RefCell 版。

reference/src/tree.rs 的 rc_refcell::insert 為什麼把 borrow() 包在一個 { ... } 裡、還特地註解「Ref 在此釋放」?就是為了避開這個 panic。 第三顆按鈕跑的就是那個版本:block 結束 → Ref 的 Drop 把 flag 減回 UNUSED → borrow_mut() 才拿得到 Writing。

這裡真正該記住的不是「加個大括號就好」,而是誰在檢查: arena 版那個錯誤是 error[E0502],程式從來沒有機會執行; RefCell 版那個錯誤是一次 panic!,而且只在那條路徑真的被走到時才炸—— 可能是上線後第三天、某個罕見的樹形狀、某個 Ord 的相等分支。 你把一個編譯期的保證換成了一個測試覆蓋率問題。

4 · 成本表:一次配置 vs n 次配置

T = i32、x86-64、含 parent 連結。每一格都可以用 std::mem::size_of 自己驗:

arena(索引)Rc<RefCell>
heap 配置次數(n 個節點) Vec 倍增 → O(log n) 次 realloc,n=1000 約 11 次 n 次 malloc,一個節點一次
每節點 heap 56 B:val 4 + 3 個 Option<usize> ×16。 Option<usize> 沒有 niche,一個連結就吃 16 B——這是天真寫法的稅。
換成 Option<NonZeroU32>:16 B,直接砍 3.5 倍。 		56 B:RcBox 16(strong + weak)+ RefCell borrow flag 8 + Node 32。
而且縮不下去——指標就是 8 B,refcount 就是兩個 word。
走訪 索引算術打進同一塊 buffer;prefetcher 認得這個 pattern pointer chasing 到 allocator 給的任意位址;每一跳都可能 cache miss
refcount 流量 0。cur = nodes[i].left 是暫存器搬移 2n 次讀改寫 / 一趟 inorder;每次都寫進節點的 cache line
借用檢查 編譯期,執行期成本 0 執行期:每次 borrow() 檢查 + 寫 flag;違反 = panic
parent 連結 一個 usize。環是合法的、免費的、無害的 必須 Weak。用 Rc = 洩漏,編譯器不救
整棵樹 Drop 一次 free。i32 無 Drop,連走訪都不用 遞迴解構,深度 = 樹高;n 次 free;深鏈爆 stack
刪除單一節點 留洞。要回收得配 free list + generation(見 arena_lockfree) strong 歸零就還記憶體,不用你操心

表裡最反直覺的一格是「每節點 heap 都是 56 B」——天真的 arena 版並沒有比較省。 arena 的勝利不在單節點大小,在:一次配置、連續佈局、零 refcount、 以及你可以把「指標」縮成 32 bit(真指標永遠做不到這件事)。

5 · 對 Rc<RefCell> 公平一點

上面四節看起來像在處決 Rc<RefCell>。它不該被處決——它換到了真東西, 而 arena 也不是白吃的午餐。

Rc<RefCell> 買到了什麼

· 真的所有權語意:strong 歸零就還記憶體,不留洞、不用 free list、不用世代標記。
· 真的共享:同一棵子樹可以掛在兩個地方(persistent / DAG),arena 要自己再造一套 refcount。
· 不用索引紀律:一個活著的 Rc 就是一個活著的節點,型別系統掛保證。
· 小樹、原型、非熱路徑:它就是能用,而且少寫一堆 plumbing。這是預設值,不是恥辱。

arena 的誠實代價:stale index

// 從一棵樹拿到的索引,拿去點另一棵樹
let i = tree_a.find(&5);   // i = 3
tree_b.nodes[i].val;       // 編譯過。跑得動。
                           // 讀到 tree_b 的第 3 個節點。
// borrow checker 一個字都不會說。

// 或者:槽位被回收再利用之後
let i = tree.insert(5);    // i = 3
tree.remove(5);            // 槽 3 進 free list
tree.insert(99);           // 槽 3 被重用 → 現在是 99
tree.nodes[i].val;         // 99。安靜地錯。
usize 沒有 provenance:它不知道自己屬於哪個 arena、指的節點死了沒。 這是邏輯 bug,不是記憶體不安全——所以 Rust 不會攔你, 而「安靜地錯」通常比 panic 難抓一個數量級。
解法:generation-tagged index((idx, gen),取用時比對世代)—— 正是 arena_lockfree 那一模組在教的東西。

所以真正的判準是:這棵結構有沒有共享或回指? 沒有(純樹) → Box 就夠了,別上 arena 也別上 Rc。 有回指但單一所有者(BST + parent、圖、chain) → arena。 真的多個 owner 共享同一個節點 → Rc,而且 parent 一定 Weak。

6 · 面試怎麼講(兩分鐘版)

被問「Rust 怎麼寫樹/鏈結串列」,不要直接開始寫 Option<Box<Node>>。先講判準,再挑一條路, 然後主動說出你放棄了什麼——那才是 senior 的訊號。

他問你答
為什麼選 arena? 所有權永遠屬於 Vec,節點之間只有 usize——借用檢查根本不參與這個問題。 順便拿到連續佈局跟 O(1) 的整棵樹 drop。
那如果要 parent 指標? arena 就多一個 usize。Rc 版必須用 Weak, 否則 parent ⇄ child 形成 refcount 環,strong 永遠不歸零,Drop 不執行,整棵樹洩漏。 而且這件事編譯器不會擋——Rc 的契約允許環。
RefCell 的風險? 借用檢查搬到執行期。持著 Ref 再 borrow_mut() 同一個節點 → already borrowed: BorrowMutError,而且只在那條路徑被走到時才炸。 所以 borrow() 的區間要手動縮到最小。
arena 的缺點呢? (他沒問你也要說) 索引沒有 provenance。stale index 或跨 arena 的索引會安靜地讀到錯的節點, borrow checker 抓不到。要刪除節點就得上 generation tag。
那 unsafe 裸指標? std 的 LinkedList 是這樣寫的,但面試不主動選這條—— 除非對方明確要求,或你能當場說清楚 aliasing 與 Miri 的驗證計畫。
