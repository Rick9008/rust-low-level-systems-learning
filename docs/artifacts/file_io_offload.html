file_io_offload

epoll 只回答一個問題:「這個 fd 現在做 IO 不會擋住你」。 對 socket,這個問題有意義。對 regular file,它沒有答案—— 所以 kernel 連問都不讓你問。

1 · 把檔案 fd 丟進 epoll 會發生什麼

下面是一條 event loop 執行緒,服務四條連線。每個 tick 一次 epoll_wait, 回報哪些 fd 就緒,你自己去 read()。穩態延遲 1 ms。

現在 conn#3 送來 GET /data.bin——你需要讀一個檔案。 保持在 naive 模式(read() 直接寫在 handler 裡),按下注入鍵,盯著 loop 執行緒。

naive 模式你會看到三件事。一、epoll_ctl(ADD) 對 regular file 回 EPERM ——模擬器假裝 kernel 收下了,才看得到它為什麼拒絕。 二、這個 fd 永遠 readable:不是「有資料時 readable」,是無條件、每一輪、直到你把它拿掉。 三、你照 readiness 的規矩去 read()——然後整條 loop 停在那裡 8 ms, page cache miss,O_NONBLOCK 一點用都沒有。其他三條連線的延遲計數器就在你眼前爬。

切到 offload 再按一次。同一個檔案、同樣的磁碟時間、幾乎同樣的檔案總耗時—— 差別是阻塞發生在一條沒人在乎的 thread 上。loop 一個 tick 都沒停, socket 延遲全程 1 ms。這就是 spawn_blocking 買到的東西:它不讓 read 變快, 它讓 read 不再是所有人的問題。

2 · regular file 沒有「還沒好」這個狀態

readiness 的定義是「現在做這個 IO 不會把你擋住」。 socket 有「對端還沒送」這個狀態,所以「還沒 ready」是有意義的話。 regular file 沒有——資料就在磁碟上,kernel 不會跟你說「這個檔案還沒準備好」, 它會直接把你的執行緒丟進 D state 去等磁碟。 於是「ready」對它是一句恆真式:永遠成立,問了等於沒問。

fd 種類有「還沒有資料」的狀態?O_NONBLOCKepoll_ctl(ADD)read() 會不會擋住你
socket / pipe / tty 有:對端還沒送 有效 → EAGAIN OK 就緒時不會
eventfd / timerfd / signalfd 有:計數器為 0 有效 → EAGAIN OK 就緒時不會
regular file 沒有:資料就在磁碟上 對它無效 EPERM 會:page cache miss 就等磁碟

Linux 的 epoll_ctl(EPOLL_CTL_ADD) 對 regular file 直接回 EPERM。 這不是「還沒支援」,是這個問題對它沒有答案——kernel 拒絕假裝有。 (kqueue 選了另一條路:EVFILT_READ 收下檔案 fd,然後永遠報就緒。 同一個真相,兩種說法。)

3 · readiness 與 completion

「ready」對檔案沒有意義,但「done」有。這一句就是整個模組。

readiness — epoll / kqueuecompletion — io_uring / IOCP
kernel 說什麼 「現在做這個 IO 不會擋住你」 「你要的那個 IO 做完了,結果在這」
誰真的做 IO 你,在你自己的執行緒上 kernel(可能在它的 worker 或 SQPOLL 執行緒上)
buffer 什麼時候要在 read() 當下 提交當下——生命週期是硬約束,Rust 包裝它並不好玩
對 socket 天生契合:有「還沒好」可講 也行
對 regular file 無意義:ready 恆真 天生契合:done 有定義

所以檔案 IO 在 async 世界只有兩條路:offload(在 readiness loop 上手工模仿 completion), 或 io_uring(直接用真的 completion model)。本模組走第一條, 因為第一條是 tokio、libuv、Node 今天實際在跑的東西。

4 · offload:在 readiness loop 上假裝 completion

spawn_blocking(pool, f) -> JoinFuture<T>。worker 阻塞是被允許的—— 它是 pool 的執行緒,不是 loop 的執行緒;它的整個存在意義就是替別人挨這一下。 完成通知走 waker 而不是 callback,才跟 async 生態同形; 而跨執行緒把睡在 epoll_wait 裡的 loop 叫醒,唯一的辦法是 寫一個它有在聽的 fd——那就是 eventfd。

交棒點是 Mutex<(Option<Result<T>>, Option<Waker>)>: 一格放結果,一格放「誰在等」。兩個時序都會發生,兩個都必須對。

waiter — executor thread

worker — pool thread

結果 按「執行這組交錯」。

第三個時序是這個模組唯一真正的陷阱:「檢查結果」與「登記 waker」必須在同一次持鎖裡。 分成兩段,worker 就能在中間的縫隙裡完成——它看到 waker 是 None,不叫任何人; 等待者接著登記了一個永遠不會被叫的 waker,然後 park。 這是 lost wakeup:沒有 panic、沒有錯誤碼,程式只是安靜地停在那裡。 executor 的 park permit 是同一課——交棒的訊號要帶狀態。

另一個無聲失敗:worker panic。結果永遠不會放進去,等待者永遠 hang。 所以 job 內自己 catch_unwind,把 panic payload 當成一種結果送回, JoinFuture::poll 在等待端 resume_unwind 重拋—— panic 跟著在乎它的人走(tokio JoinError 的簡化版)。

5 · 代價,以及真正的答案

上面的模擬有一個誠實的地方值得再說一次:offload 沒有讓 read 變快。 兩種模式下檔案的總耗時幾乎一樣,磁碟該轉多久就轉多久。 offload 買到的是「阻塞發生在哪條執行緒上」——僅此而已,而這已經是一切。

一次 offload 的 overhead:job 入隊(一次鎖)+ worker 喚醒 + 結果回傳(一次鎖) + eventfd write + epoll_wait 返回,合計微秒級。 對 ms 級的磁碟 IO 是零頭;對 page cache 命中的讀(幾百奈秒)則是純虧—— 你付了微秒去避免奈秒的阻塞。這正是 io_uring 在「小 IO、高併發」下贏很大的地方。

pool 大小也跟 CPU-bound 不同:磁碟 IO 是等待為主,執行緒可以開得比核數多 (tokio 的 blocking pool 預設上限 512);CPU-bound 才該鎖在核數。

io_uring 才是真正的答案。提交一個 read 請求,kernel 完成後給你一個 CQE: 沒有 offload 執行緒、沒有兩次鎖、沒有 eventfd 往返,還能 batch 提交、 SQPOLL 連 syscall 都省掉、registered buffer 省掉 pin 的成本。 libuv 到今天仍然是 thread pool offload(就是本模組),tokio 的 fs 全家也是 spawn_blocking;走另一條路的是 tokio-uring 與 glommio。 offload 是在 readiness 世界裡能做到最好的事——但它終究是模仿。
