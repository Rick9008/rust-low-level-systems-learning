tcp_echo

收什麼吐什麼,零協定解析。難的不是 echo—— 是當你 write() 回去,kernel 說「送緩衝滿了,我一個 byte 都不收」的那一刻。 你手上還握著沒送出去的資料,而整個 server 只有一條執行緒。

1 · 一條 thread,三個客戶端

這個 server 只有一條執行緒。倉庫裡的 multiple_clients_interleaved 測試 同時開三條連線、亂序寫、亂序讀,全部通過——thread 數不會跟著連線數長。 這就是 readiness model 的全部意義:不是「一條 thread 等一條連線」, 而是「一條 thread 等任何一條連線有事」。

代價是一條鐵律:event loop 裡的每一個 fd 都必須 nonblocking。 listener、每一條 accept 出來的 stream,通通要 set_nonblocking(true)。 漏掉一個,那個 fd 上的一次阻塞 accept / read / write 就會把所有連線一起凍住——因為它們共用那條執行緒。

epoll 只告訴你「現在可以做這件事而不會阻塞」。它不替你做 IO, 也不保證你要的量能一次做完。「可寫」的意思是「送緩衝現在有空位」, 不是「你的 8 KiB 一定塞得進去」——下一節整個都在處理這個差別。

2 · 讀很簡單。寫才是題目。

快的客戶端灌 8 KiB 進來,server 讀出來、要 echo 回去。 但對端讀得很慢,kernel 送緩衝(這裡設成 4 KiB)一下就滿了—— write() 只吃下一部分,剩下的回 EWOULDBLOCK。 剩下那幾千個 bytes,現在是你的責任。選一個策略,然後一步一步走。

3 · 四個答案,只有一個是對的

面試時這題會被問成「write 回 EWOULDBLOCK,你怎麼辦?」。 三個錯的答案都能跑,這正是它們危險的地方——上面每一個都親手按過一遍。

做法會發生什麼為什麼錯
迴圈重試 write() CPU 100%,數百萬次 EWOULDBLOCK 餓死所有人——單執行緒。你在 write() 裡忙等的每一奈秒, 是 conn-2、conn-3、和還沒 accept 的新連線的每一奈秒。而且醒來時機由最慢的那個客戶端決定。
丟掉剩餘 CPU 正常,event loop 順暢 靜默資料遺失——最陰險的一個。 小訊息測試全過(hello 5 bytes 一次就寫完),直到你灌 1 MiB, client 的 read_exact 永遠等不到最後那幾 KB。
改回 blocking,等它可寫 CPU 0%,執行緒睡在 write(2) 裡 凍住整個 event loop——比忙等更安靜,一樣致命。 連 listener 都不 accept 了。你把服務的可用性外包給了對端的 read 速度。
緩衝 + EPOLLOUT 寫多少算多少,剩的進 conn.out,interest 加上 WRITABLE 唯一正確——執行緒立刻回到 epoll_wait。 可寫事件來了再 flush 欠帳;所有其他連線一輪都沒少。 這就是 tokio 的 TcpStream 在 .await 底下替你做的事。

有一個第五種答案,production 一定要有、本實作誠實地沒做:欠帳緩衝設高水位。 conn.out 無上限 ⇒ 一個永遠不 read 的客戶端能把 server 記憶體吃爆。 正解是超過水位就暫停讀該連線(把 READABLE 拿掉)—— backpressure 就沿著 TCP 視窗一路傳回發送端。interest 狀態機的第三個維度。

4 · interest 是狀態機,不是設定

註冊什麼 interest,是連線當下狀態的函數,不是開一次就不動的組態。 整條規則只有兩行:還在讀就聽可讀;有欠帳才聽可寫。

第三列是最容易漏的:對端送了 EOF 不代表你可以立刻關。 它的最後一批資料可能還躺在你的 out 裡。先 flush 完欠帳,清空了才關—— 上面按「client 送 FIN」在有欠帳時就會走這條路。

而第四列的鏡像是一個真 bug:flush 完不把 WRITABLE 拆掉。 LT 模式下 socket 幾乎永遠可寫 ⇒ 每一輪 epoll_wait 都立刻返回一個「可寫」事件 ⇒ 你去 flush 一個空的 out ⇒ 什麼都沒做 ⇒ 再 epoll_wait ⇒ 又立刻返回。 100% CPU,沒有任何事情在發生。把上面那個「bug: 清空後不拆 EPOLLOUT」按下去,連按幾次 epoll_wait 就看得到。

「忘了加 EPOLLOUT」讓你的資料永遠送不出去;「忘了拿掉 EPOLLOUT」讓你的 CPU 燒光。 這是同一顆硬幣的兩面,而它們都源自同一個誤解:把 interest 當成靜態組態。 程式碼裡 conn.registered 這個欄位存在的唯一理由,就是「算出來的 interest 跟現在掛著的不一樣才 epoll_ctl(MOD)」—— 順便省掉每輪一次的 syscall。

5 · 誠實的簡化

LT 而非 ET。LT 漏處理下次還報,好寫。ET 假醒少,但必須讀寫到 EAGAIN—— 漏一次就是永久 stall。本實作的讀寫本來就到 WouldBlock 為止,改 ET 只差註冊旗標; 但 accept 沒收乾淨,在 ET 下是永久掛掉的連線,LT 下只是慢一輪。面試先講 LT。

單執行緒。多核擴展要 SO_REUSEPORT 開多個 loop,或 accept 後把 fd 派發給 worker。 但先讓一條 loop 正確——上面那四個答案裡選錯一個,加再多核也是白搭。
