async 追問串:從「wake 之後」一路問到 cancel safety

一個晚上的連環追問,照原本的脈絡收錄:park 是對誰?task 跟 future 差在哪?unpark 先到會丟嗎?pin 之前為什麼能動?釘住的 future 怎麼「放著等」?busy-wait 為何不愛 async?join!/select! 憑什麼零 alloc?Redis 單線不就夠了?read_exact 怎麼把 stream 弄錯位?Waker 基礎(電話的一生)在前置頁 qa_waker_lifecycle.html;這頁從它結束的地方開始。先立一句公理:wake ≠ poll,wake = enqueue——喚醒只是把 task 推回佇列,執行永遠由 executor 稍後 poll。

Q1 · park 是針對 task 還是 thread?multi-thread runtime 怎麼看?

park 永遠是 thread 的事;task 沒有 park。task 的「睡」不是任何 OS 操作——只是「不在 run queue 裡」這個資料結構狀態。

兩層睡眠 —— task : worker thread :: thread : CPU core(同一套排程思想搬上一層)

Task 層(純資料結構)

睡 = poll 回 Pending 後不在佇列,只剩 waker 被存著
醒 = wake() 推回 run queue,零 syscall

Worker 層(OS thread)

單一 task 回 Pending → 不 park,撈下一個
整個佇列空(連偷都偷不到)→ 才 park
wake() = 入隊 + 順便 unpark 一條睡著的 worker
block_on = 兩層退化重合的特例:一 task 一 thread → 「task 醒」=「thread 醒」→ waker 直接填 unpark

「park」可以廣義化:「這條 thread 用某個阻塞原語睡到有活」——thread::park / condvar wait(thread_pool)/ epoll_wait(mini_runtime V1;tokio 的 idle worker 之一抱著 IO driver 直接睡進 epoll_wait,醒來順手就是 reactor)。原語是實作選擇,「沒活就睡、來活就醒」是不變骨架。

Q2 · task 跟 future 哪裡不一樣?

Future 是「可組合的值」;Task 是「可排程的單位」。spawn 是把一棵 future 樹升格成 task 的那道門。

FutureTask
是什麼實作 Future 的 struct(狀態機),被動等人 pollexecutor 帳本的一格:root future + 排程簿記
排程不可排程——佇列裡放的從來不是裸 future排程最小單位;「睡 = 不在佇列」的主詞
Waker沒有自己的per-task:樹裡任何 leaf 回 Pending,存的都是同一個 task 的 waker

類比釘死:future : task :: 函式呼叫 : thread。stack frame 不可排程、thread 才可;future 不可排程、task 才可。並發階梯:.await(循序)→ join!/select!(單 task 內並發,永不平行)→ spawn(多 task,可平行;所以要 Send——誰撈到誰 poll)。

喚醒粒度 = task:epoll 叫醒的是整個 task,executor re-poll 的是 root,每層狀態機憑存的狀態導航回暫停的 leaf——不存在「直接跳到 leaf」;所以 spurious wake 無害(重走一遍,沒好就再 Pending)。

Q3 · unpark 搶在 park 之前到,訊號會丟嗎?

不丟。std::thread 的 park/unpark 是 token(狀態)語意:每條 thread 天生一枚 token 停車位;unpark() 設 token(上限一枚、不累積),park() 有 token 就消耗、立即返回。事件語意才會讓喚醒蒸發 → 永睡。park() 還允許 spurious 返回——都沒關係,因為外面是 re-poll 迴圈兜底。

同一個幽靈(lost wakeup)解法(全是「狀態閂」)
condvar lost wakeup(thread_pool 親手抓的 bug)predicate + 持鎖重查
park/unpark race(本題)token 狀態閂
wake-during-poll(task 層:wake 打在正在 running 的 task 上)task atomic 狀態機:閂成 notified,Pending 收尾看到就直接重入隊
「喚醒必須是狀態,不能是事件;狀態允許粗糙(合併/假醒),因為消費端永遠用迴圈重查真相。」pillar-4 口述金句,三個場景通用。

Q4 · 為什麼 pin 之前 future 可以隨便 move?

因為它是 inert(惰性)的:async fn 回傳的 future 誕生在狀態 0——struct 裡只裝函式參數,body 一行沒跑、沒 local、沒借用,自引用還不存在。自引用是 poll 執行中誕生的:跑到 .await 要暫停時,活著的 locals(含互相借用的)被存回狀態機 struct。

時間線 —— pin! 是分界,poll 才是自引用的產房
建構(狀態0)只裝參數
可自由 move
pin! / spawn簽「永不再動」合約
第一次 poll借用跨 await 被存回 struct
自引用誕生
之後永不准動,直到 Ready / Drop

poll(self: Pin<&mut Self>) 這個簽名的全部用意:型別系統強迫「先 pin 才能 poll」——「move 自由期」與「自引用期」被 API 硬隔開。「future 是 lazy 的」=「poll 前可自由 move」,同一事實兩面;tokio::spawn(fut) 敢把 fut move 進 heap 也是這個理由。

Q5 · Pending 時,釘住的 future 要怎麼「放進去等」?

動的是指標,bytes 從 spawn 那刻起再也沒動過。spawn 把(還 inert 的)future move 進一塊 heap 配置(task),從此釘死;run queue 裡放的是指向 task 的指標——入隊、出隊、work-stealing 搬的都是 8 bytes,heap 上那塊 future 位址不動。

類比:future = 蓋死在地基上的房子;流通的是地址,不是房子

heap task(bytes,不動)

root future 釘在這,活到 Ready/Drop
靠引用計數活著(waker / JoinHandle 各持一份)

run queue(指標,亂跑)

裝 task pointer;worker 撈到就走過去現場 poll(in place),絕不搬房子
Pending 的 task「放哪等」?哪都不放——就是不在佇列;waker 的引用保活;wake() 把指標推回佇列

兩個 pin 的家:block_on 用 pin!(stack)——唯一的 future 哪都不用去;spawn 用 heap(Box::pin 本質)——指標要旅行,bytes 必須住在不隨 frame 死的地方。搬 Box 永遠不搬 pointee,這就是 Pin<Box<T>> 能到處傳的原因。

Q6 · async 逃不過 spawn 的 heap,所以 busy-wait 場景不愛它?

方向對,歸因要修:per-spawn 一次 alloc 攤在 task 生命週期上是幾十 ns,不是主犯。而且 async ≠ heap——Embassy(embedded)在 no_std 零 heap 跑 async,task 靜態配置;「逃不過 heap」是 tokio 式動態 spawn 的性質。真正讓低延遲場景嫌棄的三件事:

  • 排程間接層 = 延遲抖動:事件 → wake → 入隊 → 誰撈到 → poll 導航,每跳都是不可預測的延遲;busy-poll 的反應是 inline 的,個位數 ns 零抖動。
  • 控制權讓渡:runtime 決定何時何核跑你;work-stealing 毀 cache locality。低延遲要 pin core、cache 熱著(seqlock / kernel bypass / cache warming 那一側)。
  • 最根本:async 的全部價值 = 「等待很便宜」。busy-wait 場景根本不想等、沒東西可多工——沒有等待可省,收益零、成本全留。
「不是 async 慢,是 async 在解『等待很多』的問題;熱路徑如果『從不想等』,它就是錯的工具。」選型軸:waiting-dominated(萬連線 → async/evented)vs latency-dominated(專核少流 → pinned thread + busy-poll)。對照 hw_bridge 五 server:evented 吃高並發,spsc 版就是 busy-poll 派。

Q7 · join!/select! 憑什麼零 alloc?是「重組了一個 task」嗎?

不是重組 task——是根本沒讓第二個 task 出現。組合發生在值的層次:join!(a,b,c) 展開成一個新 struct,三個子 future 以值內嵌成欄位(無 Box 無間接層);整棵樹 = 一個扁平 struct,大小編譯期算好;task 在 root 才誕生、只誕生一次。

// 概念展開:「組合 = struct 內嵌」,跟 async fn 存子狀態機同一招
struct Join { a: FutA, b: FutB, c: FutC, out_a: Option<A>, /* … */ }
// poll:輪流 poll 還沒完成的子欄位;全樹共用同一個 per-task waker
alloc備註
join! / select! / async fn 嵌套(編譯期已知個數)0純 struct 疊加
join_all(vec) / FuturesUnordered(動態個數)容器一次 + per-child 簿記仍只有一個 task,遠便宜於 N 次 spawn

join! 的 O(N) re-poll 在 N 大時會痛 → FuturesUnordered 存在的理由:給每個子 future 一個中介 waker,記下是誰叫的、只 re-poll 那一個。零配置 ↔ 精準喚醒,又一條 trade-off 軸。select! 的差別在語意:first-Ready-wins,輸家當場 drop——這就是下面 Q9 的主角。跨語言一句:Go 每 goroutine 一條 heap stack、C++ coroutine 每 frame 一次 alloc;Rust 把並發結構編譯成 struct 嵌套 = "perfectly sized stack",所以下得了嵌入式。

Q8 · epoll + 單執行緒也能萬連線(Redis),為什麼還要 async runtime?

你對:「等待便宜」是 epoll(evented)給的,不是 async 給的。async runtime = epoll loop + 兩個增值服務:

增值服務解決什麼Redis 為什麼不需要
① 編譯器幫你寫 per-connection 狀態機協定深時,手寫狀態機被剁碎成轉移邏輯(「fd 就緒了,我剛做到哪?」)RESP 邏輯淺:讀→查記憶體→寫回,狀態機三格,手寫毫無壓力
② multi-thread 排程handler 成本不均 → 單線 evented 有 head-of-line blocking,p99.9 爆handler 小而勻(μs 級);單執行緒 = 資料結構零鎖,是主動要的紅利

判準一句話:協定深不深(狀態機誰來寫)、handler 勻不勻(要不要多線吸收)。兩個都「否」→ 手搓 evented;任一「是」→ runtime 開始回本。完整光譜:thread-per-conn → evented 手搓 → async runtime → sharded/spsc(專核)。

Q9 · read_exact 掛進 select! 為什麼會讓 stream 錯位?

先立定義:Rust 的 cancellation 不是訊號、不是異常,就是 Drop(select 輸掉 / timeout / abort 同一機制)。cancel-safe = 被中途 drop 不遺失任何已發生的消費。單發 read() 安全;多步驟有中間進度的 read_exact 不安全——進度住在 future 肚子,Drop 即滅證。盯住三個位置走一遍;切到 framer 模式看免疫版:

生死簿:future 自有的(pos)drop 陪葬;借來的(buf、socket)drop 後歸還、活著——但活下來的 buf 失去「前 3 格有效」的詮釋,等於死了。kernel 那邊消費即逝、不重播,兩邊夾殺。framer 的解法 = 把進度本身(acc 的長度)也搬到 future 外面,全部狀態活過取消;追問「上 tokio 呢?」→「我的 framer 搬進 select! 不用改一行」。配套坑:loop {{ select! }} 每輪重建分支 future;要跨輪續跑 → pin 在 loop 外、分支用 &mut fut。

Q10 · 手寫狀態機 / callback / stackless / stackful,各自優缺?

一條軸講完:狀態表示從顯式到隱式——你的 struct → 散裝閉包 → 編譯器 struct → 真 stack。越右越像同步碼;越左越省記憶體、控制越強。

①手寫狀態機②Callback③Stackless(Rust/co_await)④Stackful(asio spawn/goroutine)
狀態機誰寫你(顯式 enum)你(散裝閉包)編譯器沒有——用真 stack
per-task 記憶體最省可池化每步閉包 alloc一個貼身 frame整條 stack(KB~MB)
暫停點事件邊界每步結尾顯式 await,著色傳染任意深度、無著色
除錯好(state 可印)慘邏輯≠實體 stack真 stack 真 trace
取消trivial手動易漏統一=Drop(cancel-safety)unwind 活 stack,難

判決:①協定淺時最優(Redis / framer);②是①的打散版,今天沒理由選;③甜蜜點 = ④的直線寫法 + ①級記憶體精確,帳單是著色 + Pin;④無著色是殺手優點,天花板是 stack 記憶體經濟學(Go 綁 GC 才能搬 stack;C++ 裸指標不能搬)。Go 選④所以必須養 runtime;Rust 要零 runtime 只能③——「複雜度沒有消失,只是從 runtime 搬到型別系統」。Asio 橫跨②③④三格。

Q11 · 不是 epoll 的 future(timer / channel)要「放去哪」?

先翻轉預設:future 從來不是「放去 epoll」——它把 waker 存進「它等的那個資源自己的等待結構」;epoll 的 fd 表只是 IO 資源的那一種。

leaf 在等什麼waker 存哪誰按 wake()
IO(TcpStream…)reactor 的 fd → waker 表driver(epoll 回報就緒後)
時間(sleep/timeout)timer wheel(時間輪)driver(檢查到期後)
channel / Mutex / Notify該原語自己的 waker 槽 / waiter list另一個 task 的 thread(send/unlock 當下,純 userspace)
三種喚醒源,收斂進 driver 的同一個 syscall
driver 的 park 其實是:
epoll_wait( [IO fds…, 自家 eventfd],  timeout = 下一個 timer 到期 )
              ↑ IO 就緒      ↑ 別 thread 的 wake       ↑ 時間到
時間不是事件、是 deadline → 翻譯成 timeout 參數;userspace 的喚醒 → 翻譯成 eventfd 寫入(kernel 只聽 fd 的語言)

eventfd = kernel 給的「64-bit counter 假裝成 fd」(write 加一、read 清零)——存在目的就是讓「叫醒」這件事有 fd 的形狀,epoll 才看得見。類比:值班室只聽門鈴;IO 天生自帶門鈴,同事(userspace 的 send)想叫醒值班的人,喊沒用,只能也去按那顆裝給自己人按的門鈴。

Q13 · recv 到底做什麼?waker 會幫我搬資料嗎?

recv 自己不等,waker 也不搬資料。recv-future 的 poll 只做三步;「等」是 executor 的事(不再 poll 這個 task),資料靠下一次 poll 自取:

// Recv future 的 poll,概念版:
// ① 先查真相
if let Some(msg) = queue.try_pop() { return Ready(Some(msg)); }
// ② 空 → 把「這個 task 的」waker 存進 channel 的 waker 槽
channel.rx_waker.register(cx.waker());
// ③ 存完「再查一次」——擋 wake-before-register race
if let Some(msg) = queue.try_pop() { return Ready(Some(msg)); }
Pending

③ 是性命攸關的:①查到空、還沒走到②之間,send 可能塞了資料並按了 wake——那時槽裡還沒有你的 waker,鈴按給了空氣;不做③就帶著永遠不響的鈴回去睡 = lost wakeup。這是同一個幽靈的第四次現身(condvar predicate / park token / task notified 閂 / register-then-recheck)。wake 的契約只有「值得再 poll 一次」——跟 epoll 的 readiness 同構:告訴你可讀了,bytes 還是自己去拿。

channel 的 state:tokio mpsc(單 consumer)= 一格 AtomicWaker(每次 poll 覆蓋);多等待者的 Mutex/Notify 才升級成 intrusive waiter list(sync 版存 Thread+park,async 版存 Waker——同構雙生)。

Q14 · Context 跟著誰走?Waker 到底是什麼指標?

Context 是「單次 poll 的信封」;Waker 是「task 的耐久身分證」= task ptr + runtime vtable 的胖指標。

RawWaker { data: *const (),  vtable: &'static RawWakerVTable }
//          ↑ tokio 填:task 的 heap 指標(帶引用計數)  ↑ runtime 填 {clone, wake, wake_by_ref, drop}
// wake() = vtable.wake(data) = 把 data 當 task ptr 推進 run queue
// block_on 版:data = Thread 把手,wake = unpark —— 同一個殼,換線路
箭頭方向(最容易反的一格):資源持有 waker,waker 只指向 task
fd 表 / timer wheel / channel 槽 ──(存著 Waker 的 clone)──→ Waker ──(data)──→ Task
        ↑ 資源知道 waker 在哪              waker 對「自己被存在哪」一無所知     wake 時入隊

三種流向一次記:poll 期間往下(executor 現場造 cx,以 &mut 傳下整棵樹,這次 poll 結束就死——lifetime 逼你想留門鈴就得 cx.waker().clone());需要等就往旁存(leaf 存進資源);稍後往回敲(資源按 wake → 指標入隊)。

樹的分工:中間節點純水管,leaf 是唯一的註冊點

中間節點(async fn 狀態機 / join! / select!)

把 &mut Context 往下傳,從不碰 waker 存放

leaf future(runtime/函式庫作者寫好的)

poll = 查資源 → 不 ready 就把 waker clone 存進自家資源的等待結構(每次 poll 覆蓋)→ Pending
推論:tokio 的 sleep/TcpStream 離開 tokio 會 panic(leaf 要找自家 timer wheel/reactor);channel future 到哪都能跑(資源就是 channel 自己)。leaf 依賴什麼基礎設施,決定它綁不綁 runtime。

waker 是 per-task、不是 per-資源的鐵證:select! 同時等 timer + IO + channel = 同一個 task 的 waker 被 clone 三份、存進三個家;誰先好誰先按,按下去做的事完全相同。而 waker 的 data 帶引用計數 → 「Pending 的 task 靠 waker 的引用保活」就是這麼落地的。

面試句庫

“Wake never executes anything — it just re-enqueues the task (or unparks the executor). Execution always happens later, when a worker polls. That separation is what keeps ‘only the executor polls’ a single-entry invariant.” wake = enqueue,一句話。
“A future is inert until first polled — state zero only holds the arguments, so it's freely movable. Self-references are created during poll, when locals borrowing each other get saved across an await point. That's why poll takes Pin<&mut Self>.” inert → pin → poll 的時間線。
“Cancellation in Rust is just Drop. read_exact keeps its progress inside the future, so select! dropping it loses consumed bytes and desyncs the stream. Own the accumulation buffer in your struct and only do single-shot cancel-safe reads — exactly what a hand-rolled framer does by construction.” cancel safety + framer 免疫。
“An async runtime is just an epoll loop plus two services: the compiler writes your per-connection state machines, and the scheduler absorbs uneven handler costs. Redis needs neither — that's why hand-rolled evented is the right call there.” Redis 問題的完整回擊。
“Non-IO futures don't go into epoll — each resource keeps its own waiter structure: the timer wheel, the channel's waker slot, intrusive waiter lists. What converges on epoll_wait is the wakeup delivery: timers become the timeout argument, and cross-thread wakes write an eventfd registered in the same epoll set. Three wake sources, one syscall.” 「timer / channel 怎麼叫醒 driver」的完整版。
“A Waker is just a fat pointer — task pointer plus the runtime's vtable. Resources hold clones of it; it holds the task; wake() feeds that pointer back into the run queue. The waker never knows where it's stored — storage is the resource's business, and the channel never touches the eventfd; that's the runtime's unpark, three layers down.” waker 胖指標 + 三層分工,一句講完。
