sharded_map

一把鎖、八個執行緒,第二個以後永遠在排隊。分片把一把鎖換成 N 把—— 但它沒有消滅競爭,只是把競爭切成 N 份。 切不開的那一份,就是你的瓶頸,而面試官問的正是那一份。

1 · 一批 op,兩種鎖

下面兩條 lane 收到完全相同的一批操作。 左邊是 Mutex<HashMap>:一把鎖,誰先搶到誰先做,其餘全部 park。 右邊是 [Mutex<HashMap>; 8]:每個 op 先算 hash(key) & mask 挑出 shard, 再去搶那一把鎖——落在不同 shard 的 op 是真的同時在跑。 按 burst,然後只看一個數字:blocked。

scoreboard 按 burst,兩條 lane 會收到同一批 op。看 blocked 那一格。

一個 tick = 一輪臨界區。每把鎖每輪只放一個 op 進去,其餘在 queue 裡多等一輪。 blocked = 至少等過一輪的 op 數;rounds = 這條 lane 排空所需的輪數。 單鎖那邊 op/tick 恆為 1.00——這就是「吞吐上限 = 1 / 持鎖時間」的意思, 加再多核也不會動。

按單顆 get(key):兩邊都 0 blocked。分片不會讓單執行緒變快, 它多做的那次 hash 反而是純成本。把 shards 切到 1:右邊逐格退化成左邊, 數字一模一樣——那正是 ShardedMap::new(1),測試 boundary_single_shard_degenerate_still_correct 釘的就是「退化了也還是對的」。

2 · 誠實的失敗:hot key

把 workload 切到 hot key 再按 burst。8 個 op 全打 "session:hot"——同一個 key、同一個 hash、同一個 shard。 右邊有 8 把鎖,能用的只有 1 把。blocked 兩邊一樣是 7,rounds 也一樣是 8。 分片一次都沒省到。

skewed 那顆按鈕更陰險:8 個不同的 key,但 hash & mask 全撞進同一格。 log 裡的 hash 值各不相同,shard 索引卻一路相同。key 不一樣不代表鎖不一樣—— hash 分佈是機率,不是保證。

真實世界的 hot key:被搶爆的商品 id、"total" 這種全域計數器、被 DDoS 的那個 session。 分片對它們一點忙都幫不上。這句話要在面試時主動講,而不是等對方問—— 「我用分片降競爭」是初階答案,「分片把競爭 partition 掉,但 hot key 會讓某個 partition 變回全域鎖, 所以我會先量 key 分佈」才是。

hot key 只能換維度救,不能靠加 shard 救:key 加隨機後綴打散成 M 份、讀時再聚合(counter sharding); 或把熱值提到 AtomicU64 / per-thread cache;或整條讀路徑換成無鎖(第 6 節)。

為什麼 uniform 會贏,數學上:N = 8、8 個 op,期望用到的相異 shard 數是 8 × (1 − (7/8)^8) = 約 5.2,所以期望 blocked 約 8 − 5.2 = 2.8。 單鎖那邊永遠是 7。分片贏的是期望值,不是最壞情況—— 最壞情況(全撞一格)分片跟單鎖完全一樣慘,而且還多付了 hash 的錢。

3 · shard 數:兩邊都是懸崖

「多切幾片就好」是錯的。shard 數是個 U 形取捨,兩端都掉下去。

shard 數鎖競爭記憶體 / 快取全域操作(len / iter)
1 全域序列化,吞吐上限 1 / 持鎖時間 最省。locality 最好,一張大 table O(1) 把鎖,而且是線性化的
2–4 × 核數
(典型 16–64)		 兩個隨機 op 撞同一把鎖:1 / N N 個 HashMap + N 個 Mutex,可接受 O(N) 依序取放鎖,非線性化快照
過大
(如 4096)		 幾乎不撞——但你早就不缺這個了 每個 shard 都太小:table 撐不滿一條 cache line, entry 分散、TLB / prefetch 全失效;N 個 Mutex 的 header 本身就是幾十 KB O(N) 變成真成本,len() 要摸 4096 把鎖

shard 數取 2 的冪不是美感,是為了把 % 換成 &。 hash % N 是整數除法,x86 上 div 要 20–40 cycle 且不好 pipeline; hash & (N − 1) 是 1 cycle、無分支。 new() 用 num_shards.max(1).next_power_of_two() 上取, mask = n − 1 存起來——之後每次操作都省下那次除法。

還有一個沒寫在程式碼裡的坑:Box<[Mutex<HashMap>]> 裡相鄰的 Mutex 很可能落在同一條 64 位元組 cache line。兩個執行緒鎖不同 shard,硬體層卻在同一條 line 上互相 invalidate——false sharing,分片的效果被打掉一截。dashmap 的作法是把每個 shard 對齊/填充。 這與 spsc_ring 給 head/tail 各自 #[repr(align(64))] 是同一課。

4 · 咬人的不變量:全域視角不再是原子的

分片買到並發,賣掉的是「一把鎖看得到整張表」這件事。任何需要全域視角的操作都碎了。

操作本實作怎麼做你必須知道的代價
len() 依序 lock → 讀 len → unlock,加總 非線性化快照。數到 shard 3 時 shard 0 可能已經被改。 它是監控值:能畫成 dashboard,不能拿來做決策。 if map.len() == 0 { assume_empty() } 是 bug。
iter() 不提供 同一個理由。要提供就得說清楚它是「拼接起來的快照」,而不是某個時刻真的存在過的狀態。
跨 key 原子更新
(把 a 的錢搬給 b)		 不提供 需要同時持兩把鎖。要做就必須按 shard index 由小到大取鎖—— 否則 T1 拿 3 等 5、T2 拿 5 等 3,死鎖。

所以這個模組把不變量寫死成一句話:任何操作最多持有一把 shard 鎖。 永不同時持兩把 ⇒ 不存在 lock ordering ⇒ 死鎖從設計上被排除,不是靠紀律避免。 len() 也遵守它:取一把、放一把、再取下一把,絕不疊著拿。 這是一個刻意放棄的能力,不是一個沒做完的 TODO。

同一條不變量的另一面:with(&k, |v| ...) 的 closure 在持鎖期間執行。 在 f 裡再碰同一個 map,若 k2 撞到同一個 shard,就是自己等自己—— std::sync::Mutex 不可重入,直接死鎖。f 必須短、必須純。

upsert 為什麼要一段式:get_cloned 然後 insert 是兩把鎖區間, 兩個執行緒都讀到 5、各自寫回 6,更新掉了一次。upsert 在同一把 shard 鎖裡做完 entry().or_insert() + 修改,天然原子。 這跟 fetch_add vs load; store 是同一課,測試 boundary_same_key_contended_upsert_loses_nothing(8 執行緒 × 1000 次遞增 = 8000,一次不丟) 就是釘這個。

5 · get(&K) -> Option<&V> 編不出來,而編譯器是對的

你會很想寫這個簽名。它編不過:&V 指向 shard 內部的記憶體, 而保護那段記憶體的 MutexGuard 在函式返回時就 drop 了。 回傳的引用會立刻懸空。Rust 不是在刁難你——它是在攔下一個 C++ 寫得出來、上線後 use-after-free 的簽名。

出路簽名代價
複製值 get_cloned(&K) -> Option<V> where V: Clone 一次 clone。V 小(數十 byte)時最省事;V 大時是純浪費。
closure with<R>(&K, impl FnOnce(Option<&V>) -> R) -> R 零複製,借用只活在持鎖區間內。代價:f 執行期間佔著鎖, f 要短、不可重入(見上一節)。
Arc<V> 值本身存 Arc<V>,clone 只是 refcount +1 一次原子遞增 + 一層間接。適合 V 大、且要讓值逸出鎖之外長期持有。
guard 型別
(dashmap 的解)		 回傳 Ref<'_, K, V>——把 guard 跟引用綁在一起一起逸出 API 最像 HashMap,但 caller 握著鎖而不自知。 忘了 drop 它就去碰同一個 shard = 死鎖。

另一個非踩不可的坑,在 ShardedMap 的欄位裡:build_hasher: RandomState 必須存在 struct 上、全 map 共用一份。若每次操作都 RandomState::new(), seed 每次不同,同一個 key 這次落 shard 2、下次落 shard 5——key 會憑空「消失」, 而且測試在單執行緒下多半還會過。上面模擬器的 hash 也是全域共用一份,原因一樣。

6 · 產品裡不要自己寫這個

這個模組的價值在於你講得出上面五節,不在於這 100 行程式碼上線。 真的要用:

選項機制什麼時候選它
dashmap 就是這東西的產品版:分片 + RwLock + guard 型別(Ref / RefMut) 預設選它。RwLock 讓同一個 shard 的多個 reader 也能並行,比純 Mutex 又多一層。
crossbeam crossbeam-skiplist 的 SkipMap:lock-free、有序; 背後是 crossbeam-epoch 的 epoch-based reclamation 要有序迭代或 range query,且不想為了迭代鎖住全表。 沒有分片,也就沒有 hot-shard 問題。
papaya / flurry epoch-based,讀路徑完全無鎖 讀極多、寫少,而且讀延遲 tail latency 不能有鎖抖動。
RwLock<HashMap>
/ arc-swap		 單鎖讀寫分離,或整張表 immutable、換的時候整個換掉 寫極少(設定檔、路由表)。分片在這裡是過度工程。

面試時的完整答案長這樣:「先量讀寫比和 key 分佈。讀寫比 100:1 就先問要不要 RwLock<HashMap> 或 arc-swap;真的是高並發讀寫混合,才上分片, shard 數取 2–4 倍核數的 2 的冪;然後我會盯 key 分佈,因為分片對 hot key 沒有用。 產品裡我用 dashmap,不自己寫。」
