Waker 是什麼:st、cx.waker() 與白板上那格電話的一生

你已經知道「waker 是把 park 的 thread 叫起來」——方向對,但主角搞錯了。真正的主角是「怎麼把這個 task 重新排回去 poll」。這頁用一個貫穿到底的比喻,把 st、cx.waker()、以及那格電話的三態 none → stored → taken 一次講清,最後用一個可以逐步走的 stepper 讓你親手把順序寫反、看它掛死。

1 · 一個比喻解開全部

把 async 想成一間餐廳。你(task)點了一道現做的菜(這個 future 要等的資源)。核心難題是:

一個 future 被 poll,發現資料還沒好,想說「我還沒好,等等再叫我」——但「再叫我」到底怎麼叫? future 自己根本不知道它是 run queue 裡的第幾個 task、要怎麼把自己排回去。只有 executor 知道。

所以每次 executor poll 一個 future,會順手塞給它一張「怎麼重新叫我」的說明書。那張說明書就是 Waker,裝說明書的公事包就是 cx。future 把說明書複製一份、貼到廚房門口的共用白板(st)上,然後回座位;廚師(producer)做好菜、撕下白板上的說明書、照著把你叫回來。

一句話定位:park / unpark 是「executor 沒事做就去睡、有事就醒」;wake() 的主戲是「把 task 放回 run queue」,叫醒睡著的 executor 只是順帶的副作用。

2 · 角色表:把每個詞釘在比喻上

詞在比喻裡是在程式裡是
executor餐廳大廳、排隊系統那個一直呼叫 poll() 的永恆迴圈,擁有 run queue。不認識 fd
run queue大廳的候位名單(FIFO)「現在就緒、可被 poll」的 task 排隊清單
task / future你這位客人 + 你點的套餐一個狀態機,被 poll 一步步推進,每個 .await 是存檔點
poll()走到櫃台問「好了嗎?」future.poll(&mut cx)
cx(Context)櫃台遞給你的公事包poll 的參數,裡面裝著這次的 Waker
cx.waker()公事包裡「你的電話號碼」回傳 &Waker——一個物件(不是裸 fn),包著「怎麼重排這個 task」的 callback
st(shared State)廚房門口的共用白板 📋Arc<Mutex<State>>,future 與 producer 兩邊都看得到
st.waker白板上「貼客人電話」那格State 裡的 Option<Waker> 欄位
producer廚師(把菜真正做好那方)「做完事就按 waker」的泛稱:另一條 thread、或 kernel(經 reactor 代打)、或通道另一端
reactor傳菜口的叫號員 📣跑 epoll_wait 的那條 thread;手握 interest table「fd → waker」,fd 就緒就替 IO future 打電話。不認識 task
.wake()照號碼打電話給你把 task 重新排回 run queue(順便 unpark executor)
Pending「還沒好,我先回座位」return Poll::Pending

cx.waker() 回傳的是 function 嗎?——接近,但精確一點:

它回傳 &Waker,一個物件的參照。Waker 底層是手工版的 trait object:{ 資料指標, vtable },vtable 裡就是四根函式指標 clone / wake / wake_by_ref / drop。

  • 為什麼是物件、不是純 fn? 因為「怎麼重排這個 task」需要帶狀態——它得記住是哪個 task(那個 Arc<Task> 指標)。純 fn 沒地方存。函式指標 + 資料指標,剛好是 trait object 的形狀。
  • 你不會寫 cx.waker()()。你呼叫它的方法:.clone() 複製一份自己擁有的、.wake() / .wake_by_ref() 才是真的「按下按鈕」。
  • 為什麼要 .clone() 才能存? cx.waker() 只借你看;要留到「以後 producer 來按」,得複製一份放進白板 st.waker。clone 一個 Waker 通常只是底層 Arc refcount +1,很便宜。

3 · 互動:白板上那格電話的一生

逐步走一次完整環路。右邊「共用白板 st」與「大廳(executor)」會跟著每一步變色。切到 反例,把「先寫菜、再打電話」的順序寫反,看 task 怎麼永久掛死——這就是你上一題要預測的那個 bug。

「可是 Mutex 不是會擋住 re-poll 嗎?」——好問題,這決定了反例成不成立。 上面的掛死,前提是那通 wake 比它要通知的 result 更早被 re-poll 看見:wake 打在鎖外(先 drop(lock) 再 wake(),result 之後才在另一個臨界區寫),或 result 用 lock-free / relaxed atomic 發佈。 反過來,若 result 與 wake() 包在同一個 Mutex 臨界區、而 re-poll 也搶同一把鎖——那把鎖會強迫 re-poll 卡到 producer 寫完 result、放鎖之後才讀,順序就不影響、不會掛(單/多執行緒皆然)。 所以鐵則不是「wake 一定放最後」,而是:notify 絕不能比它所通知的狀態更早被觀察到(release-store-then-notify)。同一把鎖罩住兩者是最省事的達成方式;lock-free 就得靠 Release/Acquire 排序。

4 · 放大來看:executor 怎麼一直跑、run queue 長怎樣、reactor 是誰

上面的 stepper 是「一個 task」的特寫。拉遠一點,整個 runtime 其實是一個永不結束的迴圈在輪流服務很多 task。

run queue:大廳的候位名單(先進先出)

run queue 只放「現在就緒、可以被 poll」的 task。一個 task 回 Pending 就離場(不占位置,它的 waker 已存好等著被按);某個 waker.wake() 一按,對應 task 就被推回 queue 尾端排隊等下一輪。

run queue（先進先出 FIFO）

  front ─▶ [ task A ][ task B ][ task C ] ◀─ back
            │                              ▲
            │ pop_front → poll             │ wake() 把 task 推進尾端
            ▼                              │
   poll 回 Pending → 離場（waker 存著）────┘   ← queue 於是忽長忽短

所以 queue 會忽長忽短:一堆 task 同時 Pending 讓出時它空空的;一批事件同時到齊時它瞬間變長。

executor 怎麼「一直跑下去」:永恆迴圈

executor 不是「跑完就結束」,是清空 queue → 沒事就睡 → 被叫醒 → 再清空的無限循環:

loop {
    // 1) 把 run queue 清乾淨:有 task 就 poll
    while let Some(task) = run_queue.pop_front() {
        match task.poll(cx /* cx 帶著 task 自己的 waker */) {
            Poll::Ready(_) => { // 完成 → 丟掉這個 task }
            Poll::Pending  => { // 什麼都不做——waker 已存好,task 離場等被叫 }
        }
    }
    // 2) queue 空了 → 沒事做 → 睡,等 reactor 叫醒
    reactor.wait();   // epoll_wait / park:阻塞到某 fd 就緒或計時器到
    // wait() 內部對就緒事件做 waker.wake() → 把 task 推回 run_queue,loop 再轉一圈
}

整個程式什麼時候停?通常是頂層 task 完成(block_on 等的那個)或收到關閉信號——否則這個 loop 就一直轉,這正是「server 跑一整天」的樣子。

一個 task 怎麼「續命」跨過好幾個 .await

一個 async fn 被編譯成狀態機,每個 .await 是一個「存檔點」。poll 一次 = 從上個存檔點往前推,直到撞上下一個 .await 卡住(回 Pending)或整個 function 跑完(回 Ready)。同一個 task 因此會被 poll 很多次,每次都從上次那道菜接著吃。

餐廳版:你點的是套餐,一道一道上(前菜 .await、主菜 .await、甜點 .await)。每次櫃台叫你,你就吃到下一道、又開始等下一道;吃完甜點整桌才結束離開。狀態機記得你走到哪——所以 task「一直執行下去」其實是「被反覆喚回、每次續一小段」,它不占著一條 thread 空等。

reactor:誰替「等 IO」的 future 打電話?

stepper 裡的「廚師」是 producer 的泛稱——「把事情做完、然後按 waker」那方。它是誰,看 future 在等什麼:

  • 等別條 thread / 通道(像 oneshot):producer 就是那條 thread,做完直接 waker.wake()。就是上面 stepper 演的。
  • 等 IO(socket / fd):真正「做完」的是 kernel——但 kernel 不會幫你打電話。中間得有個 reactor 代打。

reactor = 傳菜口的叫號員 📣。它手上一張 interest table:fd → waker。IO future 在 poll 時,除了貼白板,還去 reactor 登記「fd X 好了、請按這支 waker」。reactor 一條 thread 跑 epoll_wait 睡著等 kernel;kernel 說「fd X 就緒」→ reactor 醒 → 查表 → 對 X 的 waker 打電話 → task 回 run queue。

 ┌── executor(大廳)──┐      ┌── reactor(叫號員)──┐      ┌ kernel ┐
 │ run queue + poll 迴圈│      │ epoll_wait 睡著等    │      │  網路  │
 │                     │      │ interest: fd → waker │      │  磁碟  │
 └─────────┬───────────┘      └──────────┬──────────┘      └───┬────┘
           │ poll:登記 (fd, waker) ─────▶ 存進 interest table   │
           │ 回 Pending → task 離場        │                    │
           │                              │ ◀──── fd X 就緒 ─────┘
           │   task 回 run queue ◀── wake(interest[X])  查表打電話
           ▼
      再 poll → Ready ✓
分工金句:executor 不認識 fd,reactor 不認識 task。Waker 是中間唯一的橋——executor 製造 waker、塞進 cx;future 把它同時貼白板 + 登記給 reactor;reactor 保管、在 fd 就緒時引爆它。 這也是 tokio 的骨架:executor(排程)與 reactor(mio → epoll)是兩顆獨立引擎,靠 Waker 縫起來。

5 · 逐步走一次 reactor:epoll 版的「登記 → 睡 → 就緒 → 打電話」

§4 那張圖是靜態的。這個 stepper 把 reactor 那條 epoll 迴圈逐步走一次:leaf future 怎麼登記 interest、reactor 怎麼睡在 epoll_wait、fd 就緒後怎麼查表打電話。切到壞掉版——leaf 忘了登記 interest——看事件到了卻沒人可 wake、task 永遠睡。

1 / 9
🍽️ leaf future
試 read(fd)、登記 interest、回 Pending/Ready
📣 reactor
epoll_wait 睡、查 interest table、wake
🏛️ executor
poll 迴圈 + run queue
📣 reactor(看 fd 的那顆)
fd 狀態(kernel)
interest table
🏛️ executor
run queue
executor 狀態
橋還是同一座:reactor 的 interest table 存的是 fd → waker——跟白板上那格電話是同一個 Waker。leaf 這次不只「貼白板」,還「去 reactor 掛號」:貼白板是給直接 wake 的 producer(別條 thread);掛號是給看 fd 的 reactor。忘了掛號,fd 就緒時 reactor 手上沒有你的電話 → lost wakeup。

6 · 如果今天不是 epoll?——換的是 reactor,不是 executor

上面 stepper 的 reactor 用 Linux 的 epoll。但 executor 完全不用改(還是 run queue + poll + Waker);換掉的只有 reactor 這顆——它睡在哪個 syscall、interest table 存什麼、醒來怎麼找 waker:

機制平台模型reactor 存什麼醒來做什麼
select/pollPOSIXreadiness沒有持久表——每次呼叫重傳整個 fd 集合掃全部 fd 找就緒,O(n);N 大就慢
epollLinuxreadinessinterest table fd → waker(kernel 持久保存)kernel 只回就緒的 fd,O(ready);對那些 waker wake
kqueueBSD/macOSreadinesskevent filter → waker同 epoll,API 不同
io_uringLinuxcompletionin-flight table op_id →(waker, buffer)kernel 已做完 IO,completion queue 出 (op_id, result);對那個 op 的 waker wake
IOCPWindowscompletioncompletion key →(waker, buffer)同 io_uring 概念
timer thread / spawn_blocking任意自己做完自己 wake一條 thread(睡到時間到 / 跑完阻塞工作)直接 waker.wake()——就是本頁第一個 stepper 的 producer

readiness vs completion 是最大的分水嶺:

  • readiness(epoll / kqueue / select):reactor 說「可以做了」,你被 wake 後自己去 read()。interest table 存 fd → waker。
  • completion(io_uring / IOCP):你先把「請幫我 read 進這塊 buffer」整個 op 交出去,reactor 說「做好了」時資料已經在 buffer 裡。in-flight table 存 op_id →(waker, buffer)。
為什麼需要 completion? readiness 對 regular file 永遠回報「可讀」,但真的 read() 還是會阻塞整條 thread(磁碟不是 socket)——epoll 幫不上,只能丟去 spawn_blocking 的 thread,或改用 io_uring completion。(細節見 file_io_offload / async_runtime 兩頁。)
面試場上(本 repo 的立場):CoderPad 單檔、std-only,不要手搓 epoll。把 reactor 抽象成三行 Poller trait stub(Abstract the Noise),講清楚「這裡接 mio → epoll」就好——45 分鐘手刻 FFI 是壞賭注。

7 · 三種等待、同一個骨架:channel / timer / I/O

tokio 裡「等 channel」「等 timer」「等 socket」看起來是三種東西,其實 waker 機制永遠拆成兩半:存放(waker 放哪)+ 觸發(誰知道事件發生了、由誰呼叫 wake())。三種等待的「存放」長得一模一樣——都是某塊 shared state 裡的一格 Option<Waker>(比喻裡的白板);差別全在「觸發」:事件源在哪裡。

等什麼存放:waker 放哪觸發:事件源在哪要 kernel 訂閱嗎?
channelchannel state 的 waker 格process 內——sender 本人。send() 那一刻就有現成的 code 在跑,順手 wake()不用。佇列、waker、closed flag 全是 user-space 記憶體
timertimer wheel 的 entry時間軸——driver 把「離最近 deadline 還多久」當 epoll_wait 的 timeout 參數,timer 寄生在同一個 park 點上不用(連 fd 都沒有)
I/O(fd)driver 的 ScheduledIo(§5 interest table 的那格)kernel——封包進 socket buffer 發生在 kernel,process 裡沒有任何一行 code 會自然得知要:epoll_ctl(ADD) 一次,留一個 u64 token 給 kernel
channel:
  rx.poll:  佇列空 → waker 存 channel state → Pending
  tx.send:  push → 取 waker → wake()            ← 事件源 = sender 本人(user space)

timer:
  poll:     沒到期 → waker 存 timer wheel → Pending
  driver:   epoll_wait(timeout=離最近 deadline)到點醒 → wake()   ← 事件源 = 時間軸

I/O:
  poll:     read() → WouldBlock → waker 存 ScheduledIo → Pending
  [kernel]  封包到 → fd readable                ← 事件源在 kernel
  driver:   epoll_wait 醒 → 吐回 token(u64)→ 查表 → ScheduledIo → wake()

所以「註冊 fd」不是在存 waker,是在僱 kernel 當 sender。kernel 不會說 Rust、不可能呼叫 Waker::wake;它唯一肯替你保管的是那個 u64 token,事件發生時原封不動吐回來,driver 拿 token 查表換回 ScheduledIo、翻譯成 wake()。waker 本體從頭到尾留在 user space。而且註冊只發生一次(fd 建立時);之後每次 poll 只是更新 ScheduledIo 裡的 waker,不再碰 kernel。這也解釋兩個現象:TcpStream 這類型別必須在 runtime context 裡建立(要找 driver 註冊,在外面呼叫直接 panic);tokio::sync::mpsc 的等待路徑完全不經過 runtime,丟到任何 executor 都能跑。

「channel 全 user space 就存得完,那還缺什麼?」存確實存得完;縫在「叫醒」的最後一哩。wake() 把 task 推回 run queue 仍是 user space——可是 task 要被執行,得有一條醒著的 worker thread 來拿。如果 worker 全都睡著(睡著 = blocked 在 syscall 裡),不存在任何純 user-space 手段能把一條睡在 kernel 裡的 thread 弄醒——你往記憶體寫再多東西,它不會自己睜眼。所以 runtime 自備一顆「門鈴」→ 下一節。

8 · N 條 worker 在幹嘛:driver 是床位,不是職務

§4 的永恆迴圈是單 thread 版。tokio 的 multi-thread runtime 是 N 條完全相同的迴圈——worker 對稱、無分工,沒有「專職聽 epoll 的 thread」。driver(epoll + timer wheel)是一件搶著用的資源,誰先閒下來誰值班:

loop {
    tick += 1;
    if tick % 61 == 0 { 搶得到 driver 就 poll(timeout=0) }   // 忙碌時也順路收一次 I/O
    task = local.pop()            // 自己的佇列
        或 inject.pop()           // 全域佇列(runtime 外 spawn 丟進來的)
        或 steal(隨機兄弟)        // work stealing:偷走對方一半
    if task { run(task); continue; }
    // 真的沒事 → 睡。睡哪張床,看搶不搶得到 driver:
    if 搶到 driver { epoll_wait(timeout = 最近的 timer deadline) }  // 床A:聽 kernel + 門鈴
    else           { condvar.wait() }                                // 床B:futex,只聽門鈴
}

futex 是什麼

futex(fast userspace mutex)是 Linux 給「thread 想睡 / 想叫醒別人」的最底層一對 syscall:futex_wait(addr, expected) =「如果 *addr 的值還是 expected,就讓我睡在這個位址上」;futex_wake(addr, n) =「叫醒睡在這個位址上的至多 n 條 thread」。Mutex、Condvar、thread::park/unpark 全蓋在它上面:平常用 user-space atomic 搶,搶得到就 0 syscall;真的要睡才進 kernel 付錢。

expected 參數就是 §3 那道縫的 kernel 版。kernel 讓你睡之前會原子地再檢查一次 *addr == expected——若對方在你「檢查完、還沒睡著」的空隙裡改了值並 futex_wake,這次 wait 立刻返回、不睡。跟 wake-before-park 要靠 token(狀態)而不是 notify(事件),是同一題。

它的真面目是一個 6 參數 raw syscall(glibc 長年連 wrapper 都不給,要 syscall(SYS_futex, …) 自己呼):

futex(uint32_t *uaddr,   // addr:一顆 u32 的「位址」——kernel 拿它當等待佇列的 key
      int       op,      // FUTEX_WAIT / FUTEX_WAKE / …
      uint32_t  val,     // WAIT:expected;WAKE:最多叫醒幾條
      timeout, uaddr2, val3);  // 進階用途,平常用不到

FUTEX_WAIT:  原子檢查 *uaddr == val ? 睡 : 立刻回 EAGAIN
FUTEX_WAKE:  叫醒睡在 uaddr 上的至多 val 條,回傳實際叫醒數

兩個常被誤會的點:kernel 端沒有「futex 物件」——不用建立、不用註冊、沒有 fd;等待佇列拿記憶體位址(雜湊)當 key,沒人睡著時什麼都不存在。對比 §7:fd 事件要 epoll_ctl 註冊,因為等的人不是事件源;futex 不用註冊,因為睡的人自己就是要被叫醒的人。另外 futex_wait 會假醒(訊號/EAGAIN),所以外面永遠包一個 loop 重查狀態——「wakeup 是提示不是保證」到 kernel 這層仍然成立。

addr / expected 要自己管嗎?不用——除非你就是在寫 runtime。三層樓: 
你寫的:    Mutex / Condvar / thread::park        ← 面試寫 code 的樓層
std 內部:   AtomicU32 狀態機 + futex_wait/wake    ← 面試「用講的」樓層
kernel:     以位址為 key 的等待佇列               ← 知道它無狀態即可
addr 就是 std 結構裡那顆 AtomicU32 的位址、expected 就是「剛讀到、據以決定要睡的那個值」——都是 std 替你管的(Rust 1.62 起,Linux 上的 Mutex/Condvar 直接建在 futex 上,不再繞 pthread)。std Mutex 的狀態字:0=沒鎖、1=鎖著、2=鎖著且有人等,lock 搶輸就 futex_wait(&state, 2);parker 的 EMPTY/NOTIFIED/PARKED 是同一顆 u32。你用 thread::park/unpark 寫 mini executor,就已經站在正確的樓層。
“On Linux, Mutex, Condvar and park are all built on futex: the fast path is a single userspace CAS — zero syscalls; only contention pays futex_wait plus a context switch. And futex_wait takes an expected value the kernel atomically re-checks before sleeping — that's the lost-wakeup guard at the kernel boundary.” 面試定位:不寫 code、不背 6 個參數。兩個時機講——cost model(無競爭 vs 有競爭差 100× 的來源)與 lost wakeup(expected = kernel 版的 park token)。
一顆 futex 可以睡很多條 thread 嗎?可以——kernel 對每個位址維護一條等待佇列,睡幾條都行;futex_wake(addr, n) 的 n 就是「叫幾條」:n=1 是 notify_one、n=INT_MAX 是 notify_all(另有 FUTEX_REQUEUE:notify_all 的防驚群版——叫醒 1 條,其餘直接搬去 mutex 的佇列排隊,不白醒)。但 tokio 的床B 不是全員睡同一顆:每條 worker 有自己的 parker(自己的狀態字),runtime 另外維護一份 idle 名單記錄誰在睡;要叫人時從名單點名一條特定的 worker unpark。「一次叫一個」是靠名單點名,不是靠共享佇列碰運氣——下面的「接力」才能精準指定下一棒。
寫 runtime 要自己管 futex 嗎?連 tokio 都不碰。tokio 的 parker 是用 Mutex+Condvar+AtomicUsize 拼的三態,站在 std 層——硬理由是可攜性(futex 是 Linux-only,raw futex 得每個 OS 寫一套 backend)與 loom 可測性(loom 模擬 Mutex/Condvar/atomic,不模擬 raw syscall)。真的往下鑽的只有:寫 std 的、寫 parking_lot 的(要 1-byte lock + 自管等待佇列)、寫語言 runtime 繞過 libc 的(Go)。你寫 mini runtime 用 thread::park/unpark 就是正確樓層;C++20 那邊的對應物是 std::atomic<T>::wait/notify_one——可攜版的 futex,連 wait(expected) 語意都一樣。一句收束:futex 之於 runtime 作者,像 epoll 之於 45 分鐘面試——知道底下是它,但正確的動作是站在上一層抽象。

兩張床、一顆門鈴

叫醒一條睡進 kernel 的 thread,必然付一次 syscall。門鈴對應兩張床:睡床A 的聽 eventfd(runtime 啟動時就註冊進同一個 epoll——對它而言 epoll 只是「可以被打斷的睡覺地點」,不是資料來源);睡床B 的聽 futex_wake。門鈴是 per-runtime 一顆,不是 per-channel;只在「真的有人睡著」時才響:

send() → push → 取 waker → wake() → task 進 run queue    (全 user space)
  → 需要叫醒睡著的 worker 嗎?
      ├─ 否 → 結束。0 syscall(這就是 channel 快的原因)
      └─ 是 → write(eventfd) 叫床A / futex_wake 叫床B     (1 syscall)
              → thread 醒 → 撿 run queue

逐步走兩個情境:值班者被 kernel 叫醒(I/O),與全員睡著時 sender 按門鈴(channel)。

防驚群 + 飢餓上界:叫人永遠一次叫一個(notify_one + 接力):被叫醒的 worker 進「找活」狀態,真偷到活才接力叫下一個——負載低時一條醒著就夠,事件雪崩時喚醒鏈自己展開。鏡像問題「全員忙碌、沒人睡床A,I/O 誰聽?」——迴圈第二行:每 61 tick,忙碌 worker 也拿 timeout=0 順路 poll 一次 driver,所以 I/O 延遲有上界,不需要專職者。

wake 的落點:丟給「按鈴的人」,不是丟回「原主」

wake() 把 task 推回 run queue——推回哪個 queue?tokio 不記 task↔worker 的 affinity(上次在哪條 worker 跑過,沒人記得);規則看的是 wake() 這行 code 此刻跑在哪條 thread 上:

wake() 發生在哪?
├─ runtime 的 worker thread 上(例:worker 跑的 task 裡呼叫 tx.send())
│     → 丟「自己」的 LIFO slot                // 下一個就跑它
│        LIFO 已被佔 → 丟自己的 local queue
│        local 滿(256)→ 溢一半到 global inject
└─ runtime 外的 thread(std thread 呼叫 send、外部 spawn)
      → 沒有 local 可用 → global inject queue,需要才按門鈴

為什麼不「丟回原本跑它的 worker」?三層理由:(1)資料結構不允許——local queue 是單生產者 ring,只有主人能 push、別人只能從頭偷;允許遠端 push 等於把整個 runtime 最熱的路徑加上同步成本。(2)cache 論證其實是反的——原主的 cache 早冷了(它 Pending 之後那條 worker 跑過一堆別的 task);此刻真正熱的是 sender 剛摸過的那則 message,所以「丟給按鈴的人自己」是最優解:send → wake → receiver 緊接著同一條 thread 跑,訊息還在 L1。這就是 LIFO slot 存在的理由(message-passing 最佳化)。(3)落點錯了也沒關係——work stealing 自動修正,affinity 不值得花記憶體去記。

LIFO slot 的防餓閥:兩個 task 互相 send/wake 會無限霸佔 LIFO(ping-pong);所以連續走 LIFO 吃 coop budget,超了就降回一般佇列——最佳化不能餓死別人。一句話收束:task 落在「按 wake 的 thread」附近——cache 熱度跟著「現在誰摸著資料」走,不跟著 task 的過去走。上面情境1 driver-holder 醒來就近跑 task,是同一條規則的 I/O 版。
為什麼不乾脆開一條專職 reactor thread?合體設計有個實質紅利:聽到事件的那條 thread 醒來時,被喚醒的 task 就近落在它自己的 queue——cache 還是熱的、直接跑;專職 reactor 則每個事件都得把 task 丟過牆(跨 thread handoff)一次。 你的 mini block_on 是這套結構的最小版:單 task 單 thread,「門鈴」就是 park token,unpark 底層就是 futex_wake。EMPTY/NOTIFIED/PARKED 三態、task 的 NOTIFIED 位元、eventfd 的 counter——同一題,三個尺度。

9 · st.waker 的三態:none → stored → taken

你在 legend 看到的 none / stored / taken,講的就是白板上那格電話 Option<Waker> 一生的三個狀態:

none
白板上沒電話。還沒被 poll,或剛被廚師撕走。
st.waker = None
→
stored
future 這次沒等到 → 貼上「這次的電話」,回 Pending 讓出座位。
st.waker = Some(cx.waker().clone())
→
taken → wake
廚師把電話撕下來、打了。白板那格又空了。
st.waker.take() // 然後 w.wake()
為什麼 .take() 不是 .clone()? 這通電話打一次就夠了;take() 把 Some(waker) 拿走、順手把白板換回 None,剛好清空。

10 · 為什麼「每次 poll 都要覆蓋」電話

存電話那行 st.waker = Some(cx.waker().clone()) 是覆蓋,不是「只存第一次」。

同一位客人可能換了座位、甚至換人來取餐(同一個 future 可能被不同 task poll,或被 combinator 用 proxy waker 包起來,waker 會變)。白板還貼著舊電話,廚師照舊號碼打——打給一個已經不在的人,你就永遠醒不過來(lost wakeup)。

所以規矩:每次回 Pending 前都把電話重寫成「這一次」的 cx.waker(),保證白板上永遠是打得通的最新號碼。(在單執行緒 block_on 裡 waker 每次都一樣,bug 不會顯現;但那是巧合,契約是為通用 executor 存在的——面試寫「只存第一次」會被追問這點。)

11 · 一句話帶走

A Waker is a type-erased callback that says “re-schedule this task.” A pending leaf clones cx.waker() into shared state; the producer publishes its result first, then takes the waker and calls wake(). Reverse that order and a single poll can observe the stale state, re-park, and the already-consumed wakeup is lost forever. 先發佈狀態、再通知(release-store-then-notify);反過來就是經典的 lost wakeup。
