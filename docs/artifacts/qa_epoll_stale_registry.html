qa 圖解 · epoll internals · e2 fd_registry 的 why

epoll 內部與 stale fd:events 卷、generation 證件、雙 waker

訂閱面(epoll_ctl 的招式)見 qa_epoll_subscribe.html;這頁講身份面:kernel 裡到底是哪三個資料結構在動、epoll_wait 交到你手上的「卷子」是什麼語意、為什麼 close 得再快也擋不住 stale fd 事件、generation 證件怎麼用 4 bytes 把它變成 O(1) 拒收——最後接到 tokio 真實的 per-fd 雙 waker 設計。這條鏈就是彩排 e2(fd_registry)必脫口的完整故事。

0 · kernel 三結構:誰有 log、誰 O(1)、誰線性

interest set(常駐)

紅黑樹
「我在關注誰」。epoll_ctl ADD/MOD/DEL 走這裡,每條連線的生命週期只付幾次。
O(log N_watched)

ready list(kernel 內)

雙向鏈結串列
封包到達 → socket 的 wait-queue callback 把 epitem append 上來。事件發生的當下就記好帳。
O(1) / 事件

events 卷(你的)

你 malloc 的陣列
epoll_wait 把 ready list 抄進來,回傳「填了幾格」。每次呼叫整卷重填。
O(min(ready, maxevents))

注意 ready 路徑上連排序都不存在——epoll 對就緒事件不承諾任何順序,所以鏈結串列(O(1) append)就是下限。對照 timer queue:它的 API 問題是「誰最早」,這才逼出 min-heap 的 O(log n)。一句收束:資料結構跟著 API 要回答的問題走——要順序,付 log;不要順序,付 O(1)。

“epoll is fast because it never searches: the cost was paid when the event arrived — the callback appended it to a ready list — so epoll_wait just collects.” 「不是找得快,是根本不找」的英文版。

1 · events 卷的語意:答案卷,不是名冊

常見誤解是把它想成「註冊時往後推的清單」。不是——註冊進的是 kernel 的 interest set;events 陣列是你自己準備的空白答案卷,每次呼叫遞給 kernel 當場填:

let mut events = vec![epoll_event::default(); 1024]; // 空白卷,1024 格
loop {
    let n = epoll_wait(epfd, events.as_mut_ptr(), 1024, timeout);
    //  ^ 回傳值就是 n:「這次幫你填了幾格」——kernel 說的
    for ev in &events[..n] {          // 只有前 n 格有效!
        // 第 n 格之後 = 上次呼叫的垃圾,不歸零、不可讀
    }
}
  • 回傳 0 = timeout 到了沒人 ready(timer queue 靠這條接手)。
  • ready 的比卷子大(2000 條 ready、卷只有 1024 格)→ 這批填滿,剩的留在 kernel ready list,下次再給,不會丟。maxevents 是批次大小,不是上限承諾。

2 · bitmask 三旗標:是 AND,不是掃描

每格 entry 的 events 欄是一個 u32,旗標是同一個 socket 的獨立事實,可以同時亮(進來了資料 + 送出 buffer 有空位 = EPOLLIN|EPOLLOUT 一起亮)。檢查是每旗標一條 AND 指令——沒有任何「從頭掃 bit」存在:

for ev in &events[..n] {                     // O(ready) 走訪
    if ev.events & (EPOLLHUP | EPOLLERR) != 0 { /* 先處理死亡 */ }
    if ev.events & EPOLLIN  != 0 { /* 可讀:read 不會卡 → 餵 framer */ }
    if ev.events & EPOLLOUT != 0 { /* 可寫:write 不會卡 → flush 待送 */ }
}

慣例順序 HUP/ERR → IN → OUT:先確認人還活著,再收貨,再出貨。

3 · data 是證件欄:entry 上根本沒有 fd

註冊時交出去的是「fd(當 key)+ 一個小結構(當值)」,而那個結構的 data 欄(u64 union)kernel 從頭到尾不看、不解釋,只在每次事件時原樣奉還:

struct epoll_event {
    uint32_t     events;  // 註冊時 = 興趣遮罩;回來時 = ready 遮罩
    epoll_data_t data;    // union { void*; int fd; uint32_t; uint64_t }——你的 cookie
};

而多數人漏掉的重點:epoll_wait 回來的 entry 裡沒有 fd 欄位。你收到的只有 events + data——想知道「這是誰」,唯一管道就是你當初塞進 data 的東西。塞裸 fd(data.fd)是 union 給你的偷懶選項;塞 (index, generation) 是 e2 的正解,差別就是下面 stepper 的兩條分支:

// 組證件:generation 高 32、slot index 低 32(先升寬再移!u32 << 32 是 UB 級錯誤)
let token: u64 = (generation as u64) << 32 | (index as u64);
// 拆證件:0xFFFF_FFFF = 32 個 1 的遮罩(跟 1 AND = 保留、跟 0 AND = 清除)
let index      = (ev.u64 &  0xFFFF_FFFF) as u32;
let generation = (ev.u64 >> 32) as u32;
// 驗證件:不合 = stale,O(1) 丟棄
if slots[index].generation != generation { continue; }

4 · 互動:stale fd 事件的一生——裸 fd vs generation

fd 是 OS 會回收重發的「名字」(POSIX 保證發最小可用號碼——你剛 close 的 5,正是下一個 accept 必然拿到的 5)。切換兩種 cookie,逐步走一次「同一批卷子裡 close + 重發」,看舊事件怎麼跳出來:

kernel

ready: [fd9, fd5]
fd5 = 舊連線 A 的資料到了

你的 events 卷

卷[0] fd9 · 控制連線
卷[1] fd5 · EPOLLIN
 

registry slot 5

A 的連線狀態
generation = 7

關鍵不對稱:kernel 保證「close 之後不再產生新的舊事件」(epitem 連同 ready list 上的殘留一起蒸發),但收不回已經抄到你手上的卷子。所以防禦必須放在 dispatch 查表那一刻,不能指望 close 得夠快。

5 · 三條時間線 + 一個殭屍

close 的時候,舊事件在哪?會跳出來嗎為什麼
已抄進你 userspace 的卷(同一批)會——唯一的跳出點快照已離開 kernel,收不回
還躺在 kernel ready list不會close 銷毀 epitem 時連 ready list 上的一起拔掉
根本還沒 ready不會事件從未存在;新連線的事件是自己的、帶新證件
殭屍案:fd 被 dup() 過 / 傳給過子行程持續跳close 你的號碼不銷毀底層 description,epitem 不死——generation 是唯一防線;best practice:先 EPOLL_CTL_DEL 再 close

「同一批」聽起來罕見?三個放大器把它變例行公事:① 跨連線 close(timeout 收割器、gateway 關 backend 腿、聊天室踢人——某人的 handler 會關別人的 fd);② 最小號碼分配在幫倒忙(重發同號是保證,不是巧合);③ 多執行緒 + 高 churn(視窗擴到任意時刻;低機率 × 每秒幾千次 × 跑好幾天 = 必然)。而踩中的代價不是 crash,是 A 使用者的資料進了 B 使用者的連線——無聲資料錯亂,資安事故等級;保費是每 slot 4 bytes + 一次整數比較。沒有不買的選項。

6 · registry 的帳:O(max_fd) 為什麼是划算的

結構lookupstale 防禦記憶體
HashMap<fd, T>hash + probe(常數大、cache 差)沒解O(live)
Vec<Option<T>> by fd一次 array load沒解O(max_fd)
世代 slot map(e2)一次 array load + 一次比較O(1) 拒收O(max_fd) + 4B/slot
  • O(max_fd) 的入場券是 fd 的密集性:POSIX 永遠發最小可用號碼 → max_fd ≈ 尖峰同時連線數,不會稀疏爆炸。key 若是隨機 u64(session id),這招就死,只能回 HashMap——面試講出這個對比是加分題。
  • 「stale 防禦沒解」跟查找結構無關——那不是 lookup 問題,是 token 身份設計問題;mutex 也救不了(鎖擋「同時」,擋不住「時間」)。
  • generation 用 u32:單一 slot 要重用 2³² 次才繞回——以連線壽命計是幾十年,wrap-around 可接受。

7 · 再上一層:reactor 的 per-fd 雙 waker

裸 event loop(hw_bridge 的 server_evented)查到表就當場幹活,沒有 waker。放上 async runtime 後,迴圈的工作從「做事」變成「叫醒要做事的 task」,而標準設計是每個 fd 兩個槽:

interest table entry(per fd):
    reader_waker: Option<Waker>   // poll_read 回 Pending 時存入
    writer_waker: Option<Waker>   // poll_write 回 Pending 時存入
// EPOLLIN → wake(reader);EPOLLOUT → wake(writer);HUP/ERR → 兩個都叫

為什麼兩槽:等讀的和等寫的常是不同 task(TcpStream::split() 讀半寫半分家)。叫錯人 = 白醒(spurious,無害——poll 會再檢查);漏叫人 = lost wakeup,task 永眠。不對稱決定設計:寧可多叫、槽要分開——跟 condvar 的「先發佈狀態再 notify」是同一條定律。

收尾彩蛋:tokio 真實的這張表叫 ScheduledIo(tokio/src/runtime/io/scheduled_io.rs)——readiness 原子位 + reader/writer 兩個 waker 槽 + 一條 intrusive wait list;而它的 mio token 正是「slab 位址 + generation」打包,驗證失敗就丟。你在 e2 手搓的,就是 tokio IO driver 心臟的教學版。

8 · 面試句庫

“The events array is an answer sheet, not a roster — epoll_wait's return value tells me how many entries the kernel filled, and everything past that is last call's garbage.” events 卷語意一句話。
“A lock protects against concurrent access; generations protect against temporal confusion — the fd is a name the OS recycles, so the token must carry proof of which incarnation it refers to.” mutex 為什麼救不了 stale。
“Stale events are rare per event but guaranteed at scale, and the failure mode is silent cross-connection data corruption — so the 4-byte generation is non-negotiable: one array load plus one compare, O(1) worst-case.” e2 的完整電梯句:機率 × 代價 × 保費。
