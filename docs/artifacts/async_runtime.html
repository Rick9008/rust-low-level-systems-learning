async_runtime — 誰該跑、誰該醒、誰做 IO

executor 管「誰該跑」,reactor / proactor 管「誰該醒」;兩邊唯一的信物是 Waker。這頁把 executor、event_loop、 file_io_offload 三個模組接成一張圖,並補上 repo 沒有實作的 第四塊:completion model(io_uring)。

1. 那一圈:poll → Pending → wake → 再 poll

executor 不認識 fd,reactor 不認識 task。Waker 由 executor 製造、 葉子 future 搬運、reactor 引爆。按「下一步」走完一圈;然後切到壞掉版, 看葉子 future 忘記登記 waker 會發生什麼。

executor run queue: [task]
leaf future 等著被 poll
reactor interest table: {}
  1. 按「下一步」開始。
lost wakeup 事件到了,但 interest table 是空的——沒有 waker 可引爆。executor 繼續睡, task 永遠 Pending。這和 executor 模組裡 「park 沒有 token」的死法是同一族:喚醒沒有掛到人身上,就等於沒發生。

repo 對映:executor 的 block_on 就是左邊那格 (park/unpark 的 token 語意保證「wake 先於 park」不丟); event_loop 是右邊那格的 callback 版——把 callback 換成 waker 表, 它就是 runtime 裡的 reactor。

2. 成本模型:不是每個 future 一條 thread

async fn 疊一百層還是一個 task、一次 poll;需要 wake 來源的只有 最底下真正卡住的葉子等待點。真正的問題是:這一類葉子, 有沒有「一個東西等全部」的原語?拉桿看三種模型的 thread 數怎麼長。

並發連線/等待數 10
thread-per-connection 10 std 沒有多路等 socket 的原語,一個 blocking read 佔一條 thread。 面試規模無妨;規模上去 stack + context switch 吃掉你。
thread-as-reactor(timer 類) 1 BinaryHeap<(deadline, Waker)> + Condvar::wait_timeout:一條 thread 服務所有 Delay。純 std、45 分鐘寫得出來的真 reactor。
epoll reactor(socket 類) 1 一條 thread 等 N 個 fd、O(ready) 通知。 epoll 買的是把左邊那格壓成 O(1)——效率條件,不是 async 的存在條件。

注意拉桿只影響左邊那格。而且不管葉子上面疊幾層 async fn、 join!、select!,三格數字都不動——組合 future 是狀態機,不是 thread。

3. Reactor vs Proactor:「可以做了」vs「做好了」

readiness(epoll):通知你 fd 可以讀了,IO 你自己做,buffer 從沒離開你手上。 completion(io_uring / IOCP):你先把 buffer 交出去,kernel 做完再通知你。 兩邊同步走一遍;走到一半按「drop future(取消)」,看差異在哪裡爆開。

readiness 葉子(epoll)

buffer:在你手上
  1. poll:試 read(fd) → WouldBlock
  2. 登記 interest(fd, waker) → Pending
  3. fd ready → waker.wake()
  4. 再 poll:這次自己 read → Ready(n)
cancel = drop,安全 buffer 從來沒交出去;反登記 interest 即可,頂多一次假醒。 Rust 的 cancel-by-drop 就是為這個模型生的。

completion 葉子(io_uring)

buffer:在你手上
  1. poll:組 op,把 buffer 所有權交給 kernel
  2. op 進 submission queue,submit → Pending
  3. kernel 做完 IO → completion queue 出現 (id, result) → waker.wake()
  4. 再 poll:拿回 (result, buffer) → Ready(n)
cancel ≠ drop op 還在 kernel 手上,buffer 收不回來——直接 drop 並回收 buffer 就是 use-after-free。解法:owned buffer 進出(tokio-uring), 或 cancel 本身也是一個要等完成的 op。

executor 兩邊完全同一顆:還是 run queue + poll + Waker。變的是葉子的合約, 以及「誰該醒」那張表存什麼(interest table vs in-flight op table)。

4. 兩種「誰該醒」的迴圈,並排看

reactor(readiness)proactor(completion)
表存什麼fd → 誰想被叫醒op id → 誰在等 + 它的 buffer
syscall 節奏每個 ready fd 醒來後各補一次 readsubmit 一批、收割一批,syscall 數與操作數脫鉤
regular file無效——永遠 ready(file_io_offload 的主題)有效——真 async file IO
取消drop 即可,頂多假醒要 owned buffer 或 cancel op

順帶對齊:tokio 今天 = executor(work-stealing)+ readiness reactor(mio → epoll); io_uring 生態(tokio-uring、glommio、monoio)是 completion driver,多半改走 thread-per-core——buffer 綁在 op 上之後,task 亂跑核心的代價變高。 executor 的合約不變,但最優策略被 IO 模型牽動。
