同一條 ring,五種睡法

SPSC ring 本身不帶通知——「沒貨時誰睡、誰叫醒」是一個獨立插槽。 這頁做三件事:比較五種睡法(含「沒有 epoll 是不是只能 sleep」的答案)、 把掛牌握手拆到指令層(真 code、x86 對照表、靜態 timeline、 互動 stepper、三題 FAQ),以及多源扇入為什麼是 per-source SPSC 不是 MPSC。

① 等待策略階梯——「按事件醒」vs「按時間醒」

先分兩種睡:按事件醒 = kernel 幫你睡,事情發生時提早叫醒 (blocking read、condvar、park、epoll);按時間醒 = sleep,時間到才醒,事件來了也叫不動你。 沒有 epoll ≠ 用 sleep:sleep 只在「多路 × 無多路原語 × 不開多 thread」三個條件 同時成立時出場,而且它買的是「別燒死 CPU」,不是「等到事件」。

①-2 喚醒鏈的終點站——五種睡法殊途同歸(2026-07-26 補)

你睡在 condvar 上,producer 的 notify_one 叫醒你——但 notify 只是中繼: 它自己是個 syscall,得有一個「已經醒著的人」來呼叫它。睡在 epoll 上也一樣, epoll_wait 本身在睡,誰叫醒 epoll?把「誰叫醒我的叫醒者」一路追到底, 總得有一棒在沒有任何軟體醒著時,無中生有製造喚醒——那一棒是矽做的:

硬體 —— 無中生有的第一棒
封包到網卡 / sensor 出資料沒有任何 CPU 指令參與
↓
DMA 把資料落進記憶體仍然不打擾 CPU
↓
⚡ IRQ:拉中斷線,CPU 被硬體強制跳進 ISR喚醒在這裡誕生——不需要誰醒著
kernel —— 接力
ISR → driver 收包,標記 fd ready
↓
走 wait queue:把睡在 epoll / futex 上的執行緒搬回 run queue
↓
scheduler 派 CPU 給它
userspace —— 接力
epoll_wait / futex 返回,event loop 醒來
↓
它再 notify_one / unpark 傳下一棒
↓
aggregator 醒來收貨

一句記走:軟體只能接力喚醒,無中生有的喚醒只有硬體中斷。 連「按時間醒」的 sleep 終點也是它——timer tick 就是一顆 IRQ。 五種睡法只是睡在不同的中繼站,終點站全部同一個。 唯一不在這條鏈上的是 busy-poll:不睡的人不需要被叫醒——HFT 燒一顆核, 買斷的正是整條接力鏈的延遲與變異。

② 掛牌握手:從真 code 到指令層

spin 額度用完後,consumer 想睡。producer 每筆 unpark = 每筆一次 syscall, 所以改成:consumer 掛牌才睡、producer 看到牌才 unpark。 問題出在:兩邊都是「先寫自己的變數,再讀對方的變數」——這個形狀 叫 store-buffering(SB),是教科書 litmus,x86 上真的會發生。

②-1 真 code:兩個半邊,各四步

CONSUMER — idle_park()(reference/src/concurrency/signal_pipeline.rs;server_evented_spsc.rs 同款)

fn idle_park(jobs: &mut Consumer<Job>,
             parked: &AtomicBool,
             stop: &AtomicBool) -> Option<Job> {
    parked.store(true, SeqCst);     // ❶ 掛牌:「我要睡了」
    fence(SeqCst);                  // ❷ 柵欄:牌先出門,才准讀
    if let Some(j) = jobs.pop() {   // ❸ re-check:最後看一眼佇列
        parked.store(false, Release);
        return Some(j);             //    有貨 → 摘牌,不睡
    }
    if !stop.load(Acquire) {
        thread::park();             // ❹ 真的空 → 睡
    }
    parked.store(false, Release);
    None
}

PRODUCER — push 之後

job_tx.push(job);          // ❶ 貨進 ring(內部 Release store)
fence(SeqCst);             // ❷ 柵欄:貨先出門,才准看牌
if parked.load(Relaxed) {  // ❸ 看牌(Relaxed 就夠,秩序柵欄扛)
    worker.unpark();       // ❹ 有牌才付 syscall
}
// ❸ 同時就是合併通知:醒著就不叫,
//    一次 unpark 攤掉整段忙碌期的所有 push。

兩邊的形狀一模一樣:寫自己 → 柵欄 → 讀對方。 consumer 寫牌讀佇列;producer 寫佇列讀牌。柵欄就插在「寫」與「讀」中間。

②-2 store buffer:為什麼「寫了」不等於「別人看得到」

每顆核寫出去的值,會先停在自己私有的 store buffer 排隊, 晚一點才進共享記憶體;但自己後面的 load 不用排隊,可以先跑。 於是「我先寫、再讀」在別人眼裡可能變成「先讀、後寫」——這就是 StoreLoad 重排,x86-TSO 唯一允許的重排。 Release/Acquire 管不到它:Release 只保證「我之前的寫跟著這筆寫一起可見」, 對「我後面的讀」一個字都沒說。

Rust 寫法x86 編譯結果會不會沖 store buffer
load(Relaxed)mov不會
load(SeqCst)mov(一模一樣)不會——標籤不是魔法
store(Release)mov不會,進 buffer 排隊
store(SeqCst)xchg會(寫+沖)
fence(SeqCst)mfence會,且前後讀寫不許穿越

這張表就是「為什麼把 load 換成 SeqCst 沒用」的硬體版答案: 它編譯出來還是同一條 mov,你 buffer 裡沒出門的 push 它一個都沖不動。

②-3 靜態 timeline:沒有柵欄的那次睡死(全景圖)

      CONSUMER(core 0)                     PRODUCER(core 1)
 t1   parked ← true ──進自己的 store buffer
 t2                                          push(x) ──進自己的 store buffer
 t3   ❸ pop():讀共享記憶體的 ring
      → 讀到舊值「空」(x 還悶在對面 buffer)
 t4                                          ❸ load parked:讀共享記憶體
                                             → 讀到舊值 false(牌還悶在對面 buffer)
 t5   ❹ park() ──睡
 t6   (此刻兩邊 buffer 才 flush:x 和牌都到了共享記憶體——太遲,沒人會再看)
      → x 卡在 ring;consumer 睡死;producer 以為沒人在睡,走人。

注意 t3、t4:兩筆 load 都沒有錯,它們忠實讀了共享記憶體—— 錯的是兩筆 store 都還沒到貨。柵欄修的就是這個:插在 ❶ 和 ❸ 之間, 強制「我的 store 先出門,才准做我的 load」。

②-4 為什麼「兩邊都插柵欄」就不可能互相錯過

單看一邊,柵欄只是對自己的規定,不保證對方讀到你的新值。 它消滅的是一種組合。把四種結局攤開:

consumer 看到貨?producer 看到牌?結局
看到—❸ 收貨摘牌,不睡 ✅
—看到unpark,睡了也被叫醒 ✅
看到看到多叫一聲,無害(park permit 收下)✅
沒看到沒看到睡死 💀 ——唯一致命,也是唯一被柵欄禁止的

禁止的理由只有一條規則:所有 SeqCst 柵欄排在全機器同一條時間線上,必有先後。 若 consumer 的柵欄在前:掛牌發生在它的柵欄之前,producer 的看牌在自己的柵欄之後 → 也就在 consumer 的柵欄之後 → producer 保證看到牌。 反過來,若 producer 的柵欄在前 → consumer 保證看到貨。 誰先誰後不用知道——兩種排法裡都至少一邊看見,「雙盲」在邏輯上不存在, 不是機率上很少。

②-5 六題 FAQ(2026-07-22 實際問過的)

Q1:把 parked.load(Relaxed) 換成 load(SeqCst) 不就好了?

不行,兩層理由。模型層:SeqCst 的全序只收「掛了 SeqCst 標籤的操作」。 push 內部的 store 是 Release,不在全序裡——全序只能說「這筆 load 排在其他 SeqCst 操作的哪」,對「我的 push 出門了沒」隻字未提。

硬體層:x86 上 load(SeqCst) 編譯成普通 mov(見 ②-2 的表), 它不沖 store buffer——故障劇本一步都不會變。

要用純標籤修,得把四筆操作全部掛 SeqCst,包括 ring 內部的 store/load:①那些 ordering 在 Producer/Consumer 實作裡,外面改不到; ②就算改得到,從此每次 push/pop 都付錢,而你只有睡與叫這一瞬需要。 柵欄是外科手術:只在握手點插一刀。

Q2:fence 是「強制把我的值推給對方」嗎?

不是。柵欄管的是自己:「我的 store 先對全世界可見, 才准執行我後面的 load」。對方什麼時候讀到你的值,單邊看仍然沒有保證。

魔法在組合:兩邊都守這條規定 + 柵欄有全機器的先後(②-4), 「兩邊同時讀到舊值」就變成邏輯上不可能。它禁止的是一種結局, 不是加速一筆傳輸。

Q3:condvar 版(thread pool)為什麼不用 fence?

因為 mutex 就是那道秩序。condvar 的規矩:改共享條件 (哪怕它是 atomic)要在 waiter 的同一把 mutex 底下做, 而 wait 放鎖與入睡是原子的一步。於是只有兩種排法: 通知方先拿到鎖 → waiter 之後檢查必看到新條件,不睡; waiter 正拿著鎖檢查 → 通知方被擋在門外,等 waiter 真的睡著才進得來 → notify 必然叫得醒人。「決定睡了但還沒睡著」的窗,通知方進不去。

park 版沒有 mutex,SeqCst 柵欄就是它的替代品。同一個病(lost wakeup), 兩帖藥:鎖序,或柵欄全序。

Q4:摘牌的 parked.store(false, Release) 為什麼不是 Relaxed?

老實說:這裡換成 Relaxed 也不會睡死。危險是不對稱的: 「掛牌(true)沒被看見」= producer 不叫 = 睡死,安全攸關; 「摘牌(false)沒被看見/晚到」= producer 多叫一聲 unpark = permit 被吸收, 下一次 park 直接穿過再重走 re-check,只是效能攸關。 所以 SeqCst+柵欄只出現在 true 那一側。

那為什麼還寫 Release?買兩件事:①把「收完貨才摘牌」的順序寫進程式碼, 讀的人不用重推理;②x86 上 Release store 本來就編譯成普通 mov (見 ②-2 的表)——既然免費,就把意圖寫清楚。

面試層級的一句:「true 側攸關 liveness,所以 SeqCst;false 側最多多一次 spurious unpark,Release 是紀律不是必要。」講得出方向的不對稱,比背標籤值錢。

Q5:fence 針對的對象到底是誰?fence(Acquire/Release) 和 fence(SeqCst) 差在哪?

對象:你自己這條執行緒、柵欄前後的「所有」記憶體操作——不綁定 任何變數;SeqCst 柵欄額外參加全機柵欄全序(②-4 靠的就是這個)。

三種柵欄各擋哪些重排(四種重排:Load→Load、Load→Store、Store→Store、Store→Load):

重排方向fence(Acquire)fence(Release)fence(SeqCst)
Load→Load / Load→Store(讀側)擋—擋
Store→Store / Load→Store(寫側)—擋擋
Store→Load(SB 的元凶)——只有它擋

把「重排」具象化:程式序 A 在前、B 在後,重排 = B 超車到 A 前面。A、B 各可能是 Load 或 Store,恰好四種:

① Load→Load ② Load→Store ③ Store→Store ④ Store→Load(SB 元凶)

兩種 fence 是兩張單向牆,各自只認一種錨點(直欄=程式順序,由上而下):

fence(Acquire)|錨點=牆【上方】的 load(讀側)
load X← 被釘住的錨
══════ fence(Acquire) ══════
load Y↑✗ 不許爬上去
store Z↑✗ 不許爬上去
「我上方 load 之後的事,都留在後面」→ 擋 ①②(凡【前者是 Load】的超車)
fence(Release)|錨點=牆【下方】的 store(寫側)
load Y↓✗ 不許沉下去
store Z↓✗ 不許沉下去
══════ fence(Release) ══════
store X← 被釘住的錨
「我下方 store 之前的事,都先做完」→ 擋 ②③(凡【後者是 Store】的超車)
fence(SeqCst)=雙向全封牆:兩種錨都認、四向全擋——唯一罩得住 ④ Store→Load 的牆(mfence:排乾自家 store buffer 才准跑後面的 load)。

表格的形狀由此而來:② Load→Store 兩張牆都擋(前者是 load → Acquire 管;後者是 store → Release 也管),所以它在表裡出現兩次、標「讀側/寫側」。 ④ Store→Load 兩張牆都撲空——前者是 store(不在 Acquire 的錨點名單, 它只認 load)、後者是 load(不在 Release 的名單,它只認 store)。漏網之魚, 只有 SeqCst 這道雙向全封牆罩得住。

用法對照:data=…; fence(Release); flag.store(1, Relaxed) 是把後面的 Relaxed store 升級成發布;flag.load(Relaxed)==1; fence(Acquire); 讀 data 是把前面的 Relaxed load 升級成消費——它們是「替 Relaxed 操作補秩序」的工具。 但掛牌握手要殺的是 Store→Load,acq/rel 柵欄兩個都殺不動,只能 SeqCst。

Q6:fence 跟 CAS 差在哪?

不同工種。CAS 是對「一個變數」的原子讀改寫:仲裁工具—— 決定誰搶到票、誰的更新算數;它可以順便掛 ordering 標籤,但標籤只管它自己那筆。 fence 不碰任何資料:純排序工具——決定我前後的操作誰先被全世界看見。

口訣:CAS 決定「誰贏」;fence 決定「誰先被看見」。 掛牌握手沒有競爭要仲裁(parked 只有 consumer 寫),缺的是秩序,所以用 fence; MPMC 取號有競爭要仲裁,所以用 CAS。

註腳:x86 上帶 lock 前綴的 RMW(CAS/swap/fetch_add)副作用上也會沖 store buffer, 所以有些實作用 parked.swap(true, SeqCst) 一筆兼掉「寫+柵欄」——認得就好。

③ 扇入:多源就 per-source SPSC,不是 MPSC

source_0 thread ──SPSC ring_0──┐
source_1 thread ──SPSC ring_1──┼──▶ consumer(round-robin 掃,每輪每條最多 B 筆)
source_2 thread ──SPSC ring_2──┘

每源一條自己的 ring:每條仍是單寫者(零 CAS)、某源爆量只塞滿自己的 ring、 per-source FIFO 保住(跨源全域順序沒有——說出口,這是 clarify 的料)。 按下爆源,看隔離發生:

公平性:bounded batch(每輪每條最多 B 筆)——熱源不能餓死其他源。 scale:source 靜態分片給多條 consumer;work-stealing 同時破壞單寫者與 per-source FIFO,不選。拓撲每一步都在守單寫者。 另外:SPSC 上做不到 drop-oldest(head 是 consumer 單寫的)——SPSC-safe 的 是 drop-newest + 計數;要「新蓋舊」換 per-key conflation slot。
