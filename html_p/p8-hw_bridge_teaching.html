hw_bridge — 橋接軟硬體的 binary-protocol server/client std-only · edition 2021 · rustc 1.75 編譯 + 測試通過 · 45 分鐘白板增量順序

題目與心智模型

寫一個 server 模擬硬體控制器,回應 READ_SENSOR / SET_FAN 之類命令;client 用 binary 協定呼叫。核心不是演算法,是兩件事:通訊協定怎麼定 與 thread/task 責任怎麼切。

一句話地基

TCP 是 byte stream,不是 message queue。你 write() 一個「命令」,對方 read() 拿到的可能是半個、剛好一個、或一個半命令。所以你得自己在 byte stream 上劃出 message 邊界 —— 這叫 framing。本教材用 length-prefix framing。

四張圖 = 四個責任邊界

  • ① Wire Format — 一個 frame 的 byte 佈局,對應 protocol.rs(encode / try_decode)。off-by-one 最愛的地方。
  • ② Framing 狀態機 — FrameReader:把 byte stream 切回 frame。整題的肉,互動 stepper 在這。
  • ③ Server 並發模型 — thread-per-conn vs event-loop,兩種責任切法並排。45 分鐘該選哪個。
  • ④ Client 往返 — 一來一回;順帶點出 async 版靠 request-id → pending map。
  • ⑤ async / Future — 同一套 protocol/framer 換 async fn;附一個 std-only 手寫 block_on executor(tokio 藏起來的那半,= 你 Etched 挑戰 #2)。

① Wire Format — 一個 frame 長怎樣

推導:naive → 失敗 → 修

NAIVE

「命令就直接送啊」:client 送 [opcode][payload],server read() 出來解析。

失敗模式

server read() 回傳的 byte 數是任意的(受 MTU、Nagle、對方 write 節奏影響)。沒有邊界資訊時:

  • 兩個命令黏在一起 → server 不知道第一個到哪結束。
  • 一個命令被切兩半 → server 拿到半個 payload,不知道還要等多少。

根因:TCP 沒有 message 邊界。你送的「一次 write」和對方「一次 read」沒有一對一關係。

修法:length-prefix framing

在每個 message 前面加一個固定寬度的長度欄位。reader 先讀長度,就精確知道還要收多少 byte 才是一個完整 message。

佈局圖

lenu32, big-endian
4 bytes
opcodeu8
1 byte
payloadlen − 1 bytes
└─ len 計算的範圍(opcode + payload)─┘　　　len 不含自己那 4 bytes
off-by-one 熱區(這格最容易錯)
  • len = 1 + payload.len()(含 opcode,不含 len 欄位)。
  • 整個 frame 在線上的長度 = 4 + len(那 +4 就是 len 欄位本身)。這個 +4 忘記加 = 經典 bug。
  • 解出來:opcode = buf[4],payload = buf[5..4+len]。5 = 4(len) + 1(opcode)。

設計選擇要在面試講出來

決定選了什麼理由 / 代價
len 寬度u32單 frame 上限 4 GiB;u16 省 2 bytes 但封頂 64 KiB。多數協定 u32。
len 含不含自己不含(只算 opcode+payload)兩種都行,但要一致;混用就是 bug。decode 端 total = 4 + len。
byte orderbig-endian= 網路序,跨平台無歧義。std to_be_bytes 直接給。
DoS 上限MAX_FRAME_LEN = 64 KiB拒絕宣稱超大 len 的惡意 frame,避免無限配置。

server_threaded.rs — serve_threaded + handle_conn

  


  
(b) 程式碼:std-only busy-poll 近似(真 epoll 需 FFI)

  

    為什麼是 busy-poll 而非 epoll
    
std 沒有 safe 的 epoll_wait。這裡把每個 socket 設 nonblocking,每圈掃過所有 fd 試讀試寫 —— 正確、std-only、能跑,但每圈 O(n) CPU spin(所以結尾 sleep(1ms) 避免燒滿一核)。真正 scale 要把「掃所有 fd」換成 epoll_wait 只回報 ready 的 fd。epoll 沒有 std safe wrapper,但可以自己宣告 extern "C"(libc 已被 link)→ 仍是 std-only,見 ⑥ epoll 的可編譯 + 端到端測通版本。結構(per-fd FrameReader + wbuf + 部分寫)兩版一致,差的只是 readiness 通知機制。

    sync 一來一回 vs async pipelined 的分水嶺
    
sync 版:一次一個 request,送完 block 等它的 response,天生對得上,不需要標記。

    
async 版(tokio 世界):同一條連線上同時丟出多個 request(pipelining),response 回來順序可能交錯 → 得在 frame 裡加 request_id,收到 response 用 id 去 pending map(HashMap<u32, oneshot::Sender> / Waker)找對應的等待者喚醒。這就是你 tokio 內部熟的那套 Pin/Waker 對應機制的協定層版本。std sync 版不需要,是刻意砍掉的複雜度。

⑤ async / Future 版

  
同一套 protocol + FrameReader + handler,把 I/O 邊界換成 async fn + .await。std-only 下這代表:你得自己寫 executor —— 這就是 tokio 藏起來的那半。


  

    先分清三層

    •

    • 
      
  • reactor(誰在 fd ready 時 wake 對應的 task)—— std 沒有,需 epoll = libc FFI。這是 async socket server 的另一半。

    失敗模式
    
serve_one(...) 回傳的是一個 惰性的 Future —— 什麼都還沒發生。Future 不會自己跑;沒有人 poll 它,程式碼一行都不會執行。.await 只在「已經被某個 executor 驅動」的 Future 裡才有意義。

  

  

    修法:executor(poll 迴圈)+ Waker(何時 re-poll)
    
    
      
  • executor:一個迴圈,不斷 future.poll(&mut cx)。Poll::Ready(v) → 完成,回傳 v;Poll::Pending → 還沒好,先讓出(park)。
    • 
      
  • Waker:傳給 poll 的 Context 裡。future 回 Pending 前把 waker 存起來;等條件滿足時呼叫 waker.wake() = 「請 re-poll 我」。executor 收到 wake 就重跑一輪 poll。
    • 
      
  • token 語意(關鍵):wake 可能發生在 executor 還沒 park 之前 → park 必須先檢查「有沒有待處理的 wake token」,有就不 park。掉了這個 token = 永久卡死。

追問(async 專屬,≥3 層)

  

    
L1
你的 block_on 收到 Pending 就 signal.wait()。YieldOnce 在回 Pending 前就 wake 了,wait 會卡住嗎?
      
答:不會。wake 先把 token 設 true;wait() 進來看到 token=true → 不 park,消費 token 直接返回。這正是要處理的 wake-before-park。

    

    
L2
這個 block_on 只跑一個 future。要同時跑多個 task(真 runtime)差在哪?
      
答:需要一個 task queue 與「每個 task 各自的 Waker」。Waker 的 wake() 不再只是 unpark 一條 thread,而是把該 task 的 id 推回 ready queue;executor 迴圈從 queue 取 ready task 來 poll。單 future 版沒有排程,只有一個 future 一路 poll。

    

    
L3
多 task 下,一個 .await 在 socket 上,是誰、什麼時候呼叫那個 task 的 wake()?
      
答:reactor。task poll 到 socket 未就緒 → 把自己的 Waker 註冊到 reactor(對應那個 fd 的 EPOLLIN)→ 回 Pending。reactor 的 epoll_wait 醒來發現該 fd 可讀 → 查表拿到 Waker → wake() → task 回 ready queue。這一整套 std 沒有,是 tokio 的核心;std-only 只能 in-memory 或 busy-poll 近似。

    

  


  

    面試取捨話術
    
什麼時候提 async? 被問到「怎麼 scale」時。sync thread-per-conn 簡單但 1 thread/conn;async(單 reactor thread + 多 task)是 event-loop 的 ergonomic 版 —— 但 std-only 下你得手寫 executor + reactor(epoll FFI),45 分鐘寫不完。所以:白板寫 sync,async 當口頭 scale 答案 + 秀你懂 executor/reactor 分工。request-id → pending map(圖④)就是 async 版在一條連線上多工的那層。

  







  
⑥ epoll — 真正的 reactor(std-only 也做得到)

  
前面說「std 沒 epoll,只能 busy-poll 近似」講太滿。精確版:std 沒有 safe 的 epoll wrapper,但 Rust runtime 本來就 link 了 libc,所以自己宣告那三個 syscall 的 extern "C",只用 std + 一個 unsafe extern block 就摸到真 reactor,零外部 crate。下面這份是實際編譯 + 端到端跑通的。


  

    epoll 解決什麼
    
readiness notification:你把一堆 fd 註冊給 kernel,epoll_wait 阻塞著,一旦有 fd 就緒就只回報就緒的那些。相對 busy-poll「每圈掃全部 fd」= O(n),epoll 是 O(ready)。這就是 event-loop 從「能跑」變「scale C10K」的關鍵。

  


  
推導:naive(busy-poll)→ 失敗 → 修

  

    NAIVE
    
圖③(b) 的 busy-poll 版:每圈把所有 fd 設 nonblocking,逐個試讀試寫,WouldBlock 就跳過,結尾 sleep(1ms)。

  

  

    失敗模式
    
    
      
  • 每圈 O(n):1 萬條連線只有 1 條有資料,你還是掃了 1 萬次。
    • 
      
  • CPU 空轉:沒事也要醒來掃 + sleep,浪費週期、增加延遲抖動。
    • 
      
  • sleep 是延遲與 CPU 的兩難:睡短 = 燒 CPU,睡長 = 反應慢。
    • 
    

  

  

    修法:讓 kernel 幫你盯
    
把 fd 註冊進一個 epoll instance,epoll_wait 睡到有事才醒,且直接告訴你哪些 fd 就緒。沒事 = 0 CPU;有事 = 只處理就緒的。O(ready)。

epoll_ctl(epfd, op, fd, ev)對 epfd 增/刪/改一個 fd 的關注事件。op = ADD/DEL/MODaccept 新連線 → ADD;有待寫 → MOD 加 EPOLLOUT;斷線 → DEL

    
epoll_wait(epfd, buf, max, timeout)阻塞到有 fd 就緒,把就緒事件填進 buf,回傳數量 n。timeout=-1 = 無限等主迴圈的心臟;回來後只跑 buf[0..n]

  


  

    ABI 眉角:epoll_event 在 x86 是 packed
    
struct epoll_event = events(u32)後面直接接 data(union,取 u64),x86 上 __attribute__((packed)) → 12 bytes(無 padding)。忘了 #[repr(C, packed)] → 自然對齊變 16 bytes(data 前面塞 4 bytes padding)→ kernel 照 12-byte 佈局讀 → 讀到垃圾、fd 全錯。本機實測(x86_64):packed 12 / unpacked 16。非 x86 有些 arch 不 packed;libc crate 幫你分 arch,手刻就得自己認 target。存取 packed 欄位只能整份 copy 出來再讀(不能取 &field 參照,會 misaligned)——所以 code 裡是 let slot = events[i]; 先 copy。

  


  
Level-triggered vs Edge-triggered

  

    

      
Level-triggered(預設,本教材用)

      
只要條件成立(還有資料可讀 / 還可寫),每次 epoll_wait 都會回報。沒 drain 完沒關係,下次還會叫你。

      
簡單、不易漏資料高頻下 wakeup 較多

    

    

      
Edge-triggered(EPOLLET)

      
只在「狀態轉變」時通知一次(新資料到)。沒把 buffer read 到 WouldBlock 就停 → 剩下的資料不會再觸發 → 卡死。必配 nonblocking + drain loop。

      
wakeup 最少、最省忘了 drain 就漏 / 死鎖

    

  

  
※ 本 serve_epoll 是 LT,但 read/write 仍 drain 到 WouldBlock(好習慣,高負載下也需要)。所以切成 ET 也安全 —— 但一般人會在 ET 上踩漏 drain 的坑。

追問(≥3 層)

  

    
L1
你的 serve_epoll 是 level-triggered。改成 edge-triggered(EPOLLET)會有什麼坑?
      
答:ET 只在「狀態轉變」通知一次。若 read 沒 drain 到 WouldBlock 就停,剩下的資料不會再觸發 → 那條連線卡死。ET 下 read/write 必須 loop 到 EAGAIN。(我這版 LT 已經 drain-to-WouldBlock,切 ET 也安全,但這是最常見的 ET bug。)

    

    
L2
ET 這麼容易踩,為什麼還用?
      
答:減少 wakeup。LT 下只要條件成立,每次 epoll_wait 都回報同一個 fd;高頻小封包場景,重複 wakeup + syscall 開銷大。ET 一次轉變一次通知,配 drain loop,wakeup 次數最少。

    

    
L3
多執行緒共用一個 epfd,同一個就緒 fd 會不會被兩條 thread 同時處理?
      
答:會 —— 多 worker 對同一 epfd 各自 epoll_wait,同一個 ready fd 可能被多條 thread 各拿一次(thundering herd / 重複派工,還有資料競爭)。解法:EPOLLONESHOT(觸發後自動 disable 該 fd,處理完再 MOD 重新武裝),accept 場景用 EPOLLEXCLUSIVE 避免驚群,或每 thread 各自 epfd + SO_REUSEPORT 讓 kernel 分流。

常見面試追問(≥3 層深)

  
L4 modal = medium 題 + follow-up。每條 chain 往下鑽三層,答案是要點不是逐字稿。


  
Chain 1:惡意 / 畸形 frame

  

    
L1
對方送一個 len 宣稱 4 GB 的 frame,你的 try_decode 會怎樣?
      
答:所以要 MAX_FRAME_LEN 上限 → 超過回 Err(FrameTooLarge),caller 丟連線。沒上限的話 buffer 會為了湊「永遠湊不到」的 frame 無限長大(記憶體 DoS);且 4 + len 在 32-bit usize 上可能 overflow,上限一併擋掉。

    

    
L2
加了上限之後,buffer 還是可能無限長大嗎?攻擊者慢慢送 sub-max frame 但永不湊齊一個。
      
答:會 —— 這是 slowloris。單一 frame 有上限,但「一直餵不完整」耗住連線。需要 idle timeout / 「多久沒推進就砍」:thread 版用 stream.set_read_timeout;或記 per-conn 最後活動時間,超時關閉。

    

    
L3
set_read_timeout 在 event-loop(nonblocking)模型下有用嗎?
      
答:nonblocking socket 的讀是立刻返回 WouldBlock,SO_RCVTIMEO 的語意不適用。epoll 模型要自己做:per-fd 存 last-activity timestamp,用一個 deadline 的 min-heap / timing wheel,每次 epoll_wait 帶 timeout 參數,醒來掃過期的 fd 關掉。

    

  


  
Chain 2:buffer 效能

  

    
L1
drain(0..consumed) 每次 O(n) 搬移,高吞吐會痛嗎?
      
答:會。一個 read 夾很多小 frame 時,每 pull 一個就把殘量整段前移,burst 下可退化 O(n²)。

    

    
L2
怎麼改?
      
答:加一個 read-offset 游標:try_decode(&buf[start..]),start += consumed,只在 start 大到一定程度才 compact(把殘量搬回頭並重置 start)。攤還 O(1)。再進一步就是 ring buffer。

    

    
L3
ring buffer 遇到 frame 跨越 wrap 邊界,怎麼讀 len 那 4 bytes?
      
答:len 欄位可能被 wrap 切成「尾端 2 bytes + 開頭 2 bytes」。要嘛先確認連續可讀 ≥ 4 再讀(不足就先 compact),要嘛用一個小 staging array 把兩段拼起來再 from_be_bytes。這正是 wrap-boundary off-by-one 熱區 —— 跨界時刻(不是 index 0)才會爆,random fuzz 常常打不到,要刻意造跨界測資。

    

  


  
Chain 3:連線資源

  

    
L1
thread-per-conn 用 blocking read;一個 client 連上但不送資料,佔著一條 thread。一萬個這種連線?
      
答:thread 耗盡 / 記憶體爆(每 thread 預設 stack ~數 MB)。這也是 slowloris 的一種。無界 spawn 就是攻擊面。

    

    
L2
用有界 thread pool 呢?連線數 > pool size 時新連線怎麼辦?
      
答:要嘛排隊(accept 後塞 queue,backpressure)、要嘛拒絕。但 blocking-read 的 pool 有 head-of-line:一條慢連線佔住一個 worker。這正是 event loop 勝出的點 —— 慢連線只是「還沒 ready」,不佔 thread。

    

    
L3
那 event loop 版,單執行緒會不會被一個 CPU-heavy 的 handler 卡死全部連線?
      
答:會 —— 單 reactor thread 上任何 handler 阻塞(重運算、同步 I/O)就 stall 整個迴圈。解法:handler 只做輕量分派,重工作丟 worker thread pool,完成後把 response 送回 reactor 佇列(這就是 tokio 的 spawn_blocking 心智模型)。

Self-Quiz(5 題)

  
先自己答,再展開對照。答案裡點名了具體 off-by-one 點與砍留清單。


  

    Q1. 為什麼 TCP 需要 framing?length-prefix 怎麼處理「半個 frame」與「一次收到多個 frame」?
    

      
TCP 是 byte stream,沒有 message 邊界 —— 一次 write 和一次 read 沒有一對一關係,對方可能一次讀到半個、剛好一個、或多個命令。所以要在 stream 上自己劃邊界。

      
length-prefix:每個 frame 前面放 u32 len(不含自己)。decode 端維護累積 buffer:

      
    
        
  • 半個 frame:讀出 len,算出需要 total = 4 + len;buffer 不足 total → try_decode 回 None,保留已收的、等下次 feed。連 4 bytes 都不夠(讀不出 len)也回 None。
    • 
        
  • 多個 frame:切出第一個後 drain(0..total),殘量留前端,while 迴圈繼續 pull,直到剩餘不夠一個完整 frame 才停。
    • 
      

      
關鍵是 buffer + parse loop + consumed/remainder 三件一起,不是單次 decode。

    

  


  

    Q2. 45 分鐘只夠寫到 naive 一來一回,你會先砍什麼、保什麼?
    

      
保(絕不砍): ① wire format 定義(length-prefix 佈局)② encode + FrameReader 的 parse loop(處理 partial / 多 frame)③ 一次能 demo 的端到端往返 ④ 全程明講 Big-O ⑤ 至少一次 dry-run partial-read。MAX_FRAME_LEN 是一行 guard,便宜,可留。

      
先砍(依序): request-id 對應 → event-loop 實作(只留 thread-per-conn,5 行增量)→ 多 opcode / graceful shutdown → 真的不行連多 client 都砍,只留單 client。

      
理由:一個能編譯、能跑一次 READ_SENSOR 的 naive,遠贏一個號稱 scalable 但編不過的半成品。scale 用嘴巴講 tradeoff(圖③)拿分,不用真寫完。

    

  


  

    Q3. encode 時 len 該不該含自己那 4 bytes?兩種設計 decode 差在哪?off-by-one 點在哪?
    

      
兩種都可行,但必須一致;混用就是 bug。

      
    
        
  • 不含自己(本教材):len = 1 + payload.len(),decode total = 4 + len,payload = buf[5..total]。
    • 
        
  • 含自己:len = 5 + payload.len(),decode total = len(不再 +4),payload = buf[5..len]。
    • 
      

      
off-by-one 陷阱:用「不含自己」的 encode 卻用「含自己」的 decode(total = len),會少收 4 bytes → 把下一個 frame 的前 4 bytes 當這個 frame 的尾;反之會越界。這種 bug 小測資(單 frame)常常看不出,要跨 frame 才爆。

    

  


  

    Q4. event-loop 模型為什麼「寫」也需要 buffer 和 EPOLLOUT?blocking 模型不用?
    

      
blocking 版: write_all 內部迴圈直到全部寫完(kernel send buffer 滿就 block 等),呼叫回來就保證寫完,不用自己管。

      
nonblocking(event-loop)版: 一次 write 可能只接受一部分,或回 WouldBlock(send buffer 滿)。你必須把沒寫出去的殘量存進 per-fd wbuf,並向 epoll 註冊 EPOLLOUT —— 等 socket 可寫時 epoll 通知你,再 flush 殘量。沒有 wbuf 就會丟資料;沒有 EPOLLOUT 就得 busy-poll 空轉試寫(本教材 std-only 版正是這樣,靠 sleep 壓 CPU)。

    

  


  

    Q5. try_decode 回 Err(ZeroLen / FrameTooLarge) 後,FrameReader 該怎麼辦?為什麼不能只 skip 這個 frame 繼續?
    

      
丟連線,不 resync。 協定違規代表這條 byte stream 已經 desync 或對方是惡意/有 bug 的 peer。

      
為什麼不能 skip N bytes 繼續:skip 的前提是你知道這個壞 frame 有多長 —— 但「多長」正是從那個已經壞掉的 len 算出來的。ZeroLen 根本沒有有效長度;FrameTooLarge 的 len 不可信。你無法確定下一個 frame 邊界在哪,任何 resync 都是猜。唯一安全動作是關連線,讓對方重連重新對齊。（若協定有 magic-byte / sync marker 才可能做 resync,但本 wire format 沒有。）

    

  


  

    Q6. async fn 為什麼「呼叫了卻什麼都沒發生」?executor 與 reactor 各負責什麼?std 少了哪個?
    

      
呼叫 async fn 只回傳一個惰性 Future,一行都還沒跑。Future 要被 poll 才會推進。

      
    
        
  • executor:一個 poll 迴圈,把 Future 驅動到 Poll::Ready。Pending 就 park,被 wake 後 re-poll。(本教材的 block_on。)
    • 
        
  • reactor:在 I/O(fd)就緒時,呼叫對應 task 的 Waker::wake() 把它排回去 poll。(epoll。)
    • 
      

      
std 有 Future/async/await/Waker(std::future、std::task),但沒有 executor、也沒有 reactor(reactor 需 epoll = libc FFI)。所以 std-only async 要自己寫 block_on,並用 in-memory transport 或 busy-poll 頂替 reactor。tokio 把兩者 + async TcpStream 一起給你。

    

  


  

    Q7. block_on 的 Signal 為什麼要 token(Mutex<bool>)而不是純 park/unpark?wake 發生在 park 之前會怎樣?
    

      
因為 wake 可能早於 park。 YieldOnce 在回 Pending 之前就 wake_by_ref() 了;此時 executor 還沒進 wait()。

      
純 park(無 token): executor 進 wait() 才開始等通知 —— 但通知已經來過且不會再來 → 永久阻塞(死鎖)。

      
token 版: notify() 把 bool 設 true(持久保留,即使當下沒人在等);wait() 進來先驗 token,true 就不 park、消費掉直接返回,false 才 park。這個「先檢查 token 再決定 park」就是 wake-before-park 的正確性條件,也是 Etched 挑戰 #2 的核心。

    

  


  

    Q8. level-triggered 下 wbuf 空了要把 EPOLLOUT 取消(MOD 回只剩 EPOLLIN),不取消會怎樣?
    

      
socket 幾乎永遠可寫。 LT 下只要 fd 可寫且註冊了 EPOLLOUT,每次 epoll_wait 都回報它 → 你不斷被喚醒卻沒東西可寫 = busy loop 空轉,把單執行緒 reactor 拖垮。

      
正解: 只在 wbuf 非空(有待寫、且上次 write 回了 WouldBlock)時才註冊 EPOLLOUT;flush 完就 MOD 回只剩 EPOLLIN。ET 下沒這問題(只在「不可寫→可寫」轉變時通知一次),但 ET 有 read 漏 drain 的坑 —— 兩種 triggering 各有各的節流責任。
