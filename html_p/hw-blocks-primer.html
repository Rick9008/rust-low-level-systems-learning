硬體積木入門 — 給軟體人的 device 世界觀

寫服務端的人第一次碰硬體題,霧的來源不是演算法,是名詞背後沒有物理圖像。這頁把 sim i–o 用到的每顆零件配圖講到底。姊妹頁:r2-onsite-visual-guide(作戰本,積木速查版)、watchdog-deadline-design(sim m 沉澱)、fanin-aggregator-bitmask(sim k 沉澱)。

0. 全景:桌上只有三個東西

你的 code 跑在 CPU 上;device 是插在機器裡的另一台小電腦(網卡、SSD、GPU、DMA 引擎都是)。它有自己的處理器、自己的韌體、自己的節奏——你不能叫它「執行你的函式」,只能透過兩個管道跟它協作:共享記憶體(雙方都能讀寫的桌面)和它身上的暫存器(下一節)。

全頁最重要的一句 device 看得見記憶體,看不見你的程式碼。它不知道你哪一行先寫、哪一行後寫——它只看到記憶體流量抵達的順序。而你的寫入會先經過 cache / store buffer 排隊,抵達順序 ≠ 程式碼順序。這一句是 barrier(門鈴與牆分頁)存在的全部理由,也是所有硬體題的共同世界觀。

1. MMIO 暫存器:裝在 device 身上的信箱

是什麼:MMIO(memory-mapped I/O)= 把 device 的零件「掛」在地址空間的某一段上。你用普通的讀寫指令去碰那些地址,實際發生的卻是:讀 = 看 device 掛出來的牌子,寫 = 撥它身上的開關。harness 裡的 mmio_read/mmio_write 模擬的就是這件事。

為什麼存在:device 內部的狀態你摸不到(它是另一台電腦!),所以它只把「你需要知道的」做成唯讀牌子(SubmitHead、CompTail)、把「你可以命令的」做成可寫按鈕(Doorbell)。方向性是查表就知道的事:每個暫存器要嘛是牌子、要嘛是按鈕,幾乎不會兩者都是。

兩個物理事實(面試講出來就是分) ① MMIO 讀寫是 uncached 慢路——每次都真的跑到 device 那裡,百 ns 到 µs 級(普通 RAM 命中 cache 是 1ns 級)。所以真驅動能批次就批次:填一批 descriptor、按一次鈴。② MMIO 寫跟普通記憶體寫走不同的路——這是「牆」分頁的伏筆。

ring 與工單 — 為什麼硬體世界什麼都是環

descriptor(工單)放進 ring(環形格子架),用單調序號取格。這一套是 NVMe、網卡、GPU 命令佇列的共同骨架。

2. descriptor:固定格式的小工單

你要 device 做的一件事,壓成一張固定大小的表格——這裡是 { tag: u32, payload: u64 }:tag 是你寫的單號(之後 device 拿它回報「幾號單做完了」),payload 是工作內容(你不解釋、只搬運;真硬體裡是位址+長度+旗標)。為什麼固定大小:格子架的每一格要一樣大,硬體才能用「序號 × 格寬」直接算出位址——它不會追指標。

3. ring:一排格子 + 單調序號

為什麼是環,不是 Vec 或鏈表 硬體只會數數:給它一個起點序號和一個終點序號,它會自己把中間的格子一格格吃掉。它不會 malloc、不會追指標、不會處理變長結構。固定格子 + 單調序號 = 硬體唯一讀得懂的資料結構。這也是為什麼你在 spsc_ring、mpmc_ring 練的序號算術,到硬體題一行都沒浪費。

門鈴與牆 — 放了貨為什麼要按鈴,按鈴前為什麼要砌牆

sim l 的核心,也是 8/2 深夜之霧的震央。兩張時序圖,一好一壞。

4. doorbell:為什麼放了貨還要按鈴

因為 device 不會盯著你的記憶體看——要它輪詢你的 RAM,又貴又蠢。你把工單放進格子後,寫一次 Doorbell 暫存器,做兩件事:「有事了」的訊號 + 「我放到 N 號了」的公告(寫進去的值就是你的新 tail)。device 聽到鈴,把 head..doorbell 之間的單子整批吃掉。

5. barrier:兩條郵路,先貨後鈴

你早就會這個定理 先值後訊號,第四次現身:fanin 的 push→wake、waker 的 set-result→wake、spin_lock 解鎖的 Release、這裡的 descriptor→barrier→doorbell。四個皮,一個瓤。唯一的新知識:對面是矽,Rust 的 Ordering 管不到它,所以要顯式柵欄(真驅動用 wmb()/dma_wmb())。

sim i/m 的主角(搬運工)和 sim j 的主角(插隊電話)。

6. DMA engine:會自己動的搬運工

為什麼存在:沒有它,CPU 要一個 byte 一個 byte 端盤子,什麼正事都別做了。你付出的代價是非同步:派工和完工之間隔著未知的時間,而完工通知資訊量極少——於是「記帳」成了 driver 的主要工作,這正是 sim i/m 整個題系的考點。

7. IRQ / ISR:插隊電話

IRQ vs polling(面試常考的對照) polling = 你一直打去問「好了沒」(浪費 CPU,但延遲穩定);IRQ = 它好了打給你(省 CPU,但高負載時電話響不停,接電話本身淹死你)。真實系統混用:低負載走 IRQ、高負載切 polling(網卡的 NAPI)。sim j 的「ISR 只准搬進 ring、慢活給 worker」= top-half/bottom-half,就是把「接電話」壓到最短的紀律。

8. watchdog / timeout:當硬體沉默

硬體會壞,而且壞的時候通常一聲不吭——沒有 exception、沒有 error code。你唯一的觀察手段是時間:deadline 是事件迴圈的第三種事件(前兩種「新請求」「完成」是別人推給你的,這種是你自己排的)。完整設計課在 watchdog-deadline-design 頁(deadline 與 owner 同居、殭屍=生存證明)。

9. 總表:每題用到哪些積木

題積木一句話
sim i(DMA dispatcher)DMA engine ×6、綁定表派工單給搬運工;done 只報工號,帳自己記
sim j(ISR pipeline)HW FIFO、IRQ/ISR、SPSC ring插隊電話裡只准搬進 ring,慢活交給樓下
sim k(fan-in)SPSC ring ×N(純軟體)硬體零件最少的一題:N 個生產者、一個收銀台
sim l(MMIO cmdq)MMIO 暫存器、雙 ring、doorbell、barrier零件全家福:上架→牆→按鈴;反向先看牌再拿貨
sim m(watchdog)DMA engine + 時鐘i 的世界加一個事實:搬運工會無聲失蹤
sim n(scheduler)(無硬體)worker slots純軟體排程:兩道閘,先依賴後優先權
sim o(boot planner)(無硬體)依賴 DAG演算法穿硬體皮:開機前的靜態分析(Kahn 波次+關鍵路徑)

收尾預測題:done 事件「只帶 engine id、不帶工單內容」,和 completion entry「自帶 tag」,是兩種不同的硬體介面設計。哪一種逼你在 driver 裡維護綁定表?

帶走的一句 硬體題的難度幾乎都不在演算法,在「通知的資訊量」和「你的帳」之間的差距:通知越貧瘠(只報工號、只響一聲鈴),你的 state 表就越重要。clarify 的第一要務就是量出這個差距——「When X notifies me, what exactly does it carry?」
