1. Naive 版:全 Relaxed(「我單執行緒測都過」)

最直覺的寫法:head/tail 用 AtomicUsize,但因為單執行緒測試會過,所有 load/store 都填 Relaxed。payload buffer(buf[idx])是 non-atomic 的——它的安全完全依賴 head/tail 這兩個 atomic 建立的 happens-before。

// ⚠ naive:發佈與觀察都 Relaxed(use Ordering::*;)
// producer
let cell = self.buf[t & mask].get();
unsafe { (*cell).as_mut_ptr().write(x); }            // non-atomic payload 寫入
self.tail.store(t + 1, Relaxed);                     // 「發佈」

// consumer
if self.tail.load(Relaxed) != head {                 // 看到新 tail
    let v = unsafe { std::ptr::read((*cell).as_ptr()) }; // ⚠ 無 acquire → 可能讀到未初始化
}

2. 失敗模式:這是 UB,不是「偶爾讀到舊值」

  • 兩個 Relaxed 操作之間沒有 synchronizes-with → 沒有 happens-before。consumer「看到 tail==1」不蘊含「看到 buf[0]==X」。
  • 弱記憶體序 CPU(ARM/POWER):producer 對 buf[0] 與 tail 是兩個獨立寫入,沒有 release 就可能亂序傳播——tail=1 先被別的 core 看到,buf[0]=X 還沒。consumer 讀到未初始化 / 舊值。
  • 即使在 x86(TSO,硬體不會亂序這組):編譯器仍可在 Relaxed 下把 buf[0] 的讀取重排到 tail 讀取之前(Relaxed 不禁止)→ 一樣爆。
  • 形式上:producer 對 buf[0] 的寫、consumer 對 buf[0] 的讀,無 HB 排序、對同一 non-atomic 位址、至少一寫 → data race → UB。整段未定義,不是機率問題。

2.1 先定位:「重排」可以在兩個地方發生

上面第 2、3 條 bullet 常被混成一團,其實它們是不同層的失效。從你寫的原始碼,到「別的 core 實際看到的順序」,中間有兩道關卡,每一道都會重排:

所以「x86 是 TSO、硬體不會亂序,我不標 ordering 也沒事」是錯的:它只免除你 Mode A,Mode B 照樣爆。

2.2 Mode A — ARM/POWER:兩個 store 亂序傳播

producer 的 buf[0]=X(non-atomic store)和 tail.store(1, Relaxed) 是兩個獨立寫入。Relaxed 不要求它們之間有任何順序,於是硬體可以讓後寫的 tail 先被 consumer 的 core 看到:

關鍵:consumer 沒做錯任何事。它的 program order 完全正確(先讀 tail、再讀 buf[0])。錯在 producer 那兩個 store 沒被綁定順序。Release store 的作用正是:先把它之前的所有寫入推出去,這個 store 才可見 —— 加上 Release,tail=1 就不可能超車 buf[0]=X。

圖中的「傳播快慢」是示意;微架構機制(store buffer 排空順序、cache 傳播路徑)不是重點,架構層規則才是:ARM/POWER 沒有屏障就不保證 store-store 順序。unverified:各家記憶體模型的確切條文(POWER 的 non-multi-copy-atomic、ARMv8 的 other-multi-copy-atomic)我不背原文,面試講到「無屏障則 store-store 無序」這層即可。

2.3 Mode B — x86:硬體很乖,編譯器把 bug 烤進 binary

x86-TSO 對不同位址只允許 StoreLoad 重排:store-store 不重排、load-load 不重排(另有 store-forwarding 讓 core 提前讀到自己的寫入)。所以 Mode A 在 x86 上不會發生。但 Relaxed 對編譯器同樣什麼都沒承諾——它不排序 relaxed atomic 與周圍的 non-atomic 存取。於是 LLVM 可以合法地這樣改你的 code:

你寫的(source)
// consumer:自旋等資料
loop {
    let t = self.tail.load(Relaxed);
    if t == head { continue; }   // 還沒資料
    // 讀 payload(在迴圈內)
    break unsafe { std::ptr::read((*cell).as_ptr()) };
}
→
LLVM LICM
Relaxed 不排序
非 atomic 存取
編譯器輸出(等價語義)
// 非 atomic 讀取被提出迴圈!
let v = unsafe { std::ptr::read((*cell).as_ptr()) };
loop {                           // ⚠ producer 還沒寫
    let t = self.tail.load(Relaxed);
    if t == head { continue; }
    break v;                     // ⚠ 永遠是那個舊值
}
為什麼 LICM 是「合法」的?因為語言的合約是「程式無 data race」——在那個假設下,自旋期間沒有別人會寫 *cell,所以那個非 atomic 讀取是 loop-invariant,提出迴圈天經地義。諷刺的是:你的程式正好有 race,假設是假的,於是這個「正確」的最佳化把你炸掉。
x86 硬體一個 reorder 都沒做,忠實照 binary 一條條執行 —— 但 binary 本身就已經是錯的,bug 在編譯期就烤進去了。這就是為什麼「x86 反正是 TSO」不能當成省略 Acquire 的理由:ordering 是同時對編譯器與硬體下的合約,x86 只免除你其中一半。

3. 修法:一對 Release / Acquire 縫出因果

  • 發佈端 Release(producer store tail):此 store 之前的所有寫入(含 buf[0]=X)排在它之前,且對做 Acquire 讀到此值的執行緒可見。
  • 觀察端 Acquire(consumer load tail):此 load 之後的讀取排在其後;讀到該 Release store 寫的值,即可看到其之前的所有寫入。
  • 這對 Release/Acquire 構成 synchronizes-with;加上執行緒內的 sequenced-before,buf[0]=X happens-before consumer 讀 buf[0] → 不再是 race。
  • head 那邊對稱:consumer 釋放 slot 用 Release,producer 觀察空位用 Acquire,保證「producer 覆寫舊 slot」排在「consumer 讀完舊資料」之後。
與其一開始糾結哪個該 Acquire、哪個能 Relaxed——
全部先寫 SeqCst(永遠正確,只是可能慢),再逐點 relax,每步講清楚為什麼安全。

4. 先把 state 與詞彙立起來(進 stepper 前的地基)

4.1 四種 Ordering(std 語義)

Ordering語義(store / load)
Relaxed只保證此操作原子(不可分割)+ 單一位址 modification order 一致。不建立跨執行緒 happens-before,不排序其他記憶體操作。
Release(store)此 store 之前的記憶體操作,對「以 Acquire+ 讀到此值」的執行緒可見,且不被重排到 store 之後。release-acquire pair 的發佈側。
Acquire(load)此 load 之後的操作不被重排到它之前;讀到某 Release store 寫的值即可看到其之前的所有寫入。pair 的觀察側。
SeqCst在 load/store 各自 Acquire/Release 之上,額外讓所有 SeqCst 操作參與「單一全域 total order」。最強、通常最貴。

AcqRel 給 read-modify-write(如 fetch_add)用:load 側 Acquire、store 側 Release。本題 SPSC 用不到,列此備查。

4.2 synchronizes-with / happens-before

先用一張時間軸把三個名詞的關係擺清楚,再看下面的定義。經典 message-passing:Thread A 寫資料、發旗標;Thread B 讀旗標、讀資料。

①sequenced-before(程式順序):同一條執行緒內,前面的操作排在後面之前。這是「執行緒內」的因果,不跨執行緒。
②synchronizes-with:對同一 atomic,一個 Release store 被「讀到該值的 Acquire load」觀察到時,兩者構成此關係。這是唯一能跨執行緒的因果接縫。
③happens-before = ① ∪ ② 的遞移閉包。上圖 A1 →① A2 →② B1 →① B2 串起來,就得到 A1 happens-before B2 ⟹ B2 保證看到 data==42。少了 ②(把 Acquire 降成 Relaxed)這條鏈就斷,B2 讀到的 data 變 UB。
  • synchronizes-with:對變數 M 的一個 Release store,與「讀到該值(或其 release sequence 後續值)的 Acquire load on M」構成 synchronizes-with。
  • happens-before:A hb B ⟺ A sequenced-before B(同執行緒 program order)或 A synchronizes-with B,再取遞移閉包。A hb B ⟹ A 的效果對 B 可見。
  • 一句話:synchronizes-with 是跨執行緒唯一的「因果接縫」;把兩條執行緒的 program order 縫起來,才生出 happens-before。

4.3 兩個 handshake 與 state 變數

  • state:head(consumer 寫、producer 讀)、tail(producer 寫、consumer 讀),皆 free-running(單調遞增,溢位時 wrap)。
  • 元素個數 = tail.wrapping_sub(head),恆 ∈ [0, capacity]。空:head == tail;滿:tail.wrapping_sub(head) == capacity。
  • capacity 取 2 的次方,indexing 用 idx & (capacity-1) 取代 %。
  • 為什麼 wrapping_sub 對:真實差值恆 ≤ capacity(很小),它算 (tail−head) mod 2^64;差值 < 模數時結果即真實差值——即使 tail 已 wrap 過 usize::MAX 而 head 還沒。
  • Handshake ①(資料可得,走 tail):producer 寫 payload → Release store tail;consumer Acquire load tail → 讀 payload。保證讀得到剛寫的資料。
  • Handshake ②(空間可得,走 head):consumer 讀完 payload → Release store head;producer Acquire load head → 覆寫 slot。保證不覆蓋 consumer 還沒讀完的資料。

4.4 為什麼「讀自己的 index」可以 Relaxed

producer 是 tail 的唯一寫者。它在 push 裡讀自己的 tail,只是要知道自己上次寫到哪。同執行緒 store→load 有 sequenced-before,加上單一位址的 read-your-own-writes 保證,必讀到自己最新值——不需要跨執行緒 Acquire。Acquire 的用途是看別的執行緒對別的位址的寫入,此處無此需求。consumer 讀自己的 head 同理。

4.5 效能面:false sharing 與 cache line 對齊

  • head 由 consumer 寫、tail 由 producer 寫。若落在同一條 cache line,每次任一方更新,MESI 就得把整條 line 在兩 core 的 cache 間搬(寫者取得 Modified/Exclusive、令對方副本失效)。兩個邏輯無關的變數因物理共用一條 line 互相拖累 = false sharing,line 在兩 core 間 ping-pong。
  • 修法:每個 atomic 各佔一條 line。x86-64 常見 line 64 bytes,用 #[repr(align(64))] 包 newtype。
  • std-only 注意:std 沒有 CachePadded(那是 crossbeam_utils::CachePadded);本題禁 crate,就自己用 #[repr(align(64))] 刻——這本身是不錯的面試點。
  • 進階:部分平台(某些 ARM,或 x86 spatial prefetcher 成對抓相鄰 line)用 128 bytes 連 prefetch 一起擋。unverified:crossbeam 對某些 target 用比 64 大的常數,確切值不背;面試講「64 起跳、某些平台加碼 128」即可。

3. 面試追問(三條鏈,每條 ≥ 三層)

鏈 A — ordering 為什麼不能省

L1 — consumer 讀 tail 為什麼要 Acquire,不能 Relaxed?

要和 producer 的 Release 構成 synchronizes-with,才有 happens-before,才保證看到 payload。Relaxed 無 HB → data race → UB(見 的 naive 失敗)。

L2 — x86 上 Acquire load 反正編成普通 mov,那標 Acquire 還有差嗎?

有。(1) 可攜性:ARM/POWER 上 Acquire 會編出屏障,x86 只是剛好硬體夠強。(2) Acquire 是對抽象機器 / 編譯器的合約:即使在 x86,它也禁止編譯器把後面的 payload 讀取重排到 acquire load 之前、或做不該做的 CSE/hoist。ordering 管的是「編譯器 + 硬體」兩層,不只硬體。

L3 — 給一個 x86 上 Acquire 擋得住、Relaxed 擋不住的編譯器重排。

Relaxed 下,編譯器可把 let v = buf[idx](payload 讀)重排到 tail.load 之前(Relaxed 不禁止跨這兩個操作重排),於是可能先讀到 slot 的舊/未初始化值,再讀 tail;Acquire 把 payload 讀鎖在其後,禁止此 hoist。這是純編譯期重排,硬體層看不到——所以「x86 反正 mov」不能當成省略 Acquire 的理由。

鏈 B — 為什麼 SPSC 不用 SeqCst

L1 — 為什麼一對 Release/Acquire 就夠,不用 SeqCst?

只需要成對的 synchronizes-with(tail 一對、head 一對)建立局部 HB;沒有第三條執行緒,也不需把兩個 handshake 之間排出全域順序。SeqCst 的「所有 SeqCst 操作單一 total order」是嚴格多出來的保證。

L2 — 那什麼時候才需要 SeqCst?

當多條執行緒需要對「兩個獨立變數的操作順序」達成全域一致時。典型是 store-buffer litmus(Dekker/Peterson 骨架):兩執行緒各自「寫自己的 flag、讀對方的 flag」,要禁止「兩邊都讀到 0」。

L3 — 寫出那個 litmus,說明為什麼 Release/Acquire 不夠、要 SeqCst。

// X, Y: AtomicUsize = 0;   use Ordering::SeqCst;
// Thread 1                     // Thread 2
X.store(1, SeqCst);            Y.store(1, SeqCst);
let r1 = Y.load(SeqCst);       let r2 = X.load(SeqCst);
// 問:能否 r1 == 0 && r2 == 0 ?(SeqCst 下:不可能;若改 Rel/Acq 則可能)

Release/Acquire 只排序「同一變數的發佈/觀察」,不排序「本執行緒的 store 與對另一變數的 load」——StoreLoad 重排是允許的,所以兩邊都可能讀到 0(r1==r2==0)。只有 SeqCst 的全域 total order 能禁止此結果(不存在一個總順序讓兩個 load 都排在兩個 store 之前)。SPSC 沒有「跨獨立變數的全域順序」需求,故不需 SeqCst。

鏈 C — 效能 / cache

L1 — 這裡的 false sharing 是什麼、怎麼修?

head/tail 同 line → 兩 core 寫入互相 invalidate、line ping-pong;#[repr(align(64))] 讓各佔一條 line(std 無 CachePadded,自己刻)。

L2 — 為什麼是 64?何時用 128?

64 是 x86-64 常見 line 大小;有些 CPU spatial prefetcher 成對抓相鄰 line、或部分 ARM 用 128 bytes,這時對齊 128 才連 prefetch 一起擋。unverified:crossbeam 對某些 target 用比 64 大的常數,確切值不背。

L3 — head/tail 各自對齊後,還有殘留 cache 流量嗎?怎麼再降?

有。producer 每次 push 都 Acquire load 對方的 head(跨 core 讀 consumer 的 line),consumer 每次 pop 也 load tail。優化:各自快取上次看到的對方 index——producer 存一個非共享的 cached_head,consumer 存 cached_tail。push 先用 cache 判斷是否滿;只有看起來滿時才真的 Acquire load 更新 cache、再判一次:

// delta 示意(producer 持有 cached_head: Cell<usize>,非共享;use Ordering::*;)
let tail = self.tail.load(Relaxed);
if tail.wrapping_sub(self.cached_head.get()) == CAP {
    // 只有看起來滿才碰 consumer 的 cache line
    self.cached_head.set(self.head.load(Acquire));
    if tail.wrapping_sub(self.cached_head.get()) == CAP {
        return Err(item);            // 真的滿
    }
}
// ... 寫 payload、Release store tail

如此大多數 push 完全不碰 consumer 的 cache line,跨 core 一致性流量大減(rigtorp 的經典手法,純 std 多加欄位即可)。完整驗證版是 的 base 版;此處僅示意 delta,表達式皆為合法 Rust。

Q1(指定題) 把 consumer 讀 tail 的 Acquire 誤寫成 Relaxed,給一個會出錯的 interleaving。

                                 // 沒有 acquire 屏障
                                 v = buf[0]                   // 未被排在 load 之後;
                                                              // 可取到 pre-X 的舊/未初始化值 → UB

關鍵:consumer「看到 tail==1」不蘊含「看到 buf[0]==X」。x86 上就算硬體不重排這組,編譯器在 Relaxed 下仍可把 v=buf[0] 提到 tail.load 之前;ARM/POWER 上連硬體都可能讓 tail 的更新先於 buf[0] 的寫入傳播到 consumer 的 core。無論哪條路徑,形式上都是 data race——不是「偶爾讀到舊值」而已。這是 (producer 讀 head 的 Acquire 誤降)的對稱另一半。

Q2 producer 讀自己的 tail 用 Relaxed 安全嗎?為什麼?

安全。producer 是 tail 唯一寫者,同執行緒 store→load 有 sequenced-before + 單位址 read-your-writes,必見自己最新寫入。Acquire 只為看別的執行緒對別的位址的寫入,此處無此需求。

Q3 SPSC 為什麼不需要 SeqCst?什麼情況才需要?

只需 tail、head 兩對 Release/Acquire 的局部 HB;無第三執行緒、無跨獨立變數的全域順序需求。需要 SeqCst 的是 store-buffer litmus(X=1;r1=Y ‖ Y=1;r2=X 禁 r1==r2==0)這種要全域 total order 的場景(見 )。

Q4 head 和 tail 放同一條 cache line 會怎樣?怎麼修?

false sharing:兩 core 各寫其一,cache line 互相 invalidate、ping-pong,吞掉一截吞吐。修:#[repr(align(64))] 讓各佔一條 line(std 無 CachePadded,自己刻)。

Q5 capacity 為什麼要 2 的次方?tail.wrapping_sub(head) 為什麼正確,即使 tail 溢位 wrap 過?
  • 2 的次方 → idx & (capacity-1) 取代 idx % capacity,遮罩比除法快、且是 free-running index 折回 buffer 的正解。
  • wrapping_sub 正確性:真實元素數恆 ∈ [0, capacity](不滿不 push、不空不 pop),而 capacity ≪ 2^64。它算 (tail−head) mod 2^64;真實差值 < 模數時結果即真實差值——即使 tail 已 wrap 過 usize::MAX、head 還沒(此時直接相減會是負,但 wrapping 語義下 mod 2^64 仍給出正確的小差值)。
  • 邊界(他會追問):若差值可能 > capacity 就會誤判——但不變式保證不會;這也是為什麼滿的判斷用 == capacity 而非 >= capacity 就夠(永遠不會衝過頭)。

use std::cell::UnsafeCell;
use std::mem::MaybeUninit;
use std::sync::atomic::{AtomicUsize, Ordering};
use std::sync::Arc;

// std 沒有 CachePadded(那是 crossbeam_utils 的);std-only 就自己刻。
// 64 bytes 是 x86-64 常見的 cache line 大小;有些平台(部分 ARM)是 128。
#[repr(align(64))]
struct CachePadded<T>(T);

impl<T> std::ops::Deref for CachePadded<T> {
    type Target = T;
    fn deref(&self) -> &T { &self.0 }
}

struct Ring<T> {
    buf: Box<[UnsafeCell<MaybeUninit<T>>]>,
    mask: usize,                    // capacity - 1;capacity 必為 2 的次方
    head: CachePadded<AtomicUsize>, // consumer 寫、producer 讀
    tail: CachePadded<AtomicUsize>, // producer 寫、consumer 讀
}

// SPSC 不變式(最多一 producer / 一 consumer)由「只發一組 handle」保證,非型別系統。
unsafe impl<T: Send> Send for Ring<T> {}
unsafe impl<T: Send> Sync for Ring<T> {}

pub struct Producer<T> { ring: Arc<Ring<T>> }
pub struct Consumer<T> { ring: Arc<Ring<T>> }

pub fn channel<T>(capacity: usize) -> (Producer<T>, Consumer<T>) {
    assert!(capacity.is_power_of_two(), "capacity must be a power of two");
    let buf = (0..capacity)
        .map(|_| UnsafeCell::new(MaybeUninit::uninit()))
        .collect::<Vec<_>>()
        .into_boxed_slice();
    let ring = Arc::new(Ring {
        buf,
        mask: capacity - 1,
        head: CachePadded(AtomicUsize::new(0)),
        tail: CachePadded(AtomicUsize::new(0)),
    });
    (Producer { ring: ring.clone() }, Consumer { ring })
}

impl<T> Producer<T> {
    pub fn push(&self, item: T) -> Result<(), T> {
        let r = &*self.ring;
        let tail = r.tail.load(Ordering::Relaxed); // 讀自己的 index → Relaxed
        let head = r.head.load(Ordering::Acquire);  // 與 consumer 的 Release 握手
        if tail.wrapping_sub(head) == r.buf.len() {
            return Err(item);                        // 滿了
        }
        let slot = r.buf[tail & r.mask].get();
        unsafe { (*slot).as_mut_ptr().write(item); } // 寫 payload(non-atomic)
        r.tail.store(tail.wrapping_add(1), Ordering::Release); // 發佈
        Ok(())
    }
}

impl<T> Consumer<T> {
    pub fn pop(&self) -> Option<T> {
        let r = &*self.ring;
        let head = r.head.load(Ordering::Relaxed);  // 讀自己的 index → Relaxed
        let tail = r.tail.load(Ordering::Acquire);   // 與 producer 的 Release 握手
        if head == tail {
            return None;                             // 空的
        }
        let slot = r.buf[head & r.mask].get();
        let item = unsafe { std::ptr::read((*slot).as_ptr()) }; // 讀 payload
        r.head.store(head.wrapping_add(1), Ordering::Release);  // 釋放 slot
        Some(item)
    }
}

impl<T> Drop for Ring<T> {
    fn drop(&mut self) {
        // 把還沒 consume 的元素 drop 掉,避免 leak。
        let (head, tail) = (*self.head.0.get_mut(), *self.tail.0.get_mut());
        let mut h = head;
        while h != tail {
            let slot = self.buf[h & self.mask].get();
            unsafe { std::ptr::drop_in_place((*slot).as_mut_ptr()); }
            h = h.wrapping_add(1);
        }
    }
}
▶ 雙執行緒 FIFO 交叉驗證 harness(點開) 
// 雙執行緒 FIFO 交叉驗證(cap=1 / 2 / 1024)。edition 2024 相容(稽核見上表)。
fn main() {
    use std::thread;
    const N: usize = 2_000_000;

    for cap in [1usize, 2, 1024] {
        let (tx, rx) = channel::<usize>(cap);
        let prod = thread::spawn(move || {
            let mut i = 0usize;
            while i < N {
                // 生產環境用 std::hint::spin_loop();
                // 單核 sandbox 驗證時改用 std::thread::yield_now() 避免 busy-spin livelock。
                match tx.push(i) { Ok(()) => i += 1, Err(_) => std::hint::spin_loop() }
            }
        });
        let cons = thread::spawn(move || {
            let mut next = 0usize;
            while next < N {
                match rx.pop() {
                    Some(v) => { assert_eq!(v, next, "cap={cap}: 亂序或值錯"); next += 1; }
                    None => std::hint::spin_loop(),
                }
            }
        });
        prod.join().unwrap();
        cons.join().unwrap();
        println!("cap={cap:>5}: {N} items 依序通過,無亂序、無遺失");
    }
}

單核環境下 busy-spin 會 livelock(spin_loop() 只是 pause hint,不讓出 OS thread);驗證時把兩處 spin 換成 std::thread::yield_now() 即可,ring 本身不動。
