Runtime 逐元件 lock-free 升級地圖

對象:reference/src/runtime/mini_runtime.rs(行號以它為準)。 問題只有一個:裡面每一把 Mutex,是「不可避免」還是「第一步的正確選擇」? 換成 lock-free 要怎麼換、什麼場景才值得換?
配套程式碼:concurrency/mpsc_list(tokio 遠端 wake queue 同款,本頁 §2 的主角)、 concurrency/mpmc_ring(Vyukov MPMC)。取捨文件:docs/concurrency/mpsc_list.md。

§0 解剖圖:同步點在哪裡

§1 決策框架:換之前先問三題

  1. 誰在摸它?(單執行緒獨佔 → 鎖是型別稅;跨執行緒 → 才有題目)
  2. 是「契約逼的」還是「實作選的」?(Waker: Send+Sync 是 std 契約, run queue 的執行緒安全躲不掉;reactor 的大鎖只是實作方便)
  3. 換了買到什麼?先量再換——低競爭時 Mutex 常常更快:
操作量級備註
uncontended Mutex lock+unlock~20 ns一來一回各一次 CAS,無 syscall
contended CAS(cache line 轉移)~40–100 nslock-free 也逃不掉的物理成本
futex 陷核(鎖排隊)~1–2 µsMutex 高競爭時的真正代價
Box 配置(mpsc_list 每 push)~20–50 nslock-free 的隱藏帳單之一
epoll_wait 空轉一圈~1 µssyscall 底價
SLEEP_CAP 保底(mini_runtime)20 ms喚醒最壞延遲——本頁最大的數字
面試句:"The first question isn't how to remove the lock — it's whether anyone is actually waiting on it. An uncontended Mutex is ~20ns; a contended cache line is ~100ns either way. Lock-free buys you no-syscall worst case and no-blocking guarantees, not free throughput."

§2 run queue Mutex → mpsc_list

現況(:183)
queue: Mutex<VecDeque<Arc<Task>>>
push:任何執行緒的 wake()(:198)、spawn()(:215)
pop:只有 block_on 執行緒(:317)→ 形狀是 MPSC
為什麼躲不掉「某種」同步
std::task::Waker 型別是 Send + Sync——契約允許 waker 被 clone 到任何執行緒去 wake(file_io_offload 的 worker 就這麼做)。單執行緒 RefCell 版直接不合法。
lock-free 怎麼換
換 concurrency::mpsc_list(Vyukov):push = 一個 swap + 一個 store,wait-free、不會失敗;pop 單 consumer 免 CAS。 Inconsistent(縫)→ yield 重試,見 §6 stepper。
什麼場景才值得
①wake 頻率高且來自多條執行緒(timer/IO/worker 同時轟) ②wake 端延遲敏感(不能被 futex 排隊卡住) ③喚醒路徑要「絕不阻塞」的硬保證(訊號處理、audio callback)。 單執行緒 runtime + 低 wake 率?留著 Mutex,它是冷路徑。
生態對照:tokio 的 run queue 是三層——per-worker 固定大小 local ring (單擁有者 + 竊取者,Chase-Lev 家族)+ LIFO slot(atomic,cache 熱度) + 全域 inject queue 至今就是一把 Mutex(冷路徑);跨執行緒 remote wake 走的正是 Vyukov intrusive MPSC——mpsc_list 的原型。 「tokio 裡也有 Mutex」是面試裡最好用的一句話:鎖不是髒字,熱路徑才是戰場。

§3 poller Mutex → 其實 kernel 已經幫你上好了

現況(:184, :336)
reactor: Mutex<Reactor>,而且 ③ 是握著鎖呼叫 poller.wait(20ms)——抱著鎖睡覺。
為什麼這裡它無害
arm/disarm 只在 poll task 時呼叫,而 poll 只發生在 block_on 執行緒 ——單執行緒獨佔,zero contention。這把鎖是讓 Arc<Inner> 過 Sync 的型別稅。
lock-free 怎麼換
關鍵事實:epoll 是 kernel 保證執行緒安全的—— epoll_ctl 可與另一條執行緒的 epoll_wait 並發, syscall 層根本不需要 user-space 鎖。要拆的只有 Rust 側物件: poller 本體用 &self + raw fd(它天生 Sync), 絕不把任何鎖握過 wait()。
什麼場景才值得
多執行緒 runtime(多 worker 同時 arm/disarm)。thread-per-core (monoio/glommio)反向操作:Handle 做成 !Send, 整把鎖連型別稅一起消失——RefCell 就夠。

§4 interest table Mutex 裡的紫色部分 → sharded slab + per-entry 狀態

現況(:179)
wakers: FdRegistry<Waker>(token→waker 的世代 slot map), 跟 poller 關在同一把大鎖裡。arm 寫(:227)、收割讀(:343)。
這才是真正的共享狀態
多執行緒下 arm(poll 側)與收割(reactor 側)在不同執行緒—— 這不是型別稅,是真同步需求。大鎖的問題:每個 fd 的 arm 都跟 所有 fd 的收割互斥,N 個連線共享一個鎖倉。
lock-free(-ish)怎麼換
tokio 的 ScheduledIo slab:①slot 尋址無鎖(index+generation, fd_registry 的世代招)②readiness 是 per-entry AtomicUsize(CAS 更新)③waker 槽用 per-entry 小鎖 (waker clone 不是原子操作,鎖窄到只剩它)。 大鎖 → 每個 entry 自己的同步:競爭從 O(全部) 降到 O(同一個 fd)。
什麼場景才值得
連線數 × worker 數都大(萬級 fd、多 worker 同時 arm)。 幾十個 fd 的嵌入式 bridge?大鎖完全夠——這正是 mini_runtime 的取捨。
抽象的教訓:「把一把大鎖換成無鎖」通常是假命題,真答案是 「把一把大鎖拆成 N 個 per-entry 的小同步點」——sharding 的極限形式。 跟 sharded_map(per-shard Mutex)、hw_bridge sharded server(per-conn shard)是同一條公理:縮小共享,而不是消滅鎖。

§5 Task.future Mutex → 原子狀態機;RootWake 已無鎖

現況(:189, :321)
future: Mutex<Option<Pin<Box<dyn Future>>>>—— 保證同一時刻只有一人 poll 這個 task;None = 已完成, 之後的 spurious wake 變 no-op。
lock-free 怎麼換
tokio 的 task 狀態是一顆 AtomicUsize 位元場狀態機: IDLE / RUNNING / NOTIFIED / COMPLETE 全走 CAS。 殺手級好處不是省鎖,是解掉「poll 進行中又被 wake」: CAS RUNNING→NOTIFIED 記下這筆,poll 完看到 NOTIFIED 就自我重排—— wake 不丟、也不用把 waker 塞回鎖裡。
什麼場景才值得
多 worker 搶著 poll 同一批 task(work-stealing)時是熱路徑必需品。 單執行緒 executor 裡這把鎖永遠 uncontended——mini_runtime 留 Mutex 是正確的第一步。
RootWake.woken(:254)
AtomicBool + swap(AcqRel)——已經是 lock-free, 而且是「訊號帶狀態」的最小形式:wake 先於 check 不會丟 (對照 executor 的 park token、eventfd 的 8-byte 計數,同一個靈魂)。

§6 醒來的路:SLEEP_CAP 20ms → eventfd doorbell

mini_runtime 最大的延遲不在任何鎖裡:remote wake 只是把 task 放進 queue, 沒有任何機制打斷 ③ 正在睡的 epoll_wait → 最壞等 20ms(:173 的自白)。 升級不是換資料結構,是把 wake 接進 poller 的事件宇宙: eventfd 註冊進同一個 epoll,remote wake 時寫 8 bytes → epoll_wait 立刻返回。event_loop.rs 的 WakeHandle/WAKE_TOKEN 就是完整示範(你 7/20 深讀過的 qa_eventfd_doorbell)。

升級後的完整多執行緒圖:wake = mpsc_list.push(wait-free) + eventfd 寫一下(有 doorbell 才需要)→ 喚醒延遲從「最壞 20ms」變「一次 syscall」。 queue 換無鎖但不裝 doorbell = 白換:延遲被 20ms 蓋住,誰也看不到你的 nanoseconds。

§8 追問鏈(面試官會這樣一路挖)

L1:「你說 run queue 可以換 lock-free MPSC——為什麼不用你剛寫的 MPMC ring?」

①形狀不對:pop 只有 executor 一人,MPMC 的 head 端 CAS 是白付的錢; ②bounded 是錯的性質:wake 絕不能因為「佇列滿」而失敗或阻塞——丟 wake = task 永眠。 unbounded MPSC 的記憶體帳由上游保證(task 數有界)。選型先看形狀與失敗語意,再看速度。

L2:「mpsc_list 的 push 為什麼 wait-free,而 mpmc_ring 的 push 只是 lock-free(-ish)?」

swap 是無條件 RMW——硬體保證一次完成,沒有失敗路徑,每個 push 恰好兩步, 與競爭者數量無關 ⇒ wait-free。CAS 是有條件 RMW——輸了要重試,理論上可以 一直輸 ⇒ 至多 lock-free。而兩者其實都卡同一道縫(佔位≠發布), 所以嚴格說都不滿足 lock-free 的全系統進度定義:lockless 是誠實的用詞。

L3:「你說單 consumer 免 reclamation——多 consumer 到底哪裡壞掉?」

釋放者不唯一後,「我越過的節點沒人再碰」不再成立:C1 讀著節點 X 時, C2 可能已經越過並 free 了 X——use-after-free。這正是 epoch(crossbeam)/ hazard pointer 存在的理由:讓「還有人在讀」變成可觀測。單 consumer 是用 型別系統(Consumer: !Clone + &mut self)把整台機器拆掉。

L4:「interest table 用 per-entry 原子狀態——waker 那格為什麼還是要小鎖?」

Waker 是兩個字寬(data + vtable)還帶 clone/drop 副作用, 不是一條 CAS 換得掉的 POD。tokio 的做法:readiness(usize 位元場)走 CAS, waker 槽用窄鎖——混合設計才是常態,「全 lock-free」是投影片,不是工程。

L5:「如果面試官逼你:這個 runtime 全面 lock-free 化,你第一個動哪裡?」

反問負載形狀(先 clarify):幾條執行緒?wake 率?fd 數?然後照順序: ①先裝 eventfd doorbell(20ms → 1 syscall,最大的數字先殺) ②wake 熱就換 run queue = mpsc_list ③fd 多 worker 多才拆 interest table ④task 狀態機留到 work-stealing 才有意義。每一步都「量了再動」—— p99 沒動的優化是負分。

§9 Self-quiz(先答再翻)

Q1:mini_runtime 的兩把 Mutex,哪一把在單執行緒下其實從不競爭?為什麼還是需要它?

reactor 那把(:184)。arm/收割全在 block_on 執行緒。需要它是因為 Arc<Inner> 要跨執行緒(Handle/Waker),型別系統要求 Sync ——「型別稅」。拆法:承諾 thread-per-core(!Send)用 RefCell, 或多執行緒化時拆成 per-entry 同步。

Q2:run queue 的執行緒安全是誰逼的?能不能用 RefCell?

Waker: Send + Sync 的 std 契約逼的——wake 可以來自任何執行緒。 RefCell 不合法(除非整個 executor 走 !Send 設計且不外洩 waker, 但 std Waker 做不到「不外洩」)。

Q3:「queue 換成 lock-free 之後 wake 延遲還是很爛」——最可能的原因?

doorbell 沒裝:runtime 正睡在 epoll_wait(20ms) 裡, push 再快也要等它自己醒。先修最大的數字(20ms),再修 ns 級的。

Q4:mpmc_ring 為什麼 cap=1 不合法?一句話。

「已發布」(pos+1)與「下一圈輪空」(pos+cap)在 cap=1 時同值, 三態塌縮 → producer 會把未消費的資料當空槽覆寫。

Q5:tokio 明明是 lock-free 的代表作,哪裡還留著 Mutex?這告訴你什麼?

全域 inject queue、ScheduledIo 的 waker 槽(per-entry 窄鎖)、各種冷路徑。 教訓:工程上的答案是「熱路徑無鎖、冷路徑用鎖、共享縮到最小」, 不是意識形態的全面無鎖。
