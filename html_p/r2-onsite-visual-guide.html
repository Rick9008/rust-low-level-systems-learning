這個題型長什麼樣(R1 實測)

R1 的形式和 repo 裡 a–h 彩排最大的差別:不是從零手搓一個資料結構,而是拿到一大段英文 spec、一排已經寫好的 API、和一個 todo!() 的函式。spec 是有洞的,面試官是唯一 oracle——你問到的答案就是 spec 的一部分。閱讀量比想像大,文本分析本身是考點。

R1 暴露的兩個洞(這一輪的練習主軸)

  1. 英文對談雙向 repair:自己的構句對方有時聽不懂,要重講;對方的話有時要請他重講。處方 = rephrase 句庫 + 「複誦式確認」升為預設動作(→ Tab 4 對白道場)。
  2. 長 spec 的閱讀策略:快速定位「哪些 todo 是骨幹、哪些是配菜」沒練過。處方 = 下面的「API 三堆分類法」,拿到題先做這一步。

第一動:把 provided API 分成三堆

拿到一排 API 別逐行精讀。先按「它在事件迴圈裡扮演什麼」分堆,分完 reactor 骨架自動浮現——這一步大約 90 秒,換來的是整場的方向感:

事件源(等待/拉取)

get_dma_request() get_dma_result_done() wait_event()
迴圈的「醒來的理由」。每一個 get_* 都要問:回 None 是「現在沒有」還是「永遠沒了」?

動作(改變世界)

send_dma_request_to_engine(...)
派工。呼叫它之前,你的 state 表要先答得出「派給誰、派什麼」。

回報(對外承諾)

submit_dma_request_result_done(id)
合約的終點。什麼條件下才能呼叫它,就是這題的正確性不變量。

然後給每個名詞一張表:題目裡有 request、有 engine,就有 request 表和 engine 表;每個事件一條路由:「engine 5 做完了」這個事件要能沿著表走回「那是 request A 的第 5 塊」。state 放哪、誰持有——這才是題目的 difficulty,不是演算法。

通用骨架:reactor 五步

R1 的 run_dma_loop、sim i–n 的 run(),全都是同一個形狀。默到能閉眼寫:

loop {
    wait_event();                       // 1. 睡到有事(醒來只是提示,不是保證)
    while let Some(r) = get_request()   // 2a. 收乾新請求:登記進 request 表
        { register(r); }
    while let Some(e) = get_done()      // 2b. 收乾完成事件:沿 owner 表路由回 request
        { route_done(e); }
    dispatch();                         // 3. 派工派到「沒空引擎」或「沒待派工作」為止
    submit_finished();                  // 4. 檢查誰的計數歸零 → 對外回報
}

「收乾」(drain)是關鍵字:每次醒來把兩個事件源都 while-let 抽到 None,才回去睡。只抽一個就睡,另一邊的事件可能永遠等不到下一次喚醒。

R1 的洞,和它的正解

R1 當場的解法是 sequential:一次處理一單,用「剩餘塊數歸零 且 空閒 queue 長度回到 6」當完成判定。這個判定只在單 request 模式下成立——一旦兩單同時在飛,「engine 空不空」和「哪一單完成了」就再也沒有關係。

完成判定只有一個正解:per-request 計數歸零(done == blocks_total)。
任何借「engine 空閒度」推斷完成的判定,在 pipeline 下都是巧合正確。這是 sim i 要親手關掉的洞。

三張表(sol_sim_i_dma 的骨架)

表型別回答的問題誰動它
freeVecDeque<engine_id>誰有空?派工時 pop,收到 done 時 push
owner[Option<(req_id, block)>; 6]這台 engine 在做誰的哪一塊?派工時寫入,done 事件靠它路由,路由完清空
reqsHashMap<req_id, ReqState>每一單派到哪、完成幾塊、在飛幾塊?register 建、route_done 更新、歸零時 submit + 移除

外加一條 queue: VecDeque<req_id>(還有塊沒派完的單,FIFO)。done 事件只給你 engine id——沒有 owner 表,事件就路由不回正確的 request,這是三張表裡最不能省的一張。

互動 stepper:pipeline 分水嶺劇本

劇本(即 sol 的 Dry-Run scenario 2):A = 6 塊、B = 1 塊幾乎同時到達;engine 完成順序是 LIFO(最後派的先回來)。看 pipeline 版怎麼讓 B 先完成——sequential 版在同一個劇本下,B 永遠排在 A 後面。

看完 stepper 要能講出來的三句話(英文版在 Tab 4 場景四)

  • done 事件只帶 engine id,所以路由靠 owner 表;先 take() 確認這台 engine 真的在做這一單,才動計數。
  • B 能插進來,是因為派工看的是「free 有沒有人 + queue 有沒有單」,跟 A 完成與否無關——這就是 pipeline。
  • B 先 submit 不是 bug:完成判定是 per-request 的 done == blocks_total,單與單互不相干。

sol 檔頭的三個 trade-off(讀完要能複誦)

  • 派工順序 FIFO 填滿:先來的單先吃滿 engine——實作最短、單內延遲最低;代價是大單會餓小單。要公平就換 round-robin(queue 輪轉),多約 5 行。
  • cancel 採惰性收尾:停止再派 + 在飛的塊等它自然 done 但不計數。不能「立刻拔 engine」——硬體上沒有搶佔這回事。
  • 0 塊的單:沒有工可派,收單即完成(boundary,register 時就 submit)。

這一頁只給概念地形:每題的場景、硬約束、和上場前值得問的 clarify 種子。刻意不給解法——解法要在計時場上自己長出來,寫完再開 sol_sim_*.rs 對答案。五題共用同一個 reactor 骨架(Tab 1),差別全在「事件源是誰、硬約束是什麼」。

積木圖鑑五題共用的硬體零件——每顆是什麼、為什麼存在、你的 code 怎麼碰它先讀這節再進各題(8/3 增訂)

寫服務端軟體的人第一次碰硬體題,霧的來源通常不是演算法,是名詞背後沒有物理圖像。這節把五題的零件一顆一顆放上桌。

0. 全景:桌上其實只有三個東西

所有硬體題的共同世界觀:device 是「另一個讀者/寫者」,而且不歸 Rust 記憶體模型管。你們唯一的溝通方式是這張桌面(共享記憶體)加上幾個裝在它身上的信箱(暫存器)。五題全部都是「跟一個看不見你程式序的同事協作」的故事。

1. MMIO 暫存器——裝在 device 身上的信箱

是什麼:一些「地址長得像記憶體、背後其實是硬體零件」的格子。你 mmio_read/mmio_write 的時候不是在讀寫 RAM,是在撥動 device 身上的開關 / 看它掛出來的牌子。為什麼存在:device 內部的狀態你摸不到,它只把「你需要知道的」用暫存器掛出來、把「你可以命令的」做成可寫的格子。兩個物理事實:每個暫存器有方向性——唯讀的是進度牌(SubmitHead、CompTail),唯寫的是按鈕(Doorbell);MMIO 是 uncached 的慢路(百 ns 到 µs 級),所以真驅動能批次就批次,不每筆都按鈴。

2. ring(格子架)+ descriptor(工單)——為什麼硬體世界什麼都是環

descriptor = 固定格式的小工單(這裡是 tag + payload):tag 是你寫的單號、之後認領完成用;payload 是工作內容,你不解釋、只搬運。ring = 一排固定數量的格子,用單調遞增序號取格:slot = seq % cap。為什麼是環不是鏈表:硬體只會數數,不會追指標——它能做「從 head 號拿到 doorbell 號」這種算術,做不了 malloc 和 pointer chasing。ring 放在普通共享記憶體上,所以你寫格子就是普通的記憶體寫(slot_write),不走 MMIO。

3. doorbell(門鈴)——為什麼放了貨還要按鈴

因為 device 不會盯著你的記憶體看——要它輪詢你的 RAM 太貴也太蠢。你把工單放好之後,寫一次 Doorbell 暫存器告訴它「我的 tail 現在到 N 了」。注意寫進去的值就是你的新 tail:門鈴同時是「有事了」的訊號和「到幾號」的公告,一石二鳥。

4. barrier(牆)——兩條郵路的問題

① slot_write
普通記憶體寫:走 cache/store buffer,可能在路上排隊
vs
② doorbell
MMIO 寫:uncached 直達

兩種寫走不同的郵路,抵達順序不保證跟你的程式碼順序一樣——對你自己永遠看不出差別,但 device 是另一個觀察者:沒有牆,鈴聲可能比貨先到,它開格子讀到半張工單。barrier() 的合約一句話:「我之前的所有寫入,先讓所有觀察者看得見,才准放行之後的寫入」。這就是「先值後訊號」定理的硬體版(fanin 的 push→wake、waker 的 set-result→wake、spin_lock 的 Release,同一個瓤)——只是對面是矽,語言層的 Ordering 管不到它,得用顯式柵欄。

5. completion ring——同一套零件反著轉

device 做完工,把成品(帶著你的 tag)寫進另一條 ring、推進它的 CompTail 進度牌。你收貨的鐵律跟出貨對稱:先讀進度牌(CompTail),再碰牌子以前的格子——acquire 方向。成品自帶 tag,所以就算 device 亂序完成,你也不用猜是哪筆:tag 自己認路。

規律:自己的游標自己存,對方的游標當場讀,永遠不要抄一份別人的進度(抄了就會過期——sim m 的 stale 鬧鐘就是這麼死的)。而「driver」這個詞聽起來嚇人,其實就是這幾個計數器 + 兩三個函式:一本記事本,不是執行緒、不會自己跑。

7. DMA engine(搬運工)——sim i / m 的主角

是什麼:會自己動的搬運零件。你給它「從哪搬、搬多少」(一個 block 的位址與長度),它就不經過 CPU 自己把資料搬完,然後回報一聲 done。為什麼存在:不然 CPU 要一個 byte 一個 byte 端盤子,什麼正事都別做了。它的殘酷面:done 訊號通常只告訴你「幾號搬運工完工」,不附工單——誰派給它什麼,得靠你自己的綁定表記得(sim i 的 owner 表、sim m 的整套 watchdog 都長在這件事上)。

8. IRQ / ISR(插隊電話)——sim j 的主角

IRQ = device 打給 CPU 的插隊電話:「我有事,現在」。CPU 接起來跑的那段短程式叫 ISR(中斷服務程式)——它是劫持了某顆核當下的執行,不是一條執行緒,所以三禁:不能配置記憶體、不能阻塞、不能做慢事。跟 polling 的對照:polling 是你一直打去問「好了沒」,IRQ 是它好了打給你——低負載時 IRQ 省電省 CPU,高負載時電話響不停反而不如你定期去問(NAPI 就是兩者的混血)。

9. watchdog / timeout——當硬體沉默(sim m 的主角)

硬體會壞、會 hang,而且壞的時候通常一聲不吭。沒有 health API、沒有 error 訊號時,你唯一的觀察手段是時間:「正常 10ms 會回來的東西,30ms 沒回來就當它死了」。這是一場賭——「慢」和「死」從軟體內部無法區分(能給確定性的只有 reset/fence 這類硬體幫忙)——所以 timeout 值要對著誤判成本選,而 deadline 是事件迴圈的第三種事件:前兩種(新請求、完成)是別人推給你的,這種是你自己排的。

ISR 三禁:不能配置記憶體、不能阻塞、不能做慢事。所以 push 端必須是 try_push(wait-free)——在中斷 context 裡,「等一下」不是效能問題,是正確性問題(這正是卡#5 的皇冠句)。這題就是 signal_pipeline 的 spec-heavy 版,7/31 白天先複讀那一頁 30 分鐘再上。

互動 stepper:一次 burst 的一生(政策這裡示範 drop-newest+計數;上場用哪個由 clarify 決定)

"What should happen when the ring is full — drop the newest sample, the oldest, or just count the loss?"
ring 滿了掉誰?掉新的、掉舊的、還是只記數?——overflow policy 是這題 spec 的天然洞,答案決定你的 push 端長相。

場景一:開場定界 + 挖 spec 洞(clarify 的標準開局)

官
"Here's the problem. Take a moment to read it, and feel free to ask questions."
(丟出長 spec)讀一下,有問題儘管問。
你
"Before I write any code, let me make sure I understand the setup: we have six engines, requests arrive through get_dma_request, and my job is to feed blocks to engines and report each request once all of its blocks are done. Is that right?"
寫 code 前先確認設定:六台 engine、request 從這支 API 進來、我的工作是餵塊給 engine,整單全部完成才回報。對嗎?
官
"That's right."
對。
你
"A few questions then. First, the big one: do requests need to make progress concurrently? Concretely — if a second request arrives while the first is still in flight, may it simply wait, or should it start using idle engines right away?"
先問最大的:多單要同時推進嗎?具體說——第二單到達時第一單還在飛,它可以排隊等,還是應該馬上用空著的 engine?
官
"Assume multiple requests can be in flight at once. Don't serialize them."
假設多單同時在飛,不要串行化。
你
"Got it — so I'll track per-request progress instead of assuming one at a time. Next: when get_dma_result_done hands me an engine id, does it also tell me which block or which request that was? Or do I keep that mapping myself?"
了解——那我就要記每一單各自的進度,而不是假設一次一單。下一個:done 事件給我 engine id 的時候,會告訴我那是哪一塊、哪一單嗎?還是要我自己記?
官
"It only gives you the engine id."
只給 engine id。
你
"Then I'll keep an owner table on my side. Last one for now: does wait_event guarantee something is ready when it returns, or can it wake spuriously?"
那我自己這邊維護一張 owner 表。最後一題:wait_event 回來保證有事嗎,還是可能空醒?
官
"Treat wakeups as hints. Always re-check."
把喚醒當提示,每次都要重查。
你
"Let me restate the contract before I code: multiple requests in flight; done events carry only the engine id, so routing is on me; wakeups are hints, so every wait is followed by a drain-and-recheck loop. Did I miss anything?"
動筆前複誦合約:多單同飛;done 只帶 engine id,路由我自己負責;喚醒只是提示,所以每次醒來都收乾再重查。有漏嗎?
為什麼有效:最後那句複誦不是禮貌,是驗收——你把「問到的答案」組裝回一個合約,面試官點頭的那一刻,spec 的洞才算補上。R1 面試官點名稱讚的就是這個動作;g#1 的教訓(「drain 語意答了還掉」)的處方也是它:答案要複誦回去才算收到。

你
"So the thing is, when the engine that, uh, the completion comes back, I need to know which one it was for, because otherwise the counting of the, the request that owns it…"
(句子纏在一起了——engine、completion、計數、request 全擠在同一句)
官

我沒跟上。

我講簡單一點。兩張表。第一張回答:哪些 engine 有空。第二張回答:這台 engine 的結果屬於哪一單。engine 做完,我查第二張表,幫那一單的計數 +1。
官
"Ah, got it. So the second table is your routing."
懂了,第二張表就是你的路由。
為什麼有效:重講的公式 = 短句 + 一句一事 + 幫東西取名字("table one / table two" 之後整場都能引用)。卡住時先說 "Let me say that more simply" 爭取兩秒重組——這句話讓重講看起來像溝通技巧,而不是英文破。

場景四:邊寫邊講(narrate-while-coding)

你
"I'll start with the simple version and tighten it after it works — first the loop skeleton, then the routing."
先寫能動的簡單版,會動了再收緊——先迴圈骨架,再路由。
你
"I know this line is subtle, so let me explain why the order matters: I bump done only after the take() confirms this engine really was working for this request. If I bump first and check later, a stale completion corrupts the count."
這行很細,講一下順序為什麼重要:我先用 take() 確認這台 engine 真的在替這一單做事,才把 done 加一。先加再查的話,一個過期的 completion 就把計數弄髒了。
你
"Quick sanity check before I move on: zero-block request — no work to dispatch, so I report it complete right at registration. Let me trace one boundary out loud: request B has one block, engine five frees up, B's block goes out, comes back, counter hits one-of-one, submit."
往下寫之前快速自檢:0 塊的單沒有工可派,登記當下就回報完成。口頭走一條邊界:B 一塊,engine 5 空出來,B 的塊派出去、回來,計數 1/1,submit。
為什麼有效:R1 證實了 narrate 就是考試本體——寫完即壓線、boundary test 零時間的那一場,「口頭 trace 不變量」是唯一的正確性展示載體,而且面試官被說服了。三句骨架:宣告策略(simple first)→ 解釋微妙行(why the order matters)→ 口頭走邊界(trace out loud)。

場景五:時間不夠的收尾 + trade-off 三拍

官
"We have about three minutes left."
剩三分鐘。
你
"I'm running short on time, so let me describe what's left and where the holes are. The dispatch path and completion routing work. What I haven't handled: engine failure — right now a hung engine silently strands its request; and I'd want a real test for the out-of-order completion case I only traced verbally."
時間不夠了,讓我把剩下的和洞在哪講清楚。派工路徑和完成路由是好的。還沒處理的:engine 故障——現在一台 hang 住的 engine 會讓那一單卡死;另外亂序 completion 那條我只口頭走過,想補一個真的測試。
你
"On the design itself, three trade-offs. The price I paid: FIFO fill is simplest and gives the lowest per-request latency, but a large request can starve a small one. The road not taken: round-robin across requests — fairer, about five more lines, slightly worse locality. Where this design holds: as long as completions are the only feedback channel and engines don't fail; add failures, and I'd need deadlines per in-flight block."
設計本身講三拍。付的代價:FIFO 填滿最簡單、單內延遲最低,但大單會餓小單。沒走的路:跨單 round-robin——更公平,多五行,locality 略差。有效範圍:只要 completion 是唯一回饋通道、engine 不故障,這設計就成立;要容錯,就得幫每塊在飛的工作記 deadline。
為什麼有效:R1 的教訓——時間不夠時,主動把洞講出來比被抓到強;而且「我知道洞在哪」本身就是訊號(JD 原話:finding your own bug = stronger signal)。收尾三拍公式(7/26 定版):價格 → 沒走的路 ≥2 條(用軸開頭)→ 有效範圍。

場景六:Phase 2 加需求的接法

R1 的節奏是「Phase 1 驗收後口頭加需求」。第一動作不是寫 code,是把新需求丟回「什麼不變/什麼變」的篩子——面試官驗收的是你改設計的過程,不是打字速度。(例子用 sim i 題本明列的 cancel 軸)

官
"Nice. Now let's extend it: a request can be cancelled while it's in flight."
不錯。現在加需求:request 在飛行途中可以被取消。
你
"Let me check what that changes in my current design before I type. What survives: the three tables and the loop shape. What changes: a request needs a cancelled flag, and dispatch must skip cancelled requests. One question first: the blocks already on engines — can I abort them, or does hardware finish what it started?"
動手前先過一遍「什麼不變/什麼變」。不變:三張表和迴圈形狀。變:request 要加 cancelled 旗標、派工要跳過已取消的單。先問一題:已經在 engine 上的塊——可以中止嗎,還是硬體開工就一定做完?
官
"No abort. Hardware finishes what it started."
不能中止,硬體開工就做完。
你
"Then cancellation is lazy: stop dispatching new blocks, let in-flight blocks drain without counting them, and reclaim engines as they report. I'll add the flag and the two checks — about six lines."
那 cancel 就是惰性的:不再派新塊、在飛的塊讓它自然回來但不計數、engine 邊回報邊回收。加一個旗標、兩個檢查,大約六行。
為什麼有效:「What survives / what changes」這對句把 Phase 2 變成增量設計題而不是重寫題;先問 abort 語意再動手,是因為答案直接決定 cancel 的形狀(能中止 = 主動收回;不能中止 = 惰性收尾)。這正是 sol_sim_i 檔頭 cancel trade-off 的口語版。

六題 30 秒英文定界(遮住英文欄,自己先講,再對)

定界宣言 = 讀完 Phase 1 之後、clarify 之前的第一段話:用自己的話把「資源、事件、我的工作、完成條件、形狀」講回去。骨架:"We have [resources]. [Events] arrive through [APIs]. My job is to [goal], and report when [invariant]. The shape is an event loop: wait, drain, dispatch, report. Before I code, I need to pin down [top clarify]."

i · DMA dispatcher — "We have six DMA engines; requests arrive carrying a run of consecutive blocks, and an engine takes one block at a time. My job is to keep the engines busy across multiple in-flight requests, and report each request when its own counter says all blocks are done. Shape: a reactor loop over three tables — free engines, owner routing, per-request progress."
六台 engine;request 帶連續塊、engine 一次一塊;多單同飛下把 engine 餵滿,per-request 計數歸零才回報。形狀 = 三張表上的 reactor 迴圈。
j · ISR pipeline — "An ISR fires in interrupt context when the sensor FIFO crosses a watermark. Samples must reach a logging thread without ever stalling the interrupt path — so the ISR only try-pushes into an SPSC ring and rings a doorbell; the worker drains and does the slow logging. The clarify that shapes everything: the overflow policy."
ISR 在中斷 context 只做 try_push + 按鈴;慢事全在 worker。定生死的 clarify = overflow policy。
k · per-core fan-in — "N cores each produce telemetry and must never block. One SPSC ring per core; a single aggregator drains them round-robin and parks when everything is empty. Clarify first: fairness across cores, and who calls unpark."
每核一條 SPSC、producer 永不阻塞;aggregator 輪詢 + 全空才 park。先問公平性與誰負責 unpark。
l · MMIO queue — "I drive an accelerator through a submission ring and a completion ring. The iron rule: write the descriptor, barrier, then ring the doorbell — in that order, so the device never reads a half-written descriptor. Clarify first: are completions in order, and what exactly does a completion entry carry."
鐵律 = 上架 → 牆 → 按鈴。先問 completion 保不保序、entry 裡帶什麼。
m · watchdog — "Same dispatcher, but engines can hang and never report. Time becomes the third event source: every dispatch records a deadline, the wait gets a timeout, and expiry means re-dispatch — but only if re-execution is safe. Clarify first: is the operation idempotent, and can a declared-dead engine still report later."
時間成為第三種事件:派工記 deadline、等待帶 timeout、過期重派。先問冪等與殭屍回報。
n · priority + DAG — "Four worker slots; jobs carry a priority and, later, dependencies. Two gates in series: the dependency gate decides who is runnable, the priority heap decides who goes first — with a sequence number breaking ties FIFO. Clarify first: is preemption expected when a hot job arrives."
兩道閘:依賴閘決定 runnable、heap 決定先後、seq 破平手。先問要不要搶佔。

1. 為什麼「空閒 queue 長度回到 6」在 pipeline 下是錯的完成判定?正解是什麼?

「engine 全空」是全域性質,「某一單完成」是 per-request 性質——多單同飛時兩者無關:A 還剩塊在飛時 B 已經可以完成,而「全空」可能因為 B 的塊在飛而永遠等不到。正解:每單記 done == blocks_total,計數歸零即 submit,單與單互不相干。任何借 engine 空閒度推斷的判定都是巧合正確(只在單 request 模式下碰巧成立)。

2. done 事件只給 engine id,路由靠哪張表?那張表的 entry 什麼時候寫、什麼時候清?

靠 owner: [Option<(req_id, block)>; 6]。派工時寫入(engine i 開始替 req r 做 block b);done 事件到達時 take() 讀出並清空,沿著它把計數記到正確的 request 上。先 take 確認、再動計數——順序反了,過期/意外的 completion 會弄髒帳。

3. MMIO 提交的鐵律三步是什麼?為什麼順序不可換?

① slot_write(descriptor)(貨上架)→ ② barrier()(對 device 也有效的牆)→ ③ 寫 doorbell(按鈴)。device 一看到 doorbell 就會去讀 descriptor;沒有牆,CPU/互連可能讓 doorbell 先到、descriptor 後到,device 讀到半成品。這是「資料先於通知 + 中間一道牆」原則的硬體版。

4. ISR 三禁是哪三件事?為什麼 push 端必須 wait-free?

不配置記憶體、不阻塞、不做慢事(log/IO)。中斷 context 裡沒有「等一下」——你擋住的可能是整顆 CPU 的中斷處理;所以交棒只能 try_push(失敗就走 overflow policy),wait-free 在這裡是正確性需求,不是效能偏好。

5. watchdog 要 retry 一塊工之前,最關鍵的 clarify 是什麼?為什麼?

「重做這塊安全嗎(idempotent)?被判死的 engine 事後又完成了怎麼辦?」冪等性決定敢不敢 retry:重做會毀資料的操作,超時後只能報錯不能重派;而「雙重完成」決定計數要不要防重(同一塊完成兩次只能算一次)。

6. 面試官講太快沒聽清,你的前三句依序是什麼(英文)?

① "Sorry, could you say that again? The audio cut out a bit."(請重講,歸因音訊)② "Just to confirm, you said [my paraphrase] — right?"(複誦求證)③ "When you say [X], do you mean [A] or [B]?"(模糊詞逼成二選一)。鐵律:絕不裝懂。

7. 收尾 trade-off 三拍的公式?

價格(我的設計付了什麼代價)→ 沒走的路 ≥2 條(每條用軸開頭:公平性軸、延遲軸、容錯軸……)→ 有效範圍(這設計在什麼假設下成立、假設破了要改什麼)。時間不夠時先講「剩什麼 + 洞在哪」再進三拍。
