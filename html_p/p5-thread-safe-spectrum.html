把 X 變 thread-safe:完整決策光譜

std-only(禁外部 crate)· Rust edition 2024 · 由簡到繁,重點是「何時停在哪一站」
錨:面試被問「怎麼把它變 thread-safe」,沿光譜由簡到繁走一遍就是最強答案; 一開口就跳 lock-free 顯得沒判斷 —— 你要展示的是「知道每一站的成本、也知道在哪一站停下來剛好夠」。

怎麼用這份

1. 先讀 ① 推導:從一把大鎖開始,每一站都是「上一站的失敗模式逼出來的修法」。狀態變數都在這裡建立,後面 stepper 不會憑空冒出新符號。

2. ② 決策光譜 是可點開的 tradeoff 速查(讀 / 寫 / reclamation / 場景 / 何時「不要」)。

3. 面試臨場:把 資料結構對映 當 cheat sheet,先講預設站位再講為什麼。

核心心法:停在「能滿足需求的最高站」。往下走每一站,都是拿通用性 / 實作簡單度換更少的 blocking。 沒有需求逼你下去,就別下去 —— 一把 Mutex 正確又零負擔,常常就是對的答案。

站 0 · coarse Mutex<T>(起點)

◆ 作法:最直接 —— 整個結構包一把鎖,任何存取都拿排他鎖。永遠正確、實作零負擔。

◆ 代價:讀不能並行;一把鎖是單一 contention 點;臨界區一長就把所有 thread 串行化。

→ 什麼時候不夠:讀多,或存取其實分佈在不同 key 上 —— 一把鎖白白吃掉並行度。把鎖切開。

▼

站 1 · sharded lock

◆ 上一站痛點:單點 contention。

◆ 修法:依 hash 把資料切成 N 個 shard,各自一把鎖;單 key 操作只鎖一把。這就是 DashMap 原理(每 shard 一把 RwLock)。

◆ 代價 / 新陷阱:跨 shard 的原子操作要鎖多把 —— 必須按固定 shard 索引順序。兩個方向相反的操作 (2,5) 與 (5,2) 若各自照給定順序鎖,就互等成 AB/BA 死鎖;正規化成「小索引先鎖」才安全。

→ 什麼時候不夠:就算切了 shard,單 shard 內「讀」仍互斥。若讀遠多於寫 → 讓讀彼此並行。

▼

站 2 · RwLock

◆ 上一站痛點:讀仍互斥。

◆ 修法:讀寫鎖 —— 多讀並行 或 單寫排他。讀爆多時吞吐大增,而且寫是 in-place 修改、不需複製。

◆ 代價:寫時阻擋所有讀;reader 仍要對共享鎖字做 atomic RMW(超高讀速下鎖字本身變 cache 熱點);且可能 writer starvation。

unverified:std RwLock 的 fairness 契約上是 unspecified;目前 Linux 的 futex 實作傾向 write-preferring,但這是實作細節、不保證跨平台。面試講「契約未定、read-preferring 會餓死 writer」是安全說法。

→ 什麼時候不夠:寫罕見、但一寫就擋光所有讀,又想 reader 永不被擋 → 別讓 reader 碰鎖,改成換整份指標。

▼

站 3 · RCU / ArcSwap 模式(std:原子換 Arc 指標)

◆ 上一站痛點:writer 會擋 reader。

◆ 修法:資料放 Arc<T> 後面。更新時離線建整份新 T,原子換指標;reader 只 load 當前 Arc(bump refcount)後無鎖讀 snapshot。

◆ 代價:每寫要複製 / 重建整份 → 一個新 Arc;舊版要等最後一個 reader drop 才回收(期間新舊並存)。

std-only 的誠實邊界:真正 lock-free 讀是 arc-swap crate 用類 hazard-pointer 機制達成的(本次禁 crate)。std 只能用 RwLock<Arc<T>> / Mutex<Arc<T>> 逼近 —— 鎖只包「clone/swap 指標」這 O(1) 臨界區,所以不是 wait-free,但臨界區極短。想要 std 下真 lock-free,得自己 AtomicPtr + reclamation scheme(hazard pointer / epoch)—— 那才是難點,不是換指標本身。

→ 什麼時候不夠:資料小、read-mostly、又不想每次 alloc 一份 Arc → 換零配置的 seqlock。

▼

站 4 · seqlock

◆ 上一站痛點:ArcSwap 每寫 alloc 一份。

◆ 修法:一個 sequence 計數。writer 寫前把 seq 變奇、寫完變偶;reader 讀 seq → 讀資料 → 再讀 seq,兩次不同或為奇就 retry。零配置、零 alloc、reader 從不阻塞 writer。

◆ 代價:writer 進行中,reader 要 spin/retry;資料必須小且 trivially copyable。

Rust 特有坑:讀期間若寫,對非原子資料的讀是 data race(UB)。這裡刻意把 payload 存成 AtomicU64 來規避 —— 一般 T: Copy 版本在 Rust 記憶體模型下不 sound。unverified:精確最小 fence 佈局仍是微妙題目,production 版需仔細 review。

→ 什麼時候不夠:需要在共享結構上並發做結構性修改(不只是換快照)而無法接受鎖 → lock-free CAS。

▼

站 5 · lock-free (CAS)

◆ 上一站痛點:前面要嘛鎖、要嘛只能整份換;想無鎖做細粒度修改。

◆ 修法:compare-exchange 迴圈 —— 讀當前值、算新值、CAS;失敗代表別人先改了,拿最新值重試。系統層級保證總有人前進。

◆ 代價:對特定 thread 沒有 progress 保證(高競爭下可能長時間空轉);而指標型結構(stack/queue)真正的難題是 reclamation —— 何時能安全 free 一個節點(ABA、use-after-free),要靠 hazard pointer / epoch。上面 running-max 沒有指標,所以沒這問題,是純 CAS 迴圈骨架。

→ 什麼時候不夠:若場景恰是 1 producer + 1 consumer,可以更省 —— 連 CAS 都不用,拿到每 thread 有界步數的 wait-free。

▼

站 6 · wait-free (SPSC ring)

◆ 上一站痛點:CAS 迴圈在競爭下會重試,沒有「有界步數」保證。

◆ 修法:限定單 producer + 單 consumer。producer 獨佔 head、consumer 獨佔 tail;每個 index 只有一個 writer,免 CAS。publish 用 release-store,對面用 acquire-load 建立 happens-before。

先把 stepper 會用到的狀態講清楚(之後 stepper 直接用這些,不新增符號)

• head = producer 下一個要寫的 slot;tail = consumer 下一個要讀的 slot。
• 用「犧牲一格」區分空 / 滿:empty ⇔ head == tail;full ⇔ (head+1)%N == tail。因此有效容量是 N−1(拿一格換「空≠滿」可判定)。
• producer 判滿要 acquire-load tail(看見 consumer 的進度);寫完 release-store head 把資料寫入「發佈」出去。
• consumer 判空要 acquire-load head(看見 producer 的發佈);讀完 release-store tail 把 slot 還回去。
• 同步邊界是 index 的 release-store → acquire-load,它把「非原子的資料寫」ordered 在「資料讀」之前。

◆ 代價:只支援 1:1。要多方 → Vyukov bounded MPMC(per-slot sequence number + CAS,處理生產者亂序完成留下的洞)。這是光譜終點。

去 SPSC Stepper 逐步看 head/tail 前進、判空判滿、與 wrap。

資料結構 → 光譜站位對映

每個給「若要 thread-safe 的預設站位 + 為什麼 + 陷阱」。面試先報站位,再講理由。

HashMap

站 1 · sharded lock

為什麼:單 key 操作只鎖一個 shard,把 contention 分散到 N 把鎖(DashMap 原理:每 shard 一把 RwLock)。

陷阱:跨 shard 的原子操作(如兩 key 間搬移)必須按固定 shard 索引順序鎖兩把,否則 (2,5) / (5,2) 互等成 AB/BA 死鎖。

config / feature flags

站 3 · ArcSwap(換整份 Arc)

為什麼:read-mostly、整批替換、複製便宜;reader 拿 snapshot 幾乎不阻塞(std 版短鎖只做 clone),讀路徑接近 wait-free。

陷阱:每次更新 alloc 一份新 Arc;若 flags 變大又頻繁改 → 考慮 RwLock。

routing table(讀爆多、偶爾整批換)

站 3 · ArcSwap;寫也頻繁 → 站 2 RwLock

為什麼:分水嶺 = 寫頻率 × 複製成本。整批換 + 讀為主 → 換指標最省(reader 全不擋);頻繁對大表就地小改 → 每次整份複製太貴,改用 RwLock。

陷阱:別把「偶爾整批換」跟「頻繁小改」混為一談 —— 前者選 ArcSwap、後者選 RwLock,選錯就是要嘛複製爆炸、要嘛 reader 被擋。

counter / metrics

relaxed atomic(不需要鎖)

為什麼:AtomicU64::fetch_add(.., Relaxed)。只需要「計數本身原子」,不需要用它去 order 其他記憶體,relaxed 足矣、也最快。

陷阱:若這計數gates 其他資料(例如當 sequence 去發佈一塊 buffer),relaxed 不夠 —— 那條 happens-before 要 Release/Acquire。

queue

SPSC → 站 6;MPMC → Vyukov bounded

為什麼:SPSC 每個 index 只有單一 owner,兩個 atomic index + acquire/release 就好,免 CAS(wait-free)。多方競爭則需 per-slot sequence number 做握手,處理生產者亂序完成留下的洞 —— 這是 Vyukov bounded MPMC 的核心。

陷阱:把 SPSC 直接加第二個 producer 會壞:兩個 producer 對同一 head 各自 store 會覆寫;必須改成 CAS 搶 slot + per-slot seq。

LRU cache(全場最難)

難點:讀即寫 → RwLock 幫助有限

為什麼難:命中(get)也要把該 entry 移到 recency list 頭 —— 讀其實是寫。於是每個 get 都得拿 write lock,RwLock 退化成 Mutex,零讀並行。

做法:(a) sharded LRU —— 按 key 切片,各片自帶 LRU + 鎖,把 contention 切開(單片內 get 仍排他,但整體吞吐上去);(b) 近似策略 —— CLOCK / second-chance:命中只設一個 reference bit(relaxed store,完全不動 list),時鐘手掃描時看 bit 決定淘汰;或 sampled-LRU(抽 K 個挑最舊)。拿「嚴格 recency」換並發。

小 POD 快照(一組 config 數值,read-mostly,不想 alloc)

站 4 · seqlock

為什麼:零配置、零 alloc、reader 不阻塞 writer;代價是讀可能 retry、且資料須小且 trivially copyable。比 ArcSwap 省掉每次的 Arc alloc。

陷阱:Rust 下要把 payload 做成 atomic 以避免 data-race UB;含指標/非 Copy 欄位就別用 seqlock。

關鍵分水嶺

A · read-mostly:RwLock vs「原子換整份 Arc」

分水嶺一句話:寫頻率 × 複製成本。ArcSwap 每寫要 rebuild 整份;寫罕見 / 整批換 / 複製便宜 → ArcSwap 讓 reader 全不擋。寫頻繁 or 結構大 → RwLock 就地改、省掉複製,即使會擋 reader。

B · writer starvation

read-preferring 的 RwLock 下,只要 reader 源源不絕,writer 可能永遠拿不到鎖。std 的 RwLock 不保證 fairness。

unverified:目前 Linux 的 std 實作傾向 write-preferring(能緩解),但契約上 unspecified、不保證跨平台。

緩解:用 write-preferring 鎖;或直接改 ArcSwap —— writer 離線建版、原子換,根本不等 reader,結構上消除 starvation。

C · LRU 的「讀即寫」為何讓 RwLock 失效

LRU 命中要把 entry splice 到 list 頭 = 改動共享的 recency 結構 = 需要 write lock。於是每個 get 都排他,RwLock 的「多讀並行」完全用不到 —— 退化成 Mutex,讀吞吐歸零。

怎麼辦(照成本由輕到重):
1. CLOCK / second-chance:命中只設 reference bit(一個 relaxed store,不動 list),淘汰時時鐘手掃 bit。把「改順序」變「設一個 bit」,讀路徑不再需要排他 —— 恢復讀並行。
2. sampled-LRU:不維護嚴格順序,淘汰時抽樣 K 個挑最舊(近似策略;Redis 的 LRU 即近似取樣,unverified 其確切參數)。
3. sharded LRU:切片分散 contention(單片內 get 仍排他,但把熱點打散)。
共同代價:用嚴格 recency 的精確度換並發。

SPSC ring 互動 Stepper

狀態(head/tail、empty/full、release-store/acquire-load)已在 ① 推導 站 6 建立。這裡 N=6、容量 N−1=5,逐步跑一段 push/pop:會經過填滿 → 判滿 Err → wrap → 排空 → 判空 None。

圖例:H = head(producer 下一個要寫) · T = tail(consumer 下一個要讀) · 綠框 = 本步寫入的 slot · 藍框 = 本步讀出的 slot · 虛線格 = 邏輯上空

看這段要抓的三件事: ① 判滿 (head+1)%N==tail 為什麼容量是 N−1(留一格才能區分空/滿); ② wrap 時 head 從 5 回到 0,index 是環狀、資料不搬; ③ 每次 push 的 release-store head 與每次 pop 的 acquire-load head 配成 happens-before,才保證 consumer 讀到的是 producer 已寫好的資料。

③ 常見面試追問(逐層加深)

鏈 1 · read-mostly 一路被逼下去
你說 read-mostly 用 RwLock。如果 writer 被餓死怎麼辦?
std RwLock fairness 未定,read-preferring 會餓死 writer。選項:換 write-preferring 鎖;或改 ArcSwap —— writer 離線建版、原子換,不等 reader,結構上消除 starvation。
改 ArcSwap 要每寫複製整份。routing table 有 100 萬條、每秒更新一萬次,現在呢?
越過分水嶺了:複製成本 × 寫頻率 太高。退回 RwLock 就地改;或 sharded 把寫打散;或批次化更新攤平頻率;std-only 下沒有便宜的 persistent 結構做 structural sharing。
選 sharded RwLock。但客戶要跨兩個 shard 的原子交易,怎麼避免死鎖、成本多少?
把涉及的 shard 按固定全域順序(如索引升冪)鎖起來,消除 AB/BA 循環。成本:交易路徑會 serialize 在較大 shard 上、失去部分並行,且多把鎖的鎖序正確性本身是 bug 溫床;若跨 shard 交易很多,單一 coarse 鎖或 2PL 反而更好維護。
如果交易要涉及不定數量的 shard 呢?
先收集所有涉及 shard 索引、排序去重,再依序上鎖(等同對「鎖集合」定義全序)。注意持鎖數上升會拉高 contention 與 deadlock 面積;可設上限、或退化為粗鎖臨界區。
鏈 2 · LRU 的讀即寫
幫我把 LRU cache 變 thread-safe。
第一版 Mutex<LinkedHashMap>:正確、簡單。
get 是熱路徑、想要讀並行,用 RwLock?
不行 —— get 命中要 splice 到 list 頭 = 改共享結構 = 需 write lock,於是每個 get 都排他,RwLock 退化成 Mutex。
那怎麼拿到真正的讀並行?
sharded LRU(切 contention)或近似:CLOCK 命中只設 reference bit(不動 list)、sampled-LRU 抽樣淘汰。用嚴格 recency 換並發。
CLOCK 的 reference bit 在命中時也是共享寫,不還是 contention?
是一個 relaxed store 到 per-entry 的位元組,不動 list、不上鎖,遠比「持鎖 splice」便宜。若很多 entry 的 bit 擠在同一 cache line 會 false sharing → padding 或接受;整體仍是壓倒性改善。
鏈 3 · SPSC → MPMC
你的 SPSC ring,擴成多 producer。
會壞:head 變競爭點,兩個 producer 各自 store 同一 slot 會覆寫。
那怎麼做?
producer 用 CAS 搶 head 佔一個 slot、再寫、再發佈。但問題來了:後搶到的 producer 可能先寫完,在序列上留下一個 consumer 不能跨過去的洞。
Vyukov bounded MPMC 怎麼處理這個洞?
每個 slot 帶一個 sequence number:producer CAS 位置後寫資料、把 slot.seq 設成「就緒」標記;consumer 靠 slot.seq 判斷自己那格是否就緒,天然處理亂序完成。等於把「兩個全域 index」升級成 per-slot 握手。
鏈 4 · memory ordering
SPSC 發佈用 Release、對面 index load 用 Acquire。為什麼不全 Relaxed?
Relaxed 只保證 index 本身原子,不建立資料寫/讀的 happens-before;consumer 可能在 producer 的資料寫可見之前就讀那格 → 讀到 garbage/torn。
為什麼 Acquire 掛在對面 index(consumer acquire head),不是掛在資料上?
資料本身非原子,無法承載 ordering。同步邊是 index-store(Release) → index-load(Acquire);這條邊遞移地把「非原子資料寫」ordered 在「資料讀」之前。index 是那把「可攜帶 happens-before」的把手。
x86 上 load 本來就是 acquire、store 本來就是 release,那 Ordering 還有差嗎?
有 —— Ordering 也約束編譯器的重排,不只 CPU。Relaxed 允許編譯器把資料存取搬到 index 操作的另一側,即使 x86 runtime 不會那樣重排。為了可攜性 + 擋編譯器重排,標註仍必要。

④ Self-Quiz(答案摺疊)

read-mostly 的 feature flags 該選光譜哪一站?分水嶺是什麼?

站 3 · ArcSwap 模式(原子換整份 Arc<Flags>)。flags 小、更新罕見且整批替換,換指標讓 reader 拿 snapshot 幾乎不阻塞(std 版短鎖只做 clone)。

分水嶺 = 寫頻率 × 複製成本(對照 RwLock)。只要「寫罕見 + 整批換 + 複製便宜」成立,ArcSwap 勝(reader 全不擋、無 writer starvation)。若 flags 變大且改成頻繁就地小改,rebuild 成本 × 頻率過線 → 改 RwLock 就地改。

LRU 為什麼不能簡單套 RwLock?你會怎麼辦?

為什麼失效:命中(get)要把 entry 移到 recency list 頭 —— 讀其實是寫。於是每個 get 都需 write lock,RwLock 退化成 Mutex,多讀並行完全用不到、讀吞吐歸零。

做法:① CLOCK / second-chance —— 命中只設 reference bit(relaxed store,不動 list),淘汰時時鐘手掃 bit;讀路徑不再排他。② sampled-LRU —— 抽 K 個挑最舊,不維護嚴格順序。③ sharded LRU —— 切片分散 contention。共同代價:用嚴格 recency 精確度換並發。

counter / metrics 用 Relaxed atomic 為什麼夠?什麼時候會不夠?

夠:你只需要「計數本身是原子的」,不需要用這個計數去 order 其他記憶體的可見性。fetch_add(.., Relaxed) 保證不掉更新,也最省。

不夠:當這個原子gates 其他資料時 —— 例如把它當 sequence/flag 去「發佈」一塊剛寫好的 buffer,讀方靠它判斷 buffer 就緒。這時需要 Release(寫方)/ Acquire(讀方) 建立 happens-before,否則讀方可能看到 flag 已設、buffer 卻還沒寫完。

同樣是 read-mostly 的小 config,seqlock 與 ArcSwap 怎麼選?

seqlock(站 4):當你在意零 alloc、資料小且 trivially copyable、且讀可容忍 retry。省掉 ArcSwap 每次更新的 Arc alloc。代價:writer 進行中 reader 要 spin;含非 Copy/指標欄位不能用;Rust 下 payload 要做成 atomic 以避免 data-race UB。

ArcSwap(站 3):當你要 reader 從不 retry、或資料含非 Copy 欄位、或想要一個乾淨的 snapshot 生命週期。代價:每寫 alloc + rebuild、新舊並存到舊 reader drop。

一句話:要零 alloc、能忍 retry → seqlock;要 reader 永不重試、資料非平凡 → ArcSwap。

sharded map 跨 shard 原子操作怎麼避免死鎖?若兩操作分別鎖 shard (2,5) 與 (5,2) 會怎樣?

避免:對涉及的 shard 一律按固定全域順序(如索引升冪)上鎖。兩個操作都會「先鎖 2、再鎖 5」,不存在循環等待。

(2,5) 與 (5,2):若不正規化、各自照給定順序鎖 —— 操作 X 持 2 等 5、操作 Y 持 5 等 2,就是教科書 AB/BA 死鎖。修法就是上面的「排序後再上鎖」,把鎖獲取定義成一個全序。多於兩個 shard 時:先收集索引 → 排序去重 → 依序鎖。
