interior mutability 階梯:選哪一階

&T 不能改。要在 &T 底下改,就是把 XOR 的檢查從編譯期搬到別的地方。 搬到哪,決定你選哪一階:

型別XOR 檢查搬到哪Sync? 成本什麼時候用
Cell<T>不用檢查 —— 根本不交出引用,只 get/set 整個值 ✗ !Sync零T: Copy 的小欄位。單執行緒。
RefCell<T>執行期:borrow flag 計數器 ✗ !Sync一個計數器 + 分支;違規 panic單執行緒共享可變。原型。
Mutex<T>執行期:作業系統的鎖 ✓ Sync 當 T: Send
不需要 T: Sync		atomic + 可能 syscall;違規 block跨執行緒。預設答案。
RwLock<T>執行期,但區分讀/寫 ✓ Sync 當 T: Send + Sync
↑ 跟 Mutex 的差別就在這		比 Mutex 貴;writer starvation 風險讀遠多於寫。要講得出 starvation。
UnsafeCell<T> 搬到你腦子裡✗ !Sync(要自己 unsafe impl) 零 —— 這是唯一真的零成本的 ring / lock-free。7/28 你會用這個。
最常被記反的一格查證 · std 原始碼: 很多人以為「多條 thread 會碰它,所以 Mutex<T> 要 T: Send + Sync」。反了。 
// library/std/src/sync/poison/mutex.rs
// L238 unsafe impl<T: ?Sized + Send> Send for Mutex<T> {}
// L257 unsafe impl<T: ?Sized + Send> Sync for Mutex<T> {}   // ← 只有 Send

// library/std/src/sync/poison/rwlock.rs
// L104 unsafe impl<T: ?Sized + Send> Send for RwLock<T> {}
// L107 unsafe impl<T: ?Sized + Send + Sync> Sync for RwLock<T> {}  // ← 這個才是 Send + Sync
直覺為什麼會反:鎖的工作就是序列化 —— Mutex 保證同時只有一個人拿得到 &mut T, 所以 T 從來沒有被共享,只是被輪流移交。Mutex<T> 本質是「一次裝一個值、跨 thread 傳遞」的通道 → T: Send。 RwLock 的 read guard 真的會同時發多個 &T 出去 → 那時 T 才必須自己 Sync。

這條對 7/28 是承重的:你 ring 的 unsafe impl<T: Send> Sync for Ring<T> 用的是完全同一個理由。記反了,你會把自己的 bound「修」成過度約束的 T: Send + Sync, 然後被問「為什麼需要 Sync?」時整段辯護垮掉。詳見 軸 3 的判別對。
面試句:「UnsafeCell 是所有 interior mutability 的底層原語 —— 它是唯一能在 &T 底下合法拿到 *mut T 的型別。 Cell/RefCell/Mutex 內部全是它。 我在 ring 裡直接用它,是因為 XOR 已經被 head/tail 的 acquire/release 保證了 —— 再套一層 RefCell 是重複檢查,而且 RefCell 還 !Sync,跨不了 thread。」

arena + index:同時繞開軸 1 跟軸 2

把整個結構當一個 owned blob,節點間用 Copy 的整數互指。 borrow checker 不追蹤整數別名 —— index 不是引用(無 lifetime,繞開軸 1), 真正存取只有一個 &mut Arena(無 XOR 衝突,繞開軸 2)。

Send = 這個值可以換一條 thread 擁有(move 過去)。
Sync = 這個值可以被多條 thread 同時 &。
兩者由一條恆等式綁死:T: Sync ⟺ &T: Send。這不是巧合,這就是 Sync 的定義。

先把恆等式吃下去,推導表就不用背

「T 可以被多條 thread 同時借」跟「T 的引用可以被送到別條 thread」是同一句話。 std 的 Sync 文件就是這樣定義的。吃下這條之後,整張表都能現推:

// std 裡 Sync 的定義,字面上就是這樣
pub unsafe auto trait Sync { }
// 且有這條 blanket impl:
unsafe impl<T: Sync + ?Sized> Send for &T {}
//                ^^^^ T 是 Sync  ⟹  &T 是 Send。反過來也成立。
編譯器親口證實這條已驗:我問它 assert_send::<&RefCell<i32>>(), 它報的錯不是「&RefCell 不能 send」,而是: 
error[E0277]: `RefCell<i32>` cannot be shared between threads safely
   |     assert_send::<&RefCell<i32>>();
   |                   ^^^^^^^^^^^^^ `RefCell<i32>` cannot be shared between threads safely
你問的是 Send,它答的是 shared(=Sync)。恆等式在錯誤訊息裡現形了。

推導表已驗 · 逐格問過 rustc 1.75

下表每一格都是我實際 assert_send::<T>() / assert_sync::<T>() 編一遍的結果 —— 過的真的過,✗ 的真的報 E0277。

型別SendSync為什麼(這欄才是被問的)
Rc<T>✗✗ refcount 是非 atomic 的。兩條 thread 同時 clone/drop → count 撕裂 → double free。 兩個都 ✗:連 move 過去都不行,因為別條 thread 手上可能還有同一個 Rc。
Arc<T>✓*✓* refcount 是 atomic。*但要 T: Send + Sync —— Arc<RefCell<i32>> 依然 !Sync, 因為 Arc 只是把 &T 發給大家,裡面的 RefCell 該炸還是炸。
Cell<T>✓✗ Send ✓:整個 move 過去,還是只有一個擁有者,沒問題。
Sync ✗:set() 只需要 &self,兩條 thread 同時 set = data race,而且沒有任何檢查。
RefCell<T>✓✗ 同上。borrow flag 是普通 Cell<isize>,不是 atomic —— 兩條 thread 同時 borrow_mut() 會雙雙成功,拿到兩個 &mut。panic 保護在並行下失效。
Mutex<T>✓✓ 要 T: Send。注意 不需要 T: Sync —— 因為 Mutex 保證同時只有一個人拿得到 &mut T, 永遠不會有兩條 thread 同時持 &T。這格常被問。
RwLock<T>✓✓ 要 T: Send + Sync。跟 Mutex 的差別就在這 —— RwLock 真的會同時發多個 &T 出去, 所以 T 自己必須扛得住被共享。
MutexGuard<'_, T>✗✓† 唯一一個 Send✗/Sync✓ 的常見型別,面試愛考。
Send ✗:某些平台(pthread)要求解鎖的 thread 必須是上鎖的那條。guard 一旦 move 到別條 thread, drop 就在錯的 thread 解鎖 → UB。
†Sync ✓ 要 T: Sync:借 &MutexGuard 出去只能 deref 成 &T,不會解鎖。
*const T / *mut T✗✗ raw pointer 一律 !Send + !Sync。這是你 7/28 會撞到的那格 —— 你的 ring 裡有 UnsafeCell(內含 raw pointer 語意),整個 struct 就被傳染成 !Sync。
&T= T: Sync= T: Sync 恆等式本身。&RefCell<i32> 不是 Send,因為 RefCell 不是 Sync。
&mut T= T: Send= T: Sync &mut T 是獨佔的 —— 送過去等於把 T 本身送過去,所以只要 T: Send。

一組判別對:同一個 T,Mutex 過、RwLock 不過已驗

這是整張表最值得記的一格,因為它把兩把鎖的語意差異壓成一行編譯結果:

assert_sync::<Mutex<Cell<i32>>>();   // ✓ 編過
assert_sync::<RwLock<Cell<i32>>>();  // ✗ error[E0277]
//              ^^^^^^^^^ 同一個 T = Cell<i32>(Send 但 !Sync)
面試句(這段值得背下來):「Mutex<T> 是 Sync 只需要 T: Send, 因為鎖保證同時只有一個 thread 拿得到 &mut T —— T 從來沒被共享過,只是被移交。 RwLock<T> 就得要 T: Sync,因為 read guard 真的會同時發多個 &T 出去。 這也是為什麼 Mutex<Cell<i32>> 能跨 thread,RwLock<Cell<i32>> 不行。」

auto trait:你平常不 impl 它,除非你有 raw pointer

Send/Sync 是 auto trait —— 編譯器結構化地推導:所有欄位都 Send,這個 struct 就 Send。 你從來不用寫。直到你在 struct 裡放了 UnsafeCell / *mut T / NonNull, !Send/!Sync 就沿著欄位傳染上來,整個型別死掉。這時你有兩條路:

路 1:接受它

型別就是不能跨 thread。單執行緒結構(Rc/RefCell 那掛)走這條。

路 2:unsafe impl 覆寫

你跟編譯器說「我知道你看不出來,但我保證安全」。這一刻起,軸 3 的網對你破了 —— 沒有人再檢查。7/28 你會走這條。

7/28 的必答題:辯護你的 unsafe impl

你敲下這兩行的下一秒,Alex 會問「為什麼這是安全的?」。答不出來 = 這題死了, 因為 unsafe impl 的全部意義就是「我用人腦替代編譯器」—— 你講不出理由,等於承認沒替代。 
unsafe impl<T: Send> Send for Ring<T> {}
unsafe impl<T: Send> Sync for Ring<T> {}
//            ^^^^^^^^ 注意:是 T: Send,不是 T: Send + Sync。這個 bound 本身就是考點。

三段式辯護模板 —— 照這個結構講,不要即興:

段你要講的Ring 的版本
① 誰碰什麼指出存取是不重疊的 「producer 只寫 tail 跟 tail 指到的那格;consumer 只寫 head 跟 head 指到的那格。 兩者觸碰的 slot 集合永遠不相交。」
② 誰保證不重疊指出哪個機制撐起① 「不相交是由 head/tail 的 acquire/release 配對保證的 —— producer 看到 head 的 acquire-load 之後才決定寫哪格,那次 load 觀察到 consumer 的 release-store, 所以 consumer 對那格的讀已經 happens-before 我的寫。」
③ 為什麼 bound 是這個解釋 T: Send 而非 T: Send + Sync 「值會從 producer thread 移動到 consumer thread,所以要 T: Send。 我從不同時把 &T 交給兩條 thread —— pop 是 move out,不是借 —— 所以不需要 T: Sync。跟 Mutex<T> 是同一個道理。」
誠實加分句:講完三段可以補一句「這是我人工論證的,編譯器不檢查 —— production 上我會拿 loom 窮舉 interleaving,再用 Miri 對 Stacked Borrows 跑一遍。」 這句話在 systems 公司是明確加分,因為它顯示你知道自己的保證是人腦等級的,需要工具兜底。
Ordering 是「哪些寫入保證被看見」的合約。它不是「快慢」的旋鈕 —— 選錯不會變慢,會變成 UB。而且 UB 在你的 x86 上不會發生,所以你測不出來。

為什麼 x86 上跑得對,卻仍然是 UB

重排的來源x86 會不會做後果
CPU:store→store 重排不會(x86-TSO 不允許) 所以 DATA=42 不會掉到 READY=true 後面。x86 免費送你半個 release。
CPU:load→load 重排不會(x86-TSO 不允許) 所以 B 讀 DATA 不會升到讀 READY 前面。x86 免費送你半個 acquire。
CPU:store→load 重排會 這是 x86 唯一允許的重排,也是 SeqCst 在 x86 上真的要付錢(mfence/lock)的地方。
編譯器:LLVM 重排會 —— 而且它有權 Relaxed 對 LLVM 就是「這裡沒有同步」,它合法地可以把 DATA=42 沉到 store 之後、 把 ready.load 提到迴圈外變成無窮迴圈、或整個消掉。今天沒做,不代表明天 -O3 不做。
其他 CPU:ARM / RISC-V會,而且常常 weakly-ordered。同一份 code 在 Apple Silicon / Graviton / 你們家的加速卡上就撕給你看。

✓ 要講:「這裡必須 release/acquire。不是因為 x86 會重排 —— x86-TSO 本來就不做 store-store 跟 load-load 重排,所以 relaxed 在這台機器上跑起來會是對的。 問題是:① 記憶體模型上它是 UB,LLVM 有權把那個 store 沉下去; ② 換到 ARM 就真的撕。「我測過沒事」在 ordering 上不構成證據 —— 這正是 loom 存在的理由,它窮舉 interleaving 而不是靠 x86 的運氣。」
這段話的價值不在「知道 acquire/release」—— 那是查得到的。價值在你展示了 「我知道我的測試證明不了什麼」。你 R1 被抓的那條軸(Independent Drive / 自己找到 bug) 在這裡有一個正面版本:主動指出自己方法的極限,比等人來抓強。
Pin<P> 的機制只有一句:它不再交出 &mut T。
因為 &mut T 是 move 一個值的唯一入口(mem::swap / mem::replace / ptr::write 全都要它)。收掉這道門,值就 move 不走了。

Pin 怎麼解:堵住 &mut 這道門

你以為實際
Pin 把值釘在記憶體位址上 Pin 是型別層的協定,執行期什麼事都沒做 —— 它就是個 wrapper,零成本。 它做的唯一一件事是在 API 上不給你 &mut。值之所以不動,是因為你拿不到搬它的工具。
Pin 是 unsafe 的東西 Pin 本身全 safe。unsafe 出現在兩端:建立(Pin::new_unchecked,你保證之後不 move) 跟逃逸(get_unchecked_mut)。中間全部 safe。
要用 Pin 就要懂一堆東西 寫 block_on 只需要 std::pin::pin!(fut) 一行 —— 它在 stack 上釘住, 安全、零成本。7/28 你只需要這一行。

投影:每個欄位都是一個決定

對 struct 的每一格問:「struct 被 pin 的時候,這格算不算也被 pin?」這是你的選擇,不是推導出來的, 而且選了就要一致。std 文件的原話是「沒有硬性規則」,並且說選「不結構性 pin」通常比較輕鬆。

// 選 A:這格「不」結構性 pin → 投影出普通的 &mut(std 文件自己的範例就長這樣)
fn tick_mut(self: Pin<&mut Self>) -> &mut u32 {
    // SAFETY: tick 不是結構性 pin 的欄位 —— 沒有指標指向它,我們也不 move 整個 Task。
    unsafe { &mut self.get_unchecked_mut().tick }
}

// 選 B:這格「要」結構性 pin → 投影出 Pin<&mut Field>
fn inner_pin_mut(self: Pin<&mut Self>) -> Pin<&mut Inner> {
    // SAFETY: Task 被 pin ⟹ inner 也被 pin。從不 move 它,Drop 也不 move out。
    unsafe { self.map_unchecked_mut(|s| &mut s.inner) }
}
選 B(結構性 pin)要背四條額外要求查證 · std pin 模組文件:
  1. Structural Unpin:struct 只有在所有結構性 pin 的欄位都 Unpin 時才能是 Unpin。 別手寫 impl<T> Unpin for Struct<T> 然後又提供指向 T 內部的結構性投影。
  2. Pinned Destruction:drop 的簽章是 &mut self,但你的解構子必須當作它收到的是 Pin<&mut Self> 來寫。 推論:這個 struct 不能是 #[repr(packed)]。
  3. Structural Notice of Destruction:必須守住 Drop guarantee —— pin 過的儲存空間不能在沒呼叫結構性欄位的解構子的情況下被重用。 文件舉 VecDeque<T> 為例:它的解構子在某個元素 drop panic 時會漏掉其他元素 → 所以它不提供 pin 投影。
  4. 不能提供任何會把資料 move 出結構性欄位的操作。例如 fn(Pin<&mut Struct<T>>) -> Option<T> 這種 take-like 的方法 —— 有它,那格就不能是結構性 pin。
這四條就是 pin-project 這個 crate 存在的理由:它機械但易錯。而 7/28 你 std-only,沒有它。
7/28 的實際答案:你手寫的 future 幾乎一定是 Unpin(除非你跨 await 借了本地變數), 所以 self.slot = Some(x) 直接就能寫 —— async 那頁的 Delay 就是活例子。 被追問「那自引用的怎麼辦?」→ 答「投影,而 std 沒有安全做法,得手寫 unsafe;生態系是用 pin-project 巨集解決的」。 不要在 45 分鐘裡真的去手刻投影,那是 deep dive 的話題。

為什麼 Future 需要它

async fn 會被展開成一個 state machine struct,每個 .await 是一個狀態。 如果你在 await 之前借了本地變數、await 之後還要用 —— 那個借用就得存進 state machine 裡, 而它指向的變數也在同一個 struct 裡。自引用就這樣長出來了:

async fn f() {
    let buf = [0u8; 1024];
    let slice = &buf[..];      // 借了 buf
    read_into(slice).await;     // ← 跨過 await 點
    use_it(slice);              // await 之後還在用 → slice 必須存活
}
// 展開後 ≈ struct F { buf: [u8;1024], slice: &'self [u8], state: u8, _p: PhantomPinned }
//                                            ^^^^^^^^^^^^ 指向同一個 struct 裡的 buf
面試句:「Future::poll 的 receiver 是 Pin<&mut Self> 而不是 &mut Self, 是因為 async fn 展開成的 state machine 可能持有指向自己欄位的引用 —— 只要跨 await 借用本地變數就會發生。executor 必須保證第一次 poll 之後那個 future 不再 move, Pin 就是把這個保證編碼進型別。手寫的 future 如果沒有自引用,它是 Unpin, 這個限制對它形同不存在 —— 我等下寫的 Delay 就是這種。」
整個 async 就是一條契約:poll 回 Pending 的人,有義務安排 wake() 被叫。
executor 只做兩件事:poll 它;回 Pending 就去睡,等人 wake 我再 poll。其他都是這條的推論。

誰去叫 wake()?—— waker 那格不能住在 Future 裡已驗

這是手寫 future 的第一個結構性關卡。天真的寫法長這樣,而且編得過:

struct Naive { done: bool, waker: Option<Waker> }   // ← 很多人第一次都這樣寫

fn poll(mut self: Pin<&mut Self>, cx: &mut Context) -> Poll<()> {
    if self.done { return Poll::Ready(()); }
    self.waker = Some(cx.waker().clone());   // 存了…然後呢?
    Poll::Pending
}
問題:誰去 self.waker.take()?
poll 的簽章是 Pin<&mut Self> —— 只有執行器拿得到它。 背景執行緒 / IO driver / 中斷處理常式手上沒有 &mut Naive, Future 一旦交出去,執行器就是唯一持有者。 → self.waker 這格永遠沒有人讀得到,block_on(Naive) 會 park 到天荒地老。

正確形狀:Future 只是「共享狀態的把手」,waker 住在 Shared 裡:

struct Shared<T> { value: Option<T>, waker: Option<Waker> }
pub struct SpawnBlocking<T>(Arc<Mutex<Shared<T>>>);   // ← Future 本身只是一個 Arc

impl<T: Send> Future for SpawnBlocking<T> {
    type Output = T;
    fn poll(self: Pin<&mut Self>, cx: &mut Context) -> Poll<T> {
        let mut guard = self.0.lock().unwrap();
        if let Some(value) = guard.value.take() { return Poll::Ready(value); }
        guard.waker = Some(cx.waker().clone());   // 每次 poll 都覆蓋(waker 會換人)
        Poll::Pending
    }
}

// ★ take() + wake() 跑在【背景執行緒】上,透過它自己那份 Arc clone:
thread::spawn({
    let inner = inner.clone();          // ← 另一邊碰得到狀態的唯一路徑
    move || {
        let value = closure();          // 做真正的苦工
        let maybe_waker = {
            let mut guard = inner.lock().unwrap();
            guard.value = Some(value);
            guard.waker.take()               // 取出來,順便標記「用掉了」
        };                                 // ← guard 在這裡 drop。這個大括號是刻意的。
        if let Some(waker) = maybe_waker {
            waker.wake();                  // ← 在【鎖外面】叫
        }
    }
});

為什麼是 take() 而不是 wake_by_ref()

理由說明
① 所有權Waker::wake(self) 吃掉所有權(比 wake_by_ref 少一次 refcount 操作)。take() 剛好給你。
② 語意標記「這個 waker 用掉了」。留著會有叫兩次的風險。
③ 能在放掉鎖之後才叫 這條才是重點。wake() 是一個 vtable call,跳進執行器的任意程式碼 —— 而執行器完全可以合法地同步重新 poll(Waker 契約只要求「安排重新 poll」,沒說不能當場做), poll 的第一件事就是 lock 同一把鎖 → 自己等自己。
實測已驗:我寫了一個「收到 wake 就同步重新 lock」的執行器去打它 —— 
[3a] ✗ 卡住了(300ms 沒回來)—— 在鎖裡面叫 wake() = 自己等自己
[3b] ✓ 順利完成 —— 先 take、放鎖、再 wake
一般規則(不是 async 專屬):永遠不要握著鎖去呼叫你不控制的程式碼。 wake() 就是那種程式碼。
有趣的是:官方 async-book 的 TimerFuture 就是握著鎖叫 wake() 的查證 —— 它 lock() 之後直接 shared_state.waker.take() 然後 waker.wake(),guard 還活著。 對它自己那個 executor 沒事(那個 waker 只是往 channel 塞東西,不碰這把鎖),但這個寫法不通用。

use std::future::Future;
use std::pin::pin;
use std::sync::Arc;
use std::task::{Context, Poll, Wake, Waker};
use std::thread::{self, Thread};

struct ThreadWaker(Thread);

impl Wake for ThreadWaker {
    fn wake(self: Arc<Self>)        { self.0.unpark(); }
    fn wake_by_ref(self: &Arc<Self>) { self.0.unpark(); }
}

fn block_on<F: Future>(fut: F) -> F::Output {
    let mut fut = pin!(fut);                       // ← 軸 5 在這裡,就這一行
    let waker = Waker::from(Arc::new(ThreadWaker(thread::current())));
    let mut cx = Context::from_waker(&waker);
    loop {
        match fut.as_mut().poll(&mut cx) {
            Poll::Ready(v) => return v,
            Poll::Pending  => thread::park(),      // ← 整段的正確性靠 park 的 token
        }
    }
}
為什麼這 18 行是對的已驗 —— 我寫了一個在回傳 Pending 之前就 wake 的 future 去打它: 
fn poll(...) -> Poll<&'static str> {
    if self.0 { return Poll::Ready("醒了"); }
    self.0 = true;
    cx.waker().wake_by_ref();   // wake 發生在 executor 還沒 park 的時候
    Poll::Pending
}
結果:[ok] wake-before-park 沒有 hang → 醒了 (817ns)
原因:thread::unpark 會留下一個 token。之後的 park() 看到 token 就直接返回,不睡。 如果 park 沒有 token 語意,這裡就是永久 deadlock —— 而這是手寫 executor 最經典的 bug。
追問預備:「那 spurious wakeup 呢?」→ park 允許無理由醒來,所以它一定要包在 loop 裡。上面的 loop 剛好處理掉: 亂醒 → 再 poll 一次 → 還沒好就再 park。「poll 是冪等的、多 poll 幾次只是浪費不會錯」 是 Future 契約的一部分,這正是為什麼 spurious wakeup 在 async 裡無害。 (同一個道理在 C++ 是 condvar.wait() 一定要走 predicate 版。)

Delay:那個「waker 會換人」的坑已驗

你 memory 裡記的那條 —— 每次 poll 都要存最新的 waker —— 長這樣:

struct Delay {
    when: Instant,
    slot: Option<Arc<Mutex<Option<Waker>>>>,   // 跟計時 thread 共用的信箱
}

impl Future for Delay {
    type Output = &'static str;
    fn poll(mut self: Pin<&mut Self>, cx: &mut Context<'_>) -> Poll<Self::Output> {
        if Instant::now() >= self.when { return Poll::Ready("時間到"); }
        match &self.slot {
            Some(slot) => { *slot.lock().unwrap() = Some(cx.waker().clone()); }  // ← 每次都換
            None => {
                let slot = Arc::new(Mutex::new(Some(cx.waker().clone())));
                let slot2 = slot.clone();
                let when = self.when;
                thread::spawn(move || {
                    let now = Instant::now();
                    if now < when { thread::sleep(when - now); }
                    if let Some(w) = slot2.lock().unwrap().take() { w.wake(); }
                });
                self.slot = Some(slot);
            }
        }
        Poll::Pending
    }
}

use std::cell::UnsafeCell;
use std::mem::MaybeUninit;
use std::sync::atomic::{AtomicUsize, Ordering};
use std::sync::Arc;

pub struct Ring<T> {
    buf: Box<[UnsafeCell<MaybeUninit<T>>]>,
    mask: usize,
    head: AtomicUsize, // consumer 下一個要讀的位置(單調遞增,不取模)
    tail: AtomicUsize, // producer 下一個要寫的位置(單調遞增,不取模)
}

// SAFETY: producer 只寫 tail、consumer 只寫 head;兩者觸碰的 slot 由
// head/tail 的 acquire/release 配對保證不重疊。T 會從 producer thread
// 移動到 consumer thread,故需 T: Send。我們從不同時交出 &T 給兩條
// thread,故不需要 T: Sync。
unsafe impl<T: Send> Send for Ring<T> {}
unsafe impl<T: Send> Sync for Ring<T> {}

impl<T> Ring<T> {
    fn cap(&self) -> usize {
        self.mask + 1
    }
}

impl<T> Drop for Ring<T> {
    fn drop(&mut self) {
        let head = *self.head.get_mut();
        let tail = *self.tail.get_mut();
        let mut i = head;
        while i != tail {
            unsafe { (*self.buf[i & self.mask].get()).assume_init_drop() };
            i = i.wrapping_add(1);
        }
    }
}

pub struct Producer<T> {
    ring: Arc<Ring<T>>,
}
pub struct Consumer<T> {
    ring: Arc<Ring<T>>,
}

pub fn channel<T>(cap: usize) -> (Producer<T>, Consumer<T>) {
    assert!(cap.is_power_of_two() && cap > 0, "cap 必須是 2 的冪");
    let buf = (0..cap)
        .map(|_| UnsafeCell::new(MaybeUninit::uninit()))
        .collect::<Vec<_>>()
        .into_boxed_slice();
    let ring = Arc::new(Ring {
        buf,
        mask: cap - 1,
        head: AtomicUsize::new(0),
        tail: AtomicUsize::new(0),
    });
    (
        Producer { ring: ring.clone() },
        Consumer { ring },
    )
}

impl<T> Producer<T> {
    pub fn push(&mut self, val: T) -> Result<(), T> {
        let tail = self.ring.tail.load(Ordering::Relaxed); // 只有我寫 tail
        let head = self.ring.head.load(Ordering::Acquire); // 看見 consumer 的釋放
        if tail.wrapping_sub(head) == self.ring.cap() {
            return Err(val); // 滿
        }
        unsafe { (*self.ring.buf[tail & self.ring.mask].get()).write(val) };
        self.ring.tail.store(tail.wrapping_add(1), Ordering::Release); // 發布
        Ok(())
    }
}

impl<T> Consumer<T> {
    pub fn pop(&mut self) -> Option<T> {
        let head = self.ring.head.load(Ordering::Relaxed); // 只有我寫 head
        let tail = self.ring.tail.load(Ordering::Acquire); // 看見 producer 的發布
        if head == tail {
            return None; // 空
        }
        let val = unsafe { (*self.ring.buf[head & self.ring.mask].get()).assume_init_read() };
        self.ring.head.store(head.wrapping_add(1), Ordering::Release); // 釋放 slot
        Some(val)
    }
}

四個 Ordering,每個寫錯的後果已驗 · 反例

這四行是全部的爭議點。被追問時要能逐行講 —— 而且要講得出「寫錯會怎樣」, 不只是「這樣寫是對的」:

那一行為什麼是這個改成 Relaxed 會怎樣
tail.load(Relaxed)
push 裡讀自己的 tail		 本來就該 Relaxed 沒事,這就是 Relaxed。tail 只有 producer 會寫 —— 我讀自己剛寫的值,不需要跟任何人同步。這格用 Acquire 是白付錢,講得出來是加分。
head.load(Acquire)
push 裡看 consumer 進度		 配對 consumer 的 release 我可能看到 consumer 已經推進的 head,卻還沒看到它把那格讀完 → 我覆寫一格 consumer 正在讀的資料。撕裂。
tail.store(.., Release)
push 的最後一行		 最關鍵的一行 consumer 看到新 tail,但看不到我剛寫進 slot 的資料 → 它讀到未初始化記憶體 → assume_init_read 一個垃圾 → 如果 T 有指標,直接 segfault。
head.load(Relaxed) / tail.load(Acquire) / head.store(Release)
pop 裡,完全對稱		 鏡像 head.store 若 Relaxed:producer 看到 slot 空了就寫進去, 但我可能還沒讀完 → 我讀到一半的值被覆寫。
x86 提醒(呼應 軸 4):上面每一個「會怎樣」, 在 CoderPad 那台 x86 上跑 20 萬次都不會發生。我實測過 relaxed message-passing 2000 次全過。 所以這些反例是用嘴講的,不是用 Run 按鈕證明的。

被追問時的三個 follow-up(先想好)

「false sharing 呢?」

head 跟 tail 在同一條 cache line → producer 寫 tail 會讓 consumer 的 head 快取失效, 互相打。解:#[repr(align(64))] 把兩者拆開。45 分鐘裡先講出來、如果有時間再加。

「為什麼 SPSC 不用 CAS?」

因為每個 atomic 只有一個 writer。CAS 是用來解決「多個 writer 搶同一個變數」的, 這裡沒有那個問題。MPMC 才需要(關鍵字:Vyukov bounded queue)。

「滿了要怎麼辦?」

我回 Err(val) 把值還給呼叫者 —— 這是刻意的:值沒地方放就不能吞掉。 三種策略:fail-fast(現在這樣)/ block(要 condvar)/ drop-oldest(要 consumer 也能動 head,就不再是 SPSC)。 講得出這三條 = pillar 4。

「怎麼測?」

守恆斷言(送出總數 == 收到總數、順序不變)+ loom 窮舉 interleaving。 不要說「我跑了很多次沒事」 —— 那在 ordering 上不是證據。
