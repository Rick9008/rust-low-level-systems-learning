Ring Buffer(bounded)

用途 固定容量的 FIFO,producer 寫、consumer 讀,不做動態配置。
Systems 場景:packet / telemetry stream 的 staging buffer。NIC 或 agent 把 sample 塞進環,下游批次抽走。容量固定 = 記憶體可預測、無 GC pause、cache 熱。

① 概念推導

Naive VecDeque 直接當環用,或自己開 Vec + 一個 head 索引 + 一個 count 欄位,索引用 % cap 繞回。
失敗模式 兩個問題疊起來:
(1) 滿/空判別:若只有 head/tail 兩個「物理索引」,head == tail 同時代表「空」與「滿」—— 無法區分。傳統補救是犧牲一格(留一個永遠不填)或多存一個 count。
(2) 共享 count 在並發下要 RMW:一旦搬到 SPSC(單 producer 單 consumer 跨執行緒),那個共享 count 每次都要 atomic fetch_add/sub,兩端互相競爭 —— 破壞 lock-free 的意義。
修法 單調遞增計數器 + power-of-2 mask。head/tail 是「邏輯計數器」,持續累加、永不取模;只在索引 storage 時才 & mask(cap 是 2 的次方 → x & (cap-1) == x % cap)。於是:
  • len = tail.wrapping_sub(head) —— 因為真實筆數恆 ≤ cap,模 2⁶⁴ 的減法剛好等於筆數。
  • 空 = head == tail;滿 = len == cap。不浪費任何一格,也不需要 count 欄位。
  • SPSC 下 head 只有 consumer 寫、tail 只有 producer 寫 → 各自 single-writer,免 RMW(見追問)。

② Rust 實作要點

  • 容器:Vec<Option<T>>(單執行緒版)。Option 讓 pop 能 .take() 把值搬出、留 None,move-out 乾淨且無 unsafe。
  • 為什麼不用 VecDeque:它會在容量滿時重新配置成長 —— bounded 環的重點正是不成長。你要的是「滿了就拒絕/覆寫」,不是自動擴容。
  • ownership 陷阱:別存 Vec<T> 然後想「就地覆寫」—— move-out 一個已初始化的 T 需要 mem::replace 或 Option。用 Option 最省事。

③ 複雜度

  • time push / pop / len / is_full 全 O(1) worst-case(無攤還、無成長)。
  • space O(cap) 固定;無隱藏配置。

⑤ 面試追問

滿了要 block 還是 drop-oldest?
看語意。command / control queue → block(命令不能掉)。telemetry / packet capture → drop-oldest(新資料較有價值,backpressure 會拖垮 producer)。
我的立場telemetry 串流我一律 drop-oldest + 計數丟棄量(exported 成 metric),而不是 block。因為 monitoring pipeline 阻塞會反噬被監控的 hot path;寧可掉舊 sample,也要留下「掉了幾筆」的可觀測性。
drop-oldest 在 SPSC 下怎麼不 race?
單執行緒直接 pop 再 push(如上)。但 SPSC 下 producer 不能改 head —— 那是 consumer 的 single-writer 領地。所以 producer 端的 drop-oldest 只能「覆寫 tail 指到的舊格 + 推進 tail」,讓 consumer 自己發現 gap;或乾脆改成 bounded try_push 回報 full,把丟棄決策上交。
那 MPMC 呢?兩個 atomic index 還夠嗎?
不夠。多 producer / 多 consumer 下,單靠兩個 index 無法界定「這格到底被誰佔了」。要 per-slot sequence number(Vyukov MPMC queue)或直接上鎖。這也是為什麼 std 不提供 lock-free MPMC —— crossbeam 用的是 epoch-based reclamation + 每格 seq counter,遠比兩個 index 複雜。

為什麼 SPSC 只需兩個 atomic index(附可編譯 unsafe 版)

關鍵是 single-writer per index:producer 只 store tail、consumer 只 store head。既然每個 index 只有一個 writer,就不需要 RMW(fetch_add),只要 plain load + store 配 acquire/release。Release store 把 payload「發佈」在 index bump 之前;對端 Acquire load 保證看到 index 時 payload 已可見(承你的 memory-ordering 筆記:release 發佈、acquire 觀測)。跨執行緒共享 buffer 這件事本身逼你用 UnsafeCell + unsafe —— 這是「何時 unsafe」的標準時機:safe Vec 無法被兩條 thread 同時 &mut。

注:為求簡短,此版未實作 Drop 去 drain 未消費的 T(會 leak)。production 版要在 Drop 把剩餘元素讀出丟棄。已跨執行緒驗證 10k 筆 FIFO 保序。

⑥ Thread-safe 階梯:lock → SPSC → MPSC → MPMC

選型軸
  • 幾個 writer / 幾個 reader 決定機制:1↔1 → SPSC(兩個 atomic index);多寫多讀 → 每格 sequence(MPMC)或鎖。
  • 要不要 block:worker 沒事做要睡 → Condvar;純交遞、caller 自己 spin/retry → lock-free。
  • 下面把 SPSC(上一節)延伸成完整階梯。

A. Lock 版:Mutex + Condvar bounded blocking queue

這是 thread pool 的 work queue primitive。兩個 condvar:not_full(producer 滿了就睡)、not_empty(consumer 空了就睡)。backpressure 天然落在 not_full。

最常見的兩個 bug
  • 用 if 而非 while:condvar 有 spurious wakeup(無人 notify 也可能醒),且醒來到重拿鎖之間別的 thread 可能已把 slot 搶走 → 條件要重驗。if 會在假設不成立時繼續往下 push/pop → 破表或 panic。
  • 只用一個 condvar:producer 和 consumer 共用一個 condvar + notify_one 時,可能喚醒「錯的那一邊」(notify 了另一個 producer 而非等待的 consumer)→ lost wakeup / 死鎖。分兩個 condvar(或用 notify_all,較浪費)。

B. Lock-free bounded MPMC(Vyukov per-slot sequence)

多 producer 多 consumer、bounded、無鎖。核心:每格帶一個 sequence number,把「這格輪到誰寫/誰讀」編碼進 seq,取代鎖。這也是回答「兩個 atomic index 為何不夠 MPMC」的正解。unverified:此設計一般歸給 Dmitry Vyukov(我沒逐字核對原始出處,但這是廣泛流傳的版本)。

已驗證:4 producer / 4 consumer 各推 disjoint id 範圍共 8 萬筆,exact-set 比對 0 重複 0 遺失(×3);valgrind memcheck 無 uninit read / 無 UAF。

C. Lock-free unbounded MPSC(Vyukov intrusive,XCHG)

多 producer 單 consumer、unbounded、linked-list。producer 端是 wait-free:一個 head.swap()(XCHG)就掛上節點。這是跟 MPMC array 完全不同的技巧,值得單獨會。跨執行緒共享 raw node → 必須 unsafe + 手動 Box::into_raw/from_raw,是「何時 unsafe」的又一標準場景。

關鍵陷阱:the gap head.swap(n) 之後、(*prev).next.store(n) 之前有一個瞬間視窗:新節點已是 head 但還沒被前一個節點的 next 連上。此時 consumer 走到尾端會看到 next == null 而暫時判定「空」,即使其實有個 push 正在進行。演算法用 stub 節點 + 「tail != head 就回 None 稍後重試」處理這個 transient(它是 linearizable 的,只是有這個 window)。面試講得出這個 gap = 深度訊號。

已驗證:8 producer / 1 consumer × 5 萬筆 disjoint id,exact-set 0 重複 0 遺失(×5);memcheck 無 UAF(節點回收正確)。

Self-quiz

為什麼 head/tail 用單調遞增而非取模儲存,能同時解決「滿/空判別」與「不浪費一格」?
物理索引版 head == tail 有二義性(空或滿),只能靠犧牲一格或 count 欄位化解。單調計數器讓 tail - head(wrapping)直接等於真實筆數(因筆數恆 ≤ cap),於是空 = 相等、滿 = 差 == cap,兩者可區分且不需犧牲格子。索引 storage 時才 & mask 繞回。
為什麼 SPSC 不需要 fetch_add,但 MPMC 需要更多機制?
single-writer per index:SPSC 中每個 index 只有一個 writer,load 後可安全 store(無他人插隊),故不需 atomic RMW。MPMC 中多個 producer 競爭同一 tail,必須 RMW 或 per-slot sequence number 來界定所有權,否則兩個 producer 會搶到同格。
producer 端 tail.store(.., Release) 換成 Relaxed 會怎樣?
consumer 可能看到 tail 已 bump,卻讀到尚未寫入的 payload(store 重排到 payload write 之前),讀到未初始化記憶體 = UB。Release↔Acquire 建立 happens-before:對端看到新 tail 時,保證也看到那之前的 payload write。
blocking queue 的 while q.is_empty() 改成 if,構造一個會出錯的 interleaving。
兩個 consumer 都在 not_empty 上睡。producer push 一筆、notify_one... 但 condvar 允許 spurious wakeup,兩個 consumer 可能都醒。用 if:consumer A 醒→拿鎖→pop_front 取走唯一元素;consumer B 醒→拿鎖→if 已跳過→直接 pop_front().unwrap() 對空 queue → panic。while 會讓 B 重驗 is_empty() 為真 → 繼續睡。
MPMC 的 push 若把 cell.seq.store(pos+1, Release) 改成 Relaxed,會發生什麼?
consumer 的 seq.load(Acquire) 看到 pos+1 就認為「payload 已寫好可讀」,但 Relaxed store 讓「寫 payload」與「更新 seq」可被重排 → consumer 可能讀到尚未寫入的格子(uninit memory)= UB。Release store ↔ consumer 的 Acquire load 建立 happens-before:看到新 seq 保證看到 payload。這與 SPSC 的 tail 發佈是同一個道理。

LRU Cache(O(1) get / put)

用途 固定容量 cache,滿了淘汰「最久沒被存取」者;get 與 put 都要 O(1)。
Systems 場景:機櫃管理 metadata cache(node → 最近狀態)、telemetry 的 hot-series cache。熱資料留住、冷資料自動退場,記憶體有界。

① 概念推導

Naive HashMap<K, V> 存值 + VecDeque<K> 記 recency 順序(隊尾 = MRU)。get 命中就把該 key「移到隊尾」。
失敗模式 「把中間某個 key 移到隊尾」在 VecDeque 是 O(n):先線性掃描找到它(O(n)),再從中間移除(O(n) 搬移)。每次 get 都 O(n) → 整個 cache 退化。淘汰時找 LRU 是 O(1)(隊首),但promote 才是致命傷。
修法 HashMap + O(1) 可摘除的雙向鏈表。鏈表給「O(1) 從任意位置摘掉再插到頭」,HashMap 給「O(1) 由 key 定位到節點」。Rust 特有取捨:雙向鏈表不要用 Rc<RefCell>(prev 要 Weak、每次存取 runtime borrow、節點散落 heap),改用 index-based slab:
  • 所有節點放進一個 Vec<Node>(arena/slab),prev/next 是 Option<usize> 索引而非指標。
  • map: HashMap<K, usize> 存 key → slot index。
  • head(MRU)/tail(LRU)是 Option<usize>;淘汰打 tail,存取後 push 到 head。
  • 被淘汰的 slot 進 free vec 回收重用 —— 避免 Vec 無限成長。

② Rust 實作要點

  • 為什麼 index 而非指標:雙向鏈表在 safe Rust 幾乎無法直接寫 —— 節點 A 的 next 指 B、B 的 prev 指 A,是互相別名的可變指標,borrow checker 直接拒絕。index 把「指標」變成 usize,不觸發 borrow checker,所有 mutation 都經 self.nodes[i] 走。
  • ownership 陷阱:key 存兩份。HashMap<K, usize> 內部持有 key;淘汰時我們從 tail 節點反查它的 key 才能從 map 移除 → node 也得存一份 key。故 K: Clone。這是無法避免的(HashMap 本來就擁有 key 的所有權)。
  • borrow checker 通關技巧:get 先把 map.get(k) 的 &usize copy 成 usize(let i = *self.map.get(k)?;),借用立刻結束,後面才能自由 &mut self。回傳 &V 綁在 &mut self 生命週期上,合法。

已對 brute-force LRU(Vec<K> 順序 + retain)在 cap 1–5、各 20k 隨機 ops 下交叉驗證通過。

③ 複雜度

  • time get / put O(1) 期望(HashMap 命中 O(1) 期望 + detach/push_front 各 O(1) worst)。
  • space O(cap);slot 靠 free-list 回收,nodes 長度最終穩定在 cap。
  • 對照 naive:time get O(n)、put O(n) —— 就是 VecDeque 中段移除的線性成本。

④ 互動 stepper

cap=3。同時看三個視圖:map(key→slot)、slab(Vec 節點的 prev/next 索引)、邏輯鏈(MRU 頭→LRU 尾)。留意 put(4) 淘汰後,被釋放的 slot 立刻被 free-list 重用。

⑤ 面試追問

為什麼不直接用 Rc<RefCell> 寫雙向鏈表?
能寫,但三個代價:prev 要用 Weak(否則 prev↔next 形成 Rc cycle → leak);每次存取要 borrow()/borrow_mut(),違反借用規則會 runtime panic(不是編譯期擋);節點散在 heap → cache miss。index 版三者全免,代價只是「index 可能失效」(而失效有 free-list 管理就穩)。
我的立場面試寫 LRU 我一律 index-based slab。Rc<RefCell> 只在「節點會被 cache 外部共享持有、生命週期不齊」時才用 —— LRU 節點的所有權完全在 cache 內,沒有外部共享需求,用 Rc 是拿 runtime borrow check + cycle 風險換零好處。
並發下「讀即寫」(get 也改動 LRU 順序)怎麼辦?
RwLock 沒用 —— 因為 get 也要寫(把節點移到 head)。選項:(a) 全域 Mutex,簡單但 get 也被序列化;(b) sharded LRU:N 個獨立 shard 各自 Mutex,key hash 分流,降低競爭;(c) 近似 LRU:用 atomic access-bit / CLOCK 或 sampled eviction,避免每次 get 都改鏈表。
我的立場高 QPS telemetry cache 我不維護精確 LRU order,改用 CLOCK / sampled(近似)。理由:精確 recency 的價值遠低於「每次 get 都要抓寫鎖去改鏈表」的競爭成本;近似 LRU 命中率通常只差幾個百分點,卻換來讀路徑幾乎無鎖。
sharded LRU 的淘汰精度問題?
分 shard 後,淘汰是各 shard 內的 LRU,不是全域 LRU —— 可能淘汰掉「全域看還算熱」的 key。實務上 shard 數不要太多(競爭與精度的權衡),且 key 分佈要夠均勻,否則某 shard 過載會提早淘汰熱 key。這是「用一致性換並發度」的典型取捨。

⑥ Thread-safe 版

先破一個常見反射:RwLock 救不了 LRU 直覺是「讀多寫少 → 包 RwLock 讓讀並行」。沒用——因為 true LRU 的 get 本身是寫(要把命中節點提到 MRU、改鏈表指標)。既然每次讀都要改結構,就拿不到 read lock 的並行性,RwLock 退化成 Mutex 還多付一層開銷。
三條實際路線
  • 全域 Mutex<LruCache>:最簡單、正確,但所有 get/put 序列化 → 高 QPS 下鎖競爭成瓶頸。
  • Sharded(下方 code):N 個獨立 Mutex<LruCache>,key hash 分流。競爭降 N 倍。代價:淘汰是 per-shard LRU,非全域。
  • 近似 LRU(CLOCK / sampled):read 只翻一個 atomic reference bit(可在 read lock 下做),或像 Redis 抽 N 個 key 挑最舊。放棄精確 recency 換讀路徑幾乎無鎖。

已驗證:8 執行緒併發 get/put,每個 key 讀回值與寫入一致(包裝於前述已驗證的 index-based LruCache 之上)。

Self-quiz

為什麼 naive 的 HashMap + VecDeque get 是 O(n),而雙向鏈表版是 O(1)?
get 命中要把該 key promote 成 MRU。VecDeque 中該 key 在中間,定位要 O(n) 線性掃、移除要 O(n) 搬移。雙向鏈表配 HashMap:map 直接 O(1) 給出節點索引,detach 只改該節點前後鄰的兩個指標(O(1)),push_front 也 O(1)。
為什麼 K 必須 Clone?能不能只存一份 key?
淘汰時我們手上只有 tail 的 slot index,要從 map 移除就得知道那個 slot 對應哪個 key → node 必須存 key。而 HashMap<K, _> 本來就擁有一份 key。兩處都需要 key,故無法只存一份,K: Clone 不可避免(除非改成 Rc<K> 共享,但那又引入 Rc 開銷)。
如果拿掉 free vec、淘汰後不回收 slot,會有什麼後果?
nodes 會無限成長:每次淘汰留下一個死 slot,新插入又 push 一個 → 記憶體隨 put 次數線性膨脹,失去 bounded 的意義。free-list 讓死 slot 被重用,nodes.len() 穩定在 cap 附近。
get 裡若寫成 let i = self.map.get(k)?;(不 deref copy)會怎樣?
i 是 &usize,對 self.map 的不可變借用還活著;接著 self.detach(i) 需要 &mut self → 與活著的不可變借用衝突,編譯失敗。let i = *self.map.get(k)?; 把 usize(Copy)拷出來,借用即結束,後續才能 &mut self。

DSU / Union-Find

用途 動態維護「哪些元素屬於同一組」,支援 union(合併)與 find(查代表)近乎 O(1)。
Systems 場景:叢集/連通性 —— 哪些 node 在同一 fault domain、哪些 sensor 屬同一 rack group、network partition 後誰還連得到誰。

① 概念推導

Naive 每個元素存一個 group id;union 時把一組所有元素的 id 改成另一組。或者 parent 指標形成森林,find 一路往上爬到 root。
失敗模式 group-id 版:union 要掃整組改 id,O(n)。樸素 parent 森林版:若總把 A 掛到 B,可能長成一條退化鏈,find 變 O(n)(爬整條鏈)。連續 union 可以把樹拉成一條線。
修法(兩個 lever 疊加)
  • union by rank:合併時把「矮樹」掛到「高樹」下,樹高不輕易增加(只有兩棵等高才 +1)。rank 是樹高上界。
  • path compression:find 爬到 root 後,把路徑上每個節點直接指向 root,下次 find 幾乎 O(1)。
兩者合用 → 攤還 O(α(n))(反 Ackermann,實務上 ≤ 4,視同常數)。

② Rust 實作要點

  • 容器:兩個 Vec —— parent: Vec<usize>、rank: Vec<u8>(樹高上界極小,u8 綽綽有餘)。全 index-based,天生無 ownership 問題。
  • find 用 iterative two-pass 而非遞迴:遞迴版 self.parent[x] = self.find(self.parent[x]) 在 Rust 需要小心 borrow(參數先求值再 &mut self,two-phase borrow 能過但讀者要愣一下);iterative「先找 root、再壓平」更清楚,且無遞迴爆 stack 之虞。
  • union 回傳 bool:回報「這次是否真的合併了」(false = 本來就同組)。面試常追問「加這條邊會不會形成環」—— 就是 !union(a,b)。

已對「BFS flood 的 ground-truth 連通性」在隨機邊集下交叉驗證通過。

③ 複雜度

  • amortized find / union O(α(n))(union by rank + path compression 合用)。
  • 只有 path compression:amortized O(log n);只有 union by rank:worst O(log n)。
  • space O(n)(parent + rank 兩個 vec)。

④ 互動 stepper

n=6。看 union 如何依 rank 決定掛法;做 find 時 path compression 把路徑上的節點直接拉到 root(森林變扁,橘色 = 這步被改動的節點)。

⑤ 面試追問

rank 還是 size,二選一都行嗎?
都能保證 O(α) 攤還。rank ≈ 樹高上界,純為平衡;size = 子樹節點數,額外能免費回答「這個連通塊多大」。
我的立場叢集管理場景我用 size,不用 rank。因為「component 大小」本身就是我要的資訊(最大 fault domain 多大、某 partition 涵蓋幾個 node),用 size 順手就有;rank 只給我平衡、不給我語意。平衡效果兩者實質等價。
path compression 的攤還怎麼論證?
直覺:一條長度 L 的鏈,find 一次把整條壓平成「全部直指 root」,付了 O(L),但這 O(L) 的成本攤到後續每個節點的下次 O(1) find。單獨 path compression 給 O(log n) 攤還;配上 union by rank(保證樹一開始就矮)才降到 O(α(n))(Tarjan 的分析)。
能不能 union 後再拆分(delete / split 一條邊)?
標準 DSU 不支援。path compression 把中間節點直接接到 root,摧毀了原本的父子歷史,無法還原「拆掉某條邊後」的結構。要動態刪邊:用 link-cut tree,或 offline reverse(把刪邊當成「時間倒著跑的加邊」離線處理)。若只是要 undo,得放棄 path compression,改 union by rank + 變更 stack(rollback DSU),find 退回 O(log n)。這是 DSU 的硬限制,面試講得出來就是深度訊號。

Self-quiz

只做 union by rank、不做 path compression,find 最差多少?反過來呢?
只 union by rank:樹高 O(log n) → find worst O(log n)。只 path compression(總把 a 掛 b):單次可能爬長鏈,但攤還後 O(log n)。兩者合用才 O(α(n))。
「加這條邊 (a,b) 會不會形成環」怎麼一行判斷?
!self.union(a, b)。union 回傳 false 表示 a、b 本來就同組 → 再連一條邊就成環。true 表示成功合併(原本不同組,不成環)。這也是 Kruskal MST 判邊是否納入的核心。
為什麼 rank 用 u8 就夠,不會 overflow?
rank 只在「兩棵等高樹合併」時 +1,而 union by rank 保證高度為 h 的樹至少含 2ʰ 個節點。要 rank 達到 255 需要 ≥ 2²⁵⁵ 個節點,遠超任何真實輸入。u8 綽綽有餘,還省 cache。

Systems 場景:service dependency graph(啟動順序 = topo)、network topology 最短路由(Dijkstra)、資源依賴的環偵測。

⑤ 面試追問

稀疏 vs 稠密怎麼選表示法?(見上表)
稀疏 → list(空間 O(V+E)、遍歷鄰居 O(deg));稠密且 V 小 → matrix(查邊 O(1))。
Dijkstra 為何要 if d > dist[u] { continue }?
std BinaryHeap 無 decrease-key,所以我們對同一節點做 lazy insertion:每次鬆弛都 push 新 entry,舊 entry 留在堆裡。pop 到「距離已被更新過的舊 entry」就跳過。代價是堆大小到 O(E),但總複雜度仍 O(E log V)。
用支援 decrease-key 的 Fibonacci heap 會更快嗎?
理論 O(E + V log V) 更漂亮,但 Fibonacci heap 常數大、cache 極差、實作複雜,實務上 binary heap + lazy deletion 幾乎總是更快。這是「理論最優 ≠ 實務最優」的經典案例。真要壓榨,改用 d-ary heap(d=4)改善 cache locality 比換 Fibonacci 實在。

Self-quiz

Kahn's topo 如何順便偵測環?DFS 版怎麼偵測?
Kahn:若最終 order.len() < n,表示有節點永遠 indegree > 0(卡在環裡出不來)→ 有環,回 None。DFS 版:用三色標記(白未訪/灰在遞迴堆疊上/黑已完成),遇到指向「灰」節點的邊 = back edge = 環。
為什麼無權最短路用 BFS 而不是 Dijkstra?
無權(或權全等)時,BFS 天然按「邊數」層層擴展,第一次到達某點就是最短,O(V+E)。Dijkstra 帶 heap 的 O(E log V) 在此是殺雞用牛刀 —— heap 的排序對等權圖毫無必要。
DFS 用顯式 stack 而非遞迴,主要好處是什麼?
避免深圖遞迴爆 call stack(Rust 預設 8MB thread stack,深度上萬節點的鏈就可能 overflow → abort)。顯式 stack 用 heap 上的 Vec,深度只受記憶體限制。代價是 pre-order 需 .rev() 才符合遞迴的自然順序。

Trie(prefix tree)

用途 字串集合,支援 O(L) 的插入 / 完整比對 / 字首查詢(L = 字串長度)。
Systems 場景:URL / path routing(/api/v1/nodes 的前綴匹配)、autocomplete、command dispatch 的 prefix match。

① 概念推導

Naive 每個 TrieNode 用 Box<TrieNode> 遞迴持有子節點(children: [Option<Box<TrieNode>>; 26])。
失敗模式 Box 遞迴結構有兩個 Rust 痛點:(1) 節點散落 heap,走一條字串 = 一連串 pointer chasing,cache 不友善;(2) drop 是遞迴的 —— 深 trie 的解構會遞迴呼叫,可能爆 stack。而且要在遞迴 Box 結構上同時持有「當前節點的 &mut」與「往下走」,borrow checker 常打架。
修法 arena:所有節點放進一個 Vec<TrieNode>(index 0 = root),children 是 [Option<usize>; 26] 索引。走訪 = 陣列索引(cache 好),配置新節點 = Vec::push(連續記憶體),drop = 一次釋放整個 Vec(非遞迴)。borrow checker 完全不參與 —— 全是 usize。

② Rust 實作要點

  • children 容器:[Option<usize>; 26](限定 a–z)。[None; 26] 能直接初始化因為 Option<usize> 是 Copy。直接索引 (b - b'a') → O(1) 無 hash。
  • 用 bytes() 而非 chars():限定 ASCII a–z 時 word.bytes() 直接給 u8,(b - b'a') 算 index;chars() 給 char(4 bytes)還要轉換。
  • 配置模式:插入時「查子節點 → 沒有就 push 新節點、記下 index、回填 parent 的 children」。注意先取 self.nodes.len() 當新 index,push 後再回頭改 self.nodes[cur].children[c] —— 兩次索引不重疊,borrow OK。

已驗證:contains("app") 為真而 contains("ap") 為假(前綴不算完整字);starts_with 與 contains 語意分離正確。

③ 複雜度

  • time insert / contains / starts_with O(L)(L = 字串長度),與集合大小無關。
  • space 最差 O(Σ N·L) 個節點(N 字串各長 L,無共用),每節點固定 26 個 slot。共用前綴越多越省。

④ 互動 stepper

⑤ 面試追問

array [Option<usize>; 26] vs HashMap<char, usize> children,怎麼選?
array:O(1) 直接索引、cache-friendly、程式碼簡單;但每節點固定 26×8 = 208 bytes,稀疏(多數 slot 是 None)時浪費。HashMap:隨實際 children 成長、支援任意 alphabet(unicode);但每次存取有 hash + pointer chasing 開銷。
立場限定 a–z 的面試題我一律用 array —— 更快、更簡單、記憶體有界且無 hash 抖動。只有 alphabet 很大(unicode、任意 byte)或極度稀疏時才換 HashMap;此時通常還會考慮換掉整個 26-ary 設計。
IP routing table(longest-prefix match)是什麼變體?
不是 26-ary,而是 bitwise / binary radix trie(每 bit 一層),或壓縮成 path-compressed radix (Patricia) trie(把單一子節點的鏈合併成一條邊)。full 256-ary 每節點太胖 → 用 multibit trie 折衷 stride(一次吃幾個 bit)。
Patricia / radix 的 path compression 省什麼、代價?
省掉「只有一個子節點」的鏈:URL routing 有長共同前綴(/api/v1/...)時,把 a-p-i-/-v-1 這種單鏈壓成一條邊,節省節點數與遍歷步數。代價:插入/刪除要 split / merge 邊,邏輯複雜很多。unverified:Rust router 如 matchit / axum 內部走的正是這類 radix 設計(細節我沒逐行核對,別當定論)。

Self-quiz

為什麼 contains 要檢查 is_end,而 starts_with 不用?
walk 走到某節點只證明「這條路徑存在」。對 contains,還需該節點是某個字的結尾(is_end)—— 例如插了 "apple",走 "app" 到得了節點但它不是字尾,contains("app") 應為 false。starts_with 只問「有無這個前綴」,走得到就是 true,不管 is_end。
用 Box 遞迴結構取代 arena,drop 深 trie 時的具體風險?
Box<TrieNode> 的 drop 是遞迴的:drop 一個節點會 drop 它的 children、再 drop children 的 children…深度 L 的 trie 遞迴 L 層。深到一定程度(數萬層)會爆 call stack → abort。arena 版 drop 整個 Vec 是線性走過陣列、無遞迴。
[None; 26] 為什麼能直接寫,換成 [Vec::new(); 26] 為什麼不行?
[x; N] 陣列字面量要求元素型別是 Copy(才能複製 N 份)。Option<usize> 是 Copy → OK。Vec 不是 Copy(擁有 heap 配置)→ [Vec::new(); 26] 編譯失敗,得用 std::array::from_fn(|_| Vec::new()) 之類。

Tree(泛用)— arena vs Rc<RefCell>

用途 泛用階層結構(可雙向父子導航),非特化的 BST/trie。

① 概念推導:為什麼 Rust 的樹比想像中麻煩

核心衝突 一般的雙向樹:parent 持有 children、child 持有 parent 的指標。這在 Rust 是互相別名的可變引用 —— borrow checker 直接違法(child 若持 &mut parent,同時 parent 又持 child,違反「同一時間至多一個 &mut」)。單向(只 parent→child、Box)可以,但一要雙向、要共享、要能改,safe 引用就走不通。
兩條出路
  • A. index-based arena:所有權集中在 Vec,節點間用 usize 當「弱指標」。不觸發 borrow checker。
  • B. Rc<RefCell>**:shared ownership(Rc)+ interior mutability(RefCell)。但 parent 回指必須是 Weak,否則 Rc cycle → 永不 drop(leak)。

雙向父子 = 互相別名的可變引用,borrow checker 禁止。要嘛 Rc<RefCell>(shared + interior mutability,但 cycle + runtime panic),要嘛 arena + index。
index 版怎麼解、代價是什麼?
所有權集中 arena Vec,節點間用 usize 當弱指標,不觸發 borrow checker。代價:usize 沒有生命週期保護 —— 刪節點(或 slot 被回收重用)後,舊 index 變 dangling。存取到會拿到錯的節點或 OOB panic,但這是邏輯 bug,不是 UB(不會記憶體不安全)。
怎麼把「index 失效」變成可偵測?
generational index:slot 存 (generation, Option<T>),handle 存 (index, generation)。存取時比對 generation —— 不符表示該 slot 已被回收重用 → 回 None,把「dangling index」變成安全的 None。std-only 手刻:Vec<(u32, Option<T>)> + free-list,回收時 generation +1。unverified:slotmap crate 與多數 ECS / game arena 用的就是這套(我沒逐行核對其實作)。
立場純內部演算法樹(BST、trie、parse tree、我這裡的依賴樹)一律 arena。Rc<RefCell> 只在「節點需要被多個外部擁有者共享持有、生命週期不齊」時才用 —— 例如 GUI widget tree、observer,或需要「把某子樹 clone 出去獨立存活」。為了避免 runtime borrow panic 與 cycle,能 arena 就 arena。

⑥ 跨執行緒:Send / Sync

兩版的並發性質正好相反
  • Arena 版天生 Send:它就是 Vec<usize> + Vec<T>(當 T: Send)。要多執行緒共享讀 → Arc<Tree>;要共享改 → Arc<Mutex<Tree>> 或 RwLock。結構本身不用動。這是 index 版在並發下更省事的又一理由。
  • Rc<RefCell> 版是 !Send:Rc 非 Send(refcount 非 atomic)、RefCell 非 Sync。跨執行緒要整組換:Rc→Arc、RefCell→Mutex(或 RwLock)、rc::Weak→sync::Weak。

已驗證:Link<i32> 通過 Send + Sync bound 斷言;arena 的 Vec 版無需包裝即為 Send。

立場換到 Arc<Mutex> 是「每個節點一把鎖」——細粒度但鎖多、易死鎖(同時鎖 parent+child 要固定順序)。演算法樹我幾乎不會這樣做;要並發改樹,更常是整棵 Arc<RwLock<Tree(arena)>>(一把大鎖包 arena),或 copy-on-write 換整棵。逐節點鎖留給真正需要獨立子樹並發的場景。

Self-quiz

B 版 parent 若用 Rc(而非 Weak)會怎樣?
parent 強持 child、child 又強持 parent → Rc cycle。兩者 strong_count 永遠 ≥ 1,即使外部全部 drop 也不歸零 → 節點永不釋放(記憶體 leak)。Weak 讓回指不計入 strong count,打破環;存取時 upgrade() 檢查目標是否還活著。
index 版與 Rc<RefCell> 版,各自「出錯」的性質有何本質差異?
index 版:失效 index → 拿錯節點或 OOB panic,是邏輯錯誤,記憶體仍安全(Rust 保證 Vec 索引不越界訪問)。Rc 版:借用規則違反 → RefCell runtime panic;或忘記 Weak → leak。兩版都不會 UB,但 index 版錯誤更「安靜」(可能默默拿錯資料),Rc 版更「大聲」(直接 panic)。
什麼情境下 Rc<RefCell> 才是對的選擇?
當節點需要被 tree 外部共享持有、生命週期與 tree 不一致時。例如:把一個子樹交給另一個系統獨立存活(clone 一個 Rc 即可,arena 版做不到);或 observer / GUI 場景多個持有者。純演算法內用、所有權都在結構內 → arena 更好。

Event / Timer Queue(min-heap by deadline)

用途 一堆帶 deadline 的任務,總是先取「最早到期」者;並回報「距下一個 deadline 還有多久」。
Systems 場景:executor 的 timer(承 P2)、event loop 的 epoll_wait timeout 計算(P3)、retry / keepalive 排程。

① 概念推導

Naive Vec<(Instant, Task)>,每次要取最早的就掃全部找 min,或每次插入後 sort。
失敗模式 掃 min:每次取到期任務 O(n)。每插入即 sort:O(n log n) per insert。timer 場景是「海量排程 + 頻繁取最早」→ 這兩種都退化。
修法 min-heap by deadline。std 的 BinaryHeap 是 max-heap,用 Reverse 把 (Instant, id) 反轉成「最早 deadline 在頂」。peek 頂 O(1)、push / pop O(log n)。Instant 本身實作 Ord(單調時鐘),tuple 依字典序比較 —— deadline 為主鍵,天然正確。

② Rust 實作要點

  • 容器:BinaryHeap<Reverse<(Instant, u64)>>。存 (deadline, task_id);payload 若大,另用 HashMap<u64, Task> 側表,heap 只排 id(避免搬 payload)。
  • next_timeout 是與 event loop 的接點:回傳「距最近 deadline 多久」,直接餵給 epoll_wait / poll 的 timeout 參數。用 saturating_duration_since —— 已過期的 deadline 回 Duration::ZERO 而非 panic 或負值。沒有 timer 時回 None(對應 epoll_wait timeout = -1,無限等)。這把「timer 到期」與「I/O 就緒」統一成同一個 park 點。
  • ownership:pop 直接 move 出 Reverse((when, id)) 解構,無借用糾纏。

已驗證:三個亂序 deadline 插入後,next_timeout 回最早者;pop_ready 按 deadline 序吐出到期任務;已過期 deadline 的 next_timeout 回 Duration::ZERO(不 panic)。

③ 複雜度

  • time schedule O(log n)、peek / next_timeout O(1)、pop 單筆 O(log n)。
  • space O(n)(n = 排程中的 timer 數)。
  • 對照 naive:掃 min 取到期 O(n)、每插入即 sort O(n log n)。

④ 互動 stepper

插入 deadline 亂序的 5 個 timer,再連 pop 兩次最早者。橘色 = 這步 sift 交換的節點。

注意:std BinaryHeap 內部就會做這些 sift-up / sift-down,API 隱藏了細節。這個 stepper 是把內部行為攤開,解釋 O(log n) 從何而來 —— 不是說你要自己寫 sift。

⑤ 面試追問

量大時為什麼 min-heap → timer wheel?
min-heap 每次 insert / expire O(log n),且 heap array 對「海量 timer、多數會被 cancel / reset」的負載 cache 不友善(sift 到處跳)。timer wheel:用 bucket by (deadline mod wheel_size),insert / expiry 攤還 O(1)。
立場TCP retransmit / keepalive 這種「海量 timer、多數提早取消、deadline 範圍有界」用 wheel;一般 app 的少量、範圍差異大的 timer 用 min-heap 就好 —— wheel 的離散解析度與 cascade 複雜度不值得為幾十個 timer 付出。
timer wheel 的代價?
解析度離散(每 tick 一格,精度受格子大小限制);deadline 範圍大時,單層 wheel 格子會爆 → 要 hierarchical wheel(多層,像時鐘秒/分/時)。cancellation 也要能 O(1) 定位到 bucket(通常 handle 記著自己在哪格)。
hashed vs hierarchical wheel?
hashed(單輪 + 每 bucket 一條 overflow list):簡單,但同 bucket 不同「輪次」的 timer 混在一條 list,tick 時要掃 list 挑出真的到期的。hierarchical(層層 cascade):插入 O(1),但 tick 到某層歸零時要把上層 timer cascade 下放到細層。unverified:Linux kernel timer 的具體演進(早期 hierarchical、後來為省 cascade 改用其他方案)我記不牢,別當定論;重點是「精度 vs 記憶體 vs cascade 成本」的三方取捨。

⑥ Thread-safe 版:worker 睡到最近 deadline

真正的 timer thread 長這樣:Mutex<BinaryHeap> + Condvar,worker 用 wait_timeout 睡到最近的 deadline。若有人排進一個更早的 timer,notify 叫醒 worker 重算睡眠長度。Tokio 的 timer driver 也是這骨架。

兩個必對的點
  • 睡的是「到最近 deadline 的差」,不是固定間隔:wait_timeout(dur) 的 dur = when − now。這正是 epoll reactor 裡 epoll_wait 的 timeout 參數來源——timer 的 next_timeout() 直接餵給 event loop。
  • 插入更早 timer 要 notify:否則 worker 還在睡舊的、較晚的 deadline,新的早 timer 會遲發。wait_timeout 被 notify 叫醒後重新 peek 算新的 dur。

已驗證:一個晚插入但絕對 deadline 更早的 timer(id 2)正確搶佔到較早排、deadline 較晚者(id 1、3)之前 → fire 序 [2,1,3,4](×3 穩定)。證明 wait_timeout + notify 的搶佔生效。

Self-quiz

為什麼要 Reverse?不加會怎樣?
std BinaryHeap 是 max-heap,peek/pop 給最大值。timer 要「最早 deadline」= 最小 Instant。Reverse 反轉比較,讓最小的浮到頂。不加就會先取到最晚的 timer,完全錯誤。
next_timeout 為什麼用 saturating_duration_since 而非 duration_since?
若 deadline 已過(when < now),duration_since 在部分平台會 panic(不允許負 Duration)。saturating_duration_since 回 Duration::ZERO —— 語意正確:「這個 timer 已到期,timeout 應為 0,立刻處理」,直接餵給 epoll_wait(0) 做非阻塞 poll。
heap 存 (Instant, u64) 而非 (Instant, Task),好處是什麼?
payload 大時,heap 的 sift 每次交換都要搬整個 Task → 昂貴。只排 u64 id、payload 放側表 HashMap<u64, Task>,sift 只搬 16 bytes 的 tuple,便宜。也讓 cancellation 容易(從側表移除即可,heap 裡的 stale id pop 到時查無側表就跳過)。

epoll + async:把 reactor、executor、future 接起來

Systems 場景:這是你 JD 裡「bridge HW/SW、定義 comm protocol」+ 「async internals(Pin/Waker)」的正面靶子。把前面的 timer(算 timeout)和一個 epoll reactor 接上一個最小 executor,做出一個真的會 park / wake 的 async runtime 骨架。承 P2(block_on)+ P3(event loop)。

① 先講清楚:std 沒有 epoll

「epoll 理論上可以用」的正解 std::os::fd 只給你 RawFd / AsRawFd,沒有 epoll_wait。所以嚴格說「std-only + epoll」是矛盾的——除非走 FFI。但有一條真 std-only 路徑:你不需要 libc crate。因為 libc.so 本來就被動態連進每個 Linux Rust binary,你可以自己 extern "C" { fn epoll_create1(..) } 手寫宣告,link 時對到系統 libc,零外部 crate。面試要 clarify 的是「我可以自己宣告 epoll 的 extern 嗎」,不是「可以引 libc crate 嗎」。
Edition 2024:unsafe extern "C" 2024 起 extern block 必須標 unsafe,寫 extern "C" { .. } 直接 error: extern blocks must be unsafe。實測:unsafe extern 在 1.81 被拒、1.82 接受,且 1.82 起所有 edition 都接受 —— 所以照 2024 寫也能在 2021 編,沒有理由不直接寫對。
同批(1.82,同樣不限 edition)還來了:block 內可把個別項目標成 safe fn,呼叫時免 unsafe:
本檔的 reactor 四個都留 unsafe:它們全都碰 fd 或 raw pointer,標 safe 是在說謊。

② x86-64 陷阱:epoll_event 是 packed 的

最容易錯的一行 struct epoll_event 在 x86-64 上是 __attribute__((packed)):u32 events 後面沒有 4 bytes padding,整個 struct 是 12 bytes。Rust 這邊必須 #[repr(C, packed)],否則會被排成 16 bytes,傳給 kernel 的 array stride 就錯位、epoll_wait 回來的 fd 是垃圾。連帶陷阱:packed struct 不能取 field 的 reference(&ev.data 是 UB,unaligned),只能整個 copy 出來(let fd = ev.data;)。unverified:此 packed 屬性僅適用 x86-64;其他架構布局不同,libc crate 幫你 per-arch 處理——手寫版要註明架構。

③ 三塊拼圖:Reactor · Waker · Executor

  • Reactor:持 epoll fd + 一張 fd → Waker 表。register 把 fd 加進 epoll 並存 waker;wait 呼叫 epoll_wait,對每個就緒 fd 觸發它的 waker。
  • Waker:用 RawWaker + RawWakerVTable 手工造——這就是 async internals 的核心。底層是一個 Arc<AtomicBool> 旗標,wake() 就把旗標設 true。vtable 的四個函式(clone/wake/wake_by_ref/drop)要正確管 Arc refcount。
  • Executor(block_on):pin future、poll;回 Pending 就 reactor.wait(timeout) 停在 epoll 上;被 wake 後回圈重 poll,直到 Ready。
  ┌─────────── block_on(reactor, future) ───────────┐
  │                                                  │
  │   flag=true ─► poll(future) ──► Ready(v) ─► return v
  │       ▲              │                           │
  │       │              ▼ Pending                   │
  │       │     leaf 把 waker 註冊進 reactor          │
  │       │              │                           │
  │       │              ▼                           │
  │  wake() 設 flag   reactor.wait(next_timeout)      │
  │       ▲              │  epoll_wait(epfd, …, ms)   │
  │       │              ▼                           │
  │       └──── fd 就緒 → 取出該 fd 的 waker ──────────┘
  │             (timeout 由 timer.next_timeout() 決定)
  └──────────────────────────────────────────────────┘

⑤ timer 怎麼接進來

reactor.wait 的 timeout = timer.next_timeout() 骨架裡 reactor.wait(None) 是「無限等 fd」。真實 runtime 同時要處理定時任務:把 併發 timer 的 next_timeout()(到最近 deadline 的 Duration)當成 epoll_wait 的 timeout 參數傳進去。於是 epoll_wait 會在「有 fd 就緒」或「最近的 timer 到期」時返回——I/O 與定時統一在一個 syscall 等待點。這就是 P3 event loop 的心臟,也是為什麼 timer 那節說「timeout 計算是 P3」。

⑥ 這個骨架簡化了什麼(面試要能指出)

  • One-shot 註冊:wait 觸發後 EPOLL_CTL_DEL 拔掉,靠下次 poll 重新 register。production 用 EPOLLONESHOT 或 edge-triggered + 妥善的重掛。
  • 單一 task:block_on 只驅動一個 future。多 task executor 要一個 ready queue(VecDeque<TaskId>),waker wake() 時把 task id 推進 queue,executor 從 queue 取 task 再 poll——waker 就不是設旗標而是 enqueue。
  • Leaf 直接回 Ready:實務 fd 設 O_NONBLOCK,poll 裡真的 read,遇 EAGAIN 才 register + 回 Pending;可能被 spurious wake,要能重試。
  • 沒處理 EPOLLHUP / EPOLLERR:對端關閉 / 錯誤事件要喚醒對應 waker 讓上層 read 拿到 EOF / error。

Self-quiz

為什麼 block_on 一開始把 flag 設 true?設 false 會怎樣?
future 從沒被 poll 過,必須先 poll 一次才會註冊 waker、才可能被喚醒。flag=true 讓第一圈的 swap 取到 true → 進行首次 poll。若設 false:第一圈 swap 取到 false → 跳過 poll → 直接 reactor.wait,但此時 epoll 裡什麼都沒註冊(leaf 還沒 poll 過)→ epoll_wait 永遠不返回 → 死鎖。
packed struct 的 let fd = evs[i].data; 改成 let fd = &evs[i].data; 為什麼是 bug?
#[repr(C, packed)] 下 data 這個 u64 可能落在非 8-byte 對齊的位址(前面只有 4-byte 的 events)。對 packed field 取 reference 會產生一個宣稱對齊、實際未對齊的指標 → 立即 UB(即使 x86 硬體容忍 unaligned load,Rust 語意上仍是 UB,且其他架構會 SIGBUS)。copy by value 讓編譯器生成正確的 unaligned load,是唯一安全的讀法。
wake_by_ref_fn 用 ManuallyDrop,但 wake_fn 沒有。為什麼?
兩者都 Arc::from_raw 重建 Arc(把 raw pointer 當作一份 strong ref 的所有權)。wake 是消耗型(by value):它「用掉」這份 ref,結束時 Arc 正常 drop → refcount 減一,對稱。wake_by_ref不消耗 waker(只借用),若讓重建的 Arc 在函式結束時 drop,會多減一次 refcount → 提早釋放 / double-free。ManuallyDrop 阻止那次 drop,保持 refcount 不變。
edition 2024 逼你在 unsafe fn 裡再寫一次 unsafe {}。這不是多餘的儀式 —— 兩個 unsafe 各自在講什麼?
它們是兩個方向相反的宣告。unsafe fn 是對外的:「我有前提條件,caller 必須保證」(MPSC 的 pop:只能有一個 consumer)。函式內的 unsafe { } 是對內的:「這裡的操作編譯器無法驗證,我已經檢查過了」。2021 把 unsafe fn 的整個 body 當成隱式 unsafe block,等於一旦函式標了 unsafe,body 裡所有危險操作都自動免審 —— 你在裡面手滑多寫一個沒被契約覆蓋的解參考,編譯器不會提醒。分開之後,/// # Safety 寫契約、unsafe {} + // SAFETY: 寫理由,兩者能被獨立審查。
