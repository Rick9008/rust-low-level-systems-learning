async fn 不是「非同步執行的函式」。它是編譯器吐出來的一台狀態機;.await 是暫停點;executor 反覆呼叫 poll 把它往前推,直到 Ready。整個非同步世界只有三個角色。

三個角色(整份教材就繞這三個)

  • Future — 一台可以被 poll 的狀態機。poll 回 Pending(還沒好)或 Ready(v)(好了,值是 v)。
  • Waker — 一個「我可以繼續了」的回呼。Future 回 Pending 前把它存起來,資源就緒時呼叫它。
  • Executor — 一個迴圈:反覆 poll root future;沒事做時睡覺,被 Waker 叫醒再 poll。

你要手搓的 block_on 就是最小的 executor:單執行緒、驅動一個 future 到完成、沒事做時 thread::park() 睡覺、Waker 用 unpark() 叫醒。

① async fn → 狀態機

一個 async fn 被編譯成一台狀態機:每個 .await 點 = 一個狀態。poll 一次,就從當前狀態往前推到下一個 await(或結束)。跨越 await 還要活著的 local,必須被存進狀態機的欄位——不然暫停後就沒了。
naive 心智模型

「async fn 就是一個晚點跑的函式——呼叫它,它就在背景跑起來。」

為什麼壞

它沒有「背景」。呼叫一個 async fn 只是建構一個 Future 值,body 一行都還沒跑。誰來跑?必須有人拿著它一直 poll。沒有 executor,async fn 就是一坨永遠不動的狀態。

推導:一個 async fn 長成什麼狀態機

async fn read_two() -> u32 {
    let a = read().await;   // await #1
    let b = read().await;   // await #2
    a + b
}

兩個 await = 兩個暫停點 = 狀態機有這些狀態。編譯器生一個匿名型別,概念上像:

// 示意,非編譯器真實輸出(真實 layout 更精巧、會挑哪些 local 要存)
enum ReadTwo {
    Start,
    AwaitingA { fut_a: ReadFut },            // 停在 await #1
    AwaitingB { a: u32, fut_b: ReadFut },    // 停在 await #2,a 要跨 await 活著 → 存進來
    Done,
}

poll 的邏輯:match 當前狀態 → poll 內層子 future → 子 future 回 Pending 就整個回 Pending(狀態不變,下次從同一個狀態繼續)→ 子 future 回 Ready 就存下結果、推進狀態、繼續往下跑到下一個 await 或 return Ready。

關鍵伏筆

注意 AwaitingB 裡存了 a: u32——因為 a 在 await #1 之後還要用,必須跨越暫停點活著。凡是跨 await 還活著的 local,都得成為狀態機的欄位。

如果那個 local 是一個借用(指向另一個 local)呢?那狀態機就會有一個欄位指向自己另一個欄位——self-referential。這正是下一頁 Pin 的起點。

executor 那條線(修法預告)

既然 future 要有人一直 poll,最 naive 的 executor 是 loop { poll(future) } 忙輪詢。它有兩個問題:(1) future 回 Pending 時你狂 poll = 100% CPU;(2) 更根本——future 怎麼告訴你「現在可以繼續了」?

答案:future 回 Pending 前,把 cx 給的一個 Waker 存起來;資源就緒時呼叫 waker.wake() 通知 executor。這條線在 生命週期 stepper 與 block_on 代碼 完成。

① 借用跨 await → self-referential → Pin

只要有一個 local 借用活過 await 點,狀態機就得同時存「那個值」和「指向那個值的參考」。這兩個欄位在同一個 struct 裡互指 = self-referential。而 Rust 的 move 是 memcpy,一 memcpy 位址就變,內部指標就懸空。Pin 就是用型別系統禁止這個 memcpy。
naive 心智模型

「Future 是個值,跟別的值一樣可以隨便 move、塞進 Vec、回傳、mem::swap。」

把 borrow-across-await 攤開

async fn borrow_across() {
    let buf = [0u8; 4];
    let r = &buf;             // 借用進 buf
    yield_now().await;        // 暫停,但 r 要跨過去
    println!("{:?}", r);      // await 之後還要用 r
}

暫停時,狀態機必須同時保住 buf(值本體)和 r(指向 buf 的參考)。概念上:

// 示意,非真實 layout
struct BorrowAcross {
    buf: [u8; 4],
    r: *const [u8; 4],   // 指向「同一個 struct 裡的 buf」 ← self-referential
    inner: YieldNow,
}
為什麼 move 會壞(具體演示)

move = 把整個 struct memcpy 到新位址 0x2000。buf 的內容跟著搬到 0x2000,但 r 的值還是舊位址 0x1000——現在指向一塊不再是 buf 的記憶體。之後 deref r = 讀到已失效/被覆寫的東西 = UB。

修法:Pin

Future::poll 的簽名是 fn poll(self: Pin<&mut Self>, cx)。Pin<&mut T> 對 !Unpin 的 T 承諾:pointee 不會再被 move。

為什麼這樣就安全:只要在狀態機開始自我指涉之前就把它 pin 住,之後 executor 只能透過 Pin<&mut Self> 碰它——拿不到裸的 &mut Self(那會允許 mem::swap/move),所以 self-reference 永遠有效。

  • Unpin:auto trait,型別不含 self-ref 就自動是 Unpin。大多數手寫 future 是 Unpin,對它們 Pin 是 no-op(可 Pin::get_mut 拿回 &mut T,零成本)。
  • !Unpin:編譯器生成、含跨-await-借用的狀態機才是 !Unpin。Pin 對它們真的鎖住 move。

這就是為什麼 block_on 第一件事是 let mut future = pin!(future);——把 future 釘在 stack 上,而且 pin! 會 shadow 掉原 binding,讓你之後拿不到能 move 它的路徑。

Scenario B 的重點

當 wake() 搶在 park() 之前發生:unpark 打在一個還沒睡著的執行緒上,不會空打——它把 park token 設成 1 存起來。executor 隨後 park() 看到 token=1,立刻返回,回頭再 poll。執行緒從沒真正睡著,也沒漏掉喚醒。這就是 naive executor 不用 condvar 也不丟 wakeup 的原因。

mini block_on · 結構 + 完整可編譯代碼

整個 executor 就是:pin! 住 future → 造一個 wake()=unpark 的 Waker → loop { poll; 若 Pending 就 park }。Waker 用 std::task::Wake trait + Arc 造,不手寫 RawWakerVTable。

結構圖

verified 以下整份代碼在 rustc 1.91.1(rustc --edition 2024 -O)實際編譯 + 執行通過,零 warning。executor core 與 demo leaf future 在同一檔,逐字可編。

完整代碼

use std::future::Future;
use std::pin::Pin;
use std::sync::{Arc, Mutex};
use std::task::{Context, Poll, Wake, Waker};
use std::thread::{self, Thread};
use std::time::{Duration, Instant};

// ── executor core ─────────────────────────────────────────────
// wake() 的語意就是「對某個執行緒 unpark」
struct ThreadWaker {
    thread: Thread,
}

impl Wake for ThreadWaker {
    fn wake(self: Arc<Self>) {
        self.thread.unpark();
    }
    fn wake_by_ref(self: &Arc<Self>) {
        self.thread.unpark();
    }
}

// 整個 executor:把一個 future 在「本執行緒」推到完成
fn block_on<F: Future>(future: F) -> F::Output {
    // 釘在 stack;pin! 會 shadow 掉原 binding,之後拿不到能 move 它的路徑。
    // 因此即使 F 是 !Unpin 的 self-referential 狀態機也安全。
    let mut future = std::pin::pin!(future);

    // 這個 Waker 的 wake() 會 unpark「當前」這個執行緒
    let waker = Waker::from(Arc::new(ThreadWaker {
        thread: thread::current(),
    }));
    let mut cx = Context::from_waker(&waker);

    loop {
        match future.as_mut().poll(&mut cx) {
            Poll::Ready(val) => return val,
            // 現在推不動:睡到有人 unpark。
            // 若 wake() 已在抵達這行「之前」發生,park token 已被設起,
            // 這裡的 park() 會立刻返回 → 回頭重新 poll。不會漏喚醒。
            Poll::Pending => thread::park(),
        }
    }
}

// ── demo leaf future ──────────────────────────────────────────
// 一個 Timer:dur 之後完成,由背景執行緒驅動就緒 + 喚醒
struct Timer {
    shared: Arc<Mutex<TimerState>>,
}

struct TimerState {
    completed: bool,
    waker: Option<Waker>,
}

impl Timer {
    fn new(dur: Duration) -> Self {
        let shared = Arc::new(Mutex::new(TimerState {
            completed: false,
            waker: None,
        }));
        let bg = Arc::clone(&shared);
        thread::spawn(move || {
            thread::sleep(dur);
            let mut st = bg.lock().unwrap();
            st.completed = true;
            // 喚醒「最近一次 poll 我的人」
            if let Some(w) = st.waker.take() {
                w.wake();
            }
        });
        Timer { shared }
    }
}

impl Future for Timer {
    type Output = ();
    fn poll(self: Pin<&mut Self>, cx: &mut Context<'_>) -> Poll<()> {
        let mut st = self.shared.lock().unwrap();
        if st.completed {
            Poll::Ready(())
        } else {
            // 每次回 Pending 都存「最新」的 waker（store-latest 契約）
            st.waker = Some(cx.waker().clone());
            Poll::Pending
        }
    }
}

fn main() {
    let start = Instant::now();
    block_on(async {
        println!("[{:>6?}] start", start.elapsed());
        Timer::new(Duration::from_millis(100)).await;
        println!("[{:>6?}] after timer #1", start.elapsed());
        Timer::new(Duration::from_millis(100)).await;
        println!("[{:>6?}] after timer #2", start.elapsed());
    });
    println!("[{:>6?}] block_on returned", start.elapsed());
}
實際執行輸出(兩個 100ms timer 串接 ≈ 200ms): [ 498ns] start [100.535969ms] after timer #1 [200.714912ms] after timer #2 [200.727529ms] block_on returned
為什麼用 Wake trait 而非手刻 RawWakerVTable
  • RawWaker/RawWakerVTable 要你手寫 4 個 unsafe fn pointer(clone / wake / wake_by_ref / drop)+ 自己管 refcount。一個 UB 就爆(double-free / leak / use-after-free)。
  • std::task::Wake(1.51+)讓你只寫安全的 fn wake(self: Arc<Self>)。Waker::from(Arc<W>) 自動用 Arc 的 refcount 幫你生 vtable:clone = refcount++(no heap alloc),drop = refcount--。
  • 面試講得出「我知道底層是 RawWakerVTable,但 Wake trait 是 std 給的安全包裝」= 加分。
兩個容易漏的點
  • Waker::from(Arc<W>) 要求 W: Wake + Send + Sync + 'static。ThreadWaker { thread: Thread } 滿足(std::thread::Thread 是 Send + Sync 的 handle)。
  • Timer::poll 每次回 Pending 都 st.waker = Some(cx.waker().clone())——這是 store-latest 契約。為什麼不能只存第一次?見 self-quiz Q3 與 追問鏈 3。

park token 語意

thread::park/unpark 背後是每個執行緒一個一次性 token(想成容量 1、單一 permit 的 semaphore)。這個 token 讓「unpark 先於 park」不會漏掉喚醒——正是 naive executor 不用 condvar 也不丟 wakeup 的原因。

語意(逐條)

  • park():若 token=1 → 消耗成 0,立刻返回;若 token=0 → 阻塞,直到有人 unpark。
  • unpark():把 token 設成 1(若已是 1,維持 1,不累加)。若目標執行緒正阻塞在 park → 喚醒它。
  • 不 stack:連續兩次 unpark 只留一個 token;下一次 park 立刻返回,再下一次 park 阻塞。
  • spurious wakeup:park 允許無故返回(std 明文如此)。所以正確的 executor loop 一定要 park 返回後重新 poll,不能假設「park 返回 = 資源就緒」。loop { poll; park } 天生免疫。

實測佐證(rustc 1.91.1 / edition 2024 實跑)

use std::thread;
use std::time::{Duration, Instant};

fn main() {
    let me = thread::current();

    // case 1: 先 unpark 再 park。token 被存起來,park 必須立刻返回。
    me.unpark();
    let t = Instant::now();
    thread::park();
    println!("case1 (unpark 後才 park):{:?} 返回", t.elapsed());

    // case 2: token 不累加。一次 unpark = 一個 token,case1 已消耗掉,
    // 這次 park 會阻塞。開一條背景執行緒 80ms 後 unpark,好讓程式終止。
    let handle = me.clone();
    thread::spawn(move || {
        thread::sleep(Duration::from_millis(80));
        handle.unpark();
    });
    let t2 = Instant::now();
    thread::park();
    println!("case2 (再 park,已無 token):{:?} 返回", t2.elapsed());
}
case1 (unpark 後才 park):374ns 返回 <- 幾乎瞬間,token 生效 case2 (再 park,已無 token):80.33777ms 返回 <- 阻塞到背景執行緒 unpark

這證明兩件事:(a) unpark-before-park 立刻返回(token 被存起來);(b) token 不累加(第二次 park 仍阻塞)。

為什麼這對 executor 正確性是關鍵

race timeline:executor poll → 回 Pending → 還沒走到 park → 背景執行緒 wake()→unpark → executor 才 park。

  • 沒有 token(想像一個只會「喚醒正在睡的人」的原始 primitive):unpark 打在一個還沒睡的執行緒上 = 空打,之後 executor 一 park 就永遠睡死 = lost wakeup / 掛住。
  • 有 token:unpark 存下 token,executor 的 park 看到 token 立刻返回 → 回頭 poll → 這次資源已就緒 → Ready。沒漏。

對照 Scenario B stepper。

陷阱:token 是 per-thread 且全域共用的

同一執行緒上如果別的地方(不是你的 executor)也用 park/unpark,會互相干擾——吃掉你的 token,或被你吃掉。把 park/unpark 當 executor 私有喚醒機制時,不要在同一執行緒混用其他 park/unpark。這也呼應 wake 契約的不對稱:executor 收到多餘的 wake(spurious poll)無害,但漏掉一次 wake(lost wakeup)致命——所以寧可多 poll 一次。

tokio 全鏈路 · 你的 block_on 放大版

tokio 沒有發明新機制。骨架跟你的 block_on 完全一樣:poll → 存 waker → 睡 → 被叫醒 → 重 poll。只有兩處被換掉:「睡」從 park() 換成 epoll_wait;「叫醒」從 unpark() 換成「把 task 推回 run queue」。

為什麼這一頁從 .await 開始

整條鏈要回答的第一個問題是:誰呼叫 poll?cx 從哪來? 呼叫 poll 的就是 .await。所以看懂鏈之前,得先確定 .await 到底編譯成什麼——這是鏈的第一環,錯在這裡,後面全歪。

你腦內大概是這個形狀

絕大多數人(包含我看過的多數筆記)對 .await 的心智模型是:「迴圈 poll 到 Ready,否則把 Pending 往外傳」。形狀是對的,鏈的骨架也確實長這樣。先不評價,往下建立正確版本,最後再回來 diff。

① 官方 desugaring(primary source:Rust Reference expr.await.desugar)

match operand.into_future() {
    mut pinned => loop {
        let mut pin = unsafe { Pin::new_unchecked(&mut pinned) };
        match Pin::future::poll(Pin::borrow(&mut pin), &mut current_context) {
            Poll::Ready(r) => break r,
            Poll::Pending => yield Poll::Pending,
        }
    }
}

Reference 自己標明這是 non-normative(近似)。三個要注意的地方:

  • operand.into_future() — .await 的第一步,不是直接 poll。
  • Pin::new_unchecked — unsafe,理由見下。
  • yield 是 pseudo-code。Reference 的原話:它回傳 Poll::Pending,再次被呼叫時從該點恢復執行。current_context 就是外層 poll 時被塞進來的 cx——這是關鍵:.await 完全不知道 tokio 存在,它只是把手上的 cx 往下遞。

② 「從該點恢復」是什麼機制?攤平成狀態機就看得見

yield 是 source level 的說法,編譯器不會真的產生一個會 yield 的東西。它把整個 async body 攤平成一個 match state 的狀態機。攤平之後,yield 變成兩件具體的事:

yield 攤平後 = 存狀態 + return Pending
  1. 狀態已經存好(st 停在 Awaiting 這個 variant,而且被 await 的那個 future 就存在 variant 裡面)
  2. return Poll::Pending

「resume 點」不是什麼神祕的東西,它就是 enum 的一個 variant。下次 poll 進來,match this.st 直接跳回 Awaiting 臂 —— Start 臂不會再跑一次。那個 loop 是靠「st 沒變 + 下次 poll 重新進來 match」來迭代的,一次 poll 只轉一圈。

verified 下面把同一個 async fn 寫兩遍——編譯器版和手寫狀態機版——在 rustc 1.91.1 / edition 2024 實跑對照。手寫版零 unsafe,因為這個例子的欄位剛好都是 Unpin。
// .await 到底變成什麼:async fn 版 vs 手寫狀態機版,行為對照
// rustc --edition 2024 -O desugar.rs   (rustc 1.91.1 實跑;CoderPad 是 1.92.0,delta 已稽核)
use std::future::Future;
use std::pin::Pin;
use std::sync::atomic::{AtomicU32, Ordering::Relaxed};
use std::sync::Arc;
use std::task::{Context, Poll, Wake, Waker};
use std::thread;

// 三個計數器:證明「哪一段程式碼跑了幾次」
static A_RUNS: AtomicU32 = AtomicU32::new(0); // await 之前那段
static B_RUNS: AtomicU32 = AtomicU32::new(0); // await 之後那段

// ---- leaf future:前 3 次回 Pending,第 4 次 Ready ----
struct Countdown(u32);
impl Future for Countdown {
    type Output = ();
    fn poll(mut self: Pin<&mut Self>, cx: &mut Context<'_>) -> Poll<()> {
        if self.0 == 0 {
            Poll::Ready(())
        } else {
            self.0 -= 1;
            cx.waker().wake_by_ref(); // 立刻自我喚醒,省掉背景 thread
            Poll::Pending
        }
    }
}

// ================= 版本一:async fn =================
async fn body() -> u32 {
    A_RUNS.fetch_add(1, Relaxed); // ← await 之前
    Countdown(3).await;
    B_RUNS.fetch_add(1, Relaxed); // ← await 之後
    42
}

// ================= 版本二:手寫狀態機 =================
// 這就是編譯器對上面那個 async fn 做的事(簡化版,但行為等價)。
enum St {
    Start,
    Awaiting(Countdown), // ← 「resume 點」的真身:它是一個 enum variant
    Done,
}
struct Body {
    st: St,
}

impl Future for Body {
    type Output = u32;
    fn poll(self: Pin<&mut Self>, cx: &mut Context<'_>) -> Poll<u32> {
        // Body 的欄位全是 Unpin,所以 get_mut() 可用,零 unsafe。
        // 真實編譯器產生的狀態機通常是 !Unpin(借用跨 await 會自我參照),
        // 那時就只能走 unsafe 的 get_unchecked_mut / Pin::new_unchecked。
        let this = self.get_mut();

        // ↓ 這個 loop 就是官方 desugaring 裡那個 loop。
        //   它在「同一次 poll 內」只負責狀態直落(Start → Awaiting);
        //   跨 poll 的迭代靠的是 st 沒變 + 下次 poll 重新進來 match。
        loop {
            match this.st {
                St::Start => {
                    A_RUNS.fetch_add(1, Relaxed);
                    this.st = St::Awaiting(Countdown(3));
                    // 不 return,直接 loop 回去進 Awaiting 臂
                }
                St::Awaiting(ref mut c) => {
                    // Countdown 剛好是 Unpin,所以 Pin::new 能用。
                    // 真實 async fn 的子 future 是 !Unpin → 編譯器只能用 Pin::new_unchecked。
                    match Pin::new(c).poll(cx) {
                        Poll::Ready(()) => {
                            B_RUNS.fetch_add(1, Relaxed);
                            this.st = St::Done;
                            return Poll::Ready(42); // = desugaring 的 `break r`
                        }
                        // ↓↓ `yield Poll::Pending` 編譯後就是這兩件事:
                        //    (1) st 已經是 Awaiting(狀態存好了)
                        //    (2) return Poll::Pending
                        //    resume 靠的是下次 poll 進來時 match 直接跳回 Awaiting 臂,
                        //    Start 臂不會再跑一次。
                        Poll::Pending => return Poll::Pending,
                    }
                }
                St::Done => panic!("polled after Ready"),
            }
        }
    }
}

// ---- 會數 poll 次數的 block_on ----
struct ThreadWaker(thread::Thread);
impl Wake for ThreadWaker {
    fn wake(self: Arc<Self>) {
        self.0.unpark();
    }
    fn wake_by_ref(self: &Arc<Self>) {
        self.0.unpark();
    }
}

fn block_on_counting<F: Future>(f: F) -> (F::Output, u32) {
    let mut f = std::pin::pin!(f);
    let waker = Waker::from(Arc::new(ThreadWaker(thread::current())));
    let mut cx = Context::from_waker(&waker);
    let mut polls = 0u32;
    loop {
        polls += 1;
        match f.as_mut().poll(&mut cx) {
            Poll::Ready(v) => return (v, polls),
            Poll::Pending => thread::park(),
        }
    }
}

fn run<F: Future<Output = u32>>(f: F) -> (u32, u32, u32, u32) {
    A_RUNS.store(0, Relaxed);
    B_RUNS.store(0, Relaxed);
    let (v, polls) = block_on_counting(f);
    (v, polls, A_RUNS.load(Relaxed), B_RUNS.load(Relaxed))
}

fn main() {
    let r1 = run(body());
    let r2 = run(Body { st: St::Start });
    // 標籤刻意等寬:"async fn  " 是 10 個半形,"手寫狀態機" 是 5 個全形 = 10 欄
    let show = |tag: &str, r: (u32, u32, u32, u32)| {
        println!(
            "{}: 回傳 {} | poll 了 {} 次 | await 前跑 {} 次 | await 後跑 {} 次",
            tag, r.0, r.1, r.2, r.3
        );
    };
    show("async fn  ", r1);
    show("手寫狀態機", r2);

    assert_eq!(r1, r2, "手寫狀態機與 async fn 行為不一致");
    assert_eq!(r1.2, 1, "await 前的程式碼被重跑了");
    assert!(r1.1 > 1, "根本沒 Pending 過,這次測試沒有意義");

    println!("\n兩者行為完全一致 —— 這就是 desugaring。");
    println!(
        "關鍵:poll 了 {} 次,但 await 前的程式碼只跑了 1 次。",
        r1.1
    );
    println!(
        "若 .await 真是「return Pending 然後從頭重跑」,它會跑 {} 次。",
        r1.1
    );
}

③ 實測:poll 4 次,await 前的程式碼只跑 1 次

async fn : 回傳 42 | poll 了 4 次 | await 前跑 1 次 | await 後跑 1 次 手寫狀態機: 回傳 42 | poll 了 4 次 | await 前跑 1 次 | await 後跑 1 次 兩者行為完全一致 —— 這就是 desugaring。 關鍵:poll 了 4 次,但 await 前的程式碼只跑了 1 次。 若 .await 真是「return Pending 然後從頭重跑」,它會跑 4 次。
這個 1 vs 4 就是整段的重點

如果心智模型是「return Pending,下次從頭重跑」,那 A_RUNS 應該是 4。它是 1。 執行是從 Awaiting 那一臂接續的,不是重來。

這不是學術細節。直接推論:spurious wakeup(莫名其妙被多 poll 一次)不會把你的 async fn 從頭重跑,所以 await 之前的副作用(送出請求、遞增 counter)不會被重複執行。這是面試會問的東西,而「return 從頭重跑」的模型會給出完全相反的答案。

④ 現在回來 diff:那個形狀差在哪三處

loop {
    match Future::poll(Pin::new(&mut inner_future), cx) {   // (1) (2)
        Poll::Ready(v) => break v,
        Poll::Pending => return Poll::Pending,               // (3)
    }
}
三處
  • (1) Pin::new 編不過。 Pin::new 的簽章要求 T: Unpin。子 future 通常是編譯器生的狀態機,借用跨 await 就會自我參照 → !Unpin → 這行連編譯都過不了。官方用 Pin::new_unchecked(unsafe),而 unsafe 的義務由「外層已被 pin 住、子 future 是它的欄位」擔保(structural pinning)。上面手寫版能用 Pin::new,純粹因為 Countdown 剛好是 Unpin——這是例子的僥倖,不是通則。背景見 借用跨 await → Pin。
  • (2) 少了 IntoFuture::into_future。 .await 的第一步是對 operand 呼叫它,不是直接 poll。所以你可以 .await 一個不是 Future 但實作了 IntoFuture 的東西(builder pattern 常用)。(future::IntoFuture stable since 1.64.0,2022-09-22,來源 RELEASES.md)
  • (3) yield 被寫成 return — 這處最要命,因為它剛好「看起來很合理」。

    問題不是「return Poll::Pending 這行不存在」——攤平後的狀態機裡確實有這行(見手寫版 Awaiting 臂)。問題是它把兩層壓成一層:

    • source level(.await 的 desugaring):有 loop,有 yield,沒有 return。
    • machine level(攤平後的 poll):有 return Poll::Pending,但配的是 match st 的 dispatch loop,語意跟前者那個 loop 完全不同。

    把 source 的 loop 配 machine 的 return,兩邊都不成立:那個 loop 永遠轉不到第二圈,變成死碼。更糟的是,return 掉了「存狀態」那一半——而存狀態正是 resume 的全部機制。剩下一個沒有 state 的 return,自然只能腦補成「從頭重跑」,於是就推出上面那個被實測打臉的結論。

你的描述漏掉的一個 race(面試會問)

poll_readiness 存完 waker 之後,又 load 一次 readiness:

let mut waiters = self.waiters.lock();
// ... *waker = Some(cx.waker().clone());

// Try again, in case the readiness was changed while we were
// taking the waiters lock
let curr = self.readiness.load(Acquire);

為什麼要這行:函式開頭 load 到「還沒 ready」,接著去搶 waiters 鎖。搶鎖的空檔裡,driver thread 可能已經 set_readiness + wake() 了——但那一刻 waker 還沒存進去,所以那次 wake 打在空氣上。沒有這個 re-check,這個 future 就永遠 Pending = lost wakeup。

標準三段式:check → store waker → re-check。你的 Timer 天生沒這個洞,因為 check 和 store 在同一個 Mutex 裡。但只要 readiness 是 atomic、waker 在另一個鎖裡(兩個不同的同步物件),re-check 就是強制的。

順帶:這裡的 Acquire 不是裝飾。它要跟 driver 側 set_readiness 的 Release 配對,才保證「看到 ready 旗標」蘊含「看到 ready 之前的所有寫入」。

為什麼 park 叫不醒 epoll_wait

driver.rs:270-272 的 unpark() 實作是 self.waker.wake(),而 self.waker 是 mio::Waker(driver.rs:50 宣告、:120 建構、綁 TOKEN_WAKEUP at :103)。Linux 上它是一個 eventfd。

為什麼不用 thread::unpark?因為 driver thread 此刻睡在 epoll_wait 裡,不在 park 裡。unpark 只會把 park token 設成 1,而 epoll_wait 根本不看那個 token。要戳醒 epoll_wait,唯一辦法是讓它監聽的某個 fd 變就緒 → 所以註冊一個 eventfd,寫它。

一句話

一個 thread 同時只能睡在一個地方。選了 park 就用 unpark 叫;選了 epoll_wait 就得用 fd 叫。park 和 epoll 不是替代關係,是不同層的睡眠原語。

對你的意義:沒有 libc = reactor 層蓋不出來

沒有 libc 就沒有 epoll_create1/epoll_ctl/epoll_wait,std 也不 export 它們。上圖的 ⑤⑥ 兩格你做不出來。

所以任何「async IO」題目你只有一條路:thread-as-reactor——拿一個 blocking thread 假裝 reactor,它做 blocking read,好了就 waker.wake()。這正是 handbook Timer 的形狀(背景 thread sleep → wake),不是玩具,是你唯一能蓋的 reactor。

代價要主動講出來:一條連線一個 thread,C10K 不可能(每 thread 預設 ~8MB 虛擬 stack、實際 RSS 看用量)。這就是「epoll 為什麼存在」的答案。面試官要聽的是你知道自己在付什麼代價,不是你能變出 epoll。

架構

verified 以下代碼在 rustc 1.91.1(rustc --edition 2024 -O)實際編譯 + 執行:開真 socket、3 條假 client、驗證 per-conn FIFO,輸出 writer wrote 15 records / per-conn FIFO: OK。
// std-only TCP log collector:thread-per-conn 讀取 → 有界 channel → 單一 writer thread 落檔
// 無 libc / 無 epoll。rustc --edition 2024 -O log_collector.rs
use std::fs::File;
use std::io::{BufRead, BufReader, BufWriter, Write};
use std::net::{TcpListener, TcpStream};
use std::sync::mpsc::{sync_channel, Receiver, SyncSender, TrySendError};
use std::thread;

struct Record {
    conn: u64,
    seq: u64, // per-connection 序號:producer-local,零競爭
    line: String,
}

// ---- writer:整個系統唯一的序列化點(serialization point)----
fn writer_loop(rx: Receiver<Record>, path: &str) -> std::io::Result<u64> {
    let mut w = BufWriter::new(File::create(path)?);
    let mut n = 0u64;
    // recv() 空的時候 block —— 這就是 event loop;
    // 所有 SyncSender drop 後 iterator 結束,是唯一的關機訊號。
    for rec in rx {
        writeln!(w, "conn{} #{} {}", rec.conn, rec.seq, rec.line)?;
        n += 1;
        if n % 64 == 0 {
            w.flush()?; // flush policy:批次,不是每行一次 syscall
        }
    }
    w.flush()?; // 明確 flush。不能靠 BufWriter 的 Drop:它會吞掉 flush 的 error
    Ok(n)
}

// ---- 每條連線一個 thread:blocking read,per-conn 程式順序 = per-conn FIFO ----
fn conn_loop(stream: TcpStream, conn: u64, tx: SyncSender<Record>) {
    let reader = BufReader::new(stream);
    let mut seq = 0u64;
    for line in reader.lines() {
        let line = match line {
            Ok(l) => l,
            Err(_) => break, // 對端斷線 / IO error:結束這條連線,不影響別人
        };
        let rec = Record { conn, seq, line };
        seq += 1;
        // 背壓策略在這裡做決定,而且必須是個「明講的決定」:
        match tx.try_send(rec) {
            Ok(()) => {}
            Err(TrySendError::Full(rec)) => {
                // 佇列滿了。兩條路:(a) blocking send = 背壓傳回 TCP,拖慢 client
                //                    (b) 丟棄 = 保護記憶體,但掉 log
                // log collector 通常選 (a),因為掉 log 是靜默的資料損失。
                if tx.send(rec).is_err() {
                    break;
                }
            }
            Err(TrySendError::Disconnected(_)) => break, // writer 死了
        }
    }
}

fn main() -> std::io::Result<()> {
    let path = "/tmp/collected.log";
    // 有界!mpsc::channel() 是無界的 → 快的 client 可以把你打到 OOM。
    let (tx, rx) = sync_channel::<Record>(1024);

    let writer = thread::spawn(move || writer_loop(rx, path));

    let listener = TcpListener::bind("127.0.0.1:0")?;
    let addr = listener.local_addr()?;
    println!("listening on {}", addr);

    // --- 假 client:3 條連線各送 5 行 ---
    let mut clients = Vec::new();
    for c in 0..3u64 {
        clients.push(thread::spawn(move || {
            let mut s = TcpStream::connect(addr).unwrap();
            for i in 0..5 {
                writeln!(s, "client{} msg{}", c, i).unwrap();
            }
        }));
    }

    // --- accept loop:只做 accept + spawn,不做任何 IO ---
    let mut conn_threads = Vec::new();
    for conn in 0..3u64 {
        let (stream, _) = listener.accept()?;
        let txc = tx.clone();
        conn_threads.push(thread::spawn(move || conn_loop(stream, conn, txc)));
    }

    for c in clients {
        c.join().unwrap();
    }
    for t in conn_threads {
        t.join().unwrap();
    }
    // 關鍵:必須 drop 原始 tx,否則 rx 永遠不會結束 → writer 永遠不 return → join 卡死
    drop(tx);
    let n = writer.join().unwrap()?;
    println!("writer wrote {} records", n);

    let content = std::fs::read_to_string(path)?;
    // 驗證 per-conn FIFO:每條連線的 seq 必須嚴格遞增
    for c in 0..3u64 {
        let seqs: Vec<u64> = content
            .lines()
            .filter(|l| l.starts_with(&format!("conn{} ", c)))
            .map(|l| l.split_whitespace().nth(1).unwrap()[1..].parse().unwrap())
            .collect();
        assert_eq!(seqs, (0..5).collect::<Vec<u64>>(), "conn{} FIFO broken", c);
    }
    println!("per-conn FIFO: OK (global order is arbitrary, and that is fine)");
    Ok(())
}
四個要主動講的決定
  • 有界 channel。mpsc::channel() 是無界的 → 一個快 client 就能把你打到 OOM。sync_channel(1024) 滿了會 block → 背壓一路傳回 TCP 接收視窗 → client 自己慢下來。這是免費的 flow control,不用自己寫。
  • drop(tx) 是關機協定。忘了 drop 原始 tx → for rec in rx 永遠不結束 → writer 不 return → join() 卡死。std mpsc 最常見的 deadlock,而且它看起來像 hang,不像 bug。
  • 明確 flush()。BufWriter 的 Drop 會 flush,但吞掉 error。log collector 靜默掉資料是最糟的失敗模式——你不會知道。
  • flush policy 是 tradeoff,沒有正解。每行 flush = 每行一次 syscall。批次 = crash 掉最近 N 筆。要講出你選哪個、為什麼。

Follow-up 1 · 多個任務分開接收

  • A. 多個 accept thread:listener.try_clone()(std)→ N 個 thread 各自 accept()。kernel 序列化,一個贏。可行,但你無法控制誰拿到哪條連線。
  • B. 一個 acceptor + thread pool:acceptor 把 TcpStream 丟進 channel,pool worker 撿。這是 Etched prep doc 字面上要的(architect a custom thread pool without external libraries)。
  • C. 按連線 sharding:conn_id % K → worker k。per-worker locality,worker 之間零競爭。
陷阱:固定 pool + blocking read = 並發上限就是 K

B 如果 worker 做 blocking read,pool 大小 K 就是你的最大並發連線數。一個慢/idle 的 client 永久占住一個 worker,其他連線連被服務的機會都沒有。thread-per-conn 至少不會互相餓死;固定 pool + blocking read 會。

沒有 epoll 的緩解:stream.set_read_timeout(Some(d))(std)→ worker 卡不住,可以輪替。但這變成 poll-ish,而且 timeout 該設多少沒有好答案——設短=空轉,設長=延遲。

誠實結論:blocking IO + 固定 pool 做不到 C10K。要嘛 thread-per-conn(吃記憶體),要嘛 epoll(要 libc)。面試時把這個講清楚,比硬掰一個「兩全其美」的方案值錢得多。

Follow-up 2 · 把寫 log 變成 async

先講真相

Linux 上沒有真正的 async file IO(io_uring 除外)。tokio::fs 的實作就是 spawn_blocking——一個 thread pool 套上 Future 門面。所以「把寫 log 變 async」= 你自己蓋那個門面,而門面的骨架就是你已經會的 Timer。

verified rustc 1.91.1 / edition 2024 編譯 + 執行通過,輸出 first/second/third 且 assert 順序正確。
// Follow-up 2:把「寫 log」變成 async 操作(std-only)
// 真相:Linux 上沒有真正的 async file IO(io_uring 除外)。tokio::fs 也是 spawn_blocking。
// 所以「async 寫檔」= 把工作丟給 thread + 給呼叫端一個 Future 門面。
// 這個 Future 的骨架 = handbook 裡的 Timer,一模一樣。
use std::fs::File;
use std::future::Future;
use std::io::{BufWriter, Write};
use std::pin::Pin;
use std::sync::mpsc::{channel, Sender};
use std::sync::{Arc, Mutex};
use std::task::{Context, Poll, Wake, Waker};
use std::thread;

// ---------- 最小 executor(與 handbook 同一份骨架)----------
struct ThreadWaker(thread::Thread);
impl Wake for ThreadWaker {
    fn wake(self: Arc<Self>) { self.0.unpark(); }
    fn wake_by_ref(self: &Arc<Self>) { self.0.unpark(); }
}
fn block_on<F: Future>(f: F) -> F::Output {
    let mut f = std::pin::pin!(f);
    let waker = Waker::from(Arc::new(ThreadWaker(thread::current())));
    let mut cx = Context::from_waker(&waker);
    loop {
        match f.as_mut().poll(&mut cx) {
            Poll::Ready(v) => return v,
            Poll::Pending => thread::park(),
        }
    }
}

// ---------- async 門面 ----------
struct WriteState {
    done: Option<std::io::Result<()>>,
    waker: Option<Waker>,
}

struct LogWrite(Arc<Mutex<WriteState>>);

impl Future for LogWrite {
    type Output = std::io::Result<()>;
    fn poll(self: Pin<&mut Self>, cx: &mut Context<'_>) -> Poll<Self::Output> {
        let mut st = self.0.lock().unwrap();
        if let Some(r) = st.done.take() {
            return Poll::Ready(r);
        }
        // store-latest:每次 Pending 都覆蓋。理由同 handbook Q3。
        st.waker = Some(cx.waker().clone());
        Poll::Pending
    }
}

enum Job {
    Write(String, Arc<Mutex<WriteState>>),
    Quit,
}

struct AsyncLogger(Sender<Job>);

impl AsyncLogger {
    fn log(&self, line: &str) -> LogWrite {
        let st = Arc::new(Mutex::new(WriteState { done: None, waker: None }));
        self.0.send(Job::Write(line.to_string(), st.clone())).unwrap();
        LogWrite(st)
    }
}

fn spawn_logger(path: &str) -> (AsyncLogger, thread::JoinHandle<()>) {
    let (tx, rx) = channel::<Job>();
    let path = path.to_string();
    let h = thread::spawn(move || {
        let mut w = BufWriter::new(File::create(&path).unwrap());
        while let Ok(job) = rx.recv() {
            match job {
                Job::Quit => break,
                Job::Write(line, st) => {
                    let r = writeln!(w, "{}", line).and_then(|_| w.flush());
                    // 順序關鍵:先發佈結果,再 wake。反過來 = lost wakeup。
                    let waker = {
                        let mut g = st.lock().unwrap();
                        g.done = Some(r);
                        g.waker.take()
                    }; // guard 在這裡 drop —— 先放鎖再 wake,避免被喚醒的 thread 立刻撞鎖
                    if let Some(wk) = waker { wk.wake(); }
                }
            }
        }
        w.flush().unwrap();
    });
    (AsyncLogger(tx), h)
}

fn main() {
    let path = "/tmp/async.log";
    let (logger, h) = spawn_logger(path);
    let out = block_on(async {
        logger.log("first").await.unwrap();
        logger.log("second").await.unwrap();   // 這行保證在 first 之後:await 建立了 happens-before
        logger.log("third").await.unwrap();
        "done"
    });
    logger.0.send(Job::Quit).unwrap();
    h.join().unwrap();
    println!("block_on -> {}", out);
    print!("{}", std::fs::read_to_string(path).unwrap());
    assert_eq!(std::fs::read_to_string(path).unwrap(), "first\nsecond\nthird\n");
    println!("ordered because each await sequences the next send");
}
兩個順序陷阱
  • 先發佈結果,再 wake。 反過來(先 wake 再填 done)→ executor 被叫醒 → 重 poll → 看到 done: None → 又存 waker 回 Pending → 而那次 wake 已經被消耗掉了 → 永久掛住。這就是 release-store-then-notify:先發佈狀態,再通知。
  • wake() 要在鎖外。 在鎖內 wake → 被喚醒的 thread 立刻 lock() → 撞上你還沒放的鎖。不會 deadlock(它會等),但白付一次 context switch。代碼用 let waker = { ...; g.waker.take() }; 讓 guard 在 block 結束就 drop,再 wake()。
值不值得?直說:多數情況不值得

如果你是 thread-per-conn,這個 async 化買不到任何東西。 conn thread 本來就 blocking,block_on(logger.log(..)) 只是把 blocking 包一層再 blocking——多了 Arc、Mutex、waker clone,吞吐一模一樣。

async 的價值只有一個:用少量 thread 多工大量 task。 沒有那個壓力,async 是純開銷。10 條連線的 log collector,thread-per-conn + 一個 writer 更簡單也更快。

真正回本的場景:conn 數 >> thread 數,且 handler 有很多 await 點(讀網路、寫檔、查 DB)。但那又需要 reactor → 又回到 libc 問題。把這個循環講出來,就是這題的滿分答案。

Follow-up 3 · multithread、不在意誰先寫;沒有時間戳怎麼保序?

Step 0:先問「哪一種順序」——這題不反問就答不對
  1. per-connection FIFO — client A 的行,按 A 送出的順序出現。
  2. 全域總序 — 所有行有一個大家同意的順序。
  3. 因果序 — X 導致 Y,則 X 在前。

這三個的難度差好幾個數量級,而且多數人要的其實是 1。

1. per-conn FIFO:免費

條件只有兩個:每條連線由恰好一個 thread 讀(程式順序即送出順序)、傳輸保 per-sender 順序。上面的代碼已經滿足,assert 也驗過。你什麼都不用做。

2. 全域總序

先戳破一個假設:時間戳不給你順序
  • SystemTime 不單調(NTP 可以往回跳)→ 要用 Instant。
  • 解析度有限 → 會平手,平手就沒有序,還是得有 tiebreaker。
  • 最根本:打戳的那一刻 ≠ 入列的那一刻。thread A 在 t=5 打戳後被 deschedule;thread B 在 t=6 打戳並先入列。檔案裡 6 在 5 前面。要按戳排序就得等——等到確定沒有更早的戳會再來(watermark),而「還會不會來」在一般情況下無法界定。

所以「訊息會標注時間」買到的是離線 sort 的能力,不是檔案的順序。而你說「不在意誰先寫入」——那這個組合就是正確且最便宜的設計:writer 任意順序寫,時間戳留給下游 sort。不要蓋 sequencer。

沒有時間戳:writer 看到的到達順序就是一個順序

任何單一序列化點都免費給你一個全域總序:Mutex<BufWriter> 的鎖取得順序、單一 consumer channel 的 recv() 順序。

這個順序任意,但一致——所有人同意、可重現、就存在檔案裡。你只是不能宣稱它對應真實時間。而對獨立的 client 來說,「真實時間順序」本來就不存在:兩個 client 在不同 core 上同時送,沒有 ground truth 說誰先。你不是失去了順序,而是那個順序從來沒有過。

如果你需要序號(掉包偵測 / 下游重組)

陷阱:拿號 ≠ 依號入列

AtomicU64::fetch_add(1, Relaxed) 給你唯一號碼,但拿號和入列之間有空隙。執行緒在空隙裡被搶佔 → 後拿號的先入列。實測(rustc 1.91.1 / edition 2024 實跑):

[陷阱] 拿號順序 = 0,1,2,3 實際到達 = [3, 2, 1, 0] <- 檔案就會長這樣
verified rustc 1.91.1 / edition 2024 編譯 + 執行,三個修法都有 assert。
// Follow-up 3:沒有時間戳時的「順序性」到底是什麼
// 論點:全域總序需要一個序列化點(serialization point)。你只能選在哪裡付代價。
use std::collections::BinaryHeap;
use std::cmp::Reverse;
use std::sync::atomic::{AtomicU64, Ordering};
use std::sync::mpsc::channel;
use std::sync::{Arc, Mutex};
use std::thread;
use std::time::Duration;

// ===== 陷阱:拿號碼 != 依號碼寫入 =====
// fetch_add 給你唯一號碼,但「拿號」和「入列」之間有空隙。
// 執行緒在空隙裡被 deschedule → 後拿號的先入列 → 檔案順序 != 號碼順序。
fn ticket_gap_demo() -> Vec<u64> {
    let counter = Arc::new(AtomicU64::new(0));
    let (tx, rx) = channel::<u64>();
    let mut hs = Vec::new();
    for i in 0..4u64 {
        let c = counter.clone();
        let tx = tx.clone();
        hs.push(thread::spawn(move || {
            let seq = c.fetch_add(1, Ordering::Relaxed); // ← 拿號
            thread::sleep(Duration::from_millis((3 - i % 4) * 20)); // ← 空隙(模擬被搶佔)
            tx.send(seq).unwrap();                                  // ← 入列
        }));
    }
    drop(tx);
    for h in hs { h.join().unwrap(); }
    rx.iter().collect()
}

// ===== 修法 A:reorder buffer(用號碼還原順序)=====
// 代價:記憶體 + head-of-line blocking —— 一個卡住的 producer 卡住全部。
fn reorder(arrivals: &[u64]) -> Vec<u64> {
    let mut heap: BinaryHeap<Reverse<u64>> = BinaryHeap::new();
    let mut next = 0u64;
    let mut out = Vec::new();
    for &a in arrivals {
        heap.push(Reverse(a));
        while let Some(&Reverse(top)) = heap.peek() {
            if top == next { heap.pop(); out.push(top); next += 1; } else { break; }
        }
    }
    while let Some(Reverse(v)) = heap.pop() { out.push(v); } // flush 尾巴
    out
}

// ===== 修法 B:把「拿號 + 入列」放進同一個鎖 =====
// 到達順序 == 號碼順序,不需要 reorder buffer。代價:producer 被序列化。
fn locked_ticket_demo() -> Vec<u64> {
    let sink = Arc::new(Mutex::new(Vec::<u64>::new()));
    let counter = Arc::new(AtomicU64::new(0));
    let mut hs = Vec::new();
    for _ in 0..4u64 {
        let (s, c) = (sink.clone(), counter.clone());
        hs.push(thread::spawn(move || {
            let mut g = s.lock().unwrap();              // 鎖先拿
            let seq = c.fetch_add(1, Ordering::Relaxed); // 拿號在鎖內
            g.push(seq);                                 // 入列也在鎖內 → 原子
        }));
    }
    for h in hs { h.join().unwrap(); }
    let v = sink.lock().unwrap().clone(); v
}

// ===== 修法 C(推薦):根本不要全域號碼,用 per-producer 號碼 =====
// 每個 producer 自己的 counter(thread-local,零競爭)。
// 得到:per-conn 總序 + 掉包偵測。失去:全域總序 —— 但獨立 client 之間本來就沒有「真正的」順序。
fn per_producer_demo() -> Vec<(u64, u64)> {
    let (tx, rx) = channel::<(u64, u64)>();
    let mut hs = Vec::new();
    for conn in 0..3u64 {
        let tx = tx.clone();
        hs.push(thread::spawn(move || {
            for seq in 0..4u64 {                 // seq 是 local 變數,沒有 atomic,沒有鎖
                tx.send((conn, seq)).unwrap();
                thread::sleep(Duration::from_millis(1));
            }
        }));
    }
    drop(tx);
    for h in hs { h.join().unwrap(); }
    rx.iter().collect()
}

fn main() {
    let arrivals = ticket_gap_demo();
    println!("[陷阱] 拿號順序 = 0,1,2,3");
    println!("       實際到達 = {:?}   <- 檔案就會長這樣", arrivals);
    assert_ne!(arrivals, vec![0, 1, 2, 3], "本次剛好沒亂序(race 本質如此)");

    let fixed = reorder(&arrivals);
    println!("[修法A] reorder buffer 還原 = {:?}", fixed);
    assert_eq!(fixed, vec![0, 1, 2, 3]);

    let locked = locked_ticket_demo();
    println!("[修法B] 拿號+入列同鎖 = {:?}  <- 天生有序,不需 buffer", locked);
    assert_eq!(locked, vec![0, 1, 2, 3]);

    let pp = per_producer_demo();
    println!("[修法C] per-producer 序號到達 = {:?}", pp);
    for conn in 0..3u64 {
        let seqs: Vec<u64> = pp.iter().filter(|(c, _)| *c == conn).map(|(_, s)| *s).collect();
        assert_eq!(seqs, vec![0, 1, 2, 3], "conn{} 亂序", conn);
    }
    println!("       每條 conn 內部嚴格遞增 (全域交錯是任意的,而且無所謂)");
}
  • A. reorder buffer:min-heap 按 seq,湊齊連號才吐。代價:記憶體 + head-of-line blocking——一個卡住的 producer 卡住全部。你在連線層拚命擺脫的 HOL,在這裡原封不動長回來。
  • B. 拿號 + 入列同一個鎖:到達序 == 號碼序,不用 buffer。代價:producer 被序列化,鎖就是瓶頸。附帶一個 tell:此時那個 AtomicU64 是多餘的——你已經持有鎖了,用普通 u64 counter 就好。在鎖裡放 atomic 通常代表沒想清楚誰在保護什麼。
  • C. per-producer 序號(推薦):每條連線自己的 counter,是區域變數——零 atomic、零鎖、零競爭。得到:per-conn 總序 + 掉包偵測。失去:全域總序——而你本來就不需要它。
不變式(這句就是整題的答案)

全域總序一定要有一個序列化點。你只能選在哪裡付代價:在點上付競爭(B),或在下游付重組(A)。沒有第三條路。

而 C 是唯一的「作弊」:重新定義問題,讓你根本不需要那個點。面試時先提 C,再說明 A/B 什麼時候才被迫用——順序是 signal。

因果序:講出「這裡不需要」比會實作更值錢

只有真的存在因果(X 的內容依賴 Y)才需要:Lamport clock(每個 producer 一個 counter,送出時 max(local, received)+1;保證 X→Y ⇒ L(X)<L(Y),反向不成立)或 vector clock(反向成立,代價 O(N)/筆)。

log collector 的連線彼此獨立 → 沒有因果 → 這是過度設計。能點名它並說明為何不用,比寫出來更能證明你懂。

實戰 · acceptor + thread pool(std-only)

這是 log collector Follow-up 1 的選項 B,也是 Etched prep doc 字面上要的:architect a custom thread pool without relying on external libraries。acceptor 只 accept,把工作丟進 channel,pool 的 worker 撿。兩個經典陷阱都會編譯過、功能也正確 —— 只有量測抓得到。

決策鏈:六個被逼出來的選擇

每一步都不是「選擇」,是被上一步逼出來的。這是 clarify 那 5 分鐘要講完的東西。

① Job 的型別 → 先問面試官(pillar 1)
  • 只收連線 → Sender<TcpStream>,worker 做 handle_conn(stream)。無 Box、無 dyn,簡單得多。
  • 通用 job pool → Box<dyn FnOnce() + Send + 'static>。「architect a custom thread pool」字面上是這個。
  • 開場問句:「你要的是連線池還是通用 job 池?」 兩個工作量差很多,不問就是賭。
② 三個 bound 各自被誰逼出來
  • FnOnce — job 只跑一次。寫 Fn 會拒絕掉所有 move 捕獲的 closure。
  • Send — 它要跨 thread 邊界。
  • 'static — worker thread 可能活得比呼叫端久,編譯器不接受任何借來的東西。
  • Box — dyn FnOnce() 是 unsized,不裝箱塞不進 channel。
③ N 個 worker 共用 Receiver → Arc<Mutex<Receiver<Job>>>,而且是被逼的

mpsc::Receiver<T> 不能 clone,也不是 Sync,而 std 到 1.97 都沒有 mpmc(RELEASES.md 全文零命中)。只剩一條路:包 Mutex 讓 worker 搶鎖。

這句要能脫口而出:「std 沒有 mpmc,Receiver 不能 clone 也不是 Sync,所以只能 Arc<Mutex<>> 讓 worker 搶鎖取任務。如果能用 crossbeam 就直接 clone receiver,不用這層。」面試官問「為什麼要包 Mutex」時,這就是答案。

④ 有界 vs 無界 → 比 log collector 多一層

sync_channel(N) 滿了 → execute() 阻塞 → acceptor thread 被卡住 → accept backlog 滿 → client 被拒。過載時 fail fast,好過無界 OOM。要講出你選哪個。

⑤ K 個 worker = K 個並發連線上限

worker 做 blocking read 的話,一個 idle client 永久占住一個 worker。這是 Follow-up 1 講過的天花板,在 pool 版本更明顯,因為 K 是你自己寫死的。

陷阱 1:鎖範圍 —— 這張圖就是那 4 倍

為什麼 while let 會握著鎖 
while let Ok(job) = rx.lock().unwrap().recv() {
    job();   // ← 鎖還握著
}

scrutinee 裡那個 MutexGuard 是 temporary,它的 drop 點是「整個 while let 陳述式結束」,不是 recv() 回傳的瞬間。所以 job() 執行期間鎖還在手上,N 個 worker 退化成 1 個。

edition 2024 沒有修掉這個。 2024 改的是 if let 的 scrutinee 生命週期(讓它在 else 之前 drop),while let 不在其中。本檔在 rustc 1.91.1 + edition 2024 實測,801ms,原封不動。

自我檢查句:寫完問自己 —— 「job() 執行的那一瞬間,鎖在誰手上?我指得出是哪一行放掉的嗎?」 答不出「已經放掉了,而且是這一行」就是錯的。

陷阱 2:關機順序 —— 反了就 deadlock

先 join 再 drop sender = 永遠回不來

sender 還活著 → worker 的 recv() 永遠不回 Err → join() 永遠不回來。順序只能是 drop sender → 再 join。

而 fn drop(&mut self) 讓你 move 不出任何東西,所以 sender 和 JoinHandle 都得包 Option 用 take()。兩個 Option 不是品味,是被 &mut self 逼的。

Terminate 訊息為什麼比 drop(sender) 差

如果面試官提到 Message::Terminate(舊版 Rust Book 的做法):它會排在還沒做完的 job 後面,而且一個 worker 可能一次撿走兩個 terminate,得另外寫一個迴圈補救。drop(sender) 靠 channel 自己的語意,乾淨得多。

實測確認的前提:drop(sender) 之後,queue 裡的訊息仍會被收完,之後才回 Err。所以「關機不掉 job」是免費的 —— 只要你別自己發 terminate 去插隊。

fn worker_buggy(rx: Arc<Mutex<Receiver<Job>>>) {
    // scrutinee 裡那個 MutexGuard 是 temporary。
    // 它的 drop 點是「整個 while let 陳述式結束」,不是 recv() 回傳的瞬間。
    // 所以 job() 執行期間鎖還握著 → N 個 worker 退化成 1 個。
    while let Ok(job) = rx.lock().unwrap().recv() {
        job();
    }
}

fn worker_fixed(rx: Arc<Mutex<Receiver<Job>>>) {
    loop {
        let job = {
            let guard = rx.lock().unwrap();
            guard.recv()
        }; // ← guard 在這個 block 結束就 drop,job() 在鎖外跑
        match job {
            Ok(j) => j(),
            Err(_) => break, // 所有 Sender 都沒了 = 關機訊號
        }
    }
}

fn measure(worker: fn(Arc<Mutex<Receiver<Job>>>), n_workers: usize, n_jobs: usize) -> Duration {
    let (tx, rx) = mpsc::channel::<Job>();
    let rx = Arc::new(Mutex::new(rx));
    let mut hs = Vec::new();
    for _ in 0..n_workers {
        let rx = Arc::clone(&rx);
        hs.push(thread::spawn(move || worker(rx)));
    }
    let t0 = Instant::now();
    for _ in 0..n_jobs {
        tx.send(Box::new(|| thread::sleep(Duration::from_millis(100))))
            .unwrap();
    }
    drop(tx); // 先讓 sender 消失
    for h in hs {
        h.join().unwrap();
    }
    t0.elapsed()
}

// ===================== 陷阱 2:先 join 再 drop sender =====================
fn deadlock_demo() {
    let (done_tx, done_rx) = mpsc::channel::<()>();
    thread::spawn(move || {
        let (tx, rx) = mpsc::channel::<Job>();
        let rx = Arc::new(Mutex::new(rx));
        let mut hs = Vec::new();
        for _ in 0..2 {
            let rx = Arc::clone(&rx);
            hs.push(thread::spawn(move || worker_fixed(rx)));
        }
        tx.send(Box::new(|| {})).unwrap();
        // ↓↓ 錯誤順序:tx 還活著 → worker 的 recv() 永遠不會回 Err → join 永遠不回來
        for h in hs {
            h.join().unwrap();
        }
        drop(tx); // 永遠執行不到
        let _ = done_tx.send(());
    });
    match done_rx.recv_timeout(Duration::from_millis(400)) {
        Ok(()) => println!("  關機完成 —— 不該發生"),
        Err(RecvTimeoutError::Timeout) => println!("  400ms 內沒關掉 → deadlock 重現"),
        Err(e) => println!("  {:?}", e),
    }
}

③ 常見面試追問(3 條鏈 × 3 層深)

鏈 1 · Pin 與 poll 簽名
L1為什麼 poll 收 Pin<&mut Self> 而不是 &mut Self?
因為含跨-await-借用的狀態機是 self-referential。&mut Self 允許 move(mem::swap/replace)→ 內部指標懸空。Pin<&mut Self> 對 !Unpin 禁止 move。
L2可是絕大多數手寫 future 是 Unpin,Pin 對它們是 no-op,那整個 trait 為何還要 Pin?
統一簽名:executor / combinator 必須能同時驅動 Unpin 的和編譯器生成的 !Unpin 的 future。對 Unpin 的,你隨時能 Pin::get_mut 拿回 &mut Self,零成本;對 !Unpin 的,型別系統才擋得住 move。成本只放在真正需要的人身上。
L3我手上有一個 own-by-value、!Unpin 的 future 在 stack 上,怎麼安全 poll?
std::pin::pin!(f):原地建 local 並 shadow 掉 binding,讓你之後拿不到能 move 它的路徑,得到 Pin<&mut F>。或 Box::pin(f) 放 heap(需 alloc,但 std)。手刻 stack pin 要 unsafe(Pin::new_unchecked + 自證不再 move),pin! 就是它的安全包裝。
鏈 2 · lost wakeup 與 busy loop
L1leaf future 回 Pending 但從不存 waker,會怎樣?
executor park 之後永遠沒人 unpark → 掛死(lost wakeup)。沒有存 waker = 沒有人握著叫醒你的把手。
L2反過來,leaf 每次 poll 都在回 Pending 前立刻 wake(),會怎樣?
wake→unpark 設 token → executor 的 park 立刻返回 → 立刻再 poll → 又 wake…→ 100% CPU busy loop。這其實正是 yield_now 的實作原理(故意讓出一輪給 executor 排程)。
L3在一個有共享 run queue 的多 task executor 裡,這種立刻自我 wake 還會 busy loop 嗎?
它把自己重新入列;若是唯一 task,還是 busy loop;有別的 task 時就變成公平讓出(cooperative yield)。引出 fairness——真實 executor(如 tokio)會給每個 task 一個 coop budget,每 poll N 次強制讓出,避免單一 task 餓死別人。
鏈 3 · waker clone 成本與 over-polling
L1waker 為什麼用 Arc?
共享所有權(資源端和 executor 端都要持有)+ clone 便宜(refcount++)+ Send+Sync 讓資源可在別的執行緒 wake。
L2Waker::from(Arc<ThreadWaker>) 的 clone 有 heap alloc 嗎?
沒有,只有 atomic refcount++;drop 是 refcount--。對照手刻 RawWakerVTable:clone/drop 要你自己在 fn 裡管理(容易 leak 或 double-free)。Wake trait + Arc 把這塊變成安全且零額外配置。
L3join! 裡多個子 future 各自 clone 同一個 task waker 並存起來。某個資源就緒時,是整個 task 重 poll 還是只 poll 那支子 future?
我們這種 block_on 是從 root 整棵重 poll:root 的 join/combinator 把所有還沒 ready 的子 future 再 poll 一遍(over-polling)。這是為什麼進階 executor 會給每個子 future 包一個 per-child waker(帶 index),wake 時只喚醒/只 poll 就緒那一支。引出「waker 其實可以攜帶 routing 資訊」這個更深的設計面。

④ Self-quiz(5 題,答案摺疊)

Q1 · self-referential 的 async 狀態機一旦被 move,為什麼是 UB?
move = memcpy 到新位址,struct 內指向「自己另一個欄位」的指標仍指舊位址 → 懸空 → 後續 deref 讀到已失效/被覆寫的記憶體 = UB。Pin 存在就是用型別系統禁止對 !Unpin 型別做這個 memcpy。
Q2 · Pin<&mut T> 對 T: Unpin 提供什麼保證?為什麼幾乎所有手寫 future 都是 Unpin?
對 Unpin 的 T,Pin 不提供任何額外保證——可 Pin::get_mut 拿回 &mut T 自由 move。原因:Unpin 是 auto trait,只要型別不含 self-reference 就自動實作。手寫 future 的欄位通常是普通值(彼此不互指),編譯器自動判定 Unpin。只有編譯器生成的、含跨-await-借用的 async 狀態機才 !Unpin。所以 Pin 的「鎖 move」能力只對後者生效,對手寫 future 是零成本的形式要求。
Q3 · waker 為什麼每次 poll 都要存最新的 clone,不能只存第一次的?必答
契約是「只有最近一次 poll 傳進來的 waker 保證喚醒後有效」。executor 允許在不同 poll 之間換 waker——例如 future 被搬到另一個 task,或被 combinator 用 proxy waker 包起來。若你快取了舊 waker,資源就緒時你 wake 的是過時的 waker,喚醒到錯的/已死的 task,而當前真正在等的 task 永遠不會被重 poll → 掛死。所以每次回 Pending 前都 cx.waker().clone() 覆蓋舊的。

(在我們單執行緒 block_on 裡 waker 每次都一樣,所以這個 bug 不會顯現;但那是巧合,契約是為通用 executor 存在的——面試若寫「只存第一次」會被追問這點。)
Q4 · wake 先於 park 發生時,為什麼不會丟失喚醒?必答
park/unpark 背後是每執行緒一個一次性 token。unpark 打在「還沒 park 的執行緒」上不會空打——它把 token 設成 1 存起來。executor 隨後 park 時看到 token=1,立刻返回(消耗 token),回頭再 poll,這次資源已就緒 → Ready。

實測:unpark 後才 park 在 374ns 返回(≈瞬間,見 park token 語意)。若用一個只會「喚醒正在睡的人」的原始 primitive(無 token),這個 race 就會 lost wakeup。
Q5 · 為什麼 block_on 的迴圈在 park() 返回後必須重新 poll,不能把「park 返回」當成「資源就緒」?
兩個理由。(1) park 允許 spurious wakeup(無故返回),std 明文如此。(2) 即使非 spurious,park 返回只代表「有人 unpark 了我」,不代表「我等的那個特定資源好了」——多個資源可能共用同一個 task waker,任何一個 wake 都會 unpark。所以唯一正確做法是回頭再 poll,由 future 自己重新檢查資源狀態。loop { poll; park } 天生滿足:park 返回就回到 loop 頂重 poll。
