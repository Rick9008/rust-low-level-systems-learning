⚠ 唸稿前要你確認的五件事(帶著洞上場 = 被追問時現場掰)

專案二(先講):system-logging daemon(Modern C++ / Asio)

90 秒 elevator

"I built the system-logging daemon for the mail platform: every service on the box sends diagnostics to it; an Asio event loop receives, parses, routes and filters; a multi-backend logging library fans out to file, remote and system sinks. Standardizing the format cut roughly 30% of duplicated logging code."
全平台服務把診斷送進來;Asio event loop 收/解析/路由/過濾;多後端 library 扇出到檔案/遠端/系統;統一格式砍掉約 30% 重複碼。
"It's a telemetry pipeline: many producers, one collector, multiple sinks — the same shape as an event-loop-over-hardware-signals problem, just with logs instead of interrupts."
Etched 定位句:它就是 telemetry pipeline——跟「event loop 蓋在硬體訊號上」同形,只是把中斷換成日誌。

Trade-off(≥2)

  • 統一 library vs 各服務自由:代價 = 遷移工 + 一個共同依賴;沒走的路 = 放任,代價是跨服務查問題要先學每一種格式。
  • 慢 sink:block vs drop vs buffer(⚠ 確認項 5,填實際選擇與理由)。
  • 單 event loop vs thread-per-source:connection 數與 CPU 的帳。

兩個 war story(strace/perf 紀律——Etched 加分區)

① FD exhaustion・全服務中斷・10 分鐘內復原

現象:程序活著但所有連線失敗。

"First split 'the program is wrong' from 'a resource is exhausted' — the two paths need completely different evidence."
先分「程式錯了」還是「資源用完了」——兩條路要看的證據完全不同。

→ 部署後負載尖峰疊 DDoS,file descriptor 耗盡。追問備案:止血與根因並行;rollback 前先保留現場。

② CPU 空轉・追到確切的 syscall

perf 熱點在 read → strace 看到同一個 fd 反覆回傳 0 → read loop 沒把 0-byte 當 EOF。

"A 0-byte read is EOF, not 'no data this time'. Loop exit conditions have to match the syscall contract."
0-byte return 是 EOF,不是「這次沒資料」。迴圈終止條件永遠對照 syscall 契約。

如果重來

(挑一個)end-to-end structured backpressure(per-source 計帳——跟 telemetry 題同構)/ 評估 completion-model IO(io_uring),並講清楚為什麼當時 readiness 就夠。

專案一:Two-node Active-Active HA(Go + Rust)

90 秒 elevator

"I built the application-state replication layer for a two-node Active-Active mail-security platform — the layer that keeps human approval decisions consistent across two nodes when the network can drop, stall, or duplicate messages. The platform already replicated data three ways; nobody replicated what the application had decided. In production 6+ months, zero reported inconsistency, survived one real failover."
兩節點 Active-Active 的「應用層決策」同步層;平台原有三條資料同步管道,沒有一條同步「做過什麼決定」;上線 6+ 個月、活過一次真實 failover。

限制(這幾條決定所有設計)

  • 只有兩個節點(產品形態)· 部署在客戶端,故障要自動收斂(⚠ 確認項 2)· 網路會斷/慢/重複 · 沒有可信全域時鐘 · 任一節點掛掉服務不能停。

為什麼現成方案都不行(必被問)

"Replication is a transport-layer concern; conflict resolution is a policy-layer concern. Off-the-shelf tools move the data, but they can't decide which write should win."
複製是運輸層,衝突解決是策略層——現成工具搬得動資料,決定不了誰該贏。
  • PG replication:streaming = 單寫者,拿不到 AA;雙向邏輯複製要 PG16 origin=none(⚠ 確認項 1);決定性:無自動衝突解決,衝突讓複製停下來等人。
  • Raft/Paxos:n=2 → quorum 2 → 任一節點掛掉全組停寫,可用性比單機還差;n=3 不允許。→ 換問題:both sides write, replay-safe, converge afterwards。

兩個核心機制(關鍵句都要逐字)

"The check and the write have to be one atomic operation — otherwise two concurrent retries both see 'not processed' and double-execute. Idempotency that isn't atomic only looks like idempotency."
冪等:查與寫必須同一個原子操作,否則兩個併發 retry 會雙做——不原子的冪等只是看起來冪等。
"An approval that already sent the mail beats a later reject — you can't recall a sent email by overwriting a row. The invariant lives in the real world, not in the database. Irreversible actions win."
split-brain:已寄出的核准贏過較晚的退回——不變量在現實世界,不在資料庫。不可逆的贏。

演進 + 數字 + 如果重來

  • v1 NFS 共享(鎖不可靠 + SPOF)→ v2 指令佇列(consumer 重啟 = 遺失視窗)→ v3 派送前本地備份、對端確認才清除。"Each version was forced by a concrete failure, not by a whiteboard."
  • 數字:2 nodes · 6+ months · 1 real failover · v3 代價 = 每操作多一次本地寫。
  • 如果重來:witness/fencing token 破對稱;day-one reconciliation job。誠實句:"Strictly speaking, what I can guarantee is that no inconsistency was ever reported or caught by our checks; proactive reconciliation is the first thing I'd invest in if I rebuilt it."(⚠ 確認項 3)

預期追問:Redis 是不是單點(誠實講 persistence + AOF fsync 視窗)| PEL/XAUTOCLAIM 卡單 | message-ID 表回收(時間窗 > 最大重試視窗)| 兩邊都不可逆?→ 設計上不允許同時發生;否則退回 fencing——誠實說是設計邊界。

專案三:Content-inspection microservices(Rust / Tokio / gRPC)

"I develop and operate production Rust microservices doing real-time email content inspection — regex, IP filtering, PII detection, exact-word matching — with Tokio running matchers concurrently, ~3,500 messages/second on one 8-core node. I also introduced Rust into the team's stack."
即時內容檢測微服務,Tokio 併行 matcher,單台 8 核 ~3,500 msg/s;把 Rust 帶進團隊。
  • 隔壁團隊三個 merged MR:thread-per-request → Tokio async(~300× max connections)+ Rayon 平行掃描(12.5× QPS,perf + load bench 驗證)+ macro trait 介面;成為 go-to Rust reviewer。
"Two runtimes for two kinds of work: Tokio owns the waiting, Rayon owns the number-crunching — mix them in one pool and you starve your IO."
兩個 runtime 管兩種工:Tokio 管等待、Rayon 管算力——混在同一個池裡就是餓死你的 IO。
⚠ 待補:最難的 bug(async 化最痛的一課?)+ 如果重來的一個具體決定。

口袋:kv-storage-rs — "A Redis-command-compatible in-memory KV engine in Rust — 60 commands, TTL, RDB snapshots, nanosecond-level benchmarks." 被問 side project 再展開。

onsite 沒有獨立 culture fit 場——這些稿的用途:每場開頭 60–90 秒自介 + 散在各場的行為題 + 最後 15 分鐘 recruiter debrief(反問三條在這裡用)。★ = 必寫稿,已全數起草;其餘 bullet 骨架。

★ 1 Tell me about yourself(60–90s)
  • Systems / infrastructure engineer at Synology's mail platform since 2023 — Rust, Go, modern C++ on Linux.
  • 三件日常:two-node Active-Active HA layer(分區下的衝突解決)· C++ telemetry/logging daemon(Asio event loop)· Rust microservices on Tokio(~3,500 msg/s)。
  • Outside work: build systems from scratch to understand them — a Redis-compatible KV engine, an async-runtime deep-dive.
"My job, in one sentence: keep systems predictable when the network is unreliable, the load spikes, and a node dies."
一句人設:網路不可靠、流量爆量、節點掛掉的時候,讓系統行為仍然可預期。
收尾鉤:"That's why a company doing hardware-software co-design is exactly where I want to be — the interesting failures live at that boundary."
收在 why-Etched:有趣的故障都住在軟硬體交界。
★ 2 Why Etched? Why leave?(不講負面)
  • Toward, not away:現職學到很多,但軟體只能貼到 kernel 為止。
  • "Etched is making the kind of bet where systems software decides whether the silicon actually delivers — schedulers, event loops, telemetry, the runtime between the model and the chip. That layer is what I already do every day; I want the other side of the API to be real hardware."
  • 證據句:daily work = event loops、backpressure、binary protocols、latency budgets — "the vocabulary transfers one-to-one."
"I'm not leaving something broken — I'm running toward the layer I've been trying to get closer to for years."
不是逃離什麼壞掉的東西,是跑向多年來一直想貼近的那一層。
★ 3 Work-life balance(陷阱題:兩個極端都扣分)
  • 誠實:"I have my own rhythm — I protect sleep, because tired engineers write outages."
  • 證據(這個月就是實例):"This past month I ran a full-time job plus a structured interview-prep schedule every night — sustainable because of scheduling and a hard sleep red-line, not willpower."
  • 邊界:"Sprints are fine when they matter — as long as they're sprints, not the steady state."
"I manage energy like I manage capacity in a system: leave headroom, or the tail latency gets you."
管理精力像管理系統容量:留餘裕,不然尾延遲遲早找上你。
★ 6 Conflict / disagreement(SAR)
  • S:split-brain 衝突解法,團隊(含我)最初傾向 Last-Write-Wins with timestamps。
  • A:I pushed back with a concrete failure scenario, not an opinion — a partition where node A approves and the mail is actually sent, node B later rejects:"you cannot recall a sent email by overwriting a row." 加上兩節點沒有可信時鐘。
  • R:改成從操作語意推規則(irreversible actions win);上線 6+ 個月零不一致。
"We didn't converge because someone argued better — we converged because a failure scenario made the answer obvious. That's how I like to disagree: bring the counterexample, not the volume."
不是誰口才好誰贏,是失敗場景讓答案自明——帶反例來吵架,不是帶音量。
⚠ 確認:當時實際的討論對象與場景,講之前把人物補真。
★ 7 Failure(具體損失 + 機制性改變)
  • 預設 = v2 遺失視窗:"I shipped a dispatch design where an operation could be silently lost if the queue was drained or the consumer restarted before the peer persisted it. That's data loss in a mail-security product — the worst kind of quiet failure."(⚠ 確認:當時怎麼發現的)
  • 機制性改變 ×2:design fix — never discard a message before the peer confirms durability(backup-before-dispatch);process fix — "design reviews now start from crash points: for every hand-off we ask 'what if the process dies right here?'"
"The lesson wasn't 'be more careful' — it was 'make the failure impossible by construction'."
學到的不是「要更小心」,是「用結構讓這種失敗不可能發生」。

備案 B(若 CPU-spin 是自己的 code):0-byte EOF 洞 + 「迴圈終止條件對照 syscall 契約」的 checklist 改變。

其餘 bullet 骨架(4/5/8/9/10)

  • 4 · Timezones:主動給方案——Taipei morning = US West afternoon → fixed overlap window;其餘 async 文件溝通。"Async-first forces better design docs."
  • 5 · Startup vs process:用實例——衝突規則沒有現成答案,自己定義/驗證/扛結果:"that's startup-shaped work inside a bigger company. I liked that part best."
