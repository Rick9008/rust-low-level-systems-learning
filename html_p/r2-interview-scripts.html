專案二(先講):log-ingestion pipeline + C++ daemon(Modern C++ / Asio)

✅ 誠實版架構:dovecot → syslog → syslog-ng(路由/過濾)→ 自寫 C++ daemon(解析/正規化)→ DB。sink 就是 DB;多後端 logging library 是另一件事(發送端統一介面,−30% 重複碼),分開講。

90 秒 elevator

"I own the tail of the mail platform's log pipeline: services log through syslog, syslog-ng does the routing and filtering, and a C++ daemon I wrote consumes that stream, parses and normalizes it, and lands it in a database — so diagnostics are queryable instead of grep-able. Alongside it, a shared logging library standardized how services emit diagnostics — roughly 30% less duplicated logging code."
我擁有平台 log 管線的尾端:服務走 syslog、syslog-ng 做路由過濾、我寫的 C++ daemon 消費串流、解析正規化後落 DB——診斷從「用 grep 撈」變成「可查詢」。另有共用 library 統一發送端格式,砍約 30% 重複碼。
"It's a telemetry pipeline: many producers, a routing layer, one structured sink — the same shape as an event-loop-over-hardware-signals problem, just with logs instead of interrupts."
Etched 定位句:它就是 telemetry pipeline——多 producer、一層路由、一個結構化 sink,跟「event loop 蓋在硬體訊號上」同形。

問題與設計(口述版,兩段連著唸)

"Before this, diagnostics lived in plain-text logs scattered across services, each with its own format — debugging one cross-service issue meant grepping three formats and joining them in your head. We needed a structured, queryable landing zone — and the collection path must never interfere with the mail-delivery hot path."
問題:散裝純文字 → 要可查詢;採集不能碰主路徑。
"I stood on the syslog ecosystem instead of fighting it: transport and routing go to syslog-ng — battle-tested, config-driven. My daemon owns exactly two things: the parsing-and-normalization logic, and the database schema. Asio drives the daemon's IO."
設計:傳輸交給生態,自己的 code 只擁有解析與 schema 兩件事。

Trade-off(≥2;口述版,中文只是標籤)

重用 vs 自建:"The off-the-shelf transport is battle-tested and cheap to walk away from; the cost is being bound to syslog's format and delivery semantics. I didn't build a transport — the interesting problem was parsing and schema, so that's where my code lives."
獨立 daemon vs 直寫 DB:"Parsing rules and schema are code — they evolve and they need tests. I didn't want that living in a config layer. And the failure modes decouple: if my daemon dies, syslog-ng still buffers."
結構化 vs 純文字:"Query power versus write cost. And I won't invent a throughput number — I don't have it from memory; the bottleneck by construction is the DB write path, not the parse."

兩個 war story(strace/perf 紀律——Etched 加分區)

① FD exhaustion・全服務中斷・10 分鐘內復原(口述版)

"The process was alive, but every new connection failed. First move: split 'the program is wrong' from 'a resource is exhausted' — the two paths need completely different evidence. It turned out a post-deploy load spike stacked on a DDoS, and we ran out of file descriptors. Service was back in about ten minutes."
現象 → 分流原則 → 根因 → 復原時間,一段講完。
追問備案:"We stopped the bleeding and chased the root cause in parallel — and we captured the scene before any rollback, because a rollback destroys your evidence."

② CPU 空轉・追到確切的 syscall(✅ 前人程式碼的陳年 bug——當 debugging 故事講,說 "a long-standing bug in inherited code",不認領不指責)

perf 熱點在 read → strace 看到同一個 fd 反覆回傳 0 → read loop 沒把 0-byte 當 EOF。

"A 0-byte read is EOF, not 'no data this time'. Loop exit conditions have to match the syscall contract."
0-byte return 是 EOF,不是「這次沒資料」。迴圈終止條件永遠對照 syscall 契約。

如果重來(口述版)

"I'd add an explicit backpressure-and-drop ledger on the daemon side. Today I inherit syslog-ng's buffering behavior, so the drop policy isn't in my hands — I want 'how much did we lose' to be a number I own. It's the same dropped-counter shape as any telemetry pipeline."
顯式丟棄帳——跟 telemetry 題的 dropped counter 同構。

專案一:Two-node Active-Active HA(Go + Rust)

90 秒 elevator

"I built the application-state replication layer for a two-node Active-Active mail-security platform — the layer that keeps human approval decisions consistent across two nodes when the network can drop, stall, or duplicate messages. The platform already replicated data three ways; nobody replicated what the application had decided. In production 6+ months, zero reported inconsistency, survived one real failover."
兩節點 Active-Active 的「應用層決策」同步層;平台原有三條資料同步管道,沒有一條同步「做過什麼決定」;上線 6+ 個月、活過一次真實 failover。

限制(這幾條決定所有設計)

  • 只有兩個節點(產品形態)· 收信必須自動、不能暫停——凌晨 AA 斷線也要兩邊各自繼續收信、事後收斂,不能等人 · 網路會斷/慢/重複 · 沒有可信全域時鐘 · 任一節點掛掉服務不能停。

為什麼現成方案都不行(必被問)

"Replication is a transport-layer concern; conflict resolution is a policy-layer concern. Off-the-shelf tools move the data, but they can't decide which write should win."
複製是運輸層,衝突解決是策略層——現成工具搬得動資料,決定不了誰該贏。
vs PG replication:"We were on Postgres fourteen. Streaming replication is single-writer, so no active-active; and bidirectional logical replication wasn't available yet — that needs Postgres sixteen. But the deeper reason holds on any version: replication can't order two partitioned writes, and it certainly doesn't know that one of them already sent an email."
版本一句結案 + 更根本的政策層理由。
vs Raft/Paxos:"With Raft or Paxos at n equals two, the quorum is two — lose either node and the whole system stops writing. Availability would be worse than a single machine, and a third node wasn't an option. So I changed the question: instead of asking who is allowed to write, both sides write, replay-safe, and converge afterwards."
n=2 的 quorum 悖論 → 換問題。

兩個核心機制(關鍵句都要逐字)

"The check and the write have to be one atomic operation — otherwise two concurrent retries both see 'not processed' and double-execute. Idempotency that isn't atomic only looks like idempotency."
冪等:查與寫必須同一個原子操作,否則兩個併發 retry 會雙做——不原子的冪等只是看起來冪等。
"An approval that already sent the mail beats a later reject — you can't recall a sent email by overwriting a row. The invariant lives in the real world, not in the database. Irreversible actions win."
split-brain:已寄出的核准贏過較晚的退回——不變量在現實世界,不在資料庫。不可逆的贏。

演進 + 數字 + 如果重來

  • 演進口述版:"Version one used shared NFS — after a link flap the file locks were unreliable, and the shared storage itself was a single point of failure. Version two moved to command queues on each node's local database — but if the queue drained or the consumer restarted, operations that hadn't landed on the peer were simply gone. That loss window forced version three: back up locally before dispatch, and only clear the backup after the peer confirms it landed. Each version was forced by a concrete failure, not by a whiteboard."
  • 數字:2 nodes · 6+ months · 1 real failover · v3 代價 = 每操作多一次本地寫。
  • 「你怎麼知道零不一致?」——武器句逐字:"We don't just hope it's consistent — the system detects divergence, re-syncs automatically, and counts every occurrence. Across every customer machine, for six-plus months, that counter stayed at zero — and support never received a single inconsistency report."
  • 如果重來:witness / fencing token 破兩節點對稱(future work #1;當時部署形態不允許額外元件——誠實講是設計邊界)。

預期追問:Redis 是不是單點(誠實講 persistence + AOF fsync 視窗)| PEL/XAUTOCLAIM 卡單 | message-ID 表回收(時間窗 > 最大重試視窗)| 兩邊都不可逆?→ 設計上不允許同時發生;否則退回 fencing——誠實說是設計邊界。

專案三:Content-inspection microservices(Rust / Tokio / gRPC)

"I develop and operate production Rust microservices doing real-time email content inspection — regex, IP filtering, PII detection, exact-word matching — with Tokio running matchers concurrently, ~3,500 messages/second on one 8-core node. I also introduced Rust into the team's stack."
即時內容檢測微服務,Tokio 併行 matcher,單台 8 核 ~3,500 msg/s;把 Rust 帶進團隊。
  • 隔壁團隊三個 merged MR:thread-per-request → Tokio async(~300× max connections)+ Rayon 平行掃描(12.5× QPS,perf + load bench 驗證)+ macro trait 介面;成為 go-to Rust reviewer。
"Two runtimes for two kinds of work: Tokio owns the waiting, Rayon owns the number-crunching — mix them in one pool and you starve your IO."
兩個 runtime 管兩種工:Tokio 管等待、Rayon 管算力——混在同一個池裡就是餓死你的 IO。
⚠ 待補:最難的 bug(async 化最痛的一課?)+ 如果重來的一個具體決定。

口袋:kv-storage-rs — "A Redis-command-compatible in-memory KV engine in Rust — 60 commands, TTL, RDB snapshots, nanosecond-level benchmarks." 被問 side project 再展開。

onsite 沒有獨立 culture fit 場——這些稿的用途:每場開頭 60–90 秒自介 + 散在各場的行為題 + 最後 15 分鐘 recruiter debrief(反問三條在這裡用)。★ = 必寫稿,已全數起草;其餘 bullet 骨架。

★ 2 Why Etched? Why leave?(~120 words ≈ 60s;不講負面)
"For me this is a toward move, not an away move. I've learned a lot where I am — but the ceiling is that software stops at the kernel; the hardware underneath is always someone else's black box."
toward-not-away 開場;被追離職負面細節就回到這句重申,不展開抱怨。
"Etched is making the kind of bet where systems software decides whether the silicon actually delivers — schedulers, event loops, telemetry, the runtime between the model and the chip. That layer is what I already do every day: event loops, backpressure, binary protocols, latency budgets. The vocabulary transfers one to one. I want the other side of the API to be real hardware."
賭注 + 日常詞彙一比一遷移(證據句已織入)。
"So no — I'm not leaving something broken. I'm running toward the layer I've been trying to get closer to for years."
收尾金句。
★ 3 Work-life balance(陷阱題:兩個極端都扣分;~135 words ≈ 65s)
"Honest answer: I have my own rhythm, and I protect sleep — tired engineers write outages."

⚠ Gjengset 引用守則(7/31):上場前把那篇 40-hours 文章自己重讀一遍;被追問講論點、不掰細節;對面「拼命文化」訊號強 → 縮成 "I optimize for sustained throughput, not heroics",論點不變、少一個可被挑戰的引用。
"I manage energy the way I manage capacity in a system: leave headroom, or the tail latency gets you."

★ 6 Conflict / disagreement(SAR)
"Sure — this happened on the two-node H-A project. When we designed the split-brain conflict resolution, the team's first instinct — mine included — was last-write-wins with timestamps. It's the intuitive answer."
S:場景。⚠ 上場前把人物補真,一句就夠:"my tech lead and I both started from..."。

You cannot recall a sent email by overwriting a row. And with exactly two nodes, there's no trusted clock to even say which write was 'later'."
A:帶反例不帶意見。

★ 7 Failure(✅ 7/29 改用 authz 故事——真正自己寫出的 bug)
"The failure that's genuinely mine: I shipped a cross-cluster operations interface without proper authentication and authorization. It was internal-only — so I treated the network boundary as the security boundary."
S:自己寫出的 bug,認領乾脆。
"It later surfaced as a critical vulnerability — CVSS ten point zero. I can't share the technical details because the CVE is still under embargo, but the design lesson is fully mine to own."
損失具體化。CVSS 10.0 唸 "ten point zero";embargo 那句本身是專業訊號。
"I also designed the fix myself: defense in depth — mutual TLS at the transport layer, application-level authentication and authorization on every call, and localhost-scoped access control for the cross-cluster operations."

"Two things changed mechanically after that. Security review moved into the design phase instead of being a bolt-on. And my personal default flipped: every interface gets auth, and 'internal-only' never counts as a boundary again."
機制性改變兩條。
"The lesson wasn't 'be more careful'. The lesson was that internal-only is an assumption, not a boundary. Assumptions rot; boundaries hold."
