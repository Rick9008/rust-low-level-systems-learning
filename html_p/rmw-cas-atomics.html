Rust RMW & CAS

read-modify-write:fetch_add / swap / compare_exchange / CAS loop  ·  姊妹頁:atomic ordering(RMW 是它的延伸) ·  std-only
「RMW = 把 讀 → 改 → 寫 焊成一步,別人插不進來。」
plain load 再 store 有縫,兩條 thread 會擠進去互相蓋掉更新(lost update)。RMW 用硬體把這三步變成不可分割的一次操作——這是它存在的唯一理由。

上一頁把 Release / Acquire / SeqCst 講完了,但那些是 load/store。真正的 lock-free 資料結構(計數器、佇列、堆疊、refcount)靠的是 read-modify-write:fetch_add、swap、compare_exchange。這頁把 RMW 的兩件正交的事拆開講清楚——要不要用 RMW(原子性)和 掛哪個 ordering(可見性)——以及 CAS 那個「吃兩個 ordering」的招牌問題。

閱讀路線

  • :先看 plain load+store 的 lost update(為什麼非 RMW 不可)→ RMW 家族 → 兩個正交問題(A 幾個寫者 / B 兩個半邊)→ fetch_add(一個 ordering)vs compare_exchange(兩個)→ weak/strong → ABA → P/C 家族(SPSC/MPSC/SPMC/MPMC,寫者數 = 難度)。
  • :兩條 thread 各用 CAS loop 對同一個計數器 +1。看 A 的 CAS 成功、B 的 CAS 失敗後重試,最後 count 不丟;最後一步示範用 plain load+store 取代 RMW 如何漏掉一次更新。
  • :三條鏈——CAS 為什麼吃兩個 ordering、CAS loop 與 weak/strong、ABA 三種解法。
  • :5 題,含指定題(MPSC 的 tail.fetch_add 該掛什麼 ordering)。
  • :CAS-loop 計數器 + fetch_add 對照 + Treiber lock-free stack(CAS 的招牌用法)。
定位。本頁是 atomic ordering 的延伸:那頁的「兩個半邊(load 側 / store 側)」在這裡直接複用——RMW 同時是 load 又是 store,所以一個 ordering 就能同時給兩半語意。ordering 本身的推導(synchronizes-with / happens-before / 為何 Relaxed 會 UB)請先看姊妹頁。 Rust 以 use std::sync::atomic::Ordering::*; 為前提;unverified:x86/ARM 指令層 lowering(lock xadd / lock cmpxchg / LL-SC)標為 typical,面試講到架構層規則即可,不背各家微架構條文。

1. 為什麼需要 RMW:plain load+store 的 lost update

想像兩條 thread 各對共享計數器 +1,用最直覺的「讀出來、加一、寫回去」:

// ⚠ 錯:load 和 store 之間有縫
let v = c.load(Relaxed);      // 讀
c.store(v + 1, Relaxed);      // 改 + 寫(分成兩步)
  • Thread A 讀到 5,Thread B 也讀到 5(A 還沒寫回)。
  • A 寫 6,B 也寫 6。兩次 +1,結果卻是 6 —— 少了一次(lost update)。
  • 問題出在 load 與 store 是兩個獨立操作,中間可以插進別人。
RMW 的作用:把「讀 → 改 → 寫」焊成一次不可分割的操作。c.fetch_add(1, Relaxed) 由硬體保證:從讀到寫之間沒有任何 thread 能改到這個變數。兩條 thread 各 fetch_add(1),兩次都算數,結果一定是 7。這就是 要演的:CAS 版怎麼靠「失敗重試」達到同樣效果。

1.1 RMW 還免費送你一個性質:讀到 modification order 的最新值

普通 Relaxed load 可能讀到 stale(舊)值。但 RMW 保證讀到的是該變數修改順序裡最新的那個寫——它 read-from 緊鄰在它前面的那次修改。所以 fetch_add(1, Relaxed) 當純計數器,一個增量都不會掉,即使 Relaxed。這是「計數器類敢用 Relaxed」的底氣。

3. 兩個正交問題(永遠拆開問)

問題 A(要不要 RMW?)= 原子性。「同一個 atomic,是不是多個 thread 在寫?」多寫者 → 要「讀+改+寫」焊成一步,否則 lost update。單一寫者(如 SPSC 的 tail)→ 一個 plain store 就夠,不需要 RMW。

問題 B(掛哪個 ordering?)= 可見性。就是姊妹頁的「兩個半邊」:

  • load 半:這一步要看到別 thread 的 payload 嗎?→ 需要 Acquire。
  • store 半:這一步要發布 payload 給下一個讀的人嗎?→ 需要 Release。
  • 兩邊都要 → AcqRel。都不要(純記帳)→ Relaxed。

兩者獨立:fetch_add(Relaxed)(原子但零排序=純計數)、compare_exchange(AcqRel)(原子+雙向=拿鎖)都合法。先答 A 決定用不用 RMW,再答 B 決定掛哪個 ordering。

4. CAS 為什麼吃兩個 ordering:結局數,不是半邊數

這是招牌追問。fetch_add 只填一個 ordering,compare_exchange 填兩個——差別不在「幾個半邊」,在「幾種結局」。

操作有分支?幾種結局ordering 參數
fetch_add / swap無條件1(一定 load+store)1(值可為 AcqRel,涵蓋兩半)
compare_exchange比對成功才寫2:成功=RMW / 失敗=只 load2:success, failure
c.compare_exchange(expected, new,
    Ordering::AcqRel,   // success:load + store 都發生 → 可到 AcqRel
    Ordering::Acquire)  // failure:只有 load 發生 → 最多 Acquire
// c.compare_exchange(expected, new, Acquire, Release)  // ✗ panic:沒有「release 的失敗」
失敗那條為什麼不能 Release / AcqRel?比對失敗 = store 沒發生,沒有寫可以「發布」。給它 Release 語意在語言層是 logic error → Rust 會 panic。所以 failure ordering 只能是 load ordering(Relaxed / Acquire / SeqCst)。fetch_update 的 fetch_order 同理(它涵蓋初次 load + 每次 CAS 失敗的 re-load)。

「一個 ordering 參數」≠「只管一個半邊」:fetch_add(AcqRel) 這單一參數照樣同時給 load 半 Acquire、store 半 Release。參數的數量只反映結局數。

5. CAS loop:為什麼要迴圈、weak vs strong

多寫者搶同一個 atomic,CAS 本來就會失敗(別人先改了)。所以 CAS 幾乎總是包在重試迴圈裡:失敗就拿新值重算再試。

let mut cur = c.load(Relaxed);
loop {
    let new = f(cur);                                   // 用現值算新值
    match c.compare_exchange_weak(cur, new, AcqRel, Acquire) {
        Ok(_) => break,                                 // 沒人插隊 → 成功
        Err(actual) => cur = actual,                    // 有人先改 → 用新值重試
    }
}
compare_exchange(strong)compare_exchange_weak
spurious 失敗不會(值真的不符才失敗)可能(值符合也可能假失敗)
底層LL/SC 架構要自己包一層 retry直接對映一次 LL/SC,更快
用在單次 CAS(不迴圈)迴圈裡(反正都要重試)

x86 有 lock cmpxchg,strong/weak 沒差;差別在 ARM/POWER 的 LL/SC(load-linked/store-conditional):weak 讓「假失敗」直接冒泡到你的 loop(你本來就會重試),strong 要在指令層多包一圈把假失敗吃掉。unverified:各架構確切 lowering 不背。

6. ABA:CAS 只看值、不看歷史

CAS 判斷「現值 == expected」就以為「沒人動過」。但值可能 A → B → A 繞回來:你讀到 A,別人把它改成 B 又改回 A,你的 compare_exchange(A, ...) 誤以為沒變、成功了——中間那段變化你完全沒察覺。

典型爆點:lock-free stack 的 pop。你讀 head = 節點1,打算 CAS 成 節點1.next;但在你 CAS 前,別人 pop 了節點1、又 pop 節點2、再 push 回節點1——head 又是節點1(A),你的 CAS 成功,卻把 head 設成一個已經被釋放/已改變的 next。

三種解:① 版本號 / tagged pointer(把值和一個單調遞增的 counter 綁在一起 CAS,值繞回但版本不會)、② epoch / hazard pointer(延遲回收,確保沒人還握著舊節點才 free)、③ 根本不重用(free-running index,如 SPSC 的計數器永不繞回同一值——這也是 SPSC 不需要 CAS 的另一個原因)。詳見 。

8. 從 RMW 到 P/C 家族:寫者數 = 難度

RMW/CAS 是機制;lock-free 佇列家族(SPSC / MPSC / SPMC / MPMC)是應用。決定每一側要不要 CAS 的,就是問題 A:那一側有幾個寫者?

單 consumer(head 單寫)多 consumer(head 多寫)
單 producer
(tail 單寫)		SPSC — 兩側各單寫者 → 零 CAS,plain load/store(你剛做的 challenge)SPMC — head 多寫 → consumer 側 CAS 搶
多 producer
(tail 多寫)		MPSC — tail 多寫 → producer 側 CAS / fetch_add 搶MPMC — 兩側都多寫 → 兩側都 CAS
  • SPSC:每 index 單寫者 → 零 CAS。free-running 計數器永不繞回同值,連 ABA 都免疫——這就是它最簡單的原因。
  • MPSC:多 producer 搶 tail → tail.fetch_add(1, Relaxed) 發號碼牌(無 payload → Relaxed)。但完成順序亂,不能拿單一 tail 當「資料備妥水位線」——payload 的 Release/Acquire 下放到 per-slot ready 旗標(slot[pos].ready.store(true, Release))。
  • SPMC:多 consumer 搶 head → head 側 CAS。其實是兩題:work-stealing(每人搶不同項,像 Tokio run queue)vs broadcast(每人都要收到同一份)——語意不同,別混。
  • MPMC:兩側都搶 → Vyukov bounded MPMC 的招牌:每個 slot 帶一個 sequence number,CAS 推進 position + 用 seq 當「這格現在輪到 producer 還是 consumer」的旋轉門。
一句話串起來:某一側的寫者數從 1 變 2,那一側就從「plain store」升級成「CAS 搶」;payload 的交接旗標也從「單一水位線」下放到「per-slot」。深挖(階梯圖解、MPSC 交錯 stepper、佇列家族手冊):docs/artifacts/qa_lockfree_pc.html · html_p/lockfree-queue-family-handbook.html · html_p/mpsc-interleaving-stepper.html。

3. 面試追問(三條鏈,每條 ≥ 三層)

鏈 A — CAS 為什麼吃兩個 ordering

L1 — 為什麼 fetch_add 填一個、compare_exchange 填兩個?

ordering 參數的數量對應「幾種結局」,不是「幾個半邊」。fetch_add 無條件、一定 load+store,只有一種結局 → 一個。compare_exchange 會分岔:成功=完整 RMW、失敗=只 load → 兩種結局、兩個參數。

L2 — 失敗那條的 ordering 能填 Release 嗎?

不能。失敗代表 store 沒發生,沒有寫可以 release。填 Release / AcqRel 是 logic error → Rust panic。failure 只能是 load ordering(Relaxed / Acquire / SeqCst)。

L3 — 那 fetch_add(AcqRel) 的「一個參數」怎麼同時管兩個半邊?

ordering 這個 enum 的值負責把語意分配到兩半:AcqRel = load 半 Acquire + store 半 Release。參數的數量只反映結局數;fetch_add 一種結局但兩個半邊,單一 AcqRel 就涵蓋兩半。這也是為什麼 CAS 的 success 那格可以填到 AcqRel。

鏈 B — CAS loop 與 weak / strong

L1 — 為什麼 CAS 幾乎總是包在迴圈裡?

多寫者搶同一 atomic,CAS 失敗是正常的(別人先改了)。失敗回傳的是當下實際值,你拿它重算新值再試,直到成功。單次不 loop 的 CAS 只有在「失敗就放棄」(如 try-lock)時才對。

L2 — compare_exchange 和 _weak 差在哪?

weak 允許 spurious failure:即使現值 == expected 也可能假失敗。因為 ARM/POWER 的 LL/SC(load-linked / store-conditional)本來就會因為 cache line 被碰、context switch 等假失敗;weak 直接把它冒泡給你,strong 要在指令層多包一圈把假失敗吃掉。

L3 — 那什麼時候用哪個?

迴圈裡用 weak(你本來就會重試,假失敗只是多轉一圈,但每次 CAS 更便宜);單次、不迴圈用 strong(不能容忍假失敗把你踢掉)。x86 上兩者編出來一樣(lock cmpxchg),差異只在弱記憶體序架構——但寫對意圖是好習慣。

鏈 C — ABA

L1 — 什麼是 ABA?

CAS 只比對「現值 == expected」,不看歷史。值 A→B→A 繞回來時,你的 compare_exchange(A,…) 誤以為沒變、成功了,但中間的變化(可能有節點被釋放/重用)你沒察覺。

L2 — 給一個會爆的場景。

Treiber stack pop:讀 head=N1、算好要 CAS 成 N1.next=N2。CAS 前別人 pop N1、pop N2、再 push N1 回來(N1 記憶體被重用)。head 又 == N1(A),你的 CAS 成功,卻把 head 設成 N2——一個已經被 pop 掉的節點,堆疊結構壞掉 / use-after-free。

L3 — 三種解法,各自代價?

  • 版本號 / tagged pointer:把指標和一個單調遞增 counter 綁成一個 double-width word 一起 CAS(x86 的 cmpxchg16b)。值繞回但版本不會 → CAS 失敗。代價:需要 double-width CAS。
  • epoch / hazard pointer:延遲回收——確保「沒有任何 thread 還握著這個舊節點」才真的 free。代價:回收機制複雜(crossbeam-epoch 那套)。
  • 不重用:free-running 單調 index,永不繞回同一值(SPSC 計數器就是這樣,所以它連 CAS 都不用)。代價:只適用「不需要重用記憶體位址」的設計。

4. Self-Quiz(答案摺疊)

Q1(指定題) MPSC 裡多個 producer 用 tail.fetch_add(1, ?) 搶 slot,ordering 該填什麼?為什麼?

Relaxed 就夠。先答問題 A:多 producer 搶同一 tail → 多寫者 → 要 RMW(fetch_add 保證每人拿到唯一格號、不丟、不重)。再答問題 B:搶格子的當下還沒寫資料,這一步沒有 payload 要交接 → 不需要 Acquire/Release → Relaxed。

關鍵陷阱:MPSC 的 producer 完成順序是亂的,不能拿單一 tail 當「資料備妥水位線」(那是 SPSC 才行)。payload 的 Release/Acquire 要下放到 per-slot 的 ready 旗標:slot[pos].ready.store(true, Release) / consumer load(Acquire)。fetch_add 只負責發號碼牌。

Q2 compare_exchange 的 failure ordering 填 Release 會怎樣?

panic(logic error)。失敗代表 store 沒發生,沒有寫可以「發布」,所以 failure 只能是 load ordering(Relaxed / Acquire / SeqCst)。這也是判斷你懂不懂「CAS 兩種結局」的照妖鏡。

Q3 compare_exchange vs compare_exchange_weak,CAS loop 裡該用哪個?

loop 裡用 weak。weak 允許 spurious failure(值符也可能假失敗),但你在迴圈裡本來就會重試,假失敗只是多轉一圈;好處是每次 CAS 對映一次 LL/SC、更便宜。單次不迴圈用 strong(不能被假失敗踢掉)。x86 上兩者一樣,差異在 ARM/POWER。

Q4 為什麼 SPSC ring 從頭到尾不用任何 CAS/RMW?

因為問題 A 的答案是「否」:每個 index 只有一方寫(tail←只有 producer、head←只有 consumer)。單一寫者 → 沒有 lost update 風險 → 一個 plain store 就夠,不需要焊成一步。RMW 是等你破壞單寫者前提(MPSC / MPMC / lock-free stack / refcount)才被迫登場的。順帶:free-running 計數器永不繞回同值,連 ABA 都免疫。

Q5 兩條 thread 各 fetch_add(1, Relaxed) 一百萬次,總和會不會少?為什麼一個 Relaxed 夠?

不會少,剛好兩百萬。RMW 保證讀到 modification order 的最新值(不像 Relaxed load 可能 stale),而且讀-改-寫不可分割 → 不丟增量。這個「原子性 + 讀最新」是 RMW 本身免費給的,跟 ordering 無關;因為純計數不 publish / consume 任何 payload,問題 B 答「都不用」→ Relaxed。

完整代碼(std-only)

三段。(1) 計數器:fetch_add 版 vs 手寫 CAS-loop 版(等價);(2) 一個會漏更新的 錯版(plain load+store)當對照;(3) Treiber lock-free stack——CAS 的招牌用法。unverified:本頁製作環境未實編這段;請在你的 pad 按一次 Run 當最終確認。Treiber stack 刻意不做記憶體回收(節點會 leak),把焦點留在 CAS 本身——真實版要配 epoch/hazard 解 ABA + reclamation。

① 計數器:fetch_add vs 手寫 CAS loop

use std::sync::atomic::{AtomicUsize, Ordering::*};

// 最簡:一步到位。多寫者也不丟,因為 RMW 不可分割。
fn inc_fetch_add(c: &AtomicUsize) {
    c.fetch_add(1, Relaxed);          // 純計數,無 payload → Relaxed
}

// 等價的手寫版:當你的「改」不是 +1 這種現成 op 時就得這樣寫。
fn inc_cas_loop(c: &AtomicUsize) {
    let mut cur = c.load(Relaxed);
    loop {
        let new = cur + 1;             // 任意計算
        // 迴圈裡用 _weak;success 這裡不 handoff payload,Relaxed 即可
        match c.compare_exchange_weak(cur, new, Relaxed, Relaxed) {
            Ok(_) => break,            // 沒人插隊
            Err(actual) => cur = actual, // 有人先改 → 用最新值重試
        }
    }
}

② 錯版:plain load+store 會漏更新(別這樣寫)

// ⚠ load 與 store 之間有縫,兩 thread 會擠進去互相蓋掉
fn inc_broken(c: &AtomicUsize) {
    let v = c.load(Relaxed);
    c.store(v + 1, Relaxed);          // A、B 都讀到 5、都寫 6 → 少一次
}

③ Treiber lock-free stack(CAS 招牌用法)

use std::sync::atomic::{AtomicPtr, Ordering::*};
use std::ptr;

struct Node<T> { val: T, next: *mut Node<T> }

pub struct Stack<T> { head: AtomicPtr<Node<T>> }

impl<T> Stack<T> {
    pub fn new() -> Self { Stack { head: AtomicPtr::new(ptr::null_mut()) } }

    pub fn push(&self, val: T) {
        let node = Box::into_raw(Box::new(Node { val, next: ptr::null_mut() }));
        let mut cur = self.head.load(Relaxed);
        loop {
            // 把新節點的 next 接到當前 head
            unsafe { (*node).next = cur; }
            // 發布這個節點(Release);失敗只 load(Acquire 拿到最新 head)
            match self.head.compare_exchange_weak(cur, node, Release, Acquire) {
                Ok(_) => return,
                Err(actual) => cur = actual,   // 有人先 push/pop → 重接重試
            }
        }
    }

    pub fn pop(&self) -> Option<T> {
        let mut cur = self.head.load(Acquire);   // 要讀 *cur,先 Acquire
        loop {
            if cur.is_null() { return None; }
            let next = unsafe { (*cur).next };
            // ⚠ 此處有 ABA 風險(見追問鏈 C);示範版不做回收
            match self.head.compare_exchange_weak(cur, next, AcqRel, Acquire) {
                Ok(_) => {
                    let boxed = unsafe { Box::from_raw(cur) };
                    return Some(boxed.val);
                }
                Err(actual) => cur = actual,
            }
        }
    }
}

// 注意:多執行緒下 pop 的 Box::from_raw 有 ABA / use-after-free 風險,
// 真實版要 epoch(crossbeam-epoch)或 hazard pointer;此處為教學單純化。
▶ 計數器的雙執行緒驗證 harness(點開) 
fn main() {
    use std::sync::Arc;
    use std::thread;
    let c = Arc::new(AtomicUsize::new(0));
    const T: usize = 8;
    const N: usize = 100_000;
    let mut hs = Vec::new();
    for _ in 0..T {
        let c = c.clone();
        hs.push(thread::spawn(move || {
            for _ in 0..N { inc_cas_loop(&c); }
        }));
    }
    for h in hs { h.join().unwrap(); }
    assert_eq!(c.load(Relaxed), T * N, "CAS loop 丟了更新");
    println!("{} 次遞增全數到帳 = {}", T * N, c.load(Relaxed));
}

把 inc_cas_loop 換成 inc_broken 重跑,assert_eq! 幾乎必爆(總和 < T·N)——那就是 lost update 的實證,也是 演的。
