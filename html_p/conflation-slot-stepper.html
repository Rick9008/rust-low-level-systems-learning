Per-key Conflation Slot

值層／通知層分離 · 一條 invariant 解釋三種 bug · std-only Rust · 2026-07-30

直覺一句話

producer 產得比 consumer 吃得快時,同一個 key 的舊值對 consumer 是死重量——它只想知道「現在」。所以每個 key 只留一格,新值直接就地蓋掉舊值;要另外記「哪些格子髒了」,consumer 才不用每次掃全表。

核心結構圖 — 值走上面,通知走下面

這張圖是全篇唯一需要背下來、能徒手重畫的東西。兩層各自的上界不同,是整個設計的價值來源。

唯一 invariant   slot.queued == true  ⟺  key ∈ ready
為什麼只記這一條 這條 invariant 是 queued 這個欄位存在的唯一理由,而三種經典 bug 都是它的三種破法:
・slot 的 queued 是 true,但 key 其實不在 ready 裡:producer 會誤以為 key 已經在 ready 裡,於是跳過通知 → lost update(tab ②)
・完全不設 queued 欄位:同一個 key 會被反覆排進 ready,ready 的長度變成 O(事件數),記憶體上界失效
・key 已經在 ready 裡,值卻還沒寫完:consumer 醒來會讀到舊值 → 通知順序(tab ③)

路由:什麼時候能用

訊號判定理由
consumer 只在乎「現在的值」✓ 用舊值是死重量
payload 是絕對狀態快照✓ 用覆蓋即合法
payload 是 delta / increment✗ 需改 merge只能用可結合運算摺疊(+= / max),不能覆蓋
需要完整事件序列(audit / replay / event sourcing)✗ 不合法中間值被結構性丟棄,換 durable log
需要知道「發生幾次」✓ 但要加 count否則分不出安靜 key 與被摺掉十萬筆的 key
key 基數無界(per-connection / 使用者輸入決定)✗ 先加 TTLO(K) 上界失效 → key 爆炸即 OOM 向量
同型結構(認出來就贏一半) epoll 的 level-triggered readiness、pending signal bitmask、GUI 的 dirty-rect repaint、CRDT 的 LWW-register、市場報價的 conflated feed —— 全都是 per-key conflation slot。這也解釋了為什麼 signal 會合併:pending 是一個 bit(一格 slot),不是計數器。

naive → optimal 階梯

每一階都由上一階的具體失效逼出來 · TC 與 SC 分開標

tier 0 · naive:每筆 update 都入無界佇列

最笨但正確:consumer 看得到每一筆歷史。

TC push O(1) / pop O(1)。SC O(N),N = 累積事件數。

失效producer 快於 consumer 時 N 單調成長 → OOM。這是背壓問題,不是效能問題。

tier 1 · 有界 ring,drop-oldest

把 SC 釘死在容量 C。丟棄策略:滿了就丟最舊的事件。

TC O(1)。SC O(C),固定。

失效(公平性軸) 丟棄粒度是「事件」而非「key」。一個吵鬧 key 灌滿 ring,就把安靜 key 的事件擠出去了。安靜 key 的更新永久消失,而吵鬧 key 保留了一堆早就過期的中間值 —— 丟錯東西了。

這一階迫使你回答 predicate:「該丟哪一筆?」tier 1 的答案是「最舊的」,而它答錯了。

tier 2 · observation → 換掉丟棄粒度

關鍵觀察 consumer 只需要每個 key 的最新值 → 同一 key 的舊事件,對 consumer 的價值是 0;不同 key 的事件價值都是正的。所以該丟的是「同 key 的舊值」,不是「全局最舊的事件」。

這個觀察直接指定資料結構:佇列(事件序列)換成 HashMap<K, V>(key → 最新值)。lever = 用 key 索引取代時序排隊。

TC publish O(1) amortized。SC O(K),K = 不同 key 的數量,與事件率脫鉤 —— 這就是全部的價值。

新失效 consumer 現在不知道「哪些 key 變了」。掃全 map = 每次 O(K),而且無法阻塞等待。

tier 3 · dirty set 逼出 queued 欄位

加一條通知路徑:ready: VecDeque<K>,只放髒 key。

但 publish 若無條件 push,吵鬧 key 會被 push 一千次 → ready 長度回到 O(事件數),tier 2 的空間成果被通知層吃掉。所以需要一個「我已經在 ready 裡了」的標記 —— 這才是 queued 出現的理由,它是去重需求逼出來的,不是憑空多一個欄位。

TC publish O(1) / recv O(1)。SC O(K) 值層 + O(K) 通知層 = O(K)。

slot.queued == true ⟺ key ∈ ready

可觀測性再補兩欄:count(這輪摺疊幾筆)與 seq(亂序保護)。count 讓 consumer 分辨「安靜」與「被摺爆」;seq 防遲到訊息蓋掉新值。

tierTCSC被什麼逼到下一階
0 無界佇列O(1)O(N) 事件數OOM
1 有界 ring drop-oldestO(1)O(C)丟棄粒度錯 → 公平性
2 per-key mapO(1)*O(K)consumer 不知誰髒了
3 map + dirty queue + queuedO(1)*O(K)—(終點)

* amortized,HashMap 攤還。若 key 空間是小的密集整數(fd、slot id),改成固定陣列 → 真 O(1) worst case + cache locality,SC 變 O(Kmax) 預配。

① 摺疊語意 stepper

看兩件事:slot 就地覆蓋、ready 靠 queued 去重

操作序列:pub(A,1,10) pub(B,1,70) pub(A,2,11) pub(A,3,12) recv() pub(B,2,71) recv() recv()

在按 next 之前先自己預測:第一個 recv() 會拿到 A 的哪一個值?那時候 count 會是多少?而 ready 裡會有幾個元素?

要帶走的兩個數字 1001 筆 update 進去,值層仍然只有 K 格,ready 仍然 ≤ K 個元素。吵鬧的 key 只能佔 ready 裡的一格 —— 這就是 per-key 隔離,tier 1 的 ring 做不到。

② lost update — 取值與清旗標必須原子

確定性可重現的 bug,不需要 race 運氣

錯誤實作

把 recv 拆成三次上鎖(看起來很無害,每次都有鎖):

// ✗ BUG:三個 phase 各自上鎖
fn recv_buggy(&self) -> Option<(u32, u64)> {
    let key = { let mut g = self.inner.lock().unwrap(); g.ready.pop_front()? };
    let val = { let g = self.inner.lock().unwrap(); g.slots[&key].val };
    //                          ↑ 鎖放掉了。producer 可以插在這裡。
    { let mut g = self.inner.lock().unwrap();
      g.slots.get_mut(&key).unwrap().queued = false; }
    Some((key, val))
}

逐格追一遍。第 4 格會問你一題,先答再看下一格。

為什麼「同一個 critical section」是正確性條件,不是風格

把 pop + 取值 + 清旗標合併後,producer 只可能落在 critical section 的外面,兩種情形窮舉:

producer 相對位置它看到的 queued它的動作200 有沒有被收到
在 recv 的鎖之前true只蓋值,不把 A 排進 ready✓ recv 讀到的就是 200
在 recv 的鎖之後false(已清)蓋值,並把 A 重新排進 ready✓ 下一輪 recv 拿到
一般化的規則 狀態變更必須 gate 在「確認取出成功」上。「我要來拿了」與「我拿走了」之間不能有可觀測的中間態 —— 有的話,別人就會根據那個中間態做出錯誤決定(這裡是 producer「決定不把 A 排進 ready」)。
測試上的陷阱 這個 bug 用多執行緒隨機跑抓不到——它要求 producer 精準落在兩次上鎖之間。要嘛把 phase 拆成可呼叫的函式做確定性重現(Code tab 的第 5 段就是這樣寫的),要嘛用 loom 窮舉交錯。跑一萬次 fuzz 不是驗證。

③ 通知順序 — 無鎖版本的兩個順序決定

publish 前後順序 + 清旗標與讀值的先後,兩個都會咬人

把 slot 換成原子操作

struct Slot { val: AtomicU64, dirty: AtomicBool }

沒有鎖了,於是「先做哪一步」變成語意的一部分。兩個獨立的順序問題:

#問題寫錯的後果
1producer:先蓋值還是先 set dirty?consumer 看到 dirty 卻讀到舊值,且 dirty 已被清 → 新值再也不通知
2consumer:先清 dirty 還是先讀值?與 tab ② 同型的 lost update

逐格追,第 3 格與第 6 格各有一題。

正確形狀

// producer
slot.val.store(v, Relaxed);
slot.dirty.store(true, Release);   // Release:把上面那個 store 推到這之前

// consumer
if slot.dirty.swap(false, Acquire) {  // 先清旗標
    let v = slot.val.load(Relaxed);   // 再讀值
    // 這之間 producer 若又寫入 → 它會看到 dirty==false → 重新 set dirty
    // → 我們下一輪再讀一次。多讀一次無害。
}
貫穿全篇的不對稱原則 通知可以多,不可以少。spurious wakeup 只是多跑一圈迴圈(對 conflation 而言是冪等的);lost wakeup 是資料永久遺失。所有順序決定都往「寧可多通知」那邊倒:先清旗標再讀值、值先可見再宣告髒、Drop 時先遞減再 notify 且 notify 時持鎖。
誠實邊界 這個無鎖版只處理單一 slot 的 val/dirty 配對。ready 佇列本身的無鎖化是另一個問題(且會帶回 ABA / reclamation),真要做通常是 per-consumer 分片或退回一把小鎖只保護 ready。面試被追問時把這個界線先講出來,不要等對方指。

// per-key conflation slot — std only
// 驗證用 edition 2021 / rustc 1.75(程式碼未用 edition-2024-only 特性)

use std::collections::{HashMap, VecDeque};
use std::sync::{Arc, Condvar, Mutex};

#[derive(Debug)]
struct Slot {
    val: u64,     // 最新快照值
    seq: u64,     // 該 key 已接受的最大 seq(亂序保護)
    count: u32,   // 自上次被取走後,被摺疊了幾筆
    queued: bool, // 是否已在 ready 裡(去重)
}

struct Inner {
    slots: HashMap<u32, Slot>,
    ready: VecDeque<u32>,
    closed: bool,
    stale: u64, // 被亂序丟棄的筆數(可觀測性)
}

pub struct Conflator {
    inner: Mutex<Inner>,
    cv: Condvar,
}

/// 契約:
/// - `val` 必須是「絕對狀態快照」,覆蓋才合法。delta 請改用 merge 版。
/// - 同一 key 的 `seq` 必須單調不遞減。seq 相等視為重送並照樣套用
///   (對快照 payload 是 idempotent);seq 較小則丟棄並計入 stale。
/// - key 基數必須有界,否則需外加 TTL / eviction(見 follow-up)。
impl Conflator {
    pub fn new() -> Self {
        Conflator {
            inner: Mutex::new(Inner {
                slots: HashMap::new(),
                ready: VecDeque::new(),
                closed: false,
                stale: 0,
            }),
            cv: Condvar::new(),
        }
    }

    /// producer。時間 O(1) amortized,空間增量 O(1)/新 key。
    pub fn publish(&self, key: u32, seq: u64, val: u64) {
        let mut g = self.inner.lock().unwrap();
        if g.closed {
            return;
        }
        let slot = g.slots.entry(key).or_insert(Slot {
            val,
            seq: 0,
            count: 0,
            queued: false,
        });
        if seq < slot.seq {
            g.stale += 1; // 亂序:舊的不許蓋掉新的
            return;
        }
        slot.val = val;
        slot.seq = seq;
        slot.count = slot.count.saturating_add(1);
        let need_enqueue = !slot.queued;
        if need_enqueue {
            slot.queued = true;
            g.ready.push_back(key);
        }
        // notify 在持鎖狀態下發出:避免 store+notify 之間的 lost wakeup 視窗
        if need_enqueue {
            self.cv.notify_one();
        }
    }

    /// consumer。回傳 (key, 最新值, 這輪摺疊掉幾筆)。
    /// 關鍵:pop_front + 清 queued + 取值,全部在同一個 critical section。
    pub fn recv(&self) -> Option<(u32, u64, u32)> {
        let mut g = self.inner.lock().unwrap();
        loop {
            if let Some(key) = g.ready.pop_front() {
                let slot = g.slots.get_mut(&key).expect("ready 中的 key 必有 slot");
                slot.queued = false;
                let count = std::mem::replace(&mut slot.count, 0);
                return Some((key, slot.val, count));
            }
            if g.closed {
                return None;
            }
            g = self.cv.wait(g).unwrap();
        }
    }

    pub fn close(&self) {
        let mut g = self.inner.lock().unwrap();
        g.closed = true;
        self.cv.notify_all(); // 持鎖 notify
        drop(g);
    }

    pub fn stale_count(&self) -> u64 {
        self.inner.lock().unwrap().stale
    }
}

// ===========================================================================
// BUG 版:取值與清 queued 拆成兩次上鎖。三個 phase 分開暴露,讓交錯可被確定性重現。
// ===========================================================================
pub struct BuggyConflator {
    inner: Mutex<Inner>,
}

impl BuggyConflator {
    pub fn new() -> Self {
        BuggyConflator {
            inner: Mutex::new(Inner {
                slots: HashMap::new(),
                ready: VecDeque::new(),
                closed: false,
                stale: 0,
            }),
        }
    }
    pub fn publish(&self, key: u32, val: u64) {
        let mut g = self.inner.lock().unwrap();
        let slot = g.slots.entry(key).or_insert(Slot {
            val,
            seq: 0,
            count: 0,
            queued: false,
        });
        slot.val = val;
        if !slot.queued {
            slot.queued = true;
            g.ready.push_back(key);
        }
    }
    // phase 1:出列
    pub fn p1_pop(&self) -> Option<u32> {
        self.inner.lock().unwrap().ready.pop_front()
    }
    // phase 2:讀值(鎖已放掉)
    pub fn p2_read(&self, key: u32) -> u64 {
        self.inner.lock().unwrap().slots[&key].val
    }
    // phase 3:清 flag(又一次上鎖)
    pub fn p3_clear(&self, key: u32) {
        self.inner.lock().unwrap().slots.get_mut(&key).unwrap().queued = false;
    }
    pub fn ready_len(&self) -> usize {
        self.inner.lock().unwrap().ready.len()
    }
    pub fn peek_val(&self, key: u32) -> u64 {
        self.inner.lock().unwrap().slots[&key].val
    }
}

fn main() {
    // ---- 1. 摺疊語意:3 筆 update 只出 1 筆,count 記錄摺疊次數 ----
    let c = Conflator::new();
    c.publish(7, 1, 100);
    c.publish(7, 2, 200);
    c.publish(7, 3, 300);
    assert_eq!(c.recv(), Some((7, 300, 3)), "只送最新值,並回報摺疊 3 筆");
    // ready 已空,count 已歸零
    c.publish(7, 4, 400);
    assert_eq!(c.recv(), Some((7, 400, 1)));

    // ---- 2. per-key 隔離:吵鬧的 key 不會擠掉安靜的 key ----
    let c = Conflator::new();
    c.publish(1, 1, 11); // 安靜 key
    for s in 1..=1000 {
        c.publish(2, s, s); // 吵鬧 key,1000 筆
    }
    assert_eq!(c.recv(), Some((1, 11, 1)), "安靜 key 仍然存活(FIFO 先出)");
    assert_eq!(c.recv(), Some((2, 1000, 1000)), "吵鬧 key 摺成 1 筆");
    // 記憶體上界 = key 基數 2,與 1001 筆 update 無關
    assert_eq!(c.inner.lock().unwrap().slots.len(), 2);

    // ---- 3. 亂序保護:seq 較小的不許覆蓋 ----
    let c = Conflator::new();
    c.publish(5, 10, 999);
    c.publish(5, 3, 111); // 遲到的舊訊息
    assert_eq!(c.recv(), Some((5, 999, 1)));
    assert_eq!(c.stale_count(), 1);

    // ---- 4. 多執行緒:assert 必須在 join 之後,否則 panic 會被吞掉 ----
    let c = Arc::new(Conflator::new());
    let p = {
        let c = Arc::clone(&c);
        std::thread::spawn(move || {
            for s in 1..=5000u64 {
                c.publish((s % 4) as u32, s, s);
            }
            c.close();
        })
    };
    let cc = Arc::clone(&c);
    let consumer = std::thread::spawn(move || {
        let mut last: HashMap<u32, u64> = HashMap::new();
        let mut got = 0u64;
        while let Some((k, v, n)) = cc.recv() {
            // 單調性:同一 key 收到的值必須嚴格遞增(摺疊不得回退)
            if let Some(&prev) = last.get(&k) {
                assert!(v > prev, "key {k} 回退 {prev} -> {v}");
            }
            last.insert(k, v);
            got += n as u64;
        }
        (last, got)
    });
    p.join().unwrap();
    let (last, got) = consumer.join().unwrap();
    // 每個 key 的最終值必須是它最後一筆 publish(最終狀態保證送達)
    for k in 0..4u32 {
        let expect = (1..=5000u64).filter(|s| (s % 4) as u32 == k).last().unwrap();
        assert_eq!(last[&k], expect, "key {k} 最終狀態未送達");
    }
    assert!(got <= 5000, "摺疊後總 count 不得超過 publish 數");

    // ---- 5. BUG 版:確定性重現 lost update ----
    let b = BuggyConflator::new();
    b.publish(9, 100);
    let key = b.p1_pop().unwrap(); // consumer phase 1
    let v = b.p2_read(key); // consumer phase 2:讀到 100
    b.publish(9, 200); // producer 插入!slot.queued 還是 true → 不入列
    b.p3_clear(key); // consumer phase 3:清掉 flag
    assert_eq!(v, 100);
    assert_eq!(b.peek_val(9), 200, "200 確實寫進 slot 了");
    assert_eq!(b.ready_len(), 0, "但 ready 是空的 → 沒人會來拿 200");
    // ↑ 200 永久遺失。修法:phase 1+2+3 合成同一個 critical section。

    println!("all conflation invariants ok");
}

面試 trade-off 三拍

① 報價:publish O(1) amortized / recv O(1);記憶體 O(K),K = 不同 key 數,與 update 速率無關。每格常數空間(val + seq + count + queued)。

② 沒選的兩條路:

方案軸為什麼不選
無界佇列記憶體SC O(事件數),背壓一來就 OOM
有界 ring drop-oldest公平性丟棄粒度是事件 → 吵鬧 key 擠掉安靜 key
取樣 / rate limit正確性可能漏掉最後一筆;conflation 保證最終狀態必達

③ 有效範圍:假設「payload 是絕對快照 + consumer 只要最新值 + key 基數有界」。任一條翻掉就要重寫 —— delta payload 要換可結合 merge,需要事件序列要換 durable log,key 無界要加 TTL/eviction。

延伸 / 未解

刻意留白的部分

可以直接動手的變體

  1. merge 版:把 slot.val = val 換成 slot.val = f(slot.val, val),payload 從快照放寬成半群。counter 用 +、latency 用 max、histogram 用桶相加。問題:f 需要單位元嗎?第一筆進來時 or_insert 該塞什麼?
  2. 密集 key 改陣列:key 是 fd / slot id 時,HashMap 換 Vec<Slot> + generation tag(你 e2 那個 fd_registry 的形狀)。問題:ready 裡的 stale key 遇到 slot 已被重用怎麼辦 —— 這正是 generation 存在的理由,兩道門都要驗。
  3. 公平性策略:ready 是 FIFO,對 key 公平。若要 priority(某些 key 必須先送)→ 換 heap,但 heap 裡的去重比 VecDeque 麻煩。問題:priority 反轉會不會餓死低優先 key?
  4. key eviction:TTL 掃描 vs LRU。問題:一個 key 被 evict 但它還在 ready 裡 → invariant 怎麼維持?(和 #2 是同一個洞的兩種外觀)
