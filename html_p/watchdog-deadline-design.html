Engine Watchdog — deadline 的住所 × 殭屍的生存證明

sim m(engine watchdog)全場 + 場後修帳沉澱 · 2026-08-02。姊妹頁:r2-sim-walkthroughs(m 分頁 code 走讀)、fanin-aggregator-bitmask(喚醒協定)、qa_timer_queue(timer 服務本體)。

題形

R1 的 DMA dispatcher,加一個新事實:engine 偶爾會 hang——拿了 block 然後永遠沉默。沒有 error 訊號、沒有 health API、沒有 reset 線。request 仍然必須完成。

定理(說出口就是 senior 訊號) 「慢」和「死」從軟體內部無法區分——這是所有 watchdog 的共同地基,跟分散式系統分不清「節點死了」和「網路斷了」是同一個不可能性。能給確定性的只有硬體幫忙(reset / fence / 撤走寫入權);平台不給,你就只能 bound risk,不能 eliminate。

所以 timeout 不是「偵測死亡」,是「下注」。賭注大小要對著誤判成本選:

timeout 選值的那句話(數字不重要,理由才是分) "A false alarm here doesn't just waste work — it re-executes a non-idempotent operation while the original may still land. So I'll take several times the normal block latency — say 3× — and lean conservative."

一個 block 的一生(六問句)

watchdog 題的 state 表和 code 檢查表是同一份——寫完六句問話,設計就完成了:

派工登記了嗎?→ done 銷帳了嗎?→ 鬧鐘響先查帳了嗎?→ 真超時三動作齊了嗎?→ 3-strikes 清帳了嗎?→ 殭屍丟掉了嗎?
問句對應 state漏掉的下場(2026-08-02 實測全中)
派工登記engine → (req, block) 綁定done 只帶 engine id,無綁定 = 全盲,第一個 done 就 panic
done 銷帳清綁定 + 清 deadline + engine 回池漏清 deadline → stale 鬧鐘(見 stepper 分頁)
鬧鐘查帳鬧鐘 vs 綁定對號重派已完成塊 = 親手踩 non-idempotent 地雷
真超時三動作隔離該台、strikes+1、換台重派掛新鐘漏隔離 → 下一塊又餵給死引擎
3-strikes 清帳submit_error + 清 waiting/map 殘票殘票後續派工 .unwrap() panic
殭屍丟掉對不上號的 done 不記帳雙記帳 → 提早謊報 request 完成
實錄傷疤(sim m 全場,65m,8+2 洞) clarify 花半場確認「block 不可重做」,實作卻在兩處主動重派:stale 鬧鐘不查帳、首超時直接 error(把「error after 3 timeouts on the same block」聽成「超時就 error」)。討論和 code 之間的斷線,才是 spec-heavy 題真正的失分點——設計時 state 表跳過,洞就不是「忘記寫」,是「沒有位置放」。

deadline 住哪裡 — 一個決定,下游全變

同一份需求(每個在飛 block 一顆鬧鐘),兩個家:全域鬧鐘堆,或 engine 的格子。這一步分岔之後,兩份實作幾乎沒有一行長得一樣。

兩個家的帳

全域堆 BinaryHeap<Reverse<Alarm>>同居 deadline[e] + owner[e]
鬧鐘是什麼派工資訊的副本,和真相(綁定表)分居兩地綁定的一個欄位,同一格
block 完成時真相更新了,堆裡的副本還躺著 → stale 鬧鐘誕生一次清兩個欄位 → stale 這個狀態無法表示
需要的對帳碼pop 出來先比 (req, pos, engine) ≈ 10 行,漏了就是毀損零——沒有副本就沒有漂移
找最近鬧鐘O(log n) peek,n 可以百萬O(N) 掃格,N=6 就是 6 個 load
回本條件timer 數量大(萬條連線各掛 timeout、tokio timer wheel)N 小且固定(本題:6 台 engine、每台至多一塊在飛)
裱框句 與其寫程式碼調解兩份狀態的漂移,不如選一個讓漂移無法表示的狀態設計。對帳碼不是「寫得夠不夠好」的問題——它的存在本身就是選錯家的稅單。
面試開場問法 "How many engines are we talking about — fixed at 6? Then I'll keep a deadline per engine next to its current job; a heap is the general answer but overkill here." 先問 N,再選形狀——這一問一答比任何一種實作都值錢。

同居版的核心(sol 形狀,簡化)

// 每台 engine 一格:現在跑什麼、幾點該回來。兩欄同生共死。
owner:    [Option<(ReqId, Block)>; 6],
deadline: [Option<u64>; 6],

fn fire_timeouts(&mut self, now: u64) {
    for e in 0..6 {
        if self.deadline[e].is_some_and(|d| d <= now) {
            let (rid, b) = self.owner[e].take().unwrap();  // 有錶必有 owner
            self.deadline[e] = None;
            // 注意:沒有 free.push_back(e) —— 隔離,不回池
            // strikes 記在 (rid, b) 上;<3 重派、==3 整單報廢+清帳
        }
    }
}
// 醒法也是設計:睡到最近的錶;.max(1) 防 deadline 貼線時 sleep(0) 空轉
fn next_sleep_ms(&self, now: u64) -> u64 {
    self.deadline.iter().flatten().min()
        .map_or(BLOCK_MS, |&dl| dl.saturating_sub(now).max(1))
}
堆版不是錯的 堆版是通用解——它多付的 stale 對帳稅,在 timer 數量大到掃不動時就回本了。真實 runtime(tokio)走的正是堆/timer-wheel 這條路。要帶走的不是「堆不好」,是兩個家都會蓋、並且知道什麼時候住哪間。

stale 鬧鐘 — 過期的錶會咬人

雙模式對照:堆版(鬧鐘與真相分居)vs 同居版。板面:E0/E1 是 engine 格(owner@deadline),heap 是全域鬧鐘堆(堆版才有)。壞模式第 4 幀有預測題,先答再 next。

帶走的一句 堆版要活命,pop 出來的第一件事永遠是查帳:「這顆鬧鐘指的 (engine, req, block) 還在飛嗎?」——對不上就丟,對上了才准動 state。同居版連這句都不用背,因為過期的錶無處存在。
實錄傷疤 ×2 ① 修帳中途版在鬧鐘 pop 時無條件 engine_doing[e].take()——stale 鬧鐘一響,把該台 engine 現在的(別塊的)綁定拿掉,新塊的 done 反被當殭屍丟、engine 永不歸隊,連鎖污染。查帳必須在任何 state 動作之前。② pub const TIMEOUT = ENGINE_COUNT * 3——拿「引擎台數」算毫秒,18ms 比自己拍板的 30ms 緊了快一半;const 抓錯鄰居是疲勞期的典型錯,寫完唸一次單位。

殭屍與冷宮 — 遲到的 done 怎麼收

被判超時的 engine 之後可能吐出當年欠的 done(zombie)。收錯一次,帳就謊了。

冷宮是免費的

engine 池用「done 才歸隊」的佇列寫法時,隔離的實作就是不 push back——超時判定成立那一刻清掉它的綁定、不把它放回 ready 佇列,一行都不用加。要加 quarantined: HashSet 也行,買到的是 debug assert 的清晰度,正確性不靠它。

殭屍 done 到達時的三種收法下場
assert!(owner[e].is_some())當場 panic——把「已預期的事件」寫成「不可能的事件」
無條件記帳 + engine 歸隊雙記帳(舊 done + 重派副本的 done 各算一次)→ 提早謊報 request 完成;死台復活繼續吃工作
查帳:對不上號 → 丟 done;engine 去留另議帳面永遠乾淨。丟完之後 engine 怎麼辦,是下一個問題 ↓

殭屍 = 生存證明(sol 的政策,比「冷宮到底」聰明一級)

sol 原文註解 // zombie:只當生存證明,隔離台復活;帳一根指頭不碰——遲到的 done 證明這台是慢不是死,而且它欠的帳已經吐完了。此刻讓它歸隊,不增加任何新風險,還把 1/6 的產能撿回來。
政策產能風險什麼時候選
冷宮到底(永不回鍋)每次誤判永久損失 1/6最低,state 最簡45 分鐘場的保守預設,先講出口再選
隔離至生存證明殭屍 done 即贖身同樣安全(帳不動,只還 engine)多一個 if 的成本,debrief 加分答案
觀察期後自動回鍋最高需要不存在的 health 訊號,探測=拿真 block 下注本題不選;真系統要配 reset 線才走

預測題:隔離中的 E1 吐出殭屍 done 的同一毫秒,它重派出去的副本也在 E2 完成了。兩個 done 都到,帳會怎樣?

3-strikes 與清帳義務

同一個 block 第 3 次超時 → 放棄整個 request:submit_dma_request_error(request_id)。這一步的另一半常被忘掉:

清帳清單(漏一項就是一顆延遲引爆的 panic) 進度表(map)移除 ✓ → waiting queue 裡的殘票(之後 pop 到要能安全跳過)✓ → 兄弟 block 還在別台飛,它們的 done 之後會到:查無此單 → 不記帳,但 engine 照樣歸隊 ✓。strikes 記在 (req, block) 上比隨票攜帶穩——票會丟,map 不會;成功路徑記得 remove,否則長跑系統無界慢漏(sol 的實刺,grep 驗證過)。

Ord 四件套 — BinaryHeap 收的入場費

堆版鬧鐘要 BinaryHeap<Reverse<Alarm>>,Alarm 就得付 Ord。四個 derive 是一條繼承鏈,不是四張貼紙。

繼承鏈,從弱到強

trait給你什麼關鍵語意
PartialEq== / !=允許「有值連自己都不等」的怪胎存在
Eq零方法,純標記承諾 x == x 恆真(HashMap key、Ord 都要這句話)
PartialOrdpartial_cmp → Option<Ordering>那個 Option 保留「這兩個值無法比較」
Ordcmp → Ordering,不准不回答全序。BinaryHeap/BTreeMap/sort() 排序時不接受「不知道」
為什麼拆四層?一個字:NaN IEEE 754 規定 NaN != NaN、NaN < 1.0 和 NaN >= 1.0 都是 false——所以 f64 只拿得到 Partial 家族。這就是 Vec<u64> 能直接 .sort() 而 Vec<f64> 要 sort_by 的原因。整數欄位的 struct 四件齊發無障礙。

derive 的規則:欄位宣告順序 = 字典序

// 心智模型 = tuple 比較:先比第一欄,Equal 才往下走
#[derive(PartialEq, Eq, PartialOrd, Ord)]
struct Alarm {
    deadline: u64,   // ⚠ 必須第一欄——堆序全靠它
    strikes:  u8,    // 之後的欄位只在 deadline 同刻時當平手決,無害
    req: u64, block: u32, pos: u64, eng: u32,
}
// BinaryHeap 是 max-heap → 要 Reverse 包成 min-heap

預測題:手滑把 strikes 宣告在第一欄。編譯器說什麼?執行期發生什麼?

手寫版鐵律:cmp 是唯一真相 只想按 deadline 比(或欄位裡混進沒有 Ord 的型別)就手寫——Ord::cmp 寫比較邏輯,partial_cmp = Some(self.cmp(other))、eq = self.cmp(other) == Equal 全部委派,impl Eq {} 空掛。四個 impl 各寫各的比較邏輯是經典事故;derive 一半手寫一半 clippy 會抓。代價:「相等」變成 deadline 相同——BinaryHeap 無害(不去重),丟進 BTreeSet 會把不同鬧鐘當重複合併。45 分鐘場首選仍是欄位排對 + 全 derive。
同場加映的鐵律 tuple 超過 3 欄就升級具名 struct。本場三個 bug(.0 的 deadline 當 request_id 上報、鬧鐘記到下一塊的 off-by-one、pos 重複加)全是「欄位沒有名字」的稅;改成 struct 之後,重派用 Alarm { deadline: now + TIMEOUT, eng: new_e, ..alarm },其餘欄位不可能抄錯。

句庫與判準

上場直接用的英文句 + 一頁判準 + 這場學費買到的三個聽力對策。

英文句庫

時機句子
開場問規模"How many engines — fixed at 6? Then per-engine deadlines next to each engine's current job; a heap is the general answer but overkill here."
timeout 選值"A false alarm re-executes a non-idempotent operation, so I'll lean conservative — several times the normal block latency, say 3×."
重派前必問"Before I re-dispatch: is re-executing a block safe if the original engine turns out to be alive? Is there any way to fence or reset it?"
不可分定理"I can't distinguish slow from dead from software; without a fencing mechanism I can only bound the risk, not eliminate it."
殭屍政策"A late done from a quarantined engine is proof of life — I discard the completion (my re-issued copy owns that block now) but I can safely return the engine to the pool."
scope 宣告(開場,不是中途)"Let me handle one request at a time first — the watchdog is the interesting part. Upgrading to pipelined requests is mechanical, and I'll do it if time allows."

失敗後路徑三問(固定 clarify 清單新條目)

clarify 別停在「怎麼偵測失敗」——事件驅動的問法到偵測就斷鏈。生命週期驅動要追完:①偵測到之後做什麼?(重派?給誰?安全嗎?)②重試幾次、誰決定?③放棄時通知誰、清哪些帳?與 lifecycle 三問(跑多久/怎麼停/在途算誰的)同族,一起背。

英文聽力三對策(spec 是用聽的,不是用讀的)

漏接型實錄對策
隱含補語蒸發"error after 3 timeouts" 聽成「超時就 error」——「前兩次要重派」靠推論,沒推read back:"So timeout 1 and 2 → redispatch, only the 3rd → error, correct?"
