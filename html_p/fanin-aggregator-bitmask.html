Per-core Fan-in — aggregator 的存在理由

sim k(per-core telemetry fan-in)對話沉澱 · 2026-08-01。姊妹頁:mesi-rmw-atomics(乒乓的機器層帳單)、conflation-slot-stepper(replace vs fold 的值層)、capacity-four-shapes(五行頭結帳)。

題形

N 顆 worker core 各自產 telemetry record,全部要送到一條 aggregator 執行緒,由它呼叫很慢的 write_out。鐵則:producer 絕不 block。

每核一條 SPSC = 每條 channel 恰好一個寫者一個讀者,「多執行緒爭搶」在設計層就被拆掉。

aggregator 到底是幹嘛的

直覺的誤解:「集中到一條執行緒,慢的 write_out 不就更塞了嗎?」——fan-in 的目的從來不是讓 log 變快,而是:

存在理由 把「慢」從工作核上搬走,集中到一條專用執行緒。worker core 的正職是它自己的工作;若每顆核自己呼叫 write_out,32 顆核就輪流卡在慢 I/O 上,還在 sink 上互相爭搶。集中之後,工作核只付一次 try_push(奈秒級)就脫身。
同一個形狀不准慢的那側慢活歸誰
sim j(ISR pipeline)ISR top-half(不能 alloc/block)bottom-half thread
sim k(本題)producer hook(絕不 block)aggregator
file_io_offloadevent loop(不准卡 I/O)offload worker
帶走的一句 掃描 N 條 channel 的頭只是幾十個 load——掃描從來不是瓶頸,sink 才是。sink 是瓶頸時怎麼辦,見下一分頁的丟/摺/批。

消化不完怎麼辦 — 丟/摺/批

「round-robin 一個一個掃,根本消化不完吧?」——這個擔心要用數字結案,不用直覺慌。

佇列吸突發,不造容量

比較兩側的持續速率(sizing 用五行頭,見 capacity-four-shapes 分頁②):

算式結果
供給(sink)1 ÷ 20 µs50k rec/s
需求 case 132 核 × 2,00064k rec/s → 1.28× 超載
需求 case 232 核 × 10,000320k rec/s → 6.4× 超載
結構性超載 需求 > 供給時,任何大小的 ring 都救不了——佇列的功用是吸收突發,不是創造容量。也沒有任何掃法救得了:瓶頸在 sink,不在掃描。出路只有三條。
實錄傷疤(2026-08-01 sizing 首答 ✗) 64k 和 50k 兩個數字都算對了,然後沒有比較它們,卷面寫著 "trivial, no alarm"。五行頭要擋的病原型:「數字一出就收筆」。兩個數字並排躺在 Chain 裡,比較那一步不准在腦中蒸發。

三條路:犧牲什麼,門檻是什麼

路做法犧牲門檻問題(spec 沉默就問)
丟 drop超量直接扔 + dropped 計數真相變抽樣(1.28×→丟 22%;6.4×→丟 84%=擺爛)遙測丟失可接受嗎?完整性有 SLO 嗎?(產品要求)
摺 foldM 筆合成 1 筆再過瓶頸:per-core 累計槽,producer fetch_add、aggregator 週期 swap(0) 收割失去單筆身分(seq、個別內容)下游要每筆原文,還是統計量就夠?(資料語意)
批 batch攢 K 筆一次寫,攤薄 per-call 固定成本延遲(等湊批)+ 記憶體那 20 µs 是 per-call 開銷還是每筆內在成本?有批次 API 嗎?(sink 性質)
批的天花板要算出來 批 K 筆成本 = 15 + 5K µs → 每筆 (15+5K)/K,K→∞ 收斂到 5 µs → 容量上限 200k rec/s。case 1(64k):K=2 就回到水面,3.1× 餘裕。case 2(320k):無限批仍超載 1.6×,這扇門單獨開不夠 → 逼你去問摺的門。
選擇律(一句話) 成本是 per-call 就批;下游只要摘要就摺;兩者都不成立而遙測可犧牲才丟——丟必計數。裁決權不在你手上,在三個門檻問題的答案上。沒得問就具名假設:"Assuming log semantics must survive, I'd batch."

摺的收割:為什麼必須 swap(0)

// producer 側(該核,每筆):
slot.fetch_add(v, Relaxed);
// aggregator 收割,兩種寫法:
let total = slot.swap(0, ...);          // A:一發 RMW
let total = slot.load(...); slot.store(0, ...);  // B:兩步分開

預測題:寫法 B 會在哪個交錯下丟量?先在腦中排出 dry-run 再點。

Dry-run slot=5 → A:load=5 → P:fetch_add(3)→8 → A:store(0) → 那 3 蒸發。atomic 單發操作沒有「寫一半」;病在 aggregator 自己把「讀」和「歸零」拆成兩發,中間開了縫。swap(0) 把讀+歸零焊回一發。定律:check-then-act 拆兩步就是 race。

喚醒協定 — 一條 flag 背兩件事的那天

Waker 是 sticky flag:先 wake 後 sleep 不丟、多次 wake 合併成一次、可能 spurious。stepper 前半走正常流,後半重演 2026-08-01 drill review 抓到的真洞。

對稱律

側順序破了會怎樣
producer先值後訊號:push → wake先 wake:A 醒、掃空、睡回,record 躺到下次 wake
consumer先銷訊號後取值:消費 flag → 掃訊號永遠不准指向還沒被處理的值
shutdown先 flag 後 wake;零收穫 → 查 stop → 才准睡順序反了 → 見 stepper 第 7 幀起

Stepper:正常流 → 睡死交錯 → 修法

板面:P=producer、ch=channel 內容、flag=sticky flag、A=aggregator、stop。第 9 幀有預測題,先答再 next。

帶走的一句 sticky flag 是合併的——一個 flag 可能代表兩個事件,而你只睡得掉一次。所以「查 stop」必須發生在每一次零收穫與 sleep 之間;mock 的 1 秒 safety timeout 只是把吊死降級成卡秒,保險絲擋住的 bug 還是 bug。

bitmask ready-set — 土製 epoll 的回本線

「用一個 word 標記哪些核有資料,醒來只掃亮著的」——這招用得了嗎?兩個帳:物理帳(乒乓)和協定帳(清 bit 順序)。

物理帳:邏輯上無等待,物理上同一條 line

mask.fetch_or(1 << core, Release) 是單發 RMW——不用 CAS loop、永遠一次成功,沒有「等待」意義上的爭搶。但所有核打的是同一條 cache line:每次 fetch_or 都要把 line 搶成 Exclusive/Modified,line 在核間乒乓(RFO 帳單見 mesi-rmw-atomics)。想拆乒乓就 per-core flag 各佔一條 padded line——但那等於回頭掃 N 個 flag,跟掃 N 條 channel 頭沒差多少,優化蒸發。

每次醒來的讀成本寫側成本划算條件
全掃 N 條 channelO(N) 個 load(N=核數時是幾十個)零額外N 小(本題:N=32)
bitmask ready-setO(活躍數)每筆一次共享 line RFO + 清 bit 協定N ≫ 同時活躍數才回本
你早就認識這個結構 select/poll = 每次醒來全掃 N 個 fd;epoll = kernel 幫你維護 ready list。bitmask ready-set 就是土製 epoll。fd 幾千、活躍幾十 → ready list 大賺;N=核數、掃描本來就便宜 → 純虧。面試把回本線講出來,比直接用或直接棄都值錢。

協定帳:清 bit 的順序(Stepper 雙模式)

consumer 醒來處理某核:先清 bit 再 drain,還是先 drain 再清 bit?切模式對照走。壞模式第 4 幀有預測題。

帶走的一句 先清再 drain 的最壞情況只是偶爾一次空掃;先 drain 再清的最壞情況是一筆 record 睡死。錯要錯在便宜的那邊——這句就是 trade-off 收尾句。跟協定分頁的對稱律同族:consumer 先銷訊號、後取值。

句庫與判準

上場直接用的英文句 + 一頁判準。

英文句庫

時機句子
問公平性(budget)"If one core is much hotter than the others, should I drain its channel completely before moving on, or cap how many records I take from a single channel per round so the cold cores don't starve?"
問 lifecycle(必問)"How long does this loop run — how do we stop it, and who owns the records still in flight when we do?"
超載三路開場"The right fix depends on three things I'd ask: is the cost per-call or per-record — if per-call, I batch. Does downstream need every record or just aggregates — if aggregates, I fold. If neither, I drop and count, and we agree that's acceptable."
換 conflation slot"That changes the loss model: with a ring, loss is accidental and I count it; with a conflation slot, loss is by design."
摺的 Verdict 範本"Fold unconditionally: per-core rate/error-count slots harvested once a second — 320k records/s collapses to 32 harvests/s. Forward a 1% sample to the debug trace, drop the rest by design, counted."

判準速查

問題判準
conflation 丟不丟資料?不是原語屬性,是操作屬性:update 是 replace 就有損,是 merge/fold 就無損(加法吸收歷史)。
ring 還是 conflation slot?問資料語意:每筆都要(log)→ ring+dropped(丟失顯式可審計);只要最新(儀表)→ slot(丟失 by design)。架構不動,換 per-core 那格就好——fan-in + wakeup 是架構,per-core 格是 policy 插槽。
bitmask ready-set?回本線 = N ≫ 同時活躍數。本題 N=核數 → 不回本;當 trade-off 講,別當 Phase 1 實作。
shutdown?先 flag 後 wake;每次零收穫先查 stop 才准睡;stop 後 drain 每條 channel 才准退。
喚醒順序?producer 先值後訊號;consumer 先銷訊號後取值。訊號永遠不指向未處理的值。
