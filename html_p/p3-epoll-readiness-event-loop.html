epoll readiness 模型 × std-only event loop

LT vs ET · 從零搭單執行緒 network event loop（Rust, std + libc FFI）· 為什麼 file IO 是另一回事

這份教材要打通的兩個核心

epoll 是 Linux 的 readiness notifier:你把一堆 fd 丟進去,它在某個 fd「可以不阻塞地做 IO」時通知你。整份教材圍繞兩件事,兩件都是面試高頻踩雷點:

① readiness 模型:LT vs ET kernel 說「ready」跟你「做了多少 IO」之間會錯位。ET 只在邊緣通知一次,沒 drain 乾淨就事件餓死。 → 看並排模擬
② file IO 是另一種模型 epoll 對 regular file 沒用(永遠 report ready,epoll_ctl 直接 EPERM)。readiness ≠ completion。 → 看誠實區別
面試開場的第一個 clarify(高信號)

題目說「std-only,不得用外部 crate」。libc 算不算 external library? 這決定了你能不能做 epoll,務必先問清楚:

  • 若允許連系統 libc(多數 systems 面試的意思):Rust 程式本來就 link glibc,你用 extern "C" 宣告 epoll_* 符號即可,不需要任何 crate。這條路可行,本教材走的就是它。
  • 若「純 std、連 FFI 都不行」:std 沒有 epoll binding —— 你做不出 epoll。此時誠實回退到 thread-per-connection 阻塞模型,或跟面試官確認範圍。能主動講出這個邊界本身就是加分。

std 給了你一半

socket 這半,std 幾乎湊齊了:

  • TcpListener / TcpStream 建立與收發;
  • .set_nonblocking(true) —— ET 的前提,沒它 drain loop 會阻塞整個 event loop;
  • std::os::fd::AsRawFd 拿 raw fd 註冊進 epoll;OwnedFd 幫你在 drop 時關 fd。

缺的那半只有 epoll 本身(create / ctl / wait)和 eventfd / timerfd —— 這幾個用 libc FFI 補。所以 socket event loop = 「std::net 拿 fd + libc FFI 做 epoll」。

本教材的代碼都是真的編過的 verified 骨架與所有片段在 x86_64 Linux, rustc 1.91.1, edition 2024 上編譯零 warning,並跑過 5 項功能測試(見骨架分頁)。sizeof(struct epoll_event)==12、以及 regular file 進 epoll 會回 EPERM,都是本機實測而非憑記憶。

版本誠實說明:CoderPad 跑的是 1.92.0,我這邊能取得的最新是 1.91.1(官方 dist 站台在此環境被擋,只能用套件庫版本)。unverified 1.92 沒實測 —— 但本教材只用到 edition 2024 + std + FFI,沒有任何 1.92 專屬特性,edition 才是真正影響語法的變數,而 edition 2024 是完整驗證過的。

那 thread::park 呢?能不能不用 epoll?

park / unpark 解的是另一個問題:「把這條 thread 睡著,直到別的 thread 叫醒它」。它是你手刻 block_on executor 時、future 回 Pending 就 park、Waker 觸發就 unpark 的那個機制 —— 屬於排程層。

park 看不到 fd 的就緒狀態。socket 何時可讀只有 kernel 知道(epoll / select / poll / io_uring)。你沒法「park 等一個 socket 變可讀」,因為在正確的時機沒有東西會 unpark 你。所以 std-only 又不准 FFI 時,唯一能得知 readiness 的辦法是:每條連線開一條 thread 做 blocking read(讀到資料再 unpark 主 thread)—— 這其實就是 thread-per-connection / offload,能用,但不是 epoll 那種單執行緒多工幾千個 fd。

一句話:park = executor 的睡/醒;epoll = IO 的就緒通知。真實 runtime 兩者疊在一起(mio 用 epoll 做 readiness、executor 用 park 做排程)。少了 epoll 那半,network IO 就退回 blocking threads。

從 naive 心智模型推到 LT/ET 的失敗

先定義:「drain 到 EAGAIN」是什麼 在 nonblocking socket 上,反覆呼叫 read(),直到它回傳 EAGAIN / EWOULDBLOCK 這個錯誤為止。這個錯誤的意思是「kernel recv buffer 此刻已經空了」。所以「drain 到 EAGAIN」= 一口氣把接收緩衝區讀乾,拿 EAGAIN 當停止信號。(blocking socket 做不到:讀空時那次 read() 會就地卡住,而不是回 EAGAIN —— 這也是為何 ET 必須配 nonblocking。)
① naive 心智模型 「epoll_wait 告訴我 socket 可讀 → 我 read() 一次、處理、回去等下一次。」

直覺上一次通知配一次讀,對稱又乾淨。問題是這個直覺只在 LT 成立,而且 LT 自己也有另一個坑。

② 失敗模式 A —— ET 下的「事件餓死」

ET(edge-triggered)只在 fd 狀態發生變化的那一瞬間通知你一次。假設三個封包 P1 P2 P3 連續到達,你只 read() 一次拿走 P1 就返回:

  • recv buffer 還躺著 P2、P3;
  • 但「有資料可讀」這件事沒有再變化 —— 沒有新的邊緣;
  • 下一次 epoll_wait 對這個 fd 什麼都不回報;
  • P2、P3 就此卡死,除非碰巧有全新資料到達製造下一個邊緣。

這就是 ET 的核心陷阱。在 stepper 裡一步步看它發生 →

② 失敗模式 B —— naive LT 的「空轉風暴」

LT 很寬容,但反過來會咬你:只要條件成立就每次都回報。兩個典型災難:

  • 沒讀完就一直被叫醒:consumer 慢時,每輪 epoll_wait 都回報同一個 fd 可讀 → CPU 空轉、syscall 爆量。
  • EPOLLOUT 常駐 = writable storm:socket 幾乎永遠可寫,若你把 EPOLLOUT 一直掛著,每輪 wait 都被喚醒寫 → 100% CPU。這是新手最常見的 100% CPU bug。
③ 修法
  • ET:每次事件都 drain 到 EAGAIN。loop read() 直到回 EWOULDBLOCK,把 buffer 讀乾。前提是 fd 必須 nonblocking —— 否則最後那次「其實沒資料」的 read 會阻塞整個 event loop(為何 nonblocking 是 ET 前提,細節在進階機制 →)。
  • EPOLLOUT 要按需開關(LT/ET 皆然):只有當你「有殘量寫不出去(write 回 EAGAIN)」時才 MOD 掛上 EPOLLOUT;寫完立刻 MOD 取消。這就是背壓(backpressure)。

把狀態變數先立起來(之後 stepper 與骨架都用這幾個)

  • recv buffer —— kernel 端每個 socket 的接收佇列。LT 看它「非空 = 可讀」;ET 只看它的「變化」。
  • edge pending(僅 ET 概念)—— 是否有一個「尚未被消費的邊緣通知」。被通知後若沒新資料到達,它就失效。
  • out_buf: Vec<u8> —— 每條連線「已收下、但 socket 暫時寫不出去」的殘量。背壓的存放處。
  • out_armed: bool —— 這個 fd 目前有沒有掛 EPOLLOUT。控制上面「按需開關」。

stepper 用前兩個把 LT/ET 的錯位演出來;骨架的 Conn 結構用後兩個實作背壓。變數不會憑空冒出來,都是這裡定義的。

packed struct:x86_64 上的 FFI 陷阱 verified

x86_64 的 glibc/kernel 把 struct epoll_event 宣告成 __attribute__((packed)):{ u32 events; u64 data; } 是 12 bytes 而非 16(自然對齊會在 events 後補 4 bytes padding)。實測 sizeof(struct epoll_event)==12。若你在 Rust 用非 packed 的 #[repr(C)],data 欄位 offset 會從 kernel 期望的 4 變成 8 → 記憶體錯位、資料損毀。所以下面 gate 在 target_arch:x86_64 用 #[repr(C, packed)],其他架構自然對齊。

packed 的連帶規矩:不能對 packed 欄位取參考(&ev.events 是 UB / 編譯錯誤,連 println!("{}", ev.events) 都會踩到,因為格式化會隱式借用)。對策:先把整個 struct 或欄位複製成 local 再用(let ev = events[i]; 然後 ev.events)。骨架裡就是這樣做的。

// ---------- libc FFI: the minimal epoll signatures ----------
// EDITION 2024: `extern` blocks must be written `unsafe extern`. Plain
// `extern "C" { ... }` is a hard error: "extern blocks must be unsafe".
//
// x86_64 glibc/kernel declare `struct epoll_event` with __attribute__((packed)):
//   { uint32_t events; uint64_t data; }  => 12 bytes, NOT 16.
// On non-x86_64 the ABI struct is naturally aligned; gate on target_arch for a
// real cross-arch impl.
#[cfg(target_arch = "x86_64")]
#[repr(C, packed)]
#[derive(Clone, Copy)]
struct EpollEvent {
    events: u32,
    data: u64,
}
#[cfg(not(target_arch = "x86_64"))]
#[repr(C)]
#[derive(Clone, Copy)]
struct EpollEvent {
    events: u32,
    data: u64,
}

unsafe extern "C" {
    fn epoll_create1(flags: i32) -> i32;
    fn epoll_ctl(epfd: i32, op: i32, fd: i32, event: *mut EpollEvent) -> i32;
    fn epoll_wait(epfd: i32, events: *mut EpollEvent, maxevents: i32, timeout: i32) -> i32;
}

const EPOLL_CLOEXEC: i32 = 0x8_0000; // == O_CLOEXEC (octal 02000000)
const EPOLL_CTL_ADD: i32 = 1;
const EPOLL_CTL_DEL: i32 = 2;
const EPOLL_CTL_MOD: i32 = 3;

const EPOLLIN: u32 = 0x001;
const EPOLLOUT: u32 = 0x004;
const EPOLLERR: u32 = 0x008;
const EPOLLHUP: u32 = 0x010;

#[allow(dead_code)]

#[allow(dead_code)]

片段 C — epoll 薄封裝(OwnedFd 負責 drop 時關 fd,所以連 close FFI 都省了)
// ---------- thin safe-ish wrapper over the epoll fd ----------
struct Epoll {
    fd: OwnedFd, // OwnedFd::drop closes it — no manual close() FFI needed
}

impl Epoll {
    fn new() -> io::Result<Self> {
        let raw = unsafe { epoll_create1(EPOLL_CLOEXEC) };
        if raw < 0 {
            return Err(io::Error::last_os_error());
        }
        // SAFETY: epoll_create1 handed us a fresh, exclusively-owned fd.
        let fd = unsafe { OwnedFd::from_raw_fd(raw) };
        Ok(Epoll { fd })
    }

    fn ctl(&self, op: i32, fd: RawFd, interest: u32) -> io::Result<()> {
        let mut ev = EpollEvent { events: interest, data: fd as u64 };
        let rc = unsafe { epoll_ctl(self.fd.as_raw_fd(), op, fd, &mut ev) };
        if rc < 0 {
            return Err(io::Error::last_os_error());
        }
        Ok(())
    }

    fn add(&self, fd: RawFd, interest: u32) -> io::Result<()> {
        self.ctl(EPOLL_CTL_ADD, fd, interest)
    }
    fn modify(&self, fd: RawFd, interest: u32) -> io::Result<()> {
        self.ctl(EPOLL_CTL_MOD, fd, interest)
    }
    fn delete(&self, fd: RawFd) -> io::Result<()> {
        // Modern kernels accept a NULL event for DEL.
        let rc =
            unsafe { epoll_ctl(self.fd.as_raw_fd(), EPOLL_CTL_DEL, fd, std::ptr::null_mut()) };
        if rc < 0 {
            return Err(io::Error::last_os_error());
        }
        Ok(())
    }

    fn wait(&self, events: &mut [EpollEvent], timeout_ms: i32) -> io::Result<usize> {
        let n = unsafe {
            epoll_wait(
                self.fd.as_raw_fd(),
                events.as_mut_ptr(),
                events.len() as i32,
                timeout_ms,
            )
        };
        if n < 0 {
            return Err(io::Error::last_os_error());
        }
        Ok(n as usize)
    }
}
片段 D — Conn(背壓狀態)+ 主迴圈:wait → dispatch → 依 bitmask 分派
// ---------- per-connection state (backpressure + half-close live here) ----------
struct Conn {
    stream: TcpStream,
    out_buf: Vec<u8>,  // bytes accepted from peer but not yet writable to the socket
    out_armed: bool,   // is EPOLLOUT currently registered for this fd?
    read_closed: bool, // peer sent FIN: nothing more will arrive, but we may still owe bytes
}

fn main() -> io::Result<()> {
    let listener = TcpListener::bind("127.0.0.1:9000")?;
    run_event_loop(listener)
}

fn run_event_loop(listener: TcpListener) -> io::Result<()> {
    listener.set_nonblocking(true)?;
    let listener_fd = listener.as_raw_fd();

    let epoll = Epoll::new()?;
    // Edge-triggered listener => MUST drain accept() to EAGAIN.
    epoll.add(listener_fd, EPOLLIN | EPOLLET)?;

    let mut conns: HashMap<RawFd, Conn> = HashMap::new();
    let mut events = vec![EpollEvent { events: 0, data: 0 }; 1024];

    loop {
        let n = match epoll.wait(&mut events, -1) {
            Ok(n) => n,
            Err(e) if e.kind() == ErrorKind::Interrupted => continue, // EINTR: just retry
            Err(e) => return Err(e),
        };

        for i in 0..n {
            let ev = events[i];    // copy the packed struct out by value first
            let ready = ev.events; // reading Copy fields off the copy is packed-safe
            let fd = ev.data as RawFd;

            if fd == listener_fd {
                accept_all(&listener, &epoll, &mut conns)?;
                continue;
            }

            // EPOLLERR = socket error; EPOLLHUP = BOTH directions gone. Either way: drop it.
            // (A peer that only half-closes shows up as EPOLLIN + read()==0, not EPOLLHUP.)
            if ready & (EPOLLERR | EPOLLHUP) != 0 {
                close_conn(&epoll, &mut conns, fd);
                continue;
            }
            if ready & EPOLLIN != 0 && handle_readable(&epoll, &mut conns, fd)? {
                continue; // connection finished inside the handler
            }
            if ready & EPOLLOUT != 0 {
                handle_writable(&epoll, &mut conns, fd)?;
            }
        }
    }
}
片段 E — accept loop 到 EAGAIN(ET listener 必 drain,否則漏 backlog)
/// ET listener: accept until EAGAIN, else you can miss backlog'd connections.
fn accept_all(
    listener: &TcpListener,
    epoll: &Epoll,
    conns: &mut HashMap<RawFd, Conn>,
) -> io::Result<()> {
    loop {
        match listener.accept() {
            Ok((stream, _addr)) => {
                stream.set_nonblocking(true)?; // accepted sockets are NOT auto-nonblocking
                let fd = stream.as_raw_fd();
                epoll.add(fd, EPOLLIN | EPOLLET)?;
                conns.insert(
                    fd,
                    Conn { stream, out_buf: Vec::new(), out_armed: false, read_closed: false },
                );
            }
            Err(e) if e.kind() == ErrorKind::WouldBlock => break, // backlog drained
            Err(e) if e.kind() == ErrorKind::Interrupted => continue,
            Err(e) => return Err(e),
        }
    }
    Ok(())
}
read()==0 ≠ 「馬上關」:我自己踩到的 bug verified

這份骨架的第一版真的寫錯了,而且在舊 toolchain 上矇混過關,換 1.91 跑才炸出來 —— 值得完整講一次,因為這正是 dry-run 該抓到的東西。

錯的寫法:handle_readable 的 drain loop 讀到 Ok(0)(FIN)就 close_conn 直接關。

為什麼錯:drain loop 的離開有兩個出口 —— EAGAIN(讀乾了)和 Ok(0)(對端關了寫端)。如果 client 把資料連同 FIN 一起送到,drain loop 會一路讀到 Ok(0) 才停,從頭到尾沒經過 try_flush。此時 out_buf 裡是滿的 echo 資料,你一關 → 全部靜默丟失。實測:2 MB payload 回來 0 bytes。

為什麼舊版沒抓到:這是 race。舊測試讓 client 併發讀,out_buf 幾乎總是即時排空,EOF 到達時剛好沒殘量 → 綠燈。測試通過 ≠ 沒有 bug,只是那天運氣好。

修法:Ok(0) 只代表對端不會再送了(half-close),不代表你不欠它。所以加一個 read_closed: bool,EOF 時只標記;真正的關閉條件交給 try_flush:out_buf 排空 且 read_closed 才關。

這是他們 prep doc 第 5 條「Dry-Run Before You Run」的實體版:離開迴圈有幾個出口?每個出口的後續處理都對嗎? —— 一個 loop 兩個 exit,只想到一個,就是這種 bug。

片段 F — 每條連線 read 到 EAGAIN;Ok(0)=EOF、WouldBlock=drain 完、Interrupted=重試
/// ET socket: read until EAGAIN.
///
/// Ok(0) means the peer sent FIN — it will send nothing more. That is NOT the same
/// as "close now": we may still owe it bytes sitting in out_buf. Closing here would
/// silently drop them. Mark read_closed and let try_flush decide when it is safe.
/// Returns Ok(true) if the connection is gone.
fn handle_readable(epoll: &Epoll, conns: &mut HashMap<RawFd, Conn>, fd: RawFd) -> io::Result<bool> {
    let mut buf = [0u8; 4096];
    let mut eof = false;
    let mut hard_err = false;
    loop {
        let res = match conns.get_mut(&fd) {
            Some(c) => c.stream.read(&mut buf),
            None => return Ok(true),
        };
        match res {
            Ok(0) => {
                eof = true; // FIN — peer half-closed its write side
                break;
            }
            Ok(nread) => {
                if let Some(c) = conns.get_mut(&fd) {
                    c.out_buf.extend_from_slice(&buf[..nread]); // echo: queue it back
                }
            }
            Err(e) if e.kind() == ErrorKind::WouldBlock => break, // recv buffer drained
            Err(e) if e.kind() == ErrorKind::Interrupted => continue, // EINTR: retry read
            Err(_) => {
                hard_err = true;
                break;
            }
        }
    }
    if hard_err {
        close_conn(epoll, conns, fd);
        return Ok(true);
    }
    if eof && let Some(c) = conns.get_mut(&fd) {
        c.read_closed = true;
    }
    try_flush(epoll, conns, fd) // closes iff read_closed AND nothing left to write
}
片段 G — write 塞住時緩存殘量 + 掛 EPOLLOUT;寫完取消。DEL 必須在 close 之前
/// EPOLLOUT fired => socket became writable again; push more of out_buf.
fn handle_writable(epoll: &Epoll, conns: &mut HashMap<RawFd, Conn>, fd: RawFd) -> io::Result<()> {
    try_flush(epoll, conns, fd)?;
    Ok(())
}

/// Write out_buf until EAGAIN. Arm EPOLLOUT iff bytes remain; disarm when empty.
/// Returns Ok(true) if the connection was closed (everything flushed AND peer done).
fn try_flush(epoll: &Epoll, conns: &mut HashMap<RawFd, Conn>, fd: RawFd) -> io::Result<bool> {
    let mut hard_err = false;
    let mut finished = false;
    let mut new_interest: Option<u32> = None;
    {
        let conn = match conns.get_mut(&fd) {
            Some(c) => c,
            None => return Ok(true),
        };
        let mut written = 0usize;
        while written < conn.out_buf.len() {
            match conn.stream.write(&conn.out_buf[written..]) {
                Ok(0) => break,
                Ok(n) => written += n,
                Err(e) if e.kind() == ErrorKind::WouldBlock => break, // kernel send buffer full
                Err(e) if e.kind() == ErrorKind::Interrupted => continue,
                Err(_) => {
                    hard_err = true;
                    break;
                }
            }
        }
        conn.out_buf.drain(..written); // drop the flushed prefix

        if conn.out_buf.is_empty() {
            if conn.read_closed {
                finished = true; // owe nothing + peer done => NOW it is safe to close
            } else if conn.out_armed {
                conn.out_armed = false;
                new_interest = Some(EPOLLIN | EPOLLET); // nothing pending: stop asking for writable
            }
        } else if !conn.out_armed {
            conn.out_armed = true;
            // backpressure: ask to be told when writable again.
            new_interest = Some(if conn.read_closed {
                EPOLLOUT | EPOLLET // peer is done talking; only the drain-out matters now
            } else {
                EPOLLIN | EPOLLOUT | EPOLLET
            });
        }
    }
    if hard_err || finished {
        close_conn(epoll, conns, fd);
        return Ok(true);
    }
    if let Some(i) = new_interest {
        epoll.modify(fd, i)?;
    }
    Ok(false)
}

fn close_conn(epoll: &Epoll, conns: &mut HashMap<RawFd, Conn>, fd: RawFd) {
    let _ = epoll.delete(fd); // DEL before the fd is closed (dropping the stream closes it)
    conns.remove(&fd);        // Drop<TcpStream> closes the fd
}

進階機制

nonblocking 為什麼是 ET 的前提

ET 要求你 drain 到 EAGAIN —— loop read() 直到回 EWOULDBLOCK 才停。這個 loop 的終止條件就是「read 回 EAGAIN」。若 fd 是 blocking 的,當 buffer 讀空時,那次 read() 不會回 EAGAIN,而是就地阻塞 —— 你的單執行緒 event loop 整個卡死,其他所有 fd 一起陪葬。所以 set_nonblocking(true) 不是優化,是 ET 的正確性前提。(LT 因為容許「一次一讀」,勉強能用 blocking,但一旦你也想 drain 就同樣需要 nonblocking。)

EPOLLONESHOT:多執行緒共用一個 epfd 時防重入

場景:一個 thread pool,多條 worker 都對同一個 epfd 呼叫 epoll_wait。連線 X 來了新資料 → 若沒保護,thread A 正在處理 X 的 handler,thread B 又被喚醒去處理 X 的新事件 → 兩條 thread 同時碰同一個 fd 的狀態,data race、亂序。

EPOLLONESHOT 的語意:某 fd 的事件被投遞一次後,該 fd 自動停用,不再產生任何事件,直到你用 epoll_ctl(MOD) 重新 arm。於是每個 fd 同一時間只會有一條 thread 在處理 → per-fd 串行化。處理完再 re-arm。

對照 EPOLLEXCLUSIVE(不同機制):解的是「多 waiter 等同一個 listener,一個連線來了驚群喚醒全部」,讓 kernel 只喚醒其中一個。ONESHOT 管 per-fd 串行,EXCLUSIVE 管 accept 驚群 —— 別搞混。

eventfd self-wake:loop 睡在別的 thread,怎麼叫醒它

event loop 阻塞在 epoll_wait(-1)。另一條 thread 想注入工作(「連線 X 該寫了」「該關機了」「某 blocking 任務完成了」)。它既不能安全亂碰 loop 的資料結構,而且 loop 正在睡。解法是經典 self-pipe trick 的現代版:把一個 eventfd 註冊進 epoll。別的 thread 把工作丟進一個(mutex 保護的)佇列,然後寫 8 bytes 到 eventfd → epoll_wait 立刻醒 → loop 把 eventfd 讀乾(ET → drain)、處理佇列。

片段 H — eventfd self-wake(注意:ET 的 waker 也要 drain 到 EAGAIN)
// ---- eventfd self-wake ----
use std::ffi::c_void;

unsafe extern "C" {
    fn eventfd(initval: u32, flags: i32) -> i32;
    fn read(fd: i32, buf: *mut c_void, count: usize) -> isize;
    fn write(fd: i32, buf: *const c_void, count: usize) -> isize;
}
const EFD_CLOEXEC: i32 = 0x8_0000;
const EFD_NONBLOCK: i32 = 0x800; // == O_NONBLOCK (octal 04000)

#[allow(dead_code)]
fn make_waker() -> io::Result<OwnedFd> {
    let raw = unsafe { eventfd(0, EFD_CLOEXEC | EFD_NONBLOCK) };
    if raw < 0 {
        return Err(io::Error::last_os_error());
    }
    // SAFETY: fresh owned fd.
    Ok(unsafe { OwnedFd::from_raw_fd(raw) })
}

/// Called from ANOTHER thread after it pushes work onto a shared queue.
#[allow(dead_code)]
fn wake(wake_fd: RawFd) -> io::Result<()> {
    let one: u64 = 1;
    let rc = unsafe { write(wake_fd, &one as *const u64 as *const c_void, 8) };
    if rc < 0 {
        return Err(io::Error::last_os_error());
    }
    Ok(())
}

/// The loop drains the eventfd when it becomes readable (ET => read to EAGAIN).
#[allow(dead_code)]
fn drain_waker(wake_fd: RawFd) {
    let mut sink: u64 = 0;
    loop {
        let rc = unsafe { read(wake_fd, &mut sink as *mut u64 as *mut c_void, 8) };
        if rc < 0 {
            break; // EAGAIN once fully drained (nonblocking)
        }
    }
}

路 A — timerfd 掛進 epoll:建一個 timerfd,設到期時間,以 EPOLLIN 註冊。到期時 fd 變可讀,epoll_wait 回報它,你 read 出「到期次數」(u64)再跑 callback。優點:一切皆 fd,epoll_wait 可以無限期阻塞(timeout=-1),模型統一。

片段 J(路 B) — 用最近 deadline 算出 epoll_wait 的 timeout(純 std,無 FFI)
// ---- timer path B: min-heap deadline -> epoll_wait timeout (pure std) ----
use std::cmp::Reverse;
use std::collections::BinaryHeap;
use std::time::Instant;

/// Compute the timeout (ms) to pass to epoll_wait from the nearest deadline.
#[allow(dead_code)]
fn next_timeout_ms(timers: &BinaryHeap<Reverse<(Instant, u64)>>, now: Instant) -> i32 {
    match timers.peek() {
        None => -1, // no timers => block indefinitely
        Some(Reverse((deadline, _id))) => {
            if *deadline <= now {
                0 // already due => don't block, fire on return
            } else {
                let ms = deadline.duration_since(now).as_millis();
                ms.min(i32::MAX as u128) as i32 // saturate into epoll's i32 ms
            }
        }
    }
}

file IO 的誠實區別(高分點,也是最常見的誤解)

誤解:「把 file fd 塞進 epoll 就有 async file IO」verified

錯,而且錯得很直接。regular file 在 readiness 模型裡永遠算 ready —— 它沒有「會不會 block」的概念,kernel 遲早會完成 read(page cache miss 就阻塞你的 thread)。實測:

epoll_ctl ADD 的目標 fd結果(本機實測)
regular file(如 /etc/hostname)rc = −1,errno = EPERM(Operation not permitted)
/dev/null(不支援 poll 的 device)rc = −1,errno = EPERM

換句話說,你連加都加不進去:epoll_ctl 對不支援 polling 的 fd(regular file、以及像 /dev/null 這類)直接回 EPERM。就算它讓你加,epoll 回報「ready」也毫無意義 —— 後面那個 read() 照樣阻塞在 disk IO。readiness 模型只對「有真正 blocked↔ready 轉變」的 fd 有效:socket、pipe、tty、eventfd、timerfd。

兩種模型:readiness vs completion

正解 (a):io_uring —— Linux 的現代解

completion-based。你把讀寫「操作」提交到 submission queue(SQE),kernel 完成後在 completion queue 貼出結果(CQE)。兩個 queue 用 mmap 跟 kernel 共享,能批次提交、大幅省 syscall。對 file 和 socket 都是真 async。unverified 具體落地版本我不逐一背;要點是它需要 libc/專門 crate 或大量手寫 syscall + mmap ring setup —— std-only 場景做不出來,提及即可,不實作。

正解 (b):thread-pool offload —— std-only 場景的答案

既然沒法讓 file read 本身變 async,就把 blocking 的 file 讀寫丟到一個 std::thread pool 上跑。worker thread 阻塞在 disk IO 是可以的(它不是 event loop thread)。做完之後,把結果送回 event loop:worker 把結果丟進一個 completion 佇列,再寫 eventfd 叫醒 loop(正是前面 self-wake 的用途),loop 醒來收結果、跑 continuation。

這正是 tokio spawn_blocking / tokio::fs 的做法:它的檔案操作跑在一個 blocking thread pool 上,而非某種魔法 async file syscall。std-only 你手刻的就是這條:thread pool + mpsc 佇列 + eventfd 回收。

面試追問(每條鏈至少 3 層深)

L4 modal 通常是「medium 題 + follow-up」。這裡把你搭完 ET echo 之後可能被層層追進去的四條鏈攤開。

鏈 A — accept 的擴展性
L1你的 listener 用 ET,accept 到 EAGAIN。現在開 10 條 worker thread 都 epoll_wait 同一個 listener,一個連線進來,會醒幾條?
預設(LT listener)會驚群:多條被喚醒去 accept,只有一條拿到連線,其餘 accept 回 EAGAIN 空跑。ET 能減少但不保證只醒一條。乾淨解:EPOLLEXCLUSIVE 讓 kernel 只喚醒一個 waiter。
L2EPOLLEXCLUSIVE 跟 SO_REUSEPORT 分片,你選哪個?差別?
EPOLLEXCLUSIVE:單一 listen socket,kernel 挑一個 waiter 喚醒,簡單。SO_REUSEPORT:每條 thread 各 bind 自己的 listen socket(同 port),kernel 用 4-tuple hash 把新連線分派到不同 socket → 天生分流、無驚群、cache locality 好。
L3SO_REUSEPORT 的隱藏代價是什麼?什麼時候會咬你?
分派靠 hash 而非負載 → 負載不均:某條 thread 恰好接到一堆長命/重連線,其他閒著,沒有 work-stealing。且連線與 socket 綁定,某條 worker 卡住時它的連線無法被別人接手。連線壽命差異大、或需要動態均衡時,EPOLLEXCLUSIVE + 共享 accept 佇列反而更平。
鏈 B — ET 正確性延伸到公平性
L1ET 為什麼一定要 drain 到 EAGAIN?不 drain 會怎樣?
ET 只在邊緣通知一次。沒讀乾,殘料不會再觸發事件 → 事件餓死(見 stepper)。drain loop 的終止靠 read 回 EAGAIN,故 fd 必 nonblocking。
L2好,你在單一 fd 上 drain 到 EAGAIN。但如果一個又快又壞的 client 一直灌資料,你的 handler 在它身上 drain 個沒完 —— 其他 fd 怎麼辦?
單 fd drain-to-EAGAIN 會餓死其他 fd:公平性問題。對策是給每個 fd 每輪一個預算(讀 N 次或 N bytes 就先收手),把該 fd 標記「還沒讀完」放回一個 ready queue,下輪再輪它 → round-robin 公平。
L3但 ET 下你「主動停手」了,下輪 epoll_wait 不會再回報這個 fd(沒新邊緣),你怎麼記得回來讀它?這跟 EPOLLONESHOT 又怎麼交互?
關鍵:ET + 預算式停手時,不能靠 epoll 再通知你 —— 你得自己維護一個「已就緒但未讀完」的應用層 ready list,下輪優先處理它,不進 epoll_wait 就直接讀。多執行緒 + EPOLLONESHOT 時更微妙:fd 投遞後即停用,你 re-arm 的時機決定會不會漏掉「你停手期間到達」的資料 —— 正解是 re-arm 前先做一次「試讀」確認確實 EAGAIN,再 arm;或把未讀完狀態交給擁有該 fd 的那條 thread 續讀。
鏈 C — 連線生命週期與關閉
L1epoll_wait 回了 EPOLLERR / EPOLLHUP / EPOLLRDHUP,各代表什麼?
EPOLLERR:fd 有錯誤(如 socket error),總是會回報、不用你 arm。EPOLLHUP:掛斷(雙向都關)。EPOLLRDHUP:對端關了寫方向(half-close),你還能寫、但讀會到 EOF。
L2收到 EPOLLHUP 就馬上 close 嗎?buffer 裡還沒讀的資料怎麼辦?
別急著關,而且有兩個方向都會漏。讀的方向:HUP 之後 recv buffer 裡仍可能有資料,要先 drain 讀乾再關。寫的方向(更常被忘記):就算讀完了、對端也送了 FIN,你的 out_buf 可能還欠著沒寫出去 —— 這時關掉就是靜默丟資料。正解是 read_closed 標記 + out_buf 排空才關(骨架分頁有我自己踩到這個 bug 的完整案例)。
L3你 close 了 fd,但沒先 EPOLL_CTL_DEL。epoll 集合裡那個 entry 會自動消失嗎?什麼情況不會?
一般情況 close 會自動把 fd 從所有 epoll 集合移除 —— 但前提是沒有其他 fd 指向同一個 open file description。若之前 dup() 過(或 fork 後共享),close 一個 fd 不會移除該 description,epoll 集合裡的 stale entry 還在,可能繼續回報幽靈事件或 data 對到已回收的物件。安全習慣:永遠先 DEL 再 close(骨架的 close_conn 就是這順序),不要依賴 close 的自動清理。
鏈 D — 為什麼 file IO 要換模型
L1你的 event loop 現在要讀一個本地檔案回應請求。直接把 file fd 加進 epoll?
不行。epoll_ctl 對 regular file 回 EPERM(實測);就算能加,file 永遠 report ready,read() 照樣阻塞在 disk。readiness 模型對 file 無效(見 file IO 分頁)。
L2那 async file IO 的正確模型是什麼?跟 epoll 差在哪?
completion(io_uring)vs readiness(epoll)。epoll 告訴你「可以做了、你去做」;io_uring 是「你提交、我做完再通知你」。file 沒有 readiness 轉變,只能用 completion,或把 blocking read offload 到 thread pool。
L3std-only 只能 thread-pool offload。這條路本身有什麼代價?什麼時候 io_uring 明顯較好?
thread-pool 的代價:每次 offload 有 context switch、資料要在 worker 與 loop 之間搬(memcpy / 所有權轉移)、以及大量小 IO 時 thread 數與排隊延遲成本、還有回收結果的 eventfd 喚醒開銷。高 IOPS、大量小檔案讀寫時,io_uring 批次提交 + 零額外 thread + 共享 ring 省 syscall 完勝。反過來,若只是偶爾讀個設定檔,thread-pool 簡單夠用,不值得引 io_uring 的複雜度與 sandbox 相容性問題。

Self-quiz(先想再展開)

Q1 · read() 回傳 0 / EAGAIN / EINTR 各代表什麼、各怎麼處理?
  • Ok(0)(read 回 0)= 對端送出 FIN(half-close):它不會再送資料了。但這不等於「馬上關連線」 —— 你可能還欠它 out_buf 裡沒寫完的資料,直接關會靜默丟失。正解:標記 read_closed = true,先把 out_buf 寫乾,寫完了才 DEL + drop fd。注意這跟 EAGAIN 完全不同,別混。
  • EAGAIN / EWOULDBLOCK(Rust:Err(e) 且 e.kind()==WouldBlock)= 此刻沒資料,recv buffer 讀乾了。ET 下這是停止 drain loop 的信號、等下一個邊緣;不要關連線。
  • EINTR(Rust:e.kind()==Interrupted)= syscall 在傳資料前被信號打斷,不是錯誤 → 直接重試(loop/continue)。骨架的 read/write/accept 都有這一 arm。

口訣:0 = 對端說完了(標記 read_closed,寫乾再關);EAGAIN = 沒料了(停手等邊緣);EINTR = 被打斷(retry)。

陷阱:drain loop 有 兩個出口(EAGAIN 和 Ok(0))。只想到 EAGAIN 那個,就會寫出「EOF 直接關、丟掉 out_buf」的 bug —— 骨架分頁有完整案例。

Q2 · 為什麼不能把 regular file 塞進 epoll 做 async file IO,正解是什麼?

為什麼不行:regular file 在 readiness 模型裡沒有「會不會 block」的概念,永遠算 ready。poll()/select() 會把 file 一律回報為可讀可寫(對 async 毫無幫助,因為 read() 仍阻塞在 disk);epoll 更直接 —— epoll_ctl 對 regular file 回 EPERM(實測 rc=-1),你連加都加不進去。readiness 只對有真正 blocked↔ready 轉變的 fd 有效(socket/pipe/tty/eventfd/timerfd)。

正解:

  • (a) io_uring —— completion-based:提交操作(SQE),kernel 做完貼 CQE,SQ/CQ 是 mmap 共享環,對 file+socket 都真 async 且省 syscall。需 FFI/crate,超出 std-only。
  • (b) thread-pool offload —— std-only 的答案:把 blocking file 讀寫丟到 std::thread pool,做完把結果經completion 佇列 + eventfd 喚醒送回 event loop。等同 tokio spawn_blocking。
Q3 · 「一次通知只 read() 一次就返回」在 LT 與 ET 下各會怎樣?為什麼?

LT:沒事。只要 buffer 還非空,下一輪 epoll_wait 會再次回報可讀,你多輪把它讀完,自我修復。

ET:殘料餓死。ET 只在狀態轉變時通知一次;你讀一次就走,剩下的資料沒有製造新邊緣 → 下輪 wait 對此 fd 沉默 → 殘料卡死,除非有全新資料到達。

所以 ET 的鐵律是每次事件都 drain 到 EAGAIN,而 drain loop 需要 fd 是 nonblocking(否則最後一次 read 阻塞整個 loop)。

Q4 · 為什麼不能把 EPOLLOUT 一直掛著?正確的做法是?

問題:socket 幾乎永遠可寫(kernel 送出緩衝通常有空間)。若 EPOLLOUT 常駐,每一輪 epoll_wait 都因為「可寫」把你叫醒 → busy loop、100% CPU。這是新手最常見的 CPU 爆掉 bug。

正解(按需 arm/disarm,背壓):

  • 平常不掛 EPOLLOUT,直接嘗試 write。
  • 只有當 write 回 EAGAIN(送出緩衝滿、寫不完)時,把殘量存進 out_buf,並 MOD 掛上 EPOLLOUT —— 請 kernel 在「重新可寫」時通知我。
  • 下次 EPOLLOUT 觸發時把 out_buf 繼續寫;寫完立刻 MOD 取消 EPOLLOUT。

骨架的 try_flush 用 out_armed 這個 bool 精確控制開關,2 MB 測試就是走這條路徑驗證的。

Q5 · event loop 睡在 epoll_wait 時,別的 thread 要注入工作,怎麼叫醒它?為什麼要 drain?

做法(eventfd self-wake):把一個 eventfd 註冊進 epoll(EPOLLIN)。別的 thread 把工作丟進一個 mutex 保護的佇列,然後寫 8 bytes(u64=1)到 eventfd → epoll_wait 立刻返回 → loop 醒來、讀乾 eventfd、處理佇列。這是 self-pipe trick 的現代版。

為什麼要 drain eventfd:若 waker 用 ET,而多條 thread 在 loop 處理之前寫了多次,你只讀一次會漏掉後續喚醒(甚至計數器留值導致下次不觸發)→ 讀到 EAGAIN 為止(nonblocking eventfd)才乾淨。這正是 ET drain 鐵律在 waker 上的體現。

延伸用途:thread-pool offload 的 file IO 完成後,worker 也是寫這個 eventfd 把結果回收信號送回 loop。
