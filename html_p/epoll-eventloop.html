epoll 與 JS 事件迴圈

從封包到 callback 的完整通知鏈 · 建樹 → 掛鈴 → 按鈴 → 收割 · 2026-07-17
一句話
epoll 解決的是一個排隊問題:與其你每次醒來挨家挨戶問「資料到了沒」(select/poll,代價 O(全部)),不如在每一家門口裝電鈴——誰有資料誰按鈴,你只看鈴響名單(ready list,代價 O(就緒))。紅黑樹只是門牌登記簿:查重、找人用的,和鈴響本身無關。

先對齊你的三個問題

① 樹怎麼建?——沒有「批次建樹」這回事。每呼叫一次 epoll_ctl(ADD),核心就往紅黑樹插一個節點(epitem),鍵是 (struct file*, fd)。細節在 建樹。

② 註冊好了之後怎麼通知?——ADD 的當下,epoll 順手在目標 fd 的 wait queue 裡塞了一個「函式指標型」節點,函式指向 ep_poll_callback。之後核心任何喚醒這條 wait queue 的路徑,都會順路呼叫它。這就是「裝電鈴」。

③ epoll 回來時事件怎麼跳起來?——分兩跳。核心內:ep_poll_callback 把 epitem 掛上 rdllist、喚醒睡在 epoll_wait 裡的行程。使用者空間:runtime(libuv / tokio)拿 events[i].data 反查是哪條連線,呼叫對應 callback 或 wake 對應 task。data 欄位核心原封不動吐回——所以 libuv 塞指標、mio 塞 Token。全程動畫在 通知鏈 Stepper。

一個事件的一生

下面是「一個封包抵達 Node 伺服器」走完的整條路。四種顏色是四個世界;每一層只認識自己的上下鄰居。

語言層是「一組佇列規則」:JS 是 task / microtask 的插隊法;Rust 是 run queue 加 Waker。樹只存在於核心層——JS 那邊沒有樹,只有佇列。
一句話
epoll_ctl(ADD) 做兩件事:把 (file*, fd) 登記進紅黑樹(建索引),並在目標檔案的 wait queue 裡掛一顆帶函式指標的電鈴(ep_poll_callback)。樹是給 ctl 用的;鈴才是通知的來源。

三個核心物件

結構誰持有裝什麼
struct eventpollepoll fd 本體(epoll_create1 生成)rbr 紅黑樹根、rdllist 就緒串列、wq(睡在 epoll_wait 的行程)、ovflist 收割期間的溢位串列、鎖
struct epitem每個註冊的 (file*, fd) 一顆rbn 樹掛勾、rdllink 名單掛勾、關注遮罩 + data、pwqlist(裝了哪些鈴的收據)
struct eppoll_entry掛在目標檔案的 wait queue 上一個 wait queue 節點,其喚醒函式被設成 ep_poll_callback——這就是電鈴本體
epitem 的雙重身分(intrusive node)
同一顆 epitem 身上有兩個掛勾:rbn 常駐紅黑樹(只要註冊著就在),rdllink 偶爾掛上 rdllist(就緒時才在)。核心不會為「就緒」另外配一顆節點——這是核心 intrusive linked list 的典型玩法,也是為什麼掛名單只是幾個指標操作,快到可以在 softirq 裡做。

樹是怎麼一顆顆長出來的

呼叫 epoll_ctl(epfd, EPOLL_CTL_ADD, fd, &ev) 之後,核心依序:

  1. 取 ep->mtx,用 ep_find 以鍵 (file*, fd) 搜樹——已存在就回 EEXIST(查重是樹的第一個工作)。
  2. 配置 epitem,填入關注遮罩與你的 data。
  3. 裝鈴:呼叫目標檔案的 ->poll()(vfs_poll),傳入的 poll_table 回呼是 ep_ptable_queue_proc。檔案的 poll 實作照慣例呼叫 poll_wait(),於是 ep_ptable_queue_proc 被叫到:它配置一顆 eppoll_entry,把喚醒函式設成 ep_poll_callback,掛進該檔案的 wait queue(socket 就是 sk_sleep(sk) 那條)。
  4. ep_rbtree_insert 把 epitem 插進紅黑樹。
  5. 剛才那次 poll 順便回報了當下遮罩——如果 fd 此刻就已可讀,epitem 直接上 rdllist、順手喚醒 ep->wq。所以「先有資料、後 ADD」不會漏事件。

為什麼是紅黑樹

樹要回答的問題只有兩個:「這個 (file*, fd) 註冊過沒」(ADD 查重)與「找出它」(MOD / DEL)。需求是:數量無上限、最壞情況也要穩、鍵可比較——紅黑樹的 O(log n) 保底剛好,而且是核心裡現成、久經沙場的基礎設施。雜湊表要處理擴容與最壞退化,對核心路徑反而麻煩。

面試常見誤解
「epoll_wait 去樹裡找就緒的 fd」——錯。epoll_wait 從頭到尾不搜樹;它只看 rdllist。樹的三個客戶是 ADD / MOD / DEL,全在 epoll_ctl 這條慢路徑上。就緒的答案是電鈴主動送上門的,這正是 epoll 對 select/poll 的本質改進:註冊一次、常駐監聽,而非每次呼叫都重新登記 + 全量掃描。

※ 本頁函式與欄位名依 fs/eventpoll.c 慣用命名(ep_insert / ep_poll_callback / rdllist / ovflist);不同核心版本細節有搬動(例如收割路徑幾經重構),機制不變;上列 (3)(4) 兩步的先後也在版本間互換過——較新核心先插樹、再裝鈴——同樣不影響機制。

一句話
rdllist 是線索而非答案:收割(ep_send_events)時,核心對每顆 epitem 重新 poll 一次(ep_item_poll)取「當下」遮罩,才寫進你的 events[]。事件可能在你醒來前就被別的執行緒消化掉——所以即使 LT,讀取也要容忍 EAGAIN。

四個經典陷阱

① 收割窗口不丟事件 —— ovflist
copy_to_user 期間鎖是放掉的。此時若有新事件,ep_poll_callback 把 epitem 改掛 ovflist;收割結束後整條 splice 回 rdllist。事件不會因為「你正在拿名單」而遺失——這是無鎖窗口 + 側收集的教科書手法,跟你 SPSC ring 處理「消費中生產」是同一類問題。
② 驚群(thundering herd)
多個行程/執行緒各自 epoll 同一個 listen fd:一條連線進來,鈴響一次卻喚醒全部,只有一個搶到 accept,其餘白醒。解法:EPOLLEXCLUSIVE 讓核心只挑一個喚醒(from memory:Linux 4.5 引入);或 SO_REUSEPORT 從根源把連線分流到各自的 listen fd。
③ EPOLLONESHOT —— 多執行緒共用一個 epoll 的標配
報一次後,關注遮罩自動清零;要再收事件得 epoll_ctl(MOD) 重新武裝。用途:避免同一個 fd 的事件被兩個 worker 同時撿走、同時處理同一條連線。
④ close ≠ 反註冊 —— 殭屍註冊
epitem 綁的是 (file*, fd)。若 fd 曾被 dup / fork,你這邊 close 之後 file 仍活著,註冊也仍活著,事件照發——man epoll 的著名警告。正解:close 之前先 EPOLL_CTL_DEL。
跟你的 R1 復盤同一條神經
「rdllist 是線索、收割時重驗當下狀態」= 核心版的 dry-run before you trust:名單說可讀,不代表現在可讀,動手前重新驗一次。這個心智模型直接搬去答 Etched pillar 5。
一句話
JS 單執行緒還能不卡的秘密:把「等」全部外包給宿主(瀏覽器 / libuv),自己只維護一條 call stack 加幾條佇列。規則一句話講完——跑完一個 task,把 microtask 佇列整條清空,才輪得到下一個 task。

迴圈本體(HTML 規範的骨架)

loop {
  task = 從某條 task queue 取「一個」   // setTimeout、I/O、click⋯ 各有自己的隊
  執行 task                              // 一路跑到 call stack 清空
  while (microtask 佇列非空) 執行下一個   // Promise.then、queueMicrotask
                                          // 執行中新排進來的,也在本輪清完
  if (該渲染了) rAF → style → layout → paint   // 機會點,約與螢幕更新率對齊
}

三條規則、三個推論

  1. 一輪只取一個 task。瀏覽器可以在多條 task queue 之間調度優先權(使用者輸入通常優先),但一輪就是一個。
  2. microtask 一次清空,含執行中補位的。推論一:Promise.then 永遠插隊 setTimeout。推論二:microtask 無限自我補位會凍結畫面——渲染永遠等不到。
  3. 渲染是機會點,不是每輪保證。requestAnimationFrame 的 callback 屬於渲染步驟,是「畫面更新前的最後一刻」,不是普通 task。

一句話
Node 的事件迴圈就是「一個繞著 epoll_wait 打轉的 while」。libuv 把每一圈切成固定相位;poll 相位裡那一次 epoll_wait 的 timeout 參數 = 距離下一顆 timer 到期的毫秒數——「閒著不吃 CPU、時間一到秒醒」的全部機關,就這一個參數。

一圈的相位

timers→ pending callbacks→ idle / prepare→ poll ⏱ epoll_wait 在這→ check(setImmediate)→ close callbacks↺
  • timers:min-heap 裡到期的 setTimeout / setInterval 回呼。
  • poll:先算 timeout——有待辦就 0;否則取最近 timer 的差值;連 timer 都沒有就 -1(無限睡)。然後 epoll_wait(timeout),醒來派發 I/O 回呼。timer 是資料結構,epoll 是鬧鐘,兩者在這個參數上會合。
  • check:setImmediate 專屬相位,緊跟在 poll 之後。

兩個順序判例(本容器 node v22 實測)

const fs = require('fs');
fs.readFile(__filename, () => {          // 這個回呼在 poll 相位執行
  setTimeout(() => console.log('timeout'), 0);
  setImmediate(() => console.log('immediate'));
});
// 實測輸出:immediate → timeout(固定)
// 理由:poll 的下一站就是 check;timers 要等下一圈
setTimeout(() => console.log('t'), 0);
setImmediate(() => console.log('i'));
// 主模組裸寫:三次實測 → i t / t i / i t(不定序!)
// 理由:進迴圈時,那顆 1ms timer 是否已到期,取決於啟動耗時的抖動

面試級結論:I/O 回呼之內,setImmediate 恆先於 setTimeout(0);主模組頂層則不定序。能講出「為什麼」比背結論值錢。

nextTick 與 microtask

process.nextTick 自成一條佇列,優先權高於 Promise microtask。每個回呼收尾時:先清空 nextTick 佇列,再清空 microtask 佇列,然後才輪下一個回呼。(from memory:Node 11 起改為「每個回呼之間」都清,與瀏覽器語意對齊;更早的版本是相位之間才清。)遞迴 nextTick 會餓死 I/O——它比 microtask 更會插隊。

跟你的挑戰題直接相連
那顆用來「自我喚醒 epoll_wait」的 eventfd,就是你 mini block_on 挑戰裡 wake-before-park token 的 OS 版:喚醒訊號必須是「可儲存的」(eventfd 計數器 / 你的 token),否則 wake 發生在 park 之前就會永遠睡死。同一個 race,兩個尺度。

Rust:30 行摸到整條通知鏈(CoderPad 可貼)

手宣告 extern、不用 libc crate——與你 7/15 CoderPad 探針同一路數。用 eventfd 當被監聽的 fd,免網路、結果確定。

// Rust 1.92 / edition 2024(CoderPad 實機環境)
#[repr(C, packed)]      // x86-64 上 kernel 的 epoll_event 是 packed:12 bytes,data 在 offset 4
#[derive(Clone, Copy)]
struct EpollEvent { events: u32, data: u64 }

unsafe extern "C" {     // edition 2024:extern block 要標 unsafe
    fn epoll_create1(flags: i32) -> i32;
    fn epoll_ctl(epfd: i32, op: i32, fd: i32, ev: *mut EpollEvent) -> i32;
    fn epoll_wait(epfd: i32, evs: *mut EpollEvent, maxevents: i32, timeout_ms: i32) -> i32;
    fn eventfd(initval: u32, flags: i32) -> i32;
    fn write(fd: i32, buf: *const u8, count: usize) -> isize;
    fn close(fd: i32) -> i32;
}

const EPOLL_CTL_ADD: i32 = 1;
const EPOLLIN: u32 = 0x001;

fn main() { unsafe {
    let ep  = epoll_create1(0);
    let efd = eventfd(0, 0);
    assert!(ep >= 0 && efd >= 0);

    // 建樹:efd 登記進紅黑樹;data 佔滿 64-bit(當指標 / Token 用 —— mio 的原理)
    let mut ev = EpollEvent { events: EPOLLIN, data: 0xdead_beef_cafe_f00d };
    assert_eq!(epoll_ctl(ep, EPOLL_CTL_ADD, efd, &mut ev), 0);

    // 尚無事件:timeout=0 立即回 0
    let mut out = [EpollEvent { events: 0, data: 0 }; 8];
    assert_eq!(epoll_wait(ep, out.as_mut_ptr(), 8, 0), 0);

    // 另一條執行緒 50ms 後按鈴:對 eventfd 寫 8 bytes
    let h = std::thread::spawn(move || {
        std::thread::sleep(std::time::Duration::from_millis(50));
        let v: u64 = 1;
        write(efd, &v as *const u64 as *const u8, 8);
    });

    // 阻塞等待。核心裡:write → wake_up → ep_poll_callback → rdllist → 喚醒本行程
    let n = epoll_wait(ep, out.as_mut_ptr(), 8, 2000);
    assert_eq!(n, 1);

    // packed 欄位不可取參考 —— 先逐欄位「以值」取出再用(assert_eq! 會偷偷取參考)
    let e0 = out[0];
    let (evs, data) = (e0.events, e0.data);
    assert_eq!(data, 0xdead_beef_cafe_f00d);   // 佈局錯了,炸的就是這行
    assert!(evs & EPOLLIN != 0);
    println!("woken: n={n} events={evs:#x} data={data:#x}");

    h.join().unwrap();
    close(efd); close(ep);
} }

packed 實驗:一個漂亮的 false negative

把 packed 拿掉(只剩 #[repr(C)]),同一支程式,本容器實測:

  • data 佔滿 64-bit(如上,存指標的真實情境)→ 炸:assertion failed: left: 3405705229, right: 16045690984503111693。left = 0xCAFEF00D——高 32 位在「註冊」那一刻就被截掉了:kernel 以它的佈局(data 在 offset 4)去讀你的 16-byte 結構,讀到的是「padding + 你 data 的低半」。
  • data 只用 32-bit(0xdead_beef)→ 竟然通過。兩個佈局錯誤在往返中互相抵消:註冊時 kernel 多讀 4 bytes 的 padding 當低半,喚醒時寫回 offset 4,你又從 offset 8 讀——剛好把值撿回來。成立前提:padding 恰為 0、值 ≤ 32-bit、只有一個事件。
這就是「測試綠燈 ≠ 正確」的實體標本
錯的佈局 + 恰好的測資 = 假通過。對症的 dry-run 是讀 raw bytes,不信往返:用 [0xAAu8; 32] 當接收 buffer,直接印,本容器實測:
n=1 raw[0..16] = [01 00 00 00 | ef be ad de 00 00 00 00 | aa aa aa aa]
kernel 只寫了 12 bytes:events 在 0、data 在 offset 4、第 13 byte 起原封未動——佈局一翻兩瞪眼。這跟你 R1 的教訓同構:測試通過造成的確信,要用「讀出事實」來拆。

① epoll,一口氣

"epoll splits the work into two phases: a one-time registration, and a per-event O(1) notification path. On epoll_ctl ADD, the kernel inserts an epitem into a red-black tree — that part is just bookkeeping, keyed by the file pointer and the fd — and, more importantly, it hangs a callback on the target file's wait queue. From then on, when data arrives, the network stack wakes that wait queue, the callback links the epitem onto a ready list and wakes whoever is sleeping in epoll_wait. Readiness is pushed by the event source, so the cost scales with the number of ready events rather than the size of the interest set — that's the structural difference from select and poll."

中文對照:epoll 把工作拆成兩段——一次性的註冊,和每事件 O(1) 的通知路。ADD 時插樹只是登記(鍵 = file 指標 + fd),更重要的是在目標檔案的 wait queue 掛回呼。之後資料一到:協定棧喚醒 wait queue → 回呼把 epitem 掛上就緒名單 → 喚醒睡在 epoll_wait 的人。就緒由事件源推上來,成本隨「就緒數」而非「註冊數」成長——這就是與 select/poll 的結構性差異。

濃縮版:"If I had to compress epoll into one sentence: register once, get pushed forever."

② 為什麼是紅黑樹

"The tree never sits on the hot path. It answers exactly two questions: is this (file, fd) pair already registered — that's duplicate detection on ADD — and find it again, for MOD and DELETE. So the requirements are unbounded size, a predictable worst case, and a comparable key. The kernel's standard intrusive rbtree covers all of that in O(log n), with the node embedded in the epitem itself — no extra allocation, no resizing. A hash table would work too; it just buys nothing here and adds resize headaches."

中文對照:樹從不在熱路徑上,只回答兩個問題——ADD 查重、MOD/DEL 找回。需求是數量無上限、最壞情況可預測、鍵可比較;核心標準的 intrusive 紅黑樹全包,節點內嵌零配置、免擴容。雜湊也行,但在這裡買不到什麼,還多了擴容麻煩。

濃縮版:"Put differently: the tree serves epoll_ctl; the wait-queue hook serves epoll_wait."

③ LT 與 ET

"The entire difference between level-triggered and edge-triggered is one line after harvesting. In LT, the kernel puts the item back on the ready list, so the next epoll_wait re-polls it and reports it again if it's still readable — it's reporting a state. In ET it doesn't put it back, so the item only reappears when a fresh wake-up fires on the source — it's reporting a transition. That's why ET code must run the fd non-blocking and drain it until EAGAIN: bytes you leave behind will never generate another event."

中文對照:LT/ET 的全部差別是收割後那一行。LT 放回名單——下次重 poll、仍可讀就再報,報的是狀態;ET 不放回——只有源頭新的喚醒才會再上榜,報的是變化。所以 ET 必須 non-blocking、讀到 EAGAIN:留在 buffer 的 bytes 再也不會產生事件。

濃縮版:"A shorthand I use: LT reports a level, ET reports an edge — the names are literal."

④ 新鮮度細節(differentiator)

"One detail worth calling out: the ready list is a hint, not the answer. Before copying events out, the kernel re-polls each fd to get the current mask — so even if another thread consumed the data while you were waking up, you won't be handed a stale report. It's the same discipline as dry-running before you trust something: re-verify at the moment of use."

中文對照:就緒名單只是線索。搬給你之前,核心對每個 fd 重新 poll 一次拿當下遮罩——就算資料在你醒來途中被別的執行緒吃掉,你也不會拿到過期的報告。與 dry-run 同一條紀律:用的那一刻重新驗證。(這句直接掛到 Etched pillar 5。)

⑤ Node,一口氣

"Node is one thread running a loop around epoll_wait. libuv slices each iteration into fixed phases — timers, pending callbacks, poll, check, close — and the poll phase blocks in epoll_wait with a timeout equal to the time until the next timer expires; that one parameter is how Node sleeps without burning CPU and still wakes on time. Returned events carry a data field the kernel never interprets; libuv uses it to look up the watcher and dispatch into the JS callback. And after every callback, Node drains process.nextTick and then the Promise microtask queue before it touches the next event."

中文對照:Node 是一條執行緒繞著 epoll_wait 打轉。libuv 把一圈切成固定相位;poll 相位睡進 epoll_wait,timeout = 距下一顆 timer 到期的時間——不吃 CPU 又準時醒的全部機關就這一個參數。回來的事件帶著核心原封不動的 data 欄位,libuv 用它反查 watcher、派發進 JS 回呼。每個回呼收尾:先清 nextTick、再清 microtask,才碰下一個事件。

濃縮版:"One-liner: timers give the timeout, epoll gives the sleep, data gives the routing."

⑥ 接到 tokio(你的故事線)

"tokio's reactor has the same shape one level up. mio registers the fd with epoll and stores a Token in the data field; on readiness, the driver uses the Token to find that fd's ScheduledIo and calls wake() on the registered Waker, which puts the task back on the executor's run queue. So the Waker plays the role ep_poll_callback plays inside the kernel — a pre-wired 'call me when this is ready' hook. Nothing scans at any layer; it's push all the way up. In production I've mostly consumed this machinery through tokio, so I can speak to both the kernel side and what the runtime builds on top of it."

中文對照:tokio 的 reactor 是同一個形狀往上一層。mio 把 Token 放進 data 欄;就緒時 driver 用 Token 反查 ScheduledIo、對登記的 Waker 呼叫 wake(),task 回到 run queue。Waker 扮演的就是核心裡 ep_poll_callback 的角色——預先接好的「就緒時叫我」。沒有任何一層在掃描,層層都是推。收尾那句把你的 production 經驗焊上去。

濃縮版:"Shortest form: mio's Token is epoll's data field; tokio's Waker is the kernel's ep_poll_callback."
