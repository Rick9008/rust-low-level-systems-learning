一句話

T: 'static 是對型別的斷言:這個型別裡面沒有藏任何借來的東西。 它跟那個值實際活多久完全無關。

另一個長得很像的東西 &'static T 是一個具體型別: 指向的資料保證在整個程式期間都有效。兩者共用 'static 這個名字,是絕大多數混淆的來源。

核心:'static 到底在斷言什麼

直覺一句話

T: 'static 問的是「你有沒有辦法把這個值一直抱著不放」, 不是「你實際上抱了多久」。String 你想抱多久就抱多久 → 它是 'static。 借來的 &'a str 到期就得還 → 不是。

心智模型階梯:樸素 → 正確

模型判準錯在哪 / 何時失效
M0 樸素 「'static = 活到程式結束」 兩個方向都錯。String 滿足 bound 卻馬上 drop; &'a i32 可以活到 main 結束卻不滿足
M1 修補 「owned 的就是 'static」 方向對了但不完整。struct Foo<'a> 是 owned 的 struct, 照樣不滿足 —— 因為欄位裡藏著 &'a
M2 正確 看型別的 lifetime 參數:全部都是 'static(或根本沒有)才算 —— 這就是 Reference 的定義:T: 'a 表示 T 的所有 lifetime 參數都 outlive 'a
Rust Reference 的原話等價於:i32: 'static ✓、&'static str: 'a ✓、 Vec<&'a ()>: 'static ✗。第三個是關鍵 —— Vec 本身是 owned 的, 但它的型別參數把一個 'a 帶了進去。

核心概念卡

承重的那一句:

T: 'static 是「能活多久的上限」,不是「實際活多久」。

T: 'a 唸作 “T outlives 'a”。把 'a 推到最大就是 'static: 這個型別的值可以被持有到任意久而不會 dangle。至於你要不要真的持有那麼久, 是另一回事。

主圖:兩條軸互相獨立

Code Reference — 反例本身

fn takes_static<T: 'static>(_t: T) {}

fn main() {
    let s = String::from("hello");
    takes_static(s);          // 編譯通過:String: 'static
    // s 已經 move 進去,函式一返回就 drop —— 活了不到一行

    let n = 5;
    let r: &i32 = &n;         // 這個 reference 活到 main 結束
    // takes_static(r);       // 編譯失敗:&'a i32 不是 'static
    println!("{r}");
}

正確判準怎麼用

fn takes_static<T: 'static>(_t: T) {}

struct NoLifetime { v: u64 }          // 沒有 lifetime 參數     -> 'static
struct HasLifetime<'a> { v: &'a u64 } // 有一個 lifetime 參數   -> 看 'a

fn probe<'a>(borrowed: &'a u64) {
    let a = NoLifetime { v: 1 };
    let b = HasLifetime { v: &7 };              // &7 被 promote 成 'static
    println!("{} {}", a.v, b.v);

    takes_static(a);                            // OK
    takes_static(b);                            // OK:'static 的 HasLifetime
    // takes_static(HasLifetime { v: borrowed });  // FAIL:'a 不是 'static
    // takes_static(vec![borrowed]);               // FAIL:Vec<&'a u64>
    let _ = borrowed;
}

fn main() { let x = 3; probe(&x); }

NoLifetime 跟 HasLifetime 都是 owned struct,差別只在後者的定義帶了 <'a>。判準完全落在型別的宣告上,執行期發生什麼事不影響結論。

&'static 從哪裡生出來

直覺一句話

要拿到 &'static T,那塊記憶體必須真的不會被回收。 只有四種來路做得到,其中一種要你主動放棄回收。

Code Reference — 四種來源

static GLOBAL: i32 = 42;

fn main() {
    // (1) string literal:編進 binary 的唯讀段
    let a: &'static str = "in .rodata";

    // (2) static item:程式啟動前就存在,結束才消失
    let b: &'static i32 = &GLOBAL;

    // (3) rvalue static promotion:常數運算式被提升到唯讀段
    let c: &'static i32 = &42;

    // (4) Box::leak:主動放棄 heap 記憶體的所有權
    let d: &'static mut Vec<u8> = Box::leak(Box::new(vec![9, 9]));
    d.push(1);

    println!("{a} {b} {c} {d:?}");
}

實際輸出:in .rodata 42 42 [9, 9, 1]

Box::leak 不是作弊,是把「回收」換成「保證」

Rust 沒有規定「不能洩漏記憶體」—— mem::forget 是 safe function。 Box::leak 做的事是把 heap 配置的 ownership 丟掉,換回一個 &'static mut T。因為沒有人再擁有它,沒有人會 drop 它,所以 'static 這個保證成立。

判斷標準是有界性:啟動時 leak 一次 config,總量是常數 → 合理。 每個 request leak 一次 → 那是 bug。

'static 不是一個可以「宣告」出來的東西

 --> g1_any_plus_a.rs:4:53

4 | fn main(){ let s = String::from("x"); let _ = erase(&s); }
  |                -                              ------^^-  - `s` dropped here while still borrowed
  |                |                              |     |

  |                binding `s` declared here      argument requires that `s` is borrowed for `'static`

把變數標注成 &'static 不會讓被借的資料活久一點。 標注只是提出要求,borrow checker 會回頭去查供給端能不能滿足; 滿足不了就在供給端報錯。

曾經有第五種來源:static mut

在 unsafe block 裡對 static mut X 取 &mut X, 以前可以拿到 &'static mut T。edition 2024 起這是 hard error —— 因為沒有任何機制 阻止你同時拿到第二個獨佔借用。細節與遷移路線見 Edition 2024。

Follow-up

  • rvalue static promotion 只對「沒有 interior mutability、沒有 Drop」的常數運算式生效。 &42 可以,&Cell::new(42) 不行 —— 想想為什麼(提示:兩個地方寫同一塊 .rodata)。
  • OnceLock / LazyLock 是 Box::leak 的替代路線:同樣給你 &'static T,但初始化延後且不需要放棄 ownership。什麼時候該選哪個?

為什麼 spawn 一定要 'static

直覺一句話

spawn 立刻回傳,task 之後才跑,而且可能跑在別的 thread。 沒有任何東西保證呼叫者的 frame 會等它。所以 task 不能借呼叫者的任何東西。

簽章對照

APIbound它在買什麼
std::thread::spawnF: FnOnce() -> T + Send + 'static跨 thread + 可能比呼叫者活久
tokio::spawnF: Future + Send + 'static
F::Output: Send + 'static		同上,加上 output 要送回 JoinHandle
tokio::task::spawn_localF: Future + 'static
F::Output: 'static		拿掉 Send、保留 'static
Scope::spawnF: FnOnce() -> T + Send + 'scope保留 Send、放寬 'static
最後兩列是這整頁的重點:兩個 bound 可以獨立拿掉,證明它們回答不同問題。
Send 問「能不能搬到別的 thread」;'static 問「能不能活得比呼叫者久」。

Send × 'static 的四個象限(全部實測)

Send!Send
'staticString、i32、Vec<u8>Rc<i32>
!'static&'a mut i32&'a Cell<i32>

四格都有住戶。Rc<i32> 那格的錯誤是 E0277: cannot be sent between threads safely; &'a mut i32 那格是 E0521: borrowed data escapes outside of function —— 完全不同的錯誤路徑。

Code Reference — spawn vs scope

fn main() {
    let data = vec![1, 2, 3];

    // thread::spawn 要求 F: FnOnce() -> T + Send + 'static
    // std::thread::spawn(|| println!("{data:?}"));   // FAIL:借了 data

    // scope 保證所有 spawn 出去的 thread 在 scope 返回前 join 完,
    // 所以 bound 從 'static 放寬成 'scope
    let sum = std::thread::scope(|s| {
        let h = s.spawn(|| data.iter().sum::<i32>());
        h.join().unwrap()
    });

    println!("{sum}");
}

Follow-up

  • async 世界沒有 std::thread::scope 的等價物在標準庫裡,原因是 async task 可以被 mem::forget 掉(leak 是 safe 的),所以 destructor 不能被當成保證。這就是 「async Drop / structured concurrency」那一整串討論的起點。
  • tokio::task::JoinSet 和 FuturesUnordered 給的是執行期的結構化, bound 依然是 'static。跟 thread::scope 的型別層保證是兩回事。
  • 把 tokio::spawn 的 'static 拿掉需要 unsafe(tokio 內部有討論過 spawn_unchecked)。想清楚 caller 要負責證明什麼。

陷阱

陷阱 1:Box<dyn Trait> 偷偷加了 + 'static

Trait object 有一條 default lifetime bound 規則:在 reference 底下的 trait object 取最內層 reference 的 lifetime, 其他情況預設 'static。所以:

你寫的編譯器看到的
Box<dyn Error>Box<dyn Error + 'static>
&'a dyn Error&'a (dyn Error + 'a)
Arc<dyn Fn()>Arc<dyn Fn() + 'static>
error: lifetime may not live long enough
 --> f3_box_dyn.rs:4:47
  |
4 | fn wrap<'a>(x: &'a i32) -> Owner { Owner { v: Box::new(x) } }
  |         -- lifetime `'a` defined here         ^^^^^^^^^^^ coercion requires that `'a` must outlive `'static`

修法是顯式放寬:Box<dyn Error + 'a>。這就是為什麼很多 library 的 error type 定義裡會看到 那個看起來多餘的 + 'a。

陷阱 2:編譯器的建議有時候是錯的

Box<dyn Any> 借了東西,rustc 會建議加 + 'a:

error: lifetime may not live long enough
 --> f5_any.rs:3:44
  |
3 | fn erase<'a>(x: &'a str) -> Box<dyn Any> { Box::new(x) }
  |          -- lifetime `'a` defined here     ^^^^^^^^^^^ coercion requires that `'a` must outlive `'static`
  |
help: to declare that the trait object captures data from argument `x`, you can add an explicit `'a` lifetime bound
  |
3 | fn erase<'a>(x: &'a str) -> Box<dyn Any + 'a> { Box::new(x) }
  |                                         ++++

error: aborting due to 1 previous error

照做之後,錯誤搬家但沒消失:

error[E0597]: `s` does not live long enough
 --> g1_any_plus_a.rs:4:53
  |
4 | fn main(){ let s = String::from("x"); let _ = erase(&s); }
  |                -                              ------^^-  - `s` dropped here while still borrowed
  |                |                              |     |
  |                |                              |     borrowed value does not live long enough
  |                binding `s` declared here      argument requires that `s` is borrowed for `'static`
因為 Any 的 'static 是supertrait bound(trait Any: 'static), 不是 trait object 的 default bound。寫在 dyn 後面的 + 'a 根本管不到它。

而且這裡的 'static 是承重的:TypeId 會抹掉 lifetime, &'a str 和 &'b str 的 TypeId 相同。若允許非 'static 型別進 dyn Any, downcast 就能把一個短命的 reference 當成長命的取回來 —— 直接 unsound。這條 bound 拿不掉。

陷阱 3:被 'static 傳染

編譯器說「consider adding 'static」,加下去通常編過了,然後下一層又要加, 一路傳染到 API 邊界。這代表原本的問題沒解決,只是往上推。

判斷法:問「這個 'static 是需求還是妥協?」
需求 = 真的有 detached 執行(spawn、global registry、dyn Any)→ 加,而且在來源端用 owned type 滿足它。
妥協 = 只是想讓錯誤消失 → 停手,回去看資料的 ownership 該歸誰。

陷阱 4:以為 Arc 會給你 'static

Arc<T>: 'static 的前提是 T: 'static。 Arc<&'a str> 不是 'static。Arc 解決的是「多方共享同一份 owned 資料」, 它不會把借來的東西變成自己的。

陷阱 5:'static ≠ 記憶體洩漏

tokio::spawn(async move { ... }) 把資料 move 進 future,滿足 'static, task 跑完照樣 drop。'static 只表示「型別上允許活很久」,不表示「實際上不會被回收」。 這是主圖左上角那一格。

Code Reference

use std::any::Any;
use std::fmt::Debug;

struct Owner  { v: Box<dyn Debug> }             // 隱含 Box<dyn Debug + 'static>
struct Loaner<'a> { v: Box<dyn Debug + 'a> }    // 顯式放寬才借得到

fn erase(x: &'static str) -> Box<dyn Any> { Box::new(x) }

fn main() {
    let o = Owner { v: Box::new(String::from("owned")) };
    let local = 5;
    let l = Loaner { v: Box::new(&local) };

    // Any 的 'static 是 supertrait bound,寫 + 'a 也救不回來:
    // TypeId 抹掉 lifetime,允許非 'static 會讓 downcast 復活 dangling reference
    let erased = erase("literal");
    println!("{:?} {:?} {}", o.v, l.v, erased.is::<&str>());
}

Follow-up

  • Default trait object lifetime 在 type alias 底下的行為更複雜(alias 有沒有寫 T: 'a 會改變預設值)。 寫 public API 的 alias 時值得顯式標注。
  • dyn Any 的 lifetime 限制有沒有可能鬆綁?思考:要讓 TypeId 帶 lifetime 資訊,型別系統要多付什麼。

修法 & 成本

直覺一句話

看到 must outlive 'static,先問「這份資料的 owner 應該是誰」, 再從下表挑工具。順序很重要 —— 直接跳到 Arc 是最常見的過度反應。

成本階梯

#修法適用時間空間
1move 交出 ownership 呼叫者之後不需要這份資料 O(1) — 只搬 handle(指標 + len + cap) O(1) 額外
2改結構,讓 task 不需要那份資料 借用其實只是為了讀一兩個欄位 O(欄位大小) O(欄位大小)
3clone 資料小,兩邊都要獨立擁有 O(n) 深拷貝 O(n) 額外
4Arc::clone 資料大、多方共享、read-mostly O(1),但含一次 atomic RMW;refcount 落在同一條 cache line,高頻 clone/drop 會 ping-pong O(1) 額外(控制區塊攤提)
5thread::scope / structured concurrency task 保證在某個範圍內 join 0 — bound 從 'static 變 'scope,不需要任何複製 0 額外
6Box::leak / OnceLock 啟動期讀進來、之後不變的東西(config、metric registry) O(1) 一次 O(size),永不回收 — 必須是有界的
第 4 列是低延遲場景要盯的一格:Arc 的 refcount 是共享可寫狀態。 幾十個 thread 高頻 clone 同一個 Arc,瓶頸會是那條 cache line 的 coherence traffic, 跟你保護的資料本身無關。(atomic ordering 的細節我沒在這裡實測,若要下結論請直接讀 alloc::sync 原始碼。)

Code Reference — 四種修法,全部可執行

use std::sync::Arc;
use std::cell::Cell;

fn is_send<T: Send>(_: T) {}
fn is_static<T: 'static>(_: T) {}

// 正交四象限的第四格:&'a Cell<i32> 既非 'static 也非 Send
fn quadrant4<'a>(_r: &'a Cell<i32>) { /* is_send(_r); is_static(_r); 兩者都會 fail */ }

#[derive(Debug)]
struct Config { workers: usize, addr: String }

// bounded leak:啟動時洩漏一次,換掉整個程式的 Arc 傳遞
fn load_config() -> &'static Config {
    Box::leak(Box::new(Config { workers: 8, addr: "0.0.0.0:9000".into() }))
}

fn main() {
    // 修法 A:move 取得 ownership
    let owned = vec![1, 2, 3];
    let h = std::thread::spawn(move || owned.iter().sum::<i32>());
    println!("A move        = {}", h.join().unwrap());

    // 修法 B:Arc 共享 ownership(注意 Arc<T>: 'static 需要 T: 'static)
    let shared = Arc::new(vec![4, 5, 6]);
    let c = Arc::clone(&shared);
    let h = std::thread::spawn(move || c.iter().sum::<i32>());
    println!("B Arc         = {} (原本的還能用: {:?})", h.join().unwrap(), shared);

    // 修法 C:scope,結構性地不需要 'static
    let borrowed = vec![7, 8, 9];
    let total = std::thread::scope(|s| {
        s.spawn(|| borrowed.iter().sum::<i32>()).join().unwrap()
    });
    println!("C scope       = {total} (沒有 clone、沒有 Arc)");

    // 修法 D:bounded leak
    let cfg: &'static Config = load_config();
    let h = std::thread::spawn(move || format!("{} workers @ {}", cfg.workers, cfg.addr));
    println!("D leak        = {}", h.join().unwrap());

    let cell = Cell::new(0);
    quadrant4(&cell);
    is_send(String::new()); is_static(String::new());
}

實際輸出:

A move        = 6
B Arc         = 15 (原本的還能用: [4, 5, 6])
C scope       = 24 (沒有 clone、沒有 Arc)
D leak        = 8 workers @ 0.0.0.0:9000

決策順序

  • 1. 呼叫者之後還要用嗎?不要 → move,結束。
  • 2. task 保證在這個 frame 內結束嗎?會 → scope,零成本。
  • 3. 資料小嗎?小 → clone,別為了省一次 memcpy 引入 atomic。
  • 4. 程式生命週期內不變嗎?是 → OnceLock / Box::leak。
  • 5. 以上都不是 → Arc。這是最後一步,不是第一步。

Follow-up

  • 第 3 列和第 4 列的交叉點在哪?對你的資料大小和 clone 頻率做一次量測,別用直覺猜。
  • Arc<str> vs Arc<String>:少一層 indirection,但失去 push_str。共享唯讀字串幾乎都該用前者。

Edition 2024 對 'static 的影響

直覺一句話

Edition 不改 borrow checker 的語義,但它可以改預設值。 2024 改了兩個預設值,兩個都直接影響「什麼型別滿足 T: 'static」的判定結果。

好消息先講:本手冊前面六段程式碼從 edition 2021 換到 2024,一個字都不用改, 全部原樣通過。核心規則沒有變動,變的是下面兩個角落。

變更 1 — impl Trait 的 lifetime 捕獲規則

規則差異

edition 2021edition 2024
RPIT 捕獲哪些 lifetime 只捕獲出現在回傳型別 bound 裡的 捕獲所有 in-scope 的 lifetime 參數
預設偏向捕獲太少 → 想借卻借不到捕獲太多 → 不想借卻被綁住
怎麼手動控制加 + 'a 或 Captures trick寫 use<...> 精確捕獲

對 'static 的具體後果

fn takes_static<T: 'static>(_t: T) {}

// 回傳型別一個字都沒提到 'a
fn make<'a>(_x: &'a str) -> impl Fn() -> i32 { || 42 }

fn probe<'a>(x: &'a str) {
    let c = make(x);
    takes_static(c);   // edition 2021:通過 / edition 2024:E0521
}

fn main() { let s = String::from("s"); probe(&s); }

make 的回傳型別 impl Fn() -> i32 一個字都沒提到 'a。 2021 據此判定回傳值不含 'a → 滿足 T: 'static。 2024 改成無條件捕獲 'a → 不再滿足:

error[E0521]: borrowed data escapes outside of function
 --> e1_rpit.rs:8:5
  |
6 | fn probe<'a>(x: &'a str) {
  |          --  - `x` is a reference that is only valid in the function body
  |          |
  |          lifetime `'a` defined here
7 |     let c = make(x);
8 |     takes_static(c);   // edition 2021:通過 / edition 2024:E0521
  |     ^^^^^^^^^^^^^^^
  |     |
  |     `x` escapes the function body here
  |     argument requires that `'a` must outlive `'static`

error: aborting due to 1 previous error
這是升 edition 時最容易中的一槍,而且錯誤訊息指向呼叫端, 真正的原因在定義端的回傳型別。看到 impl Trait + must outlive 'static 就往函式定義去找。

修法:use<> 精確捕獲

fn takes_static<T: 'static>(_t: T) {}

// use<> = 精確捕獲,明確宣告「一個 lifetime 都不捕獲」
fn make<'a>(_x: &'a str) -> impl Fn() -> i32 + use<> { || 42 }

// 需要捕獲時就寫進去:use<'a>
fn borrow<'a>(v: &'a [String]) -> impl Iterator<Item = &'a str> + use<'a> {
    v.iter().map(|s| s.as_str())
}

fn main() {
    let s = String::from("s");
    probe(&s);
    let v = vec![String::from("a"), String::from("b")];
    println!("{}", borrow(&v).count());
}

fn probe<'a>(x: &'a str) {
    takes_static(make(x));   // 兩個 edition 都通過
}
  • use<> — 空捕獲清單,明確宣告「這個回傳值不借任何東西」。T: 'static 恢復成立。
  • use<'a> — 只捕獲 'a。需要借東西時寫這個,語意比 2021 的 + 'a 精確。
  • 兩個 edition 都接受 use<>,所以它可以在升 edition 之前先加上去,把改動拆成兩步。
對 library 作者:use<> 是寫進 API 的承諾。 加上去等於對外保證回傳值不含借用,之後想反悔就是 breaking change。 2024 的預設(全捕獲)是保守的那一側,這個方向選得對 —— 放寬是 minor,收緊是 major。

變更 2 — static mut 的 reference 變成 hard error

為什麼跟 'static 有關

static mut 曾經是唯一能寫出 &'static mut T 的語法捷徑 (在 unsafe block 裡)。它在 'static 的來源 那張圖上本來該有一格。 2024 起這條路封了。

static mut COUNTER: i32 = 0;

fn main() {
    unsafe {
        let r: &'static mut i32 = &mut COUNTER;  // 2021:warning / 2024:hard error
        *r += 1;
        println!("{r}");
    }
}
error: creating a mutable reference to mutable static
 --> e3_staticmut.rs:5:35
  |
5 |         let r: &'static mut i32 = &mut COUNTER;  // 2021:warning / 2024:hard error
  |                                   ^^^^^^^^^^^^ mutable reference to mutable static
  |
  = note: for more information, see <https://doc.rust-lang.org/edition-guide/rust-2024/static-mut-references.html>
  = note: mutable references to mutable statics are dangerous; it's undefined behavior if any other pointer to the static is used or if any other reference is created for the static while the mutable reference lives
  = note: `#[deny(static_mut_refs)]` (part of `#[deny(rust_2024_compatibility)]`) on by default
help: use `&raw mut` instead to create a raw pointer
  |
5 |         let r: &'static mut i32 = &raw mut COUNTER;  // 2021:warning / 2024:hard error

2021 下這是 static_mut_refs warning,2024 下是 deny。 理由在錯誤訊息裡寫得很清楚:&mut 是獨佔借用, 而 static mut 沒有任何機制阻止你在同一時間再拿一個 —— 拿到就是 aliasing UB, unsafe block 並不會幫你檢查。

兩條遷移路線

use std::sync::atomic::{AtomicI32, Ordering};

static COUNTER: AtomicI32 = AtomicI32::new(0);   // 首選:根本不用 static mut
static mut LEGACY: i32 = 0;

fn main() {
    COUNTER.fetch_add(1, Ordering::Relaxed);
    println!("{}", COUNTER.load(Ordering::Relaxed));

    // 機械式遷移路線:&raw mut 產生裸指標,不產生 reference
    unsafe {
        let p: *mut i32 = &raw mut LEGACY;
        *p += 1;
        println!("{}", *p);
    }
}
路線做法什麼時候選
正解換成 AtomicI32 / Mutex<T> / OnceLock<T> 放在普通 static 幾乎永遠。這些型別有 interior mutability,不需要 static mut,而且 safe
機械式&raw mut X 取得裸指標(編譯器建議的那個) FFI、或大量舊碼要先編過再重構。責任沒有消失,只是從編譯器移到你身上
&raw mut 和 &mut 的差別:前者產生 *mut T,不建立 reference, 因此不觸發 aliasing 規則。這是 addr_of_mut! 巨集的語法版。

升 edition 時的檢查清單

  • grep 所有回傳 impl Trait 而參數帶 lifetime 的函式 —— 這些是 RPIT 捕獲改變的候選點。
  • grep static mut。
  • 先在 2021 下開 #![warn(rust_2024_compatibility)] 跑一次,把兩類問題都撈出來,再切 edition。
  • cargo fix --edition 會自動加 use<...>,但它加的是保守版(照 2021 的捕獲集合)。 public API 值得手動看一遍決定要不要更緊。

edition 2024 還有其他改動(tail expression 與 if let 的 temporary scope、 gen 保留字、unsafe attributes 等)。上面兩項是我在這份手冊涵蓋範圍內實測到會改變 T: 'static 判定結果的;其他的我沒有在這裡驗證,細節請看官方 edition guide。

Follow-up

  • 2021 的 Captures<'a> trick 為什麼需要存在?想清楚之後,use<> 的設計動機就很明顯。
  • RPITIT(trait 裡的 -> impl Trait)的捕獲規則跟自由函式不同 —— 它一直都是全捕獲。為什麼 trait 那邊不需要這次 edition 變更?
  • 如果你的 async runtime 對外暴露 fn spawn(...) -> impl Future 這種簽章,use<> 的選擇會直接決定呼叫端能不能滿足 'static。這是 API 表面的一部分,不是實作細節。

延伸 / C++ 對照

C++ 的 static 跟 Rust 的 'static 是兩個不同的東西

C++ static storage durationRust 'static
在講物件存放在哪個儲存區、何時初始化／解構型別裡有沒有藏借用
檢查時機無需檢查 —— 它是儲存期的事實編譯期,borrow checker 驗證
對應物Rust 的 static ITEM: T 宣告C++ 沒有對應物

Rust 的 static ITEM: T = ...; 才是 C++ static storage duration 的對應物。 'static lifetime 在 C++ 型別系統裡沒有東西對得上。

對寫 C++ executor 的實際意義

這是兩邊差距最大的地方。Rust 用 F: 'static 讓「detached task 借了呼叫者的 stack」 在編譯期就過不去。C++ 的 coroutine 沒有這層檢查:

  • lambda 用 [&] 捕捉,包成 coroutine 再丟給 executor → 呼叫者 frame pop 之後就是 use-after-free。編譯器不會說任何話。
  • coroutine 的 dangling reference parameter 問題更隱蔽:傳進 coroutine 的 reference 參數不會被存進 coroutine frame, 第一次 suspend 之後就懸空。這是 C++ coroutine 的著名坑,跟 'static 要防的是同一類 bug。
  • 因此 C++ 這邊唯一可行的路是結構化併發:用 scope 型的設施保證 join, 等價於 Rust 的 thread::scope 那條路,而不是 'static 那條 —— 因為 C++ 沒有那條。
上面關於 C++ 的部分是從語言規則推論的,不是引用具體條文。要寫進設計文件前請對照 P2300 相關 paper 的 lifetime 章節確認措辭。

值得追下去的問題

  • 如果 C++ 要引入類似 'static 的 bound,最小需要什麼?(提示:需要 lifetime 進入型別系統, 而這幾乎等於引入 borrow checker。)
  • Rust 的 leak 是 safe 的,這件事讓 Drop 不能被當成安全保證 —— 這正是 async scope 難做的根因。 C++ 的 destructor 是保證會跑的(除非 UB),這反而讓 C++ 的結構化併發在這一點上比 Rust 好做。 兩邊各換到了什麼?
  • Pin 和 'static 解決的是不同的問題(自我引用 vs 借外部)。寫 runtime 時兩個都會遇到,別混在一起想。
  • 回到你的 async runtime:先決定 spawn 的合約是 detached 還是 scoped。這個決定會傳遍整個 API 表面, 事後改幾乎等於重寫。
