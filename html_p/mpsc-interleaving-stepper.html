場景設定:用你自己的系統當教材

設計一的場景是你的 log daemon:N 個 request-handler thread 產生 log entry、一個 flusher thread 寫盤 —— MPSC 的原型。任務性質是「不許拒收」:log 可以晚到,不能被 push 端丟掉,所以 unbounded。

設計二的場景換成 telemetry ingestion(你 7/24 rehearsal 的題):sensor threads 灌 readings、一個 aggregator 收。這裡「寧丟不塞爆」:滿了要當場拿到 Err,由上層決定丟點 + 計數。同一個 MPSC 需求,兩種失敗哲學,長出兩種結構 —— 這就是 Tab 6 選型表的第一列。

SPSC 對照:你已經會的那一格,是理解 MP 的鑰匙

SPSC 為什麼便宜
SPSC 兩個單調遞增 index 就夠、完全不用 CAS,是因為每個 index 恰好只有一個寫者:producer 寫 tail、consumer 寫 head,彼此只「讀」對方 —— acquire/release 一對握手就閉環。

MP 打破的就是這一條。「隊尾在哪」這個變數突然有 N 個寫者。整份教材其實只在回答一件事:單一寫者前提破掉之後,怎麼救 —— 設計一用 swap(無條件交換,人人成功,靠回傳值分工)、設計二用 CAS(佔位可失敗,失敗就重試或回報滿)。

為什麼縫消不掉:佔位和發布動的是兩個不同的記憶體位置(設計一:head 與 prev.next;設計二:enq 與 slot.seq),而單一原子操作一次只能動一個位置。兩個原子操作之間,天底下任何 thread 都可能被排進來 —— 包括讀者。所以設計題從「怎麼避免縫」變成「讀者撞到縫時,協議是什麼」。兩個設計的所有分支,都是這個協議的條文。

名詞先立牌:Vyukov 的 head / tail 跟你的直覺相反
兩個設計都出自 Dmitry Vyukov(1024cores)。他的命名:head = push 端(producers swap 的地方)、tail = pop 端(consumer cursor)。本教材全程沿用他的命名 —— 對話中我曾兩處混用,以這裡為準。順帶收掉稱呼問題:「Vyukov intrusive MPSC」= 設計一;設計二是他的 bounded MPMC array queue 退化到單 consumer 用。講 “Vyukov queue” 時兩者都可能被指,靠 bounded/unbounded 區分。

設計一 · 一句話 producer 只做兩件事:跟櫃檯換牌子(swap:「現在我是最後一棒」,並拿到上一棒是誰)、然後去上一棒身上掛名牌(link:prev.next = 我)。 換牌永不失敗、掛牌各掛各的 —— 所以 push 端 wait-free。全部的複雜度都被擠到 consumer 那邊。

把狀態變數一個一個逼出來

場景:log daemon。N 個 handler thread 各自產生 log entry(node),一個 flusher 收。以下每個 Q 都是「不加這個東西就做不下去」的點 —— 變數是被逼出來的,不是天上掉下來的。

多個 producer 都要「掛到隊尾」,隊尾是什麼?
必須有一個所有 producer 都看得到的單點。它會被 N 個 thread 同時寫 → 必須是 atomic。
head: AtomicUsize —— 全結構唯一的競爭點。
「掛上去」是一件事還是兩件事?
兩件:①讓 head 指向我(成為新隊尾);②讓前一棒的 next 指向我(讓讀者走得到)。兩件事動兩個記憶體位置,單一原子操作做不完 → 必須拆兩步。
縫。從這一刻起,設計題變成「讀者撞到縫的協議」。
第一步(佔位)用什麼原子操作?
CAS 迴圈(load head → CAS(old, me) → 失敗重來)可以,但有更強的:swap。無條件交換,永遠成功,而且回傳舊值 —— 我一步同時完成「成為隊尾」和「知道前一棒是誰」。沒有迴圈 = 不管幾個 producer 對撞,每人固定兩步 = wait-free。附贈:ABA 天生免疫,因為 swap 沒有 compare —— ABA 是 CAS 的病。
let prev = head.swap(me)
第二步 prev.next = me,多個 producer 會不會互相踩?
不會。prev 是各自 swap 的回傳值,swap 的原子性保證每個 producer 拿到的 prev 互不相同 —— 佇列順序在 swap 那一刻已定案,link 只是把已定的順序 materialize,各寫各的 next,零競爭。這是整個設計最漂亮的一步:把「N 人搶一個點」轉換成「N 人各寫各的點」。
link 不需要任何同步原語,一個 Release store 就完。
consumer 怎麼讀?
從某個起點沿 next 走。起點 = 它自己的 cursor。誰會寫這個 cursor?只有一個 consumer → 普通 usize,連 atomic 都不用。注意這是「型別合約」不是結構保證:Rust 裡用 pop(&mut self) + Receiver 不給 Clone,把合約編進 compiler。
tail: usize(Vyukov 命名:pop 端)
佇列空的時候,head 和 tail 指同一個節點 —— pop 掉它會怎樣?
災難:head 懸空,下一個 producer 的 swap 拿到已回收節點當 prev。兩端會在空佇列時撞進同一塊記憶體 → 需要一個永遠不被真正取走的常駐節點,把 producer 領地(head、prev.next)和 consumer 領地(tail)永久隔開。
stub(dummy node)。
pop 的規則是「回傳 tail、cursor 前進到 next」—— 那最後一棒怎麼收?
收不了:它沒有後繼。這是本設計最反直覺的一條規則 ——一個節點能被 pop 的條件是「它的後繼已經 link 上」。解法:consumer 客串一次 producer,把 stub 重新 push 進去,人工替最後一棒製造後繼。push 本來就 MP-safe,多一個呼叫者不會壞。
pop 裡的 push(stub) 分支。

縫的三張臉

consumer 撞到「swap 完成、link 未完成」的縫,有三個入口。三個都在 Tab 3 有逐格重放:

撞縫位置consumer 看到什麼協議回應Stepper

Code(rustc 1.91 · edition 2024 編譯執行通過;demo payload 用 AtomicUsize 保 safe Rust)

const NIL: usize = usize::MAX;

struct Node {
    next: AtomicUsize, // 同步骨架:鏈的下一格
    val: AtomicUsize,  // demo 用 usize 當 payload,讓 safe Rust 成立;
                       // 泛型 T 版需 UnsafeCell<MaybeUninit<T>> + unsafe,
                       // 獨佔視窗由同一組 happens-before 保證(loom 驗)
}

pub struct MpscQueue {
    nodes: Box<[Node]>,
    head: AtomicUsize, // push 端:最新節點(Vyukov 命名,注意跟直覺相反)
    stub: usize,       // 常駐 dummy
}

pub struct Consumer<'a> {
    q: &'a MpscQueue,
    tail: usize, // pop 端 cursor:單一 consumer 是「型別合約」,所以敢用普通 usize
}

#[derive(Debug, PartialEq)]
pub enum Pop {
    Data { node: usize, val: usize },
    Empty,        // 真的空:可以去睡,等 producer 通知
    Inconsistent, // 有 producer 卡在 swap 與 link 之間:spin/yield 馬上重試
}

impl MpscQueue {
    /// n_nodes 含 stub。node 0 = stub。
    /// demo 版用 Box::leak 換 'static(永不釋放,測試夠用);
    /// 正式版是 Arc<MpscQueue> + Sender(Clone)/Receiver(!Clone) 的拆法。
    pub fn new(n_nodes: usize) -> (&'static Self, Consumer<'static>) {
        let nodes: Box<[Node]> = (0..n_nodes)
            .map(|_| Node { next: AtomicUsize::new(NIL), val: AtomicUsize::new(0) })
            .collect();
        let q: &'static MpscQueue = Box::leak(Box::new(
            Self { nodes, head: AtomicUsize::new(0), stub: 0 }));
        (q, Consumer { q, tail: 0 })
    }

    /// MP 端:兩步,無迴圈,永遠成功(wait-free)。
    /// idx 必須是 caller 獨佔的空節點(freelist 是另一個結構,此處不混入)。
    pub fn push(&self, idx: usize, val: usize) {
        self.nodes[idx].val.store(val, Relaxed);   // 1. 先填內容
        self.nodes[idx].next.store(NIL, Relaxed);  //    自己是新的最後一棒
        let prev = self.head.swap(idx, AcqRel);    // 2. 佔位:順序在此刻定案
        self.nodes[prev].next.store(idx, Release); // 3. 發布:把鏈補上(帶出 val)
    }
}

impl Consumer<'_> {
    pub fn pop(&mut self) -> Pop {
        let q = self.q;
        let mut tail = self.tail;
        let mut next = q.nodes[tail].next.load(Acquire);

        if tail == q.stub {
            if next == NIL {
                // 停在 stub 且沒有後繼:「空」和「有人 swap 了還沒 link」在這裡分岔。
                // (原版 Vyukov 兩者都回 empty;分開才能讓 caller 決定睡或 spin)
                if q.head.load(Acquire) == tail {
                    return Pop::Empty;        // head 還是 stub → 沒人 push 過
                }
                return Pop::Inconsistent;     // head 被換走了 → 鏈在路上
            }
            self.tail = next;                 // 跳過 dummy
            tail = next;
            next = q.nodes[tail].next.load(Acquire);
        }

        if next != NIL {                      // 一般路徑:後繼已接上
            self.tail = next;
            return Pop::Data { node: tail, val: q.nodes[tail].val.load(Relaxed) };
        }

        // next == NIL:tail 是最後一棒,或有 producer in-flight
        let head = q.head.load(Acquire);
        if tail != head {
            return Pop::Inconsistent;         // 有人 swap 了還沒 link
        }
        q.push(q.stub, 0);                    // stub 歸隊:人工替 tail 製造後繼
        next = q.nodes[tail].next.load(Acquire);
        if next != NIL {
            self.tail = next;
            return Pop::Data { node: tail, val: q.nodes[tail].val.load(Relaxed) };
        }
        Pop::Inconsistent                     // push(stub) 途中又被 producer 插隊
    }
}
與原版 Vyukov 的 delta(同時是對前面對話的修正)
原版 pop 在「停在 stub 且 next==NIL」時一律回 empty,不分「真空」和「有人 swap 了還沒 link」。我前一輪給你的版本照抄了這個行為,但口頭把那個分支說成「真空」—— 不精確:那個分支也可能是 in-flight。上面這版加了一次 head.load 把兩者分開:Empty = caller 可以去 park 等通知;Inconsistent = spin 一下馬上會好。原版的混用在搭配 eventfd/notify 的系統裡也能活(producer push 完會叫醒你),但分開才是誠實的 API。代價:Empty 判定變保守 —— 兩次 load 之間 producer 完整跑完的話,會回 Inconsistent 而其實已 ready,caller 多 spin 一圈,無害。

為什麼要「重放」而不是「隨機跑」—— 真實數據
本頁的實作跑了多執行緒 stress:4 producers × 5000 訊息 × 6 輪(單核機器,12 萬則訊息、preemption 隨機)。 Inconsistent 分支被踩到幾次?1 次。其他五輪全是 0。

設計二 · 一句話 一排置物櫃,每格門上一個輪次計數器 seq。producer 先看計數器確認「這格空著、輪到這一圈」,再去取票機 CAS 搶票;搶到才寫貨、把計數器 +1(發布)。 consumer 只認計數器 —— seq 一個變數同時編碼「第幾圈」和「空/滿」,這是整個設計的核心發明。

把 seq 逼出來

場景:telemetry ingestion。滿了要當場 Err 讓上層丟點+計數 —— 這個需求會反過來決定佔位操作的選擇。

bounded → 固定格子的 ring。producer 怎麼決定用哪一格?
一台取票機:單調遞增的 enq counter,格子 = pos & mask(容量取 2 的冪)。跟你 SPSC 的 index 同一族慣用法 —— index 永不歸零,靠 mask 落格、靠圈數對圈。
enq: AtomicUsize
取票用 fetch_add 不就好了?
fetch_add 無條件成功 —— 票到手就退不掉。佇列滿的時候,你握著一張指向「還沒被收走的格子」的票,只能站在原地等,做不出 try_push → Err。而 Err 正是這個場景的存在理由。所以換 CAS:先看格子能不能用,再試著搶票;不能用就把原值還給 caller。(fetch_add 版是真實變體,適合「寧可等也不丟」—— 見 Tab 6 追問 #3。)
CAS 佔位 + 失敗語意的分岔。
「這格能不能用」怎麼知道?一個 occupied: bool 夠嗎?
第一圈夠,wrap 之後死:producer 看到 free,分不出是「這圈還沒人用」還是「上圈已收走、輪到我」還是「上上圈的殘影」。bool 少了圈數這個維度 → 把圈數直接編進狀態:每格一個 seq,約定 seq==pos 空且輪到你、seq==pos+1 已發布、seq==pos+N 是下一圈的空。
seq: AtomicUsize per slot —— 圈數與狀態二合一。
consumer 端呢?
單一 consumer → deq 普通 usize;判斷只有一條:slot.seq == deq+1。關鍵觀察:producer 從頭到尾不讀 deq —— 滿的判斷靠 seq(diff<0),空的判斷 consumer 自己看 seq。所有跨執行緒溝通都走 per-slot seq,這就是待會 ordering 表裡 enq 的 CAS 敢用 Relaxed 的原因。
deq: usize,以及「同步全在 seq 上」的架構事實。

Code(rustc 1.91 · edition 2024 編譯執行通過)

struct Slot {
    seq: AtomicUsize, // 每格一個回合計數器:同時編碼「第幾圈」+「空/滿」
    val: AtomicUsize, // demo payload(同前:泛型版是 UnsafeCell + unsafe)
}

pub struct BoundedMpsc {
    buf: Box<[Slot]>,
    mask: usize,
    enq: AtomicUsize, // 純粹的取票機:跨執行緒同步全部走 per-slot seq
}

pub struct RingConsumer<'a> {
    q: &'a BoundedMpsc,
    deq: usize, // 單一 consumer 合約 → 普通 usize,producer 從頭到尾不讀它
}

impl BoundedMpsc {
    pub fn new(n: usize) -> (&'static Self, RingConsumer<'static>) {
        assert!(n.is_power_of_two());
        let buf: Box<[Slot]> = (0..n)
            .map(|i| Slot { seq: AtomicUsize::new(i), val: AtomicUsize::new(0) })
            .collect();
        let q: &'static BoundedMpsc =
            Box::leak(Box::new(Self { buf, mask: n - 1, enq: AtomicUsize::new(0) }));
        (q, RingConsumer { q, deq: 0 })
    }

    /// MP 端:CAS 佔位 + per-slot seq 發布。滿了回 Err(v) — backpressure 的出口。
    pub fn try_push(&self, v: usize) -> Result<(), usize> {
        let mut pos = self.enq.load(Relaxed);
        loop {
            let slot = &self.buf[pos & self.mask];
            let seq = slot.seq.load(Acquire); // 配對 consumer 還格子的 Release
            let diff = seq.wrapping_sub(pos) as isize;

            if diff == 0 {
                // 這格空著、輪到這一圈 → 試著把 pos 佔走
                match self.enq.compare_exchange_weak(
                    pos, pos.wrapping_add(1), Relaxed, Relaxed) {
                    Ok(_) => {                                   // 佔位成功:此格只有我碰
                        slot.val.store(v, Relaxed);
                        slot.seq.store(pos.wrapping_add(1), Release); // 發布
                        return Ok(());
                    }
                    Err(cur) => pos = cur,   // 票被別的 producer 搶走 → 拿新票重試
                }
            } else if diff < 0 {
                return Err(v);               // 真的滿:上一圈的資料還沒被收走
            } else {
                pos = self.enq.load(Relaxed); // 手上的 pos 過期 → 重讀
            }
        }
    }
}

impl RingConsumer<'_> {
    /// SC 端:只認「已發布」。seq == deq(已佔未發布)和沒人佔,對它一樣是 None。
    pub fn try_pop(&mut self) -> Option<usize> {
        let n = self.q.buf.len();
        let slot = &self.q.buf[self.deq & self.q.mask];
        let seq = slot.seq.load(Acquire);            // 配對 producer 發布的 Release
        if seq == self.deq.wrapping_add(1) {
            let v = slot.val.load(Relaxed);
            slot.seq.store(self.deq.wrapping_add(n), Release); // 還格子給下一圈
            self.deq = self.deq.wrapping_add(1);
            Some(v)
        } else {
            None
        }
    }
}

把問題逼出來

consumer 拿到 Empty 之後想睡,裸的「pop → 睡」為什麼會死?
「檢查到空」是一張 snapshot,「睡著」是稍後的動作 —— 中間任何事都可能發生。若 producer 恰好在縫裡 push 並通知,而通知打在還沒睡的人身上(condvar 的 notify、futex 的 wake 都是:沒人在等就蒸發),等 consumer 真的睡下去,那筆通知已經不存在了。隊上有貨、人在睡、再也沒人叫 —— 除非下一筆 push 來救。
lost wakeup:check-then-act race 的睡眠版。
睡之前再檢查一次不就好了?
縫變窄,沒有關上:「再檢查」與「睡著」之間又是一道縫,遞迴到底。這是面試裡最經典的錯誤答案 —— 任何「多檢查幾次」都只是在調整輸的機率。要的不是更快的檢查,是把「檢查」與「睡」做成一個原子動作。
結論:這不是協議層能修的,要換原語。
原語要什麼性質?
兩件事:①通知要持久化 —— 沒人在睡也不落空,存起來(token);②park 要在內部原子地做「token 在?消費並立即返回:真的睡」。這正是 std::thread::park / unpark 的合約:unpark 存入一枚 token,park 消費它。於是「unpark 先到還是 park 先到」不再重要 —— 順序敏感性被狀態吸收了。
token:一枚會被消費的、持久的通知。

Code(rustc 1.91 · edition 2024;卡死與不睡都有計時 assert 證明)

use std::thread::{self, Thread};
use std::time::Duration;
use std::sync::atomic::AtomicBool;

// ── 壞協議:兩邊都在 check-then-act ──
// consumer:看到空 →(縫)→ 舉牌「我要睡」→ park
// producer:push → 看牌「沒人睡」→ 省掉 unpark      ← 兩個過期 snapshot 互鎖
fn buggy_consumer(mut c: Consumer<'static>, sleeping: &AtomicBool,
                  consumed: &AtomicUsize) {
    assert_eq!(c.pop(), Pop::Empty);            // snapshot:「隊是空的」
    thread::sleep(Duration::from_millis(150));  // 模擬「決定睡」與「睡著」之間被切走
    sleeping.store(true, SeqCst);               // 舉牌 —— 但通知已經在 50ms 前被省掉了
    thread::park();                             // 睡著:隊上有貨,沒人會再叫 → lost wakeup
    loop { if let Pop::Data { .. } = c.pop() { break } } // (被人工救援後收尾)
    consumed.store(1, SeqCst);
}
fn buggy_producer(q: &MpscQueue, sleeping: &AtomicBool, c_thread: &Thread) -> bool {
    thread::sleep(Duration::from_millis(50));
    q.push(1, 7);
    if sleeping.load(SeqCst) { c_thread.unpark(); true }
    else { false }          // 讀到「沒人睡」→ 省掉通知 —— wakeup 就是在這行弄丟的
}

// ── 好協議:token 把「叫過你」從事件變成狀態 ──
// producer:push 之後「無條件」unpark —— 沒人在睡也不落空,存進 token
fn producer_fixed(q: &MpscQueue, c_thread: &Thread) {
    q.push(2, 8);
    c_thread.unpark();
}
// consumer:pop → park 的裸序列直接是對的:
//   unpark 先到 → token 已在 → park 消費 token、立刻返回(根本不睡)
//   unpark 後到 → OS 喚醒
// park 允許 spurious return,所以永遠住在 loop 裡重新檢查 —— 這是合約,不是防禦
fn consumer_fixed(c: &mut Consumer<'static>) -> usize {
    loop {
        match c.pop() {
            Pop::Data { val, .. } => return val,
            Pop::Empty           => thread::park(),         // 敢睡:token 兜底
            Pop::Inconsistent    => std::hint::spin_loop(), // 不睡:馬上就好
        }
    }
}
consumer_fixed 就是整份教材的收束點
Empty → park()、Inconsistent → spin —— Tab 2 把兩者分開回報的理由,在這裡從 API 潔癖變成正確性分工: Empty 敢睡,因為 producer 每筆 push 後無條件 unpark,token 兜底;Inconsistent 不睡,因為卡在縫裡的 producer 馬上會補完,睡了純虧延遲。 驗證:4000 則訊息跑完整協議,零卡死;壞協議則在強排交錯下 600ms 卡死實錘(人工救援收尾)。
check-then-act 的三種救法(全教材統一視角)
世界在「檢查」與「行動」之間一定會變,防不了 —— 只能讓行動自帶吸收:

① swap 回傳真相(設計一 · 情境 D):consumer 以為 prev 是 A,swap 回傳 B —— 行動的回傳值就是最新事實,錯誤前提被無痛覆寫。
② CAS 失敗重試(設計二):前提過期 → 行動直接失敗,拿新前提重來。
③ token 儲存(這裡):對方的行動(通知)持久化,我的行動(park)先消費再決定 —— 順序敏感性被狀態吸收。

三個都不「防止」race,都是「讓 race 無害」。deep dive 把這段講出來,就是把三個零件講成一套世界觀。
condvar 那層本來就沒這個病 —— 你是拆鎖時把藥也拆了
Mutex<VecDeque> + Condvar 為什麼從來不談 lost wakeup?因為 wait(guard) 原子地「放鎖 + 入睡」,而 producer 的 push+notify 在同一把鎖裡 —— 「檢查空」與「睡著」之間不可能插進任何 push。拆鎖拆掉的不只是互斥,還有 condvar 免費附送的這個原子性;park/token 就是把那一小塊單獨贖回來。這也是階梯敘事的最後一塊:第 0 階不是「爛版本」,是把多個保證打包的版本 —— 往上爬 = 把保證拆開、一塊一塊自己付錢。
