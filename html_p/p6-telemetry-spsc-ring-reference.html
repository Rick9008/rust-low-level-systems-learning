整體架構：per-source ring → worker pool → aggregation → downstream

每個硬體 source 前掛一顆獨立的 bounded ring：單一 producer thread（該 source 的取樣/中斷處理）寫，單一 worker 讀 —— 這就是 SPSC，是整條 pipeline 最熱、最需要 lock-free 的邊界。ring 內部（head/tail、full/empty 區分、memory ordering）在 ② 概念推導 展開；這裡先建立責任切分與 channel 協定的全局圖。

CHANNEL 協定
  • Source → Ring：SPSC。producer 只呼叫 try_push，滿了拿回 Err(value) 自行決定 backpressure。ring 是唯一同步點，無鎖。
  • Ring → Worker：worker 只呼叫 try_pop。設計選擇：靜態 shard（worker 固定負責一組 ring，無競爭但可能負載不均）vs 全域 work queue（均衡但取 ring 有協調成本）。
  • Worker → Aggregator：MPSC（多 worker 產、單 aggregator 收）。std-only 用 std::sync::mpsc；要 bounded backpressure 用 sync_channel(k)，滿了 send 阻塞。
  • Aggregator → Downstream：單消費者，批次 flush。時間窗聚合把每秒海量 signal 摺疊成 per-(source,metric,window) 的 chunk。
→ ring 內部怎麼推導的 → 三種 backpressure 差在哪 → 為何一定要聚合（記憶體帳）

NAIVE

最笨但先能跑：Vec<Signal> 當佇列，push_back / remove(0)。

失敗模式
  • 無界成長：signal 連續流入、消費端只要短暫落後，Vec 無上限膨脹 → 記憶體受限情境直接 OOM。
  • front 移除 O(n)：remove(0) 要搬移整段,每秒海量 signal 下爆掉。
  • 非執行緒安全：producer / consumer 併發存取同一 Vec = data race。
修法 1：固定大小 + 環狀重用 index → 引入 head / tail

配一塊固定容量的 slot 陣列（記憶體上界確定）。用兩個 index 環狀繞行重用空間：tail = 下一個要寫的位置（只有 producer 動），head = 下一個要讀的位置（只有 consumer 動）。前進即 (i + 1) % cap。

新的失敗模式：full / empty 撞名

head == tail 同時可能代表「空」與「滿」（繞一圈回到原點）—— 無法區分。

修法 2：犧牲一格 → usable = cap − 1

刻意讓 buffer 永不寫到「會使 tail 追上 head」的那一格。於是：head == tail ⇒ 空；(tail + 1) % cap == head ⇒ 滿。代價是損失一格容量（usable = cap − 1）。

為何不用一個 count 取代犧牲一格？—— 因為 count 兩端都要改，會變成雙寫者競爭點，破壞「各自只寫自己的 index」這個讓後面 ordering 能放鬆的關鍵性質。詳見 ⑥ 追問。

修法 3：跨執行緒 → head/tail 原子化 + memory ordering

producer / consumer 在不同 thread，head/tail 必須是 AtomicUsize。ordering 不是背下來的 —— 由「誰要 observe 誰的哪個動作」逐條推出：

位置Orderingsynchronizes-with 邊為什麼
try_push: tail.loadRelaxed—producer 是 tail 唯一寫者,讀自己不需同步
try_push: head.load（full 判定）Acquire配 try_pop 的 head.store(Release)觀察到 head 前進（slot 已釋放）時,須連帶看到 consumer 對該 slot 的讀取已完成 → 覆寫前 read-before-write 成立
try_push: tail.store（publish）Release配 try_pop 的 tail.load(Acquire)發布:slot 寫入 happens-before consumer 看到新 tail
try_pop: head.loadRelaxed—consumer 是 head 唯一寫者
try_pop: tail.load（empty 判定）Acquire配 try_push 的 tail.store(Release)觀察到新 tail → 連帶看到 producer 的 slot 寫入,讀出的才是有效資料
try_pop: head.store（publish）Release配 try_push 的 head.load(Acquire)發布 slot 已釋放,producer 才可安全覆寫
方法論

先全部寫 SeqCst 讓它正確,再逐個 relax 成 Acquire/Release —— 每 relax 一處,要能講出那條 synchronizes-with 邊（哪個 Release-store 配哪個 Acquire-load）。講不出來的就留 SeqCst。這題逼出的核心 happens-before：producer 覆寫某格之前,必須先 observe consumer 已讀完那格（走 head 的 Release→Acquire）。

TSO 陷阱（重要）

另有一支 2M 元素的雙執行緒 FIFO stress（producer 推 0..N、consumer 斷言收到序列 == 0..N）已通過。但 x86 是 TSO（total store order）：就算把該 Release 誤寫成 Relaxed,在 x86 上照樣過 —— 這條測試抓不到 ordering 錯誤,它只證邏輯（wrap / full-empty / 無 torn read）。要真的模型檢查 ordering,離線用 loom（dev-dependency,不進 solution、不算 std-only 違規);面試現場則用嘴把那條 synchronizes-with 邊講出來。

  • step 6:tail 3→0 繞回,off-by-one 高風險點（% cap 忘了寫就爆這裡）。

Backpressure 三策略：滿了怎麼辦

此 ring 的 try_push 滿了回 Err(value),把 value 交還呼叫方 —— 策略的分岔點在呼叫方,不在資料結構裡。預設行為（呼叫方丟棄 Err 的 value）就是 drop-newest。

drop-oldest 在嚴格 SPSC 是個陷阱（naive → 失敗 → 修法）

NAIVE（誘人但錯）

直覺:滿了就 producer 自己 pop 掉最舊的再 push。

失敗模式:破壞 SPSC 單消費者不變式
  • try_pop 是 consumer 專屬。producer 也呼叫它,現在 head 有兩個寫者 —— 而「head.load 用 Relaxed」的前提正是「我是唯一寫者」,此前提被打破。
  • producer 與 consumer 可能對同一格做 assume_init_read → 同一個 T 被 move 兩次 = 讀到已移出的記憶體 + 潛在 double-drop = UB;元素遺失或重複。
  • x86 上快測可能「看起來會動」（TSO + 運氣掩蓋),更危險。
修法
  • 換結構:gauge 類要 drop-oldest,改用 overwriting ring / seqlock 風格的單 producer 覆寫環,消費端拿「最新快照」並容忍中間值遺失。契約不同(不再是精確 FIFO queue),但正好符合 gauge 語意。
  • 或把決策移到 consumer 端:唯一的 consumer 在自己落後時主動丟舊,維持單寫者。
  • 或加 CAS 版 head:讓 head 兩端都能 CAS 推進 —— 但這就多了同步成本、不再是那個乾淨的 SPSC,退化成一般 MPSC-ish 結構。

記憶體帳:存整條 raw queue vs 聚合成 chunk

給量級估算的算式,不追精確數字。重點是哪個維度隨什麼線性成長。

A. 存 raw signal

一筆 Signal ≈ { ts:u64, source_id:u32, metric_id:u16, value:f64 } → 連 padding 約 s ≈ 24 B。

要留 T 秒、每 source 每秒 M 筆、N 個 source:

量級代入 N=1e3, M=1e3, T=10, s=24 → ≈ 2.4×10¹¹ B ≈ 240 GB。爆。

B. 聚合成時間窗 chunk

每個 (source, metric, window) 存一筆聚合 ≈ { win_start:u64, source_id, metric_id, count:u32, sum/min/max:f64 } → 約 a ≈ 40 B。數量 = source × metric × 保留窗數,與 signal rate M 解耦:

量級代入 N=1e3, K=50, W=60, a=40 → ≈ 1.2×10⁸ B ≈ 120 MB。

核心 lever

raw 版的記憶體 = N·M·T·s,M（每秒筆數）直接乘進去,還跟保留時間 T 相乘 —— 兩個會爆的維度。聚合版把 M 這個維度摺進 count/sum:海量 signal 只是讓 count 變大,不讓 record 數量變多。省下的量級 ≈ M·T / (K·W/M... ) 概念上是「用固定大小的 aggregate 吃掉可變的 signal rate」。這就是記憶體受限 telemetry 一定要在 worker/aggregator 早聚合、ring 只當短期緩衝的理由 —— ring 存的是「還沒被聚合的 in-flight 幾百毫秒」,不是整段歷史。

常見面試追問（每條至少 3 層深）

這些是「有答案」的 escalation —— 對照 L4 modal = medium + follow-up。結尾 ⑦ 開放設計 才是留白給你口頭練的。

Q1:為什麼犧牲一格?用一個 count 不行嗎?
L1 — count 需要一個「兩端都改」的變數(push +1、pop −1)。SPSC 的紅利是「各自只寫自己的 index」,才能把 load 放鬆到 Relaxed。count 一引入,這性質就沒了。
L2:那 count 用 atomic RMW 不就好? — 兩端都做 fetch_add/fetch_sub,同一條 cache line 在兩顆 core 間 ping-pong = 真競爭,比兩個各自 Release 的單寫 index 慢;且 count 語意下判 full/empty 要小心跨越邊界的可見性。
L3:cache line 你剛提到 —— 那 head/tail 呢? — head 與 tail 若落在同一 cache line,producer 寫 tail、consumer 寫 head 會 false sharing,互相打掉對方的 line。修:各自 #[repr(align(64))] 塞到不同 line。std-only 沒有 crossbeam::CachePadded,要手刻一個 align wrapper struct。（unverified:實際 padding 大小該對齊到目標平台 cache line,常見 64 B 但非普世;面試講「典型 64,量測為準」。）
Q2:多 source,你怎麼把 worker 分配到 rings?
L1 — 兩種:(a) 靜態 shard,每 worker 固定負責一組 ring,零競爭但負載不均;(b) 全域 work queue,任 worker 取任一 ring,均衡但取 ring 有協調成本(且要避免兩 worker 同時 pop 同一 ring,否則又破壞 SPSC)。
L2:靜態 shard 下,單一 source 突然爆量? — 那顆 ring 先觸發自己的 backpressure(drop-oldest),把過載隔離在該 source,不會直接拖垮別人的 ring。但負責它的 worker 被灌爆,delay 會傳到同 shard 的其他 source。修:hot source 動態 re-shard,或給它更大的 ring + 專屬 worker。
L3:怎麼偵測 hot source? — 監控每顆 ring 的 drop counter(單調累積)與 depth 高水位。drop rate 突增 = 該 source 過載的直接訊號;depth 只是輔助(見 Q3)。
Q3:消費端落後,你用什麼指標觀測?
L1 — export 每顆 ring 的 len()(depth)、drop counter、per-worker 處理延遲、端到端 latency(signal ts → aggregate flush ts)。
L2:depth 抖動很大怎麼辦? — 別看瞬時值,看窗內高水位(max depth over window)與 p99 depth。瞬時 depth 取樣會漏掉短 burst。
L3:如果 drop 一直發生、但 depth 取樣看起來不高? — 表示 burst 的時間尺度短於你的 depth 取樣間隔:塞爆又被消化,取樣點之間看不到。此時 drop counter(單調)才是真訊號,depth 只能當輔助。這正是「觀測指標選錯會給假陰性」的典型。
