RAII Guard 設計學

spin_lock 教材的型別層深讀 · lifetime 綁定 / Send 裁決 / poisoning · 2026-08-01

一句話論綱

RAII guard 的全部價值:把「鎖紀律」翻譯成型別系統能檢查的語言。「存取必須在持鎖期間」「解鎖的人要是上鎖的人」「臨界區沒走完的資料不可信」——這三條紀律在 C 裡靠人肉遵守,在 Rust 裡分別對應三個型別層決策:

#紀律型別層武器分頁
1所有存取發生在持鎖期間Deref 回傳的借用綁在 guard 上——借用活著,guard 就不准死①
2臨界區屬於一條執行緒guard !Send(PhantomData<*mut ()>)——A 鎖 B 解直接編譯不過②
3被 panic 腰斬的資料不可信毒化旗標 + thread::panicking()——或誠實地選「不毒化,使用者自負」③
前置閱讀 本頁假設你已寫過 TTAS spin lock(reference/src/concurrency/spin_lock.rs)並讀過它的 unsafe impl<T: Send> Sync for SpinLock<T>——為什麼 bound 是 Send 不是 Sync:鎖保證 T 永不被兩執行緒同時觸碰,跨執行緒發生的是「獨占存取權接力」(= Send 的定義),不是「同時共享」(= Sync 的定義)。對照:RwLock 允許多讀者並存,所以那邊才需要 T: Sync。

guard 解剖

pub struct SpinGuard<'a, T> {
    lock: &'a SpinLock<T>,          // 憑證:我持有這把鎖
    _not_send: PhantomData<*mut ()>, // 決策 2:釘死在上鎖的執行緒
}
// 活著 = 持鎖;離開作用域或 panic unwind = Drop 放鎖(決策 3 的舞台)
// Deref/DerefMut 發出的借用綁在 &self/&mut self 上(決策 1 的機關)

① lifetime 綁定 — 裸指標沒有 lifetime,`&*` 是重新發明一個

為什麼綁 guard 而不是綁 lock,是安全的支點

機制兩層

第一層:裸指標抹掉 lifetime。self.lock.data.get() 回傳 *mut T——到這裡借用檢查器已經看不見它了。你寫 &*ptr 時,編譯器要給這個新借用一個 lifetime,而它純粹從上下文推(通常就是函式簽名),完全不驗證合理性。這就是 unsafe 的責任邊界:lifetime 是你說了算,說錯不會有人攔——SAFETY 註解必須替它作保。

第二層:簽名決定推出什麼。Deref 的簽名經過 lifetime elision:

fn deref<'s>(&'s self) -> &'s T
//        ↑ 對 guard 的借用          ↑ 輸出綁它——不是綁 'a(對 lock 的借用)

所以 unsafe { &*self.lock.data.get() } 造出來的 &T 活得跟這次對 guard 的借用一樣長。要 drop(guard),borrow checker 會先要求所有從它 deref 出來的借用都死光——「借用死在 guard 之前」= 「存取都發生在持鎖期間」,鎖紀律變成編譯錯誤。

Stepper:正確版 vs unsound 版

同一段呼叫序列,左右兩個世界:綁 guard(正確)vs 手寫 fn get(&self) -> &'a T(unsound API——裸指標讓它照樣編過)。

面試句 "The reference conjured from the raw pointer gets whatever lifetime the signature demands. Deref's elided signature ties it to the borrow of the guard — so the borrow checker enforces that every access dies before the guard does, which is exactly the lock discipline. Hand-rolling a method that returns &'a T compiles fine and is the classic unsound API."
DerefMut 的加碼 fn deref_mut(&mut self) -> &mut T:除了同樣的 lifetime 綁定,&mut self 還向借用檢查器要求對 guard 的獨占借用——同一個 guard 上不可能同時活著一個 &T 和一個 &mut T。跨執行緒的互斥由 lock 協定扛,同執行緒的互斥由借用檢查器扛,兩層各管一半。

② Send 裁決 — guard 該不該釘在執行緒上

!Send 是設計裁決還是 soundness 強制?兩種都存在,分清楚

先分清楚兩種 !Send

鎖guard !Send 的性質理由
pthread mutex(舊 std::Mutex 後端)強制POSIX 規定必須由上鎖的執行緒解鎖,跨執行緒解是 UB——沒得商量
記 owner 的鎖(reentrant、debug 死鎖偵測)強制owner 身分是機制的一部分,guard 搬家機制就爛
純 atomic spin lock(你的教材)設計裁決unlock 只是一個 atomic store,哪條執行緒做機器層都 sound;選 !Send 是保住推理 + 留 owner 類升級路
async mutex(tokio::sync::Mutex)guard 必須 Sendtask 會被 work-stealing 搬到別的 worker——「A 鎖 B 解」是常態不是 bug

生態系把這個選擇編進型別:lock_api::RawMutex 的關聯型別 GuardMarker 由鎖的作者宣告 GuardSend 或 GuardNoSend,guard 的 Send 跟著它走。

!Send 保住的推理:三位一體

你對鎖的整條 happens-before 論證建立在「lock 的人 = 臨界區寫入的人 = unlock 的人」上:配對就是兩方——前任 unlock 的 Release ↔ 下一任 lock 的 Acquire,一條邊講完全部故事。guard 一旦可搬家,故事變三方接力(下方 stepper),每一段都要重新論證——不是變錯,是鎖失去了自己作證的能力。

Stepper:Send guard 的接力鏈

如果簽下 unsafe impl<'a, T: Send> Send for SpinGuard<'a, T>(對純 atomic 鎖是 sound 的),「A 鎖 → guard 經 channel 到 B → B 寫 → B 放鎖」長這樣。看 happens-before 邊怎麼從一條變兩條。

async 世界:為什麼 tokio 的 guard 必須 Send

let guard = mutex.lock().await;
do_io(&mut *guard).await;   // ← future 在這裡讓出;task 可能被別的 worker 撿走
// guard 活在 future 的狀態機裡,future 搬到哪它跟到哪

work-stealing 執行器下,「上鎖的執行緒」和「解鎖的執行緒」本來就可能不同。guard !Send ⇒ future !Send ⇒ tokio::spawn 直接拒收。所以 tokio::sync::MutexGuard 是 Send(當 T: Send),等待機制整個重造成 waker 佇列——unlock 從任何執行緒做都合法。「channel」在這裡就是執行器本身:run queue 的出入隊提供接力鏈的邊①。

反向警告 同步鎖(spin lock、std::Mutex)不要跨 .await 持有:task 抱著鎖讓出、同 worker 的另一個 task 開始等鎖 = 經典 async 死鎖。guard !Send 在這裡反而是保護網——很多這類錯誤直接編譯不過。

③ poisoning — 臨界區 panic 之後,資料還能信嗎

鎖沒事,出事的是資料;兩條路:顯式化 vs 使用者自負

事故現場

臨界區 panic → unwind 照跑 guard 的 Drop → 鎖正常放開。鎖本身沒壞——但資料可能改到一半被腰斬(len 加了、元素還沒放)。下一個執行緒拿到鎖,讀到半套資料,局部 bug 靜默擴散成資料腐敗。

路線做法買到付出
poisoning(std Mutex)panic 時標記;之後 lock() 回 Err(PoisonError)腐敗不靜默——呼叫者被逼親口承認「不變量可能破了」每次 lock 多一層 Result 的人體工學稅
不毒化(parking_lot / spin / 你的教材)unwind 放鎖,僅此而已API 乾淨不變量由使用者自負;實務論點:panic 多半整個任務完蛋,稅不值得繳

注意 PoisonError 裡面還是裝著 guard:鎖照樣給你,毒化只是門上的封條,into_inner() 撕掉照拿。

偵測機制:`thread::panicking()`

guard 的 Drop 恰好會在 unwind 過程中被跑到——在 Drop 裡問一句 std::thread::panicking()(回報本執行緒是否正在 unwind),就知道自己是「正常走完」還是「被 panic 腰斬後的收屍」:

impl<T> Drop for SpinGuard<'_, T> {
    fn drop(&mut self) {
        if std::thread::panicking() {
            // 我是被 unwind 叫來收屍的 → 臨界區沒走完
            self.lock.poisoned.store(true, Relaxed);  // ①
        }
        self.lock.locked.store(false, Release);      // ②
    }
}

三個細節

  • panicking() 的原理:thread-local 計數器,panic 開始 +1、被 catch_unwind 接住 −1;panicking() = 計數器 > 0。
  • std 多防的角落:如果上鎖時就已經在 panicking(別的 unwind 的 Drop 裡又拿鎖),臨界區正常走完也會誤判。std 的 guard 在建立時先記 was_panicking,染毒條件是 !was_panicking && panicking()——只有「panic 始於臨界區之內」才算。
  • 為什麼 ① 用 Relaxed 就夠:它排在 ②(Release store)之前,下一任靠 locked 上的 Acquire/Release 邊就看得到它——搭同一班便車,不用自己買票。std 也是 Relaxed。
closure API 的另一條路 如果 API 是 with_lock(f)(教材誠實邊界裡為 loom 提的形狀),就不用 Drop 偵測:catch_unwind(AssertUnwindSafe(f)) 包住,Err 時設旗標再 resume_unwind。RAII guard 沒有 closure 邊界可包,才需要 panicking() 這招。

三不總表(教材的 Trade-offs 落位)

性質後果升級路
不重入同執行緒二次 lock() = 把自己旋死reentrant lock(記 owner + 計數)——但 guard 從此必須 !Send(強制級)
不公平誰搶到誰贏,飢餓可能ticket lock 給 FIFO;流量要再上 MCS(見 MESI 頁)
不毒化panic 後資料半套、靜默毒化旗標 + panicking()(本頁);或文件明說使用者自負

30 秒英文句庫

  • "The guard is the lock discipline translated into the type system: the deref'd borrow is tied to the guard, so 'access only while holding the lock' becomes a borrow-check error instead of a code-review comment."
  • "Guards default to !Send because the reasoning — and for pthread, the correctness — is anchored on which thread owns the critical section. An async mutex inverts this: tasks migrate between workers, so the guard must be Send and the wait machinery becomes a waker queue."
  • "On panic the unwind still runs Drop, so the lock is released — the data is what's suspect. std poisons to make that explicit; parking_lot and spin skip it and document that invariants are the user's job."

自測(先答再翻)

1. Deref 回傳的 &T 如果綁 'a(lock 的借用)而不是 &self,寫出什麼程式會爆? let r = &*guard; drop(guard); use_it(r);——r 活過放鎖,別的執行緒此刻可拿 &mut T,同時存在 &T/&mut T = data race/UB。綁 &self 讓 drop(guard) 在 r 活著時直接編譯錯誤。
2. 你的 spin lock 簽 unsafe impl Send for SpinGuard 是 sound 的嗎?條件是什麼? Sound——前提兩條:unlock 只是 atomic store(任何執行緒做都合法,pthread 就不行);T: Send(&mut T 的獨占存取權跟著 guard 搬家)。剩下的是設計問題:你放棄了 reentrant/owner-tracking 升級路,鎖也講不完整 happens-before 故事了(要靠搬運工具的同步邊)。
3. Send guard 經 channel 從 A 到 B,B 放鎖後下一任 C 為什麼看得到 A 的寫入? 兩條邊接力:A 的寫入 →(channel send=Release / recv=Acquire)→ B →(B unlock Release / C lock Acquire)→ C。safe Rust 的跨執行緒搬運原語都自帶同步邊,這是 Send + safe 搬運 sound 的原因;用不帶同步的方式偷渡(裸指標、Relaxed AtomicPtr)邊①就消失 = UB。
4. 毒化旗標為什麼 Relaxed 就夠?什麼情況下它會不夠? 它的 store 排在 locked 的 Release store 之前,下一任的 Acquire 邊順便把它護送過去。如果有人不經過 lock 協定直接讀旗標(例如監控執行緒裸讀 poisoned),沒有那條邊,Relaxed 讀到的值就沒有任何順序保證——便車只保「搭同一班車的人」。
5. 為什麼 std 的染毒條件是 !was_panicking && panicking() 而不是 panicking()? 在別的 unwind 的 Drop 裡拿鎖 → 臨界區正常走完 → guard Drop 時 panicking() 仍是 true(那個外層 panic 還在 unwind)→ 誤判染毒。記下「上鎖時是否已在 panicking」,只有 panic 始於臨界區之內才染毒。
