## 四、設計課(sol 對照三條 + 重構沉澱)

1. **deadline 與 owner 同居**(本日最該裱框):我的堆存派工資訊的**副本**,副本會漂移,漂移要 10 行對帳碼(stale 查帳);sol 讓 `deadline[e]` 和 `owner[e]` 同格,done 一次清兩個,「過期鬧鐘」**在型別上無法存在**。定律:**與其寫 code 調解兩份狀態的漂移,不如選一個讓漂移不可表示的狀態設計。**
2. **先問 N 再選形狀**:N=6 固定 → per-engine 格線性掃,heap 是通用解但在這裡是 overkill;N=一萬條連線 → min-heap/timer wheel(tokio 計時器)。英文句備用:"How many engines? Fixed at 6? Then per-engine deadlines — a heap is the general answer but overkill here."
3. **殭屍 = 生存證明**:sol 的政策比「冷宮到底」聰明一級——隔離到 proof-of-life 為止:遲到的 done 證明它是慢不是死、欠帳已吐完,復活不增加新風險;**帳一根指頭不碰**。8/6 被追問 zombie 時的現成加分答案。
4. **統一 work queue**:sol 的工作佇列裝 block 描述子 `(rid, b)`,新派與重派同形狀 → 單一派工路。我的兩形狀(request 代幣 + Alarm ticket)逼出兩段重複派工碼,而重複碼正是 pos bug 只長在其中一條的原因。
5. 小寶石兩顆:`next_sleep_ms` 尾巴 **`.max(1)`**(貼線 deadline 防 `wait_event_timeout(0)` 空轉);strikes 記 `(rid, b)` map 比隨票攜帶穩(票丟計數還在)。
6. **挑 sol 的刺**(有資格了):`tries` 只進不出(grep 驗證全檔僅 insert/increment)——sim 規模無害,長跑系統是無界慢漏;`on_done` 成功路徑該補 `tries.remove`。
7. Alarm 重構紅利實感:`..alarm` struct update 重派時只換 `deadline`/`eng`,其餘欄位不可能抄錯——具名 struct 消滅的是「整類」bug 不是「幾個」bug。

## 五、Ord 四件套課(晚間 Q&A 沉澱)

- **繼承鏈**:`PartialEq`(`==`;允許有值連自己都不等)→ `Eq`(空標記,承諾 `x==x` 恆真;HashMap key、Ord 需要)→ `PartialOrd`(`partial_cmp → Option<Ordering>`,保留「不可比」)→ `Ord`(`cmp` 必答、全序;`BinaryHeap`/`BTreeMap`/`sort()` 的約束)。**拆四層的原因一個字:NaN**——IEEE 754 下 f64 只有 Partial 家族,這就是 `Vec<u64>` 能 `.sort()` 而 `Vec<f64>` 要 `sort_by` 的原因。
- **derive = 按欄位宣告順序的字典序**(心智模型=tuple 比較):`deadline` 必須第一欄。預測題自答通過:`strikes` 放第一欄編譯**零警告**、堆改按 strikes 排 → watchdog 失明——**欄位順序是承重牆,型別系統不擋語意錯,測試才擋**。
- **手寫版鐵律:`cmp` 是唯一真相**,`partial_cmp = Some(self.cmp(other))`、`eq = cmp == Equal` 全委派、`impl Eq {}` 空掛;derive/手寫混搭 clippy 會抓不一致。
- **deadline-only 相等的語意代價**:兩顆不同 request 同毫秒到期的鬧鐘會 `eq`——`BinaryHeap` 無害(不去重),丟進 `BTreeSet`/`BTreeMap` 當 key 會**把不同鬧鐘當重複合併**。45 分鐘場首選仍是「欄位排對 + 全 derive」。
- 附:`BinaryHeap` 是 max-heap → 要 `Reverse`;LL/SC 岔路課同晚收錄——weak CAS = 單發 LL/SC 映射,假失敗是架構本性(MESI 保留失效),x86 上 weak 不假失敗但 Rust 語意跨架構保留;`compare_exchange`(strong)= 庫包好的 retry loop。7/31 spin_lock 的 weak→strong 修正根因即此。
